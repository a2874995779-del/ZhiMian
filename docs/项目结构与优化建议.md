# 智面项目结构与优化建议

更新时间: 2026-08-31

## 1. 项目定位

智面是一个面向求职者的 AI 面试刷题平台，当前主体形态是“Spring Boot 单体后端 + Vue 3 前端 + MySQL + Redis + Spring AI”。核心能力包括用户鉴权、题库管理、分类标签、答题记录、排行榜、AI 模拟面试、多轮上下文、SSE 流式输出、面试报告生成与历史查询。

当前项目更适合作为学习型/作品型项目继续演进，重点应放在链路完整、代码边界清晰、可演示、可解释、可测试，而不是过早拆分微服务。

## 3. 本次清理内容

- 删除 `src/main/java/com/zhimian/controller/AiTestController.java`：阶段文档已明确标注为 Spring AI 接入阶段的临时接口，后续真实面试接口已替代它。
- 删除 `src/main/resources/static/smoke-test.html`：这是早期接口 smoke 页面，已不再作为前后端主验收入口；继续保留会混淆静态资源与正式前端职责。
- 删除 `frontend/src/mock/questions.ts`：题库页面已接入后端 API，该 mock 文件未被任何前端模块引用。
- 重写 `frontend/README.md`：移除 Vite 默认模板说明，改为当前项目的前端说明。

未清理但建议后续归档的内容:

- `docs/` 下的学习资料体量较大，适合保留，但建议按“项目设计 / 学习笔记 / 专题复盘”拆分子目录。
- `阶段部署/` 是实现过程记录，不建议直接删除；可在项目稳定后压缩为里程碑摘要。
- 根目录 `Java面试题与标准回答汇总.md` 更像知识库原始资料，可迁移到 `docs/knowledge/` 或未来 RAG 导入目录。

## 4. 主要优化方向

### 4.1 后端结构

当前按技术分层组织代码，适合中小型学习项目。随着模块增多，建议逐步向领域分包演进，例如:

```text
com.zhimian.question/
com.zhimian.interview/
com.zhimian.user/
com.zhimian.rank/
com.zhimian.knowledge/
```

每个领域内再放 `controller/service/mapper/model`，这样可以减少大型 `controller`、`service.impl` 目录的横向膨胀，也方便未来拆服务或做模块边界说明。

### 4.2 配置与环境

- `application.yml` 中保留通用默认值，数据库密码、AI Key、模型地址统一放 `application-local.yml` 或环境变量。
- 建议补充 `application-dev.yml`、`application-prod.yml`，明确开发和部署差异。
- MyBatis SQL 日志 `StdOutImpl` 只适合开发环境，生产环境应关闭或接入标准日志框架。
- 建议提供 `.env.example` 或 `application-local.example.yml`，让新环境搭建更稳定。

### 4.3 异常、鉴权与安全

- 继续保持 `Result + ErrorCode + GlobalExceptionHandler` 的统一返回方式。
- 对 `@RequireAdmin`、`@Public` 的行为补充测试，避免新增接口时误放行。
- 登录失败、AI 调用、SSE 会话应有更清晰的错误码和前端兜底提示。
- JWT 黑名单依赖 Redis，需明确 Redis 不可用时的降级策略。
- 后续可考虑 refresh token、Token 续期、密码重置、账号封禁审计。

### 4.4 数据与缓存

- 题库列表、分类、标签适合缓存，但要明确更新后的缓存失效策略。
- 浏览量 Redis 回写需要关注重复回写、宕机丢失、定时任务并发执行问题。
- 排行榜用 Redis ZSet 是合理选择，建议增加每日榜、周榜和总榜的 key 规范文档。
- SQL 脚本建议拆分为 `schema.sql`、`seed-dev.sql`、`seed-demo.sql`，避免测试数据与正式初始化混在一起。

### 4.5 AI 面试链路

- AI 调用不应放在数据库长事务中，当前方向是正确的，后续应继续强化超时、重试、限流和降级。
- 结构化报告生成建议保留原始模型输出，便于排查 JSON 解析失败和模型漂移。
- SSE 流式输出应记录开始、结束、异常中断状态，避免会话卡在进行中。
- Prompt 建议版本化，至少记录 prompt 版本、模型名、温度参数和生成时间。

### 4.6 前端工程

- 当前前端已经有 API 层和类型层，建议继续避免页面里直接写请求细节。
- `Dashboard`、`Leaderboard` 仍使用 mock 数据，后续应补齐真实接口后删除剩余 mock。
- `http.ts` 拆包统一返回 `data`，调用方类型断言较多，建议引入统一泛型请求方法减少 `as unknown as`。
- 登录态与接口 401 处理已有基础逻辑，后续需要补齐路由守卫和无权限页面。
- 建议补充前端空状态、加载状态、错误重试状态，尤其是 AI 面试和报告页。

### 4.7 测试与质量

当前仓库缺少自动化测试目录，这是后续质量提升的优先项。

建议优先补:

- 后端 Service 单元测试：用户注册登录、题库查询、答题记录、排行榜。
- 后端 Controller 集成测试：鉴权、公开接口、管理员接口、参数校验。
- Mapper 层 SQL 测试：分页、标签筛选、逻辑删除、排行榜统计。
- 前端类型检查和构建作为最低门槛。
- 面试核心链路增加可替代 AI 的 fake client，避免测试依赖真实模型服务。

## 5. 后续功能规划

### 5.1 短期功能

- 题库后台管理页：分类、标签、题目增删改查可视化。
- 错题本：记录错题、错题次数、最近错误时间、掌握状态。
- 收藏夹：用户收藏重点题目，支持按标签和难度筛选。
- 学习进度仪表盘：答题数、正确率、薄弱分类、连续学习天数。
- 面试报告详情页增强：展示维度评分、改进建议、原始问答回放。

### 5.2 中期功能

- RAG 知识库：导入 Markdown/PDF，切分、向量化、检索并用于参考答案增强。
- AI 个性化追问：根据用户上一轮回答质量动态调整追问深度。
- 复习计划生成：结合错题、薄弱标签和面试报告生成 7 天计划。
- 题目推荐：基于难度、标签、掌握度和历史行为推荐下一组题。
- 管理端数据面板：用户活跃、题目热度、AI 调用量、失败率。

### 5.3 长期功能

- 简历解析与岗位匹配：根据目标岗位生成面试路线。
- 多模型适配：DeepSeek、OpenAI 兼容模型、本地模型可切换。
- 面试官模板市场：Java、前端、算法、系统设计、项目深挖等模板。
- 企业/班级空间：老师或管理员维护题库，学员统一练习。
- 语音模拟面试：语音输入、实时转写、语速和表达分析。

## 6. 建议执行顺序

1. 完成自动化测试最小闭环：后端核心 Service + 前端 build。
2. 将 `Dashboard`、`Leaderboard` 的 mock 数据替换为真实接口。
3. 整理配置文件和本地启动说明，补齐 example 配置。
4. 做错题本和收藏夹，增强刷题闭环。
5. 做 RAG 知识库，形成项目亮点。
6. 引入 Prompt 版本化和 AI 调用观测指标。
7. 最后再考虑领域分包或更大架构调整。

## 7. 维护原则

- 学习笔记可以多，但项目入口文档要短，保证新读者 10 分钟能跑起来。
- 临时接口、临时 mock、一次性 smoke 页面完成阶段任务后及时删除。
- 新增功能必须同时补齐接口文档、错误码、权限说明和基本测试。
- AI 相关能力要能降级，不让外部模型不可用拖垮核心刷题功能。
- 所有演示数据与正式初始化脚本分离，避免部署环境被测试数据污染。
