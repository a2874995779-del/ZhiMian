# 第一部分 · 任务 2.5:消息持久化与会话查询

## 一、先想清楚这次在解决什么

到 2.4 为止,`interview_session` / `interview_message` 两张表一直在写数据,但项目里**没有任何一个接口能把这些数据读出来**——用户看不到"我面试过哪些场、聊了什么"。2.5 补两个查询接口(列表 + 详情)。

但 2.5 真正的核心不是"加两个查询",而是**堵一个安全洞**。在 2.4 结束时,`chat` 接口里判断会话是否存在的方法长这样(简化):

```java
InterviewSession session = interviewSessionMapper.selectById(sessionId);
if (session == null) {
    throw new BusinessException(ErrorCode.NOT_FOUND, "面试会话不存在");
}
```

它只问了"这个 id 的会话**在不在**",完全没问"这个会话**是不是当前登录用户自己的**"。也就是说:只要你登录了(有一个合法 token),把请求里的 `sessionId` 换成任意一个别人的会话 id,你就能对着**别人的面试**发消息、看 AI 回复、结束它、拿到它的报告。**别人的私密面试对你完全透明。**

这个漏洞有专门的名字:**水平越权(Broken Object Level Authorization,OWASP API 安全风险常年排第一)**。"水平"指的是同一权限级别的用户之间互相越权(不是普通用户越权成管理员那种"垂直越权")。2.5 要把它堵上,而且要**在每一个"按会话 id 操作"的入口都堵**。

## 二、越权校验:`mustFindOwnSession`

改造后的方法:

```java
private InterviewSession mustFindOwnSession(Long sessionId) {
    InterviewSession session = interviewSessionMapper.selectById(sessionId);
    if (session == null || !session.getUserId().equals(UserContext.getUserId())) {
        throw new BusinessException(ErrorCode.NOT_FOUND, "面试会话不存在");
    }
    return session;
}
```

### 2.1 为什么"不存在"和"不是你的"要返回**同一个**错误码?

这是这次最值得琢磨的一个设计。直觉上你可能会想:会话不存在返回 `404 NOT_FOUND`,会话存在但不是你的返回 `403 无权限`——这样"更精确"。**但这恰恰是错的。**

如果两种情况给不同的响应,你就等于给攻击者送了一个**探测器**:他拿一堆随机 id 挨个试,凡是返回"无权限"的,就说明这个 id **确实存在**(只是不属于他);返回"不存在"的就是空号。这样他能把系统里**哪些 id 是有效数据**摸得一清二楚——这本身就是信息泄露。

**正确做法:对当前用户来说,"不属于我的资源"和"根本不存在的资源",从外部看必须完全一样。** 所以两种情况都返回 `NOT_FOUND`、同一句"面试会话不存在"。攻击者拿别人的 id 来试,得到的反馈和拿一个空号来试**没有任何区别**,探测不出任何东西。

这是安全设计里一条通用原则:**不要泄露"攻击者不该知道"的信息,哪怕只是"这个 id 存不存在"这种看起来无害的信息。**

### 2.2 方法名为什么从 `mustFindSession` 改成 `mustFindOwnSession`?

命名要**如实反映方法现在做的事**。它不再只是"确保会话存在",而是"确保会话存在**且是我的**"。如果还叫 `mustFindSession`,以后有人(包括几个月后的你)写新接口时看到这个名字,很容易以为它只做了存在性校验,于是在新接口里忘了再补一次归属校验——**漏一个入口,整个漏洞就还在**。名字里的 `Own` 就是在提醒每一个调用者:归属校验这一步已经帮你做了。

### 2.3 "一次修复,处处生效"

改完这一个方法,`chat`、`getSessionDetail`、`finishInterview` 全都调用它,所以它们的越权漏洞**同时被堵上**,不用在每个接口里各写一遍 `if (session.getUserId() != ...)`。这就是为什么把"查会话"这个动作收敛成一个私有方法的价值——安全校验这种"必须每次都做、漏一次就出事"的逻辑,最适合收敛到一个入口。

## 三、会话列表:分页三件套

```java
@Override
public PageResult<InterviewSessionListVO> listSessions(InterviewSessionQueryDTO dto) {
    Long userId = UserContext.getUserId();
    long total = interviewSessionMapper.countByUserId(userId);
    if (total == 0) {
        return PageResult.of(List.of(), 0, dto.getPageNum(), dto.getPageSize());
    }
    List<InterviewSession> records = interviewSessionMapper.selectPageByUserId(
            userId, dto.getOffset(), dto.getPageSize());
    List<InterviewSessionListVO> voList = new ArrayList<>();
    for (InterviewSession s : records) {
        InterviewSessionListVO vo = new InterviewSessionListVO();
        BeanUtils.copyProperties(s, vo);
        voList.add(vo);
    }
    return PageResult.of(voList, total, dto.getPageNum(), dto.getPageSize());
}
```

这段和你在任务 1.8(题目分页)写的 `pageQuestions` 是**同一个套路**,三步:

1. **先 `count`**:查总数。`total == 0` 直接短路返回空分页——省掉后面那次"必然查不到东西"的分页查询。
2. **再查这一页的记录**:`LIMIT offset, pageSize`,`offset = (pageNum - 1) * pageSize`(算在 `InterviewSessionQueryDTO.getOffset()` 里)。
3. **转 VO**:实体 `InterviewSession` → 返回给前端的 `InterviewSessionListVO`。

### 3.1 两个"和题库不一样"的细节

**① 天然带 `WHERE user_id = ?`。** 列表接口的越权防护不在 `mustFindOwnSession`(那是"按 id 查单条"用的),而是**直接写在 SQL 的 `WHERE` 里**——`countByUserId` / `selectPageByUserId` 都只查当前用户的会话。用户根本查不到别人的会话,连"存不存在"都问不到。

**② 列表项不带消息内容。** `InterviewSessionListVO` 只有 `id/direction/title/status/createTime/endTime`,**没有 messages**。因为列表是"扫一眼有哪些场"的场景,如果每一场都把几十条对话消息塞进来,一次分页查询的数据量会随"每场聊了多久"线性膨胀。**消息内容留给详情接口按需加载**——这就是列表页 VO 和详情页 VO 分开的原因,和 `QuestionListVO`(不含答案全文)vs `QuestionDetailVO`(含答案)是一回事。

### 3.2 `BeanUtils.copyProperties` 这里为什么够用?

`InterviewSession` 实体的字段(`id/direction/title/status/createTime/endTime`)和 `InterviewSessionListVO` 基本同名同类型,没有"要另外查一张表补进来"的字段(不像题库列表还要补 `categoryName`、`tags`),所以 `BeanUtils.copyProperties(s, vo)` 一行搞定,不用手写每个 `set`。**判断标准**:目标 VO 的字段绝大多数能在源实体里找到同名同类型的,才值得用 `BeanUtils`;只要有几个字段要"算"或"外查",那部分永远得手写。(这个判断在 `docs/数据组装与转换专题.md` 里展开讲过。)

## 四、会话详情:过滤 system 消息 + 为什么查全量

```java
@Override
public InterviewSessionDetailVO getSessionDetail(Long sessionId) {
    InterviewSession session = mustFindOwnSession(sessionId);          // ① 归属校验
    List<InterviewMessage> history = interviewMessageMapper.selectBySessionId(sessionId); // ② 查全量历史

    List<InterviewMessageVO> messageVOList = new ArrayList<>();
    for (InterviewMessage m : history) {
        if ("system".equals(m.getRole())) {                            // ③ 过滤掉 system 消息
            continue;
        }
        InterviewMessageVO vo = new InterviewMessageVO();
        BeanUtils.copyProperties(m, vo);
        messageVOList.add(vo);
    }
    InterviewSessionDetailVO detail = new InterviewSessionDetailVO();
    BeanUtils.copyProperties(session, detail);
    detail.setMessages(messageVOList);
    return detail;
}
```

### 4.1 为什么要过滤掉 `role == "system"` 的那条消息?

那条 `system` 消息是任务 2.2 里 `buildSystemPrompt` 生成的**"面试官人设"那一大段 prompt**。它是**说给模型听的内部指令**,不是这场对话里"人话"的一部分——用户从来没在界面上看到过它。如果把它混进 `messages` 返给前端:

- 要么前端得知道"第一条永远要跳过"(隐性约定,换个人写前端就会漏),
- 要么前端会把这段大段 prompt 当成"面试官说的第一句话"直接渲染出来,用户看到一堆"你是一位资深面试官,要求:1... 2..."——体验完全穿帮。

**"存了什么"和"该给外部看什么"是两回事。** system 消息是典型的"该存(重建上下文要用)、但不该对外暴露"。过滤这一步**必须在 Service 层做**,不能指望前端自觉。

### 4.2 为什么直接查 MySQL(`selectBySessionId`),不走 `contextManager.load()`?

这是个很容易踩的判断题。`contextManager.load()` 你在 2.3 写过,它里面有一步**按 token 预算裁剪**(`trim`)——那是"**喂给模型继续对话**"用的裁剪:对话太长时把最早几轮丢掉,只留最近的,免得超模型上下文窗口、免得费 token。

但"**给用户看历史详情**"完全是另一个场景:用户翻自己的面试记录,理应看到**完整**的对话,不能因为这场聊得久、被裁掉了开头几轮,用户翻到一半发现"怎么前面几句不见了"。

**同一份原始数据,"喂模型"和"给人看"是两个不同的读取场景,该用不同的读取路径**:
- 喂模型(`chat` / `finish`)→ 走裁剪(或至少要考虑长度上限)
- 给人看(`getSessionDetail`)→ 查全量,一条不少

图省事直接复用 `contextManager.load()` 就会掉进这个坑。这个判断在 2.6 的 `finishInterview` 里还会再用一次(生成报告也要查全量)。

## 五、隐藏考点:异步回调里不能读 `UserContext`

这个坑**当前代码没真的踩中**,但原理必须懂,因为你迟早会在"往异步回调里塞当前用户是谁"的场景撞上它。

回忆 2.4 的 SSE `chat`,流结束时的回调:

```java
() -> onStreamComplete(emitter, sessionId, lockKey, fullReply.toString())
```

`onStreamComplete` 跑在**另一个线程**上(Spring AI / Reactor 的响应式调度线程),不是处理这次 HTTP 请求的那个 Tomcat 线程。而 `UserContext` 底层是 `ThreadLocal`——**它存的数据绑定在某一个具体线程上,不会跟着"这次请求"的逻辑流自动漂移到另一个线程去。**

`onStreamComplete` 现在没出问题,是因为它需要的 `sessionId` / `lockKey` / `fullReply` 全是**作为方法参数**传进去的:在还处于原始 Tomcat 线程时就已经取好、"打包"进了这个 lambda,回调真正执行时根本不需要再问 `UserContext`。

**如果以后你要在这种异步回调里用到"当前用户是谁"**(比如记一个操作人 id),正确姿势是:

```java
// 在进入 subscribe 之前、还在原始线程时,先把 userId 取出来存成局部变量
Long userId = UserContext.getUserId();
...
.subscribe(
    ...,
    () -> {
        // 用上面那个局部变量 userId,绝对不要在这里再调 UserContext.getUserId()
    }
);
```

在回调内部再调 `UserContext.getUserId()`——那时候原始线程早就被 Tomcat 归还线程池、去处理别的请求了,这个新线程的 `ThreadLocal` 里要么是 `null`,要么(更可怕的是线程池复用时)是**别的请求残留的用户身份**,直接导致"记成了别人的操作"。

顺带区分两个概念(6.1.4 那次任务学的 `afterCompletion` 清理 `ThreadLocal`,和这里不是一回事):
- **线程复用**:一个线程处理完请求 A,再去处理请求 B,A 的 `ThreadLocal` 没清会污染 B。→ 靠 `afterCompletion` 里 `remove()` 解决。
- **线程切换**:同一次请求内部,主逻辑在线程 X、异步回调在线程 Y,X 的 `ThreadLocal` 到不了 Y。→ 靠"提前取出来传参"解决。

这次要理解的是后者。

# 第二部分 · 任务 2.6:结束面试 + 结构化评价报告

## 六、这次的两个新问题

前面模型一直演**面试官**(问问题)。2.6 让它换演**评委**:针对聊完的整场对话,给出打分和点评。两个新问题:

1. **怎么让模型输出"能被程序用的结构化数据",而不是一段散文?** 之前 `openingMessage` / 流式 `delta` 都是"一段文字",拿到直接存直接展示。这次不一样:你要"总分"这个数字、"亮点"这个列表、"薄弱点"这个列表,分别存进库、分别渲染。要是还问模型"给我一段评价",拿到一整段话,你**没法可靠地**从里面抠出这几样——今天它写"总分:85",明天写"我给 85 分",你的解析代码永远追不上。
2. **"结束"这个操作的状态机怎么设计、重复点会怎样?** 手滑点两次不能生成两份报告;报告生成到一半服务重启了,再点一次要能补上,而不是会话永远卡死。这是"幂等设计"要解决的。

## 七、结构化输出:模型其实还是只会吐文本

### 7.1 先破除误解

**大模型没有一个"输出 Java 对象"的开关。** 不管怎么调,它的本质永远是"输入一串文字,生成下一串文字"。所谓"结构化输出",是 Spring AI 在背后帮你做了两件事:

1. **请求发出前**:根据你给的目标类型(`InterviewReportResult`),自动生成一段"请按如下 JSON 格式回答"的指令(含字段名、类型说明),**偷偷追加到你的 prompt 后面**。模型实际收到的请求,比你写的那句长一大截。
2. **拿到回复后**:模型回复本质还是**一段文本**(只是因为你要求了格式,它大概率长得像 JSON),Spring AI 用 Jackson 把这段文本**反序列化**成你要的类型,解析失败就抛异常。

这套逻辑封装在 `BeanOutputConverter` 里,`ChatClient` 的 `.entity(Class)` 就是它的省事入口。

**结论:结构化输出不是"模型变聪明了",而是"提示词工程 + 后处理解析"的组合**,和你自己手写"prompt 里要求返回 JSON + `ObjectMapper` 解析"是同一件事,只是框架把模板代码封装好了。理解这一点,`.entity()` 这行就不再是黑盒。

### 7.2 目标类型:一个 record

```java
public record InterviewReportResult(
        Integer score,
        List<String> highlights,
        List<String> weaknesses,
        String summary
) {
}
```

两个写法细节:

- **用 `record` 不用 `@Data` 类**:这份数据从模型解析出来后**只读不改**(读出来就组装进要落库的东西),record 天然不可变,字段只有 getter 没有 setter,恰好匹配"只读数据载体"。Jackson 从 Java 17 起原生支持 record 反序列化,不用额外配置。
- **字段名取直白**(`score` 不缩写成 `s`):这些名字会被拼进发给模型的格式说明里,**模型是照字面意思理解每个字段该填什么的**,名字含糊,模型的理解也含糊。

### 7.3 调用:`.entity(...)` + 失败重试

```java
private InterviewReportResult generateReportWithRetry(String transcript) {
    for (int attempt = 1; attempt <= 2; attempt++) {
        try {
            return chatClient.prompt()
                    .system(buildJudgePrompt())
                    .user(transcript)
                    .call()
                    .entity(InterviewReportResult.class);   // 和 .content() 只差最后一步
        } catch (Exception e) {
            log.warn("评价报告生成第{}次尝试失败", attempt, e);
        }
    }
    throw new BusinessException(ErrorCode.AI_SERVICE_ERROR, "评价报告生成失败，请稍后再试");
}
```

- `.call().content()`(2.1~2.4 用的)拿一段纯文本;`.call().entity(InterviewReportResult.class)` 直接拿一个装配好的对象。7.1 讲的两件事(格式指令注入 + 回复解析)都发生在 `.entity(...)` 这一步。
- **为什么只重试 1 次(循环 2 次),不是 5 次?** 重试的前提假设是"这次失败大概率是模型输出格式的偶发抖动,再问一次很可能就好"。如果是"prompt 本身有问题 / API 整个挂了"这种**系统性失败**,重试再多次也没用,只会让用户多等好几倍时间才收到同一个失败。**重试次数要匹配"这类失败真实的可恢复概率",不是越多越保险。**

## 八、评委 Prompt:角色分离与防幻觉

```java
private String buildJudgePrompt() {
    return """
        你是一位资深技术面试评委,下面会给你一场完整的模拟面试问答记录(面试官提问与候选人回答交替出现)。
        请基于候选人的整体表现给出结构化评价:
        1. score:总分,0~100 的整数,综合回答的准确性、深度、表达清晰度。
        2. highlights:候选人表现好的地方,2~4 条,每条一句话,要具体(引用候选人实际提到的技术点),不说空泛的场面话。
        3. weaknesses:回答中不足或值得继续深挖的地方,2~4 条,同样要具体。
        4. summary:1~2 句话的总体评价,像面试官写给 HR 的结论。
        只依据对话记录里实际出现的内容打分和点评,不要编造候选人没有说过的内容。
        """;
}
```

### 8.1 为什么不复用面试官的 `buildSystemPrompt`?

`buildSystemPrompt` 开头就是"你是一位面试官……每次只问一个问题……"——那是一套专门"问问题"的行为约束。直接拿来生成报告是**文不对题**:模型的第一反应会是"接着问下一个问题",而不是"开始点评"——**它甚至不知道对话已经结束了**。所以评委要**单独一份 system prompt,不复用**。同一个模型、同一个接口,靠不同的 system prompt 扮演不同角色——这就是 system prompt 的威力。

### 8.2 那句"不要编造候选人没有说过的内容"防的是什么?

防的是大模型一个著名毛病:**幻觉(hallucination)**——编造听起来合理但实际不存在的内容。不加这句约束,模型有一定概率"脑补"出候选人没说过的话来当点评依据(比如"候选人提到了 ThreadLocal 内存泄漏"——但这场对话根本没聊到)。

**"点评类"任务比"问答类"任务更需要这句约束**,因为编造出来的评价会**直接误导用户对自己真实水平的判断**——用户会以为自己答得比实际好/差。所以"忠于给定材料、不许编造"对评价类任务是必写的一条。

## 九、拼记录稿 `buildTranscript`:两个设计判断

```java
private String buildTranscript(List<InterviewMessage> history) {
    StringBuilder sb = new StringBuilder();
    for (InterviewMessage m : history) {
        if ("system".equals(m.getRole())) {
            continue;
        }
        String speaker = "assistant".equals(m.getRole()) ? "面试官" : "候选人";
        sb.append(speaker).append(":").append(m.getContent()).append("\n\n");
    }
    return sb.toString();
}
```

### 9.1 为什么拼成一整段文本,不像 `chat` 那样用 `List<Message>`?

`chat` 里历史是 `List<Message>`(`SystemMessage`/`UserMessage`/`AssistantMessage`),因为那是让模型"**以面试官身份、接着刚才的对话往下问**"——模型需要清楚每句话是谁说的、角色边界在哪。

而这次,模型的任务是"**读一份材料、给出一份独立的评价**"——它不是这场对话的参与者,而是**事后读记录的第三方**。把整场对话当成"一份材料"整体喂给它(`面试官:xxx\n\n候选人:yyy`),比拆成一条条带角色的消息更贴近"评委读会议纪要"这个真实场景,人读起来也清楚。

### 9.2 为什么又要过滤 system + 查全量?

- **过滤 `system`**:和 2.5 详情接口同理,那段内部人设不是对话内容,混进材料只会干扰评委判断。
- **查全量(`finishInterview` 里传给它的是 `interviewMessageMapper.selectBySessionId` 的结果,不是 `contextManager.load`)**:生成报告要评的是**整场表现**,如果因 token 预算裁掉了早期几轮,评委看到的是一场残缺的面试,分数和点评会失真。**这是 2.5 那个"喂模型 vs 给人看"判断的第二次应用**——生成总结也属于"要看完整历史"的一类。

## 十、状态机:0 → 1 → 2,中间态 1 存在的意义

`interview_session.status`:

| status | 含义 | 能做什么 |
|--------|------|---------|
| 0 | 进行中 | 能 `chat`,能 `finish` |
| 1 | 已结束,报告未生成(生成中 / 生成失败) | 不能 `chat`,能再次 `finish` 重试生成 |
| 2 | 已结束,报告已生成 | `finish` 直接返回已有报告,不再调模型 |

```java
try {
    // 先把"已结束"落实(0→1),再调模型
    if (session.getStatus() == 0) {
        interviewSessionMapper.updateStatus(sessionId, 1);
    }
    List<InterviewMessage> history = interviewMessageMapper.selectBySessionId(sessionId);
    InterviewReportResult result = generateReportWithRetry(buildTranscript(history));

    InterviewReport report = new InterviewReport();
    report.setSessionId(sessionId);
    report.setScore(result.score());
    report.setContent(serializeReportContent(result));
    interviewReportMapper.insert(report);
    interviewSessionMapper.updateStatus(sessionId, 2);   // 1→2
    return toReportVO(report);
} finally {
    stringRedisTemplate.delete(lockKey);
}
```

### 为什么不是 0 直接跳 2,中间非要有个 1?

生成报告是一次**可能失败的外部调用**(调模型)。假设"生成成功才更新状态"(0→2,失败就不动),会出现一个矛盾:**用户点了结束、模型调用失败了,状态还停在 0("进行中"),于是用户还能对着一个自己已经点了"结束"的会话继续发消息**——聊天框还开着,语义上自相矛盾。

**这次设计:一进 `finish`、校验通过,就先把 0→1——"已结束、不能再聊"立刻生效,不等模型返回。** 然后才调模型;成功了 1→2、报告落库。这样即使模型调用失败,状态也稳稳停在 1("已结束但没报告"),不会出现"点了结束还能聊";而状态 1 允许再次 `finish` 触发重试,会话不会卡死在一个"既不能聊、又没报告"的死角。

## 十一、幂等:业务判断 + 唯一索引,双保险

### 11.1 第一层:业务层的状态短路

```java
InterviewSession session = mustFindOwnSession(sessionId);
// 报告已经生成过,直接返回已有的,不再调模型
if (session.getStatus() == 2) {
    return toReportVO(interviewReportMapper.selectBySessionId(sessionId));
}
```

用户手滑点两次"结束"、或两个标签页各点一次——第二次进来 `status` 已经是 2,直接把已存的报告返回,**不重新调模型**(省钱、更快)。

**为什么这个短路放在抢锁之前?** 它只读不写、不调模型,没必要为它付一次抢分布式锁的 Redis 网络往返。**能用一次快速判断挡掉"根本不需要抢锁"的请求,就不要多此一举去抢锁。**

### 11.2 第二层:数据库唯一索引兜底

建表时 `interview_report` 有 `UNIQUE KEY uk_session_id (session_id)`。这是防**极端并发**的:两个请求几乎同时通过了 `status` 检查、都想插报告——虽然那把会话锁本来就能挡住这种并发,但"锁 + 唯一索引"两道防线叠加,比只靠任何一道都稳。即使业务判断被某种极端时序绕过,数据库这一层也**绝不允许**同一个 `session_id` 插进第二条。

**通用工程习惯:业务层幂等判断负责覆盖正常场景、给用户合理提示;数据库约束负责兜底极端并发。两者都要,少一个都可能在高并发下漏。**

## 十二、`finish` 复用 `chat` 的那把会话锁

```java
String lockKey = LOCK_PREFIX + sessionId;   // 和 chat 用的是同一个 key
Boolean locked = stringRedisTemplate.opsForValue().setIfAbsent(lockKey, "1", LOCK_TTL_SECONDS, TimeUnit.SECONDS);
if (!Boolean.TRUE.equals(locked)) {
    throw new BusinessException(ErrorCode.TOO_MANY_REQUESTS, "会话正在处理中，请稍后再试");
}
```

**为什么 `finish` 和 `chat` 要抢同一把锁?** 想象:用户一个标签页正在聊(`chat` 的流式回复还没落库),另一个标签页(或手滑)几乎同时点了"结束"。`finish` 这时去查历史、拼 `transcript`,可能**刚好错过正在生成中的最后一条回复**,报告漏评了最后一轮;更糟的是,如果那条 `assistant` 消息在 `finish` 已经把状态改成 1 之后才落库,会出现"报告已经生成了,但消息表还在追加新消息"的数据不一致。

**这把锁是"整场会话级别的互斥",不区分锁的是 `chat` 还是 `finish`——只要还在处理这场会话的任何一次 AI 相关操作,别的操作(不管继续聊还是结束)都得排队。** 这是 2.3 学的"用同一把锁防同一会话的两次并发 `chat` 互相踩踏"的自然延伸。

## 十三、JSON 列的存与取:`serializeReportContent` / `toReportVO`

建表时 `content` 用的是 MySQL 8 的 **`JSON` 类型**(不是 `TEXT`):写入时会校验必须合法 JSON,读时能用 `JSON_EXTRACT` 直接取子字段。而 `score` **单独拉成普通列**——因为它是唯一以后可能要排序/筛选/算平均分的字段(比如"我的历次面试分数趋势"),普通列能直接建索引、直接 `ORDER BY`;JSON 内部字段做这些要么低效、要么得上"虚拟列+索引"。**判断标准:要被数据库直接筛选/排序/计算的字段拉成普通列,整存整取的部分打包进 JSON 列。**

### 13.1 存:record → JSON 字符串

```java
private String serializeReportContent(InterviewReportResult result) {
    try {
        return objectMapper.writeValueAsString(Map.of(
                "highlights", result.highlights(),
                "weaknesses", result.weaknesses(),
                "summary", result.summary()
        ));
    } catch (JsonProcessingException e) {
        throw new RuntimeException(e);
    }
}
```

只把 `highlights/weaknesses/summary` 三个打包进 JSON(`score` 已经单独成列了,不重复放)。存进实体的 `content`(Java 侧是 `String`,JDBC 层面 MySQL 的 JSON 列收发的就是字符串)。

### 13.2 取:JSON 字符串 → VO

```java
@SuppressWarnings("unchecked")
private InterviewReportVO toReportVO(InterviewReport report) {
    InterviewReportVO vo = new InterviewReportVO();
    vo.setScore(report.getScore());
    vo.setCreateTime(report.getCreateTime());
    try {
        Map<String, Object> content = objectMapper.readValue(report.getContent(), new TypeReference<>() {});
        vo.setHighlights((List<String>) content.get("highlights"));
        vo.setWeaknesses((List<String>) content.get("weaknesses"));
        vo.setSummary((String) content.get("summary"));
    } catch (JsonProcessingException e) {
        throw new RuntimeException(e);
    }
    return vo;
}
```

**这里为什么必须用 `new TypeReference<>() {}`,不能写 `.class`?** 因为要反序列化成的是带泛型的 `Map<String, Object>`。Java 的泛型信息在编译后会被**擦除**,运行时 `Map.class` 只知道"这是个 Map",不知道 key/value 是什么类型。`TypeReference` 借助一个**匿名内部类**的技巧,把完整泛型信息保留到运行时,`ObjectMapper` 才能正确还原。**记结论:反序列化任何带泛型的集合类型(`List<T>`、`Map<K,V>`)都要用 `new TypeReference<...>() {}`,不能直接 `.class`。**(这个坑在 `docs/数据组装与转换专题.md` 第六节、`spring-ai初学.md` 里都出现过——已经是第三次了。)

**注意 import 的是 `com.fasterxml.jackson.core.type.TypeReference`**(Jackson 的),不是 `org.springframework.asm.TypeReference`(Spring 内部 ASM 用的、完全不相干的同名类)——这次真的导错过,见第三部分坑 1。

# 第三部分 · 这次真实踩过的 8 个坑(编译不过复盘)

> 下面这些不是编出来的反面教材,是这次 2.6 代码在**实际敲的时候真的写错、导致整个项目编译不过**的问题。你自己踩过的坑比任何"最佳实践"都记得牢,专门复盘一遍。前几个是"编译器能帮你抓"的低级错,后几个是"编译器抓不到、跑起来才炸"的隐蔽错——后者才是真正要长记性的。

### 坑 1:`TypeReference` 导错包(编译不过,但报错信息会误导你)

```java
import org.springframework.asm.TypeReference;   // ❌ 这是 Spring 内部 ASM 字节码工具的类
```

应该是:

```java
import com.fasterxml.jackson.core.type.TypeReference;   // ✅ Jackson 的
```

两个类**同名**,IDE 自动补全时很容易选错那个(尤其你只敲 `TypeReference` 按回车)。选错之后,`objectMapper.readValue(json, new TypeReference<>(){})` 这行会报"没有匹配的 `readValue` 重载"——**报错点在 `readValue`,但真正的病根在最上面那行 import**,新手很容易对着 `readValue` 死磕。**教训:类名眼熟不代表包对,导包时瞄一眼包路径**,涉及 Jackson 就认准 `com.fasterxml.jackson`。

### 坑 2:`.entity(...)` 后面漏了分号

```java
return chatClient.prompt()
        .system(buildJudgePrompt())
        .user(transcript)
        .call()
        .entity(InterviewReportResult.class)   // ❌ 少了 ;
```

链式调用写长了,最后一行忘了分号。这个编译器会直接报"需要 ';'",算最好抓的一类。提一句只是因为:**链式调用换行写的时候,分号在最后一行的末尾,容易被漏。**

### 坑 3:多了一个 `}`,把整个类提前闭合(最坑的结构错)

`buildJudgePrompt` 写完之后多打了一个右花括号:

```java
    private String buildJudgePrompt() {
        return """ ... """;
    }
    }                              // ❌ 多出来的一个 }

    private String buildTranscript(...) { ... }   // 现在这个方法在"类的外面"了
```

第二个 `}` 提前把 `class` 闭合了,导致 `buildTranscript`、`toReportVO`、`serializeReportContent` 等等**全都跑到类的外面**——Java 不允许方法定义在类外面,于是从这里往下所有代码全爆红。**这类"多/少一个括号"的错最难肉眼定位**,因为报错会集中在"类外面那些方法"上,你会以为是那些方法有问题,其实病根是上面多了一个括号。**排查技巧**:用 IDE 的"折叠代码块 / 匹配括号"功能,或者像我一样数一下 `{` 和 `}` 的总数是否相等(这次修完是各 57 个,平衡)。

### 坑 4:`buildTranscript` 返回类型写成了 `Object`

```java
private Object buildTranscript(List<InterviewMessage> history) {   // ❌ 应该是 String
    ...
    return sb.toString();
}
```

方法体明明 `return sb.toString()`(返回 String),签名却写了 `Object`。单看这个方法编译不报错(String 是 Object 的子类,return 合法),但**调用点**炸:`generateReportWithRetry(buildTranscript(history))` 里,`generateReportWithRetry(String)` 要求传 String,你传了个 `Object` 进去——编译器报"`Object` 不能转成 `String`"。**教训:返回类型别图省事写 `Object`,写成方法真正返回的具体类型**,不然把"类型不匹配"的错误从定义点推迟到了调用点,更难找。

### 坑 5:`serializeReportContent` 方法整个没写(引用了但没定义)

`finishInterview` 里 `report.setContent(serializeReportContent(result));` 调了这个方法,但方法**根本没定义**。编译器报"找不到符号 `serializeReportContent`"。**这类"调了没定义"的错,和坑 3(方法被括号挤到类外)长得很像**——都表现为"某个方法找不到",但一个是没写、一个是写了但位置不对。排查时先确认:这个方法到底**存不存在**(全局搜方法名),再看**在不在类里面**。

### 坑 6:`InterviewReportMapper` 接口是空的(编译不过)

```java
@Mapper
public interface InterviewReportMapper {
    // ❌ 空的,一个方法都没有
}
```

但 `finishInterview` 里在调 `interviewReportMapper.insert(report)` 和 `.selectBySessionId(sessionId)`。接口里没这两个方法声明,编译器报"找不到 `insert` / `selectBySessionId`"。**先写了 Service 调用、后忘了在 Mapper 接口里补方法声明**,是很典型的"从上往下写"漏掉中间层。

### 坑 7:`InterviewReportMapper.xml` 完全没建(编译能过,一调就炸)

这是**编译器抓不到、运行时才炸**的一类——比前面几个隐蔽得多。Mapper 接口有方法声明、Service 也调了,Java 侧全对,**编译通过**。但 MyBatis 的 SQL 写在 XML 里,XML 是**运行时**才被解析绑定的。`resources/mapper/` 下没有 `InterviewReportMapper.xml`,于是第一次真的调 `insert` / `selectBySessionId` 时,抛 `BindingException: Invalid bound statement (not found)`。

**这类"冷路径"错误的可怕之处**:如果你只测了"聊天"没测"结束面试",这个坑根本不会暴露,直到某天真点了"结束"才炸。这也是 2.4 坑 5(XML 的 `id` 写成类名)的同类——**MyBatis 的接口↔XML 是靠字符串约定的,没有编译器兜底,写完一个新 Mapper 一定要对照检查:接口方法名 ↔ XML 的 `<select>/<insert>` 的 `id` 一字不差,`<select>` 有没有写 `resultType`。**

### 坑 8:三张表的建表 SQL 没进 `sql/init.sql`(换台机器就消失)

`interview_session` / `interview_message` / `interview_report` 三张表,之前一直是直接在 Navicat 手建的,**没写进 `sql/init.sql`**。后果:项目在你这台机器上能跑(因为库里手动建过了),但**换一台机器、或者别人 clone 下来照 `init.sql` 初始化数据库,这三张表凭空消失**,一跑就"表不存在"。尤其 `interview_report` 是这次新表,你实际库里建了没都得先确认。**教训:建表语句是项目的一部分,必须进版本控制的 SQL 脚本里,不能只存在于你本地的 Navicat 操作历史里。**
