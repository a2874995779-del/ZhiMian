## 第 0 章 · 如何介绍这个项目

**Q0.1 用两三句话介绍一下这个项目。**

智面是一个"AI 模拟面试 + 面试题库"的后端项目,Spring Boot 3.5 + MyBatis + MySQL + Redis + Spring AI。核心有两块:一块是**题库系统**(分类/标签/题目 CRUD、动态分页、详情缓存、浏览量统计、答题排行榜),练的是经典的 CRUD + 缓存 + 数据库工程;另一块是**AI 模拟面试**(创建会话 → 多轮流式对话 → 结束生成结构化评价报告),练的是大模型应用工程——prompt 设计、多轮上下文管理、SSE 流式输出、结构化输出、以及外部依赖的健壮性治理。

**Q0.2 这个项目你觉得最有含金量、最能拿出来讲的是哪部分?**

AI 模拟面试这条链路。因为它不是"调一次模型返回一段话"那么简单,而是要解决一串真实工程问题:① 大模型是**无状态**的,多轮对话的"记忆"要靠我自己每轮把历史重发,还要在 token 预算内做滑动窗口裁剪;② 回答慢,必须做 **SSE 流式**(打字机效果),这就牵出 Servlet 异步、响应式 Flux 和阻塞 MVC 混用;③ 要生成能被程序用的**结构化报告**,涉及结构化输出原理和幂等状态机;④ AI 是不可控的外部依赖,要做**超时、限流、异常收敛**。这几块串起来,就是一个小而完整的"LLM 应用后端"。

## 第 1 章 · 认证与安全

### ⭐ Q1.1 JWT 由哪三段组成?每段作用是什么?

三段用 `.` 隔开:`header.payload.signature`。

- **Header**:声明签名算法(本项目 HS256)和类型(JWT)。
- **Payload**:载荷,放 claims。我项目里只放了 `jti`(token 唯一 id,给黑名单用)、`sub`(用户 id)、`role`、`iat`(签发时间)、`exp`(过期时间)。
- **Signature**:对 `base64(header).base64(payload)` 用密钥做 HMAC-SHA256 得到的签名,防篡改。

前两段是 **base64url 编码,不是加密**,任何人都能解开看内容——所以载荷里绝不能放密码这类敏感信息。

### ⭐ Q1.2 为什么 payload 不能放敏感信息,但 signature 却能防篡改?这两者矛盾吗?

不矛盾,它们解决的是两个不同问题。payload 是**明文可读**的(只是 base64,不是加密),所以"保密"这件事 JWT 根本不负责,敏感信息不能放。而 signature 保证的是**完整性(防篡改)**:攻击者可以读、也可以改 payload,但他没有服务端的密钥,**改完算不出对应的新签名**;服务端验签时用同一个密钥重新算一遍,对不上就判定 token 被篡改、拒绝。一句话:**JWT 保证"没被人偷改",不保证"没被人看见"**。

### Q1.3 对称加密(HS256)和非对称(RS256)签发 JWT 各自适用什么场景?

- **HS256**:签名和验签用**同一个密钥**。简单、快,适合**单体服务**——签发和校验都在我自己这一个服务里,密钥不用外传。本项目就是这种。
- **RS256**:私钥签发、公钥验签。适合**多服务/第三方**场景:认证中心用私钥签发,各个业务方拿公钥验签就行,公钥泄露也没法伪造 token。代价是慢、密钥管理复杂。

### ⭐ Q1.4 拦截器和过滤器的本质区别?为什么项目选拦截器?

- **Filter** 是 Servlet 规范的东西,在 `DispatcherServlet` 之前,拦的是所有请求,拿不到"这个请求最终交给哪个 Controller 方法处理"。
- **Interceptor** 是 Spring MVC 的,在 `DispatcherServlet` 之内、Handler 前后,能拿到 `HandlerMethod`,也就是**能读到目标方法上的注解**。

我项目里权限控制是靠方法级注解 `@Public`(免登录)、`@RequireAdmin`(要管理员)实现的,拦截器能通过 `HandlerMethod` 读到这些注解、区分三种情况(不需要登录 / 登录即可 / 必须 admin),Filter 拿不到方法注解,所以选拦截器。

### ⭐ Q1.5 `postHandle` 和 `afterCompletion` 时机分别是什么?为什么清理 ThreadLocal 必须放 `afterCompletion`?

- `postHandle`:Handler 执行完、视图渲染前触发,而且**只有 Handler 正常返回才触发**——中途抛异常就不走了。
- `afterCompletion`:整个请求完成后触发,**无论正常还是抛异常都会执行**。

ThreadLocal 存的是当前登录用户,而 Tomcat 的线程是**复用**的:这个线程处理完我的请求,会被还回线程池去处理别人的请求。如果清理放在 `postHandle`,一旦 Handler 抛了异常就漏清理,ThreadLocal 里的"上一个用户"会残留到下一个复用这个线程的请求里——**张冠李戴、越权**。所以必须放 `afterCompletion`,保证任何情况下都清理干净。

### Q1.6 如果 `preHandle` 里 `UserContext.set()` 之后、`return true` 之前抛异常会怎样?

`preHandle` 返回 false 或抛异常时,Spring **不会调用 `afterCompletion`**(只有 `preHandle` 成功返回 true 的拦截器才会被回调 `afterCompletion`),于是刚 `set` 进去的 ThreadLocal 没人清,又泄漏了。所以正确做法是:**先做完所有可能抛异常的校验(解析 token、验签、查黑名单),确认无误后再 `set`**,把 `set` 放在整个 `preHandle` 最后、紧挨着 `return true`,让"set 了就一定能被 afterCompletion 清理"。

### ⭐ Q1.7 JWT 是无状态的,为什么登出还要一个有状态的黑名单?这违背 JWT 设计初衷吗?

JWT 的"无状态"意味着**服务端不存 token、只靠验签判断有效性**——但也正因为不存,**服务端没法主动让一个还没到期的 token 失效**。而"登出"本质就是"让这个 token 立即失效",这跟无状态天然冲突。所以要引入一个有状态的黑名单:登出时把这个 token 的 `jti` 写进 Redis,TTL 设成**它剩余的有效期**;拦截器验签通过后再查一下黑名单,命中就拦下。

这确实是对纯无状态的妥协,但是**有意识的权衡**:我没有为了纯粹而放弃"能登出"这个必需功能;黑名单只存已登出的少量 token、且到期自动清,成本可控。面试官要的就是你能说清这个 tradeoff,而不是假装 JWT 完美。

### Q1.8 除了黑名单,还有别的让 token 提前失效的方案吗?

- **短 token + refresh token**:access token 有效期很短(几分钟),失效影响面小;refresh token 存服务端、可撤销。登出撤 refresh token 即可。
- **token 版本号**:用户表加一个 `token_version` 字段,签发时写进 claim,校验时比对;要让某用户所有 token 失效,把库里版本号 +1 即可(改密码、强制下线场景很好用)。

对比:黑名单精确到单个 token、实现简单,但要额外存储;版本号方案不用逐个存 token,但粒度是"该用户全部 token",不能只失效其中一个。

### Q1.9 黑名单 TTL 如果写死固定 24 小时会出什么问题?

两个方向的反例:

- **TTL 比 token 剩余有效期短**:黑名单先过期,但 token 还没到期——这个已登出的 token 又"复活"能用了,登出形同虚设。
- **TTL 比剩余有效期长**:token 早就自己过期了,黑名单还占着内存,纯浪费。

所以正确做法是 **TTL = token 的剩余有效期**(`exp - now`),两者同生共死。还要加个 `remainingSeconds <= 0` 的兜底,避免给已过期 token 设一个负数 TTL。

### Q1.10 Redis 的 key 过期是"到点立刻物理删除"吗?

不是。Redis 用**惰性删除 + 定期删除**组合:惰性删除是"你下次访问这个 key 时,发现过期了才删";定期删除是后台定时**随机抽查**一批设了过期时间的 key,删掉其中过期的。两者配合:惰性删除保证不会返回过期数据,定期删除兜底清理那些"过期了又一直没人访问"的 key,避免它们永远占内存。

### ⭐ Q1.11 为什么把用户提升为 admin 后,用旧 token 访问管理员接口还是 403?

因为 `role` 是**签发 token 那一刻写死进 payload 的 claim**,之后 token 内容不再变。数据库里把 role 改成 admin,不会回头去改已经发出去的旧 token 里的 role,拦截器读的是 token 里的旧 role(user),所以还是 403。必须**重新登录换一个新 token**,新 token 才带 admin。这暴露了 JWT 的局限:**claim 是签发时的快照,不反映之后的数据变化**。要支持"改角色立即生效",得引入前面说的 token 版本号,或者每次都回查数据库拿最新 role(但那就丢了无状态的性能优势)。

### ⭐ Q1.12 什么是水平越权?为什么"会话不存在"和"会话不属于你"要返回同一个错误码?

水平越权(BOLA,OWASP API 安全榜第一名):同权限级别的用户,通过换 URL 里的资源 id,访问到别人的数据。我项目里所有"按 sessionId 操作"的接口(chat/详情/finish)都走同一个 `mustFindOwnSession`,里面既查存在性、又校验 `userId` 归属,任一不满足都抛**同一个** `NOT_FOUND`。

为什么两种情况用同一个错误码:如果"不存在"返回 404、"存在但不是你的"返回 403,就等于给攻击者一个**探测器**——他拿随机 id 挨个试,凡是返回 403 的就说明这个 id 真实存在(只是不属于他),能反推出系统里合法数据的 id 分布。**对当前用户来说,"不是我的"和"根本不存在"必须从外部看起来毫无区别**,才不泄露任何信息。

## 第 2 章 · MyBatis 与数据库

### ⭐ Q2.1 `#{}` 和 `${}` 底层分别生成什么?为什么能防注入?

- `#{}` 生成的是 **PreparedStatement 的占位符 `?`**,参数值是**后来单独绑定**上去的。SQL 结构在预编译时就定死了,用户传的值永远只当"数据"处理,不会被当成 SQL 语法解析——所以能防注入。比如传 `1 OR 1=1`,它整体被当成一个字符串值去匹配,不会改变 SQL 逻辑。
- `${}` 是**直接字符串拼接**进 SQL,用户输入能改变 SQL 结构,有注入风险。

只有在**表名、列名、ORDER BY 的字段**这类"不能用占位符的位置"才不得不用 `${}`,这时必须用**白名单**校验(只允许固定几个字段名)把风险关死。

### ⭐ Q2.2 `@Transactional` 默认什么异常回滚?抛受检异常为什么不回滚?怎么改?

默认只在 **`RuntimeException` 和 `Error`** 下回滚,**受检异常(checked exception)默认不回滚**。这是 Spring 沿用 EJB 的约定:受检异常被视为"业务上可预期、可恢复"的情况,不自动回滚。要让受检异常也回滚,加 `@Transactional(rollbackFor = Exception.class)`。我项目题目新增/修改里就踩过这个点,自测专门做了"抛 RuntimeException 验证回滚 / 抛受检异常验证不回滚"的对比实验。

### ⭐ Q2.3 事务自调用为什么失效?怎么解决?

`@Transactional` 是靠 **AOP 代理**实现的:Spring 给你的 Bean 生成一个代理对象,外部调用先进代理、代理开启事务、再进真实方法。但如果在类内部用 `this.addQuestion()` 调用本类的事务方法,**走的是原始对象、不经过代理**,事务增强逻辑压根没触发,所以失效。

解决办法(至少说两种):① 把事务方法拆到**另一个 Bean** 里,通过注入调用(跨 Bean 就走代理了);② 注入自己的代理对象(`@Lazy` 注入自身)或用 `AopContext.currentProxy()` 拿到代理再调。

### Q2.4 `<foreach>` 批量插入和 for 循环单条插入,性能差在哪?插 10 万行要注意什么?

差在:① **网络往返**——单条循环是 N 次数据库往返,批量是 1 次;② **SQL 解析**——单条要解析 N 次,批量拼成一条 `INSERT ... VALUES (),(),()` 只解析一次;③ **事务提交**边界。

插 10 万行不能一条 SQL 梭哈:要**分批**(每批 500~1000 行),否则单条 SQL 太大可能超 `max_allowed_packet`;JDBC 层可以开 `rewriteBatchedStatements=true` 让驱动真正合并批处理;分批之间注意事务粒度,别一个事务包 10 万行导致 undo log 爆炸。

### Q2.5 逻辑删除和物理删除,项目里为什么题目用逻辑、关联表用物理?

题目是**有价值、可能要恢复、被别处引用**的核心数据,用逻辑删除(`is_deleted=1`),库里还在、能找回。`question_tag` 关联表只是"题和标签的连线",本身没有独立价值,删了就删了,用物理删除更干净。

逻辑删除的**三个麻烦**(常被追问):① 所有查询都得带 `WHERE is_deleted=0`,漏一个就查出脏数据;② **唯一索引冲突**——一条被逻辑删除的记录还占着唯一键,想再插一条同名的会撞唯一约束(得把删除标记也纳入唯一索引,或者用时间戳);③ **存储膨胀**,删了的行一直堆在表里。

### ⭐ Q2.6 `LIMIT 100000, 10` 为什么慢?怎么优化?

慢在:MySQL 要**先扫出前 100010 行,再把前 100000 行丢掉**,只返回最后 10 行——扫的行数随 offset 线性增长,深翻页极慢。

优化两种思路:① **游标/记住上一页最大 id**(seek method):`WHERE id > 上一页最后一个id LIMIT 10`,直接用索引定位,不用扫再丢;② **子查询先定位主键再回表**:`... WHERE id >= (SELECT id FROM t ORDER BY ... LIMIT 100000, 1) LIMIT 10`,让深翻页只在覆盖索引上跳,减少回表。

### ⭐ Q2.7 EXPLAIN 里 `Using filesort` 是什么?为什么联合索引能消掉它?

`Using filesort` 表示 **排序没能借助索引,MySQL 得在内存/磁盘里额外做一次排序**,数据量大时很耗。我项目题库查询是 `WHERE category_id=? ORDER BY create_time DESC`,如果只有 `category_id` 单列索引,按 `category_id` 过滤后这批数据在 `create_time` 上是无序的,还得 filesort。建 `(category_id, create_time)` **联合索引**后,索引里数据已经"先按 category_id、再按 create_time"排好,过滤 + 排序一步到位,filesort 消失。这也用到**最左前缀**:`(category_id, create_time)` 同时能覆盖"只按 category_id 查"的场景,原来的单列索引就可以去掉了。

### Q2.8 列表的 categoryName/tags 为什么用"分页主查询 + 内存组装",不用一条大 JOIN?

如果用大 JOIN,一道题有 3 个标签就会 JOIN 出 3 行,`LIMIT 10` 会在这些"膨胀后的行"上截断——**你以为取了 10 道题,实际可能只取到三四道题的碎片**,分页彻底乱掉。所以正确做法:先用主查询 `LIMIT 10` 干净地分页出 10 道题,收集这 10 个 id,**再一次 `IN` 批量查出它们的标签**,在内存里用 `Map<questionId, List<tag>>` 组装回去。既保证分页正确,又只多发一条 SQL(不是 N 条)。

### Q2.9 `resultType` 自动驼峰映射和 `resultMap` 的区别?什么时候必须用 `resultMap`?

`resultType` + 开启 `map-underscore-to-camel-case`,能自动把 `create_time` 映射到 `createTime`,适合**单表、字段一一对应**的简单场景。当遇到**嵌套对象、一对多集合、列名和属性名无法用驼峰规则对应、或者要复用映射**时,就得显式写 `resultMap`。

### Q2.10 `Invalid bound statement (not found)` 一般是什么原因?

MyBatis 的 Mapper 接口和 XML 是**靠字符串约定绑定**的,没有编译器兜底。这个报错通常是:① XML 的 `namespace` 不是 Mapper 接口的全限定名;② `<select>/<insert>` 的 `id` 和接口方法名对不上;③ XML 没被扫描到(`mapper-locations` 配置)。我项目里多次踩过——尤其新建 Mapper 时,一定要对照检查"接口方法名 ↔ XML 的 id 一字不差、有没有写 resultType"。而且这类错**编译期查不出**,是运行时第一次真的调到那条语句才炸(见 Q5.x 冷路径)。

## 第 3 章 · Redis 应用

### ⭐ Q3.1 缓存穿透、雪崩、击穿分别是什么?怎么解决?本项目怎么做的?

- **穿透**:查一个**根本不存在**的数据,缓存永远不命中,每次都打到数据库(可被恶意刷)。解法:**缓存空值**(给不存在的也缓存一个空标记,TTL 设短),或**布隆过滤器**。我项目详情接口对查不到的 id 缓存了空值、且空值 TTL 明显短于正常缓存。
- **雪崩**:大量 key **在同一时刻集中过期**,瞬间全部回源,数据库被打垮。解法:给 TTL **加随机抖动**,把过期时间打散。
- **击穿**:某个**热点 key 恰好过期**的瞬间,大量并发同时回源重建。解法:**互斥锁**——只放一个请求去重建,其余等待;或**逻辑过期**。我项目热门题目/详情用了互斥锁重建,锁的释放放在 `finally` 里防死锁,重试等待设了上限。

### Q3.2 空值缓存和布隆过滤器防穿透,各自优缺点?

- **空值缓存**:实现简单,直接复用现有缓存逻辑;缺点是**要为每个被查的不存在 id 占一份缓存**,如果攻击者用海量随机 id 打,空值也会占不少内存(靠短 TTL 缓解)。
- **布隆过滤器**:用很小的空间就能判断"这个 id **一定不存在** / 可能存在",挡在缓存前面;缺点是有**误判率**(可能把不存在误判成存在,放过去查一次库)、且**不好删除**元素。数据集合相对固定、id 空间大时布隆过滤器更合适。

### ⭐ Q3.3 你那个防击穿的互斥锁,释放时没校验"锁是不是自己加的",有什么问题?生产怎么做?

问题:假设 A 拿到锁但执行超时,锁到 TTL 自动释放了;这时 B 拿到锁;然后 A 执行完来 `DEL` 锁,**删掉的其实是 B 的锁**——锁保护失效,可能又有 C 进来,和 B 并发重建。

生产做法:加锁时 value 存一个**唯一标识**(比如 UUID/线程 id),释放时用 **Lua 脚本原子地"比对 value 相等才删"**(判断和删除必须原子,不能先 get 再 del);或者直接用 **Redisson** 这类成熟的分布式锁(自带看门狗续期 + owner 校验)。

### Q3.4 防击穿除了互斥锁,还有"逻辑过期",两者取舍是什么?

- **互斥锁**:缓存物理过期,只放一个线程重建、其余等待。**牺牲可用性**(重建期间其他请求要等)**换一致性**(拿到的是最新数据)。
- **逻辑过期**:缓存**永不物理过期**,数据里存一个"逻辑过期时间"字段;发现逻辑过期了,**异步**起个线程去重建,当前请求**先返回旧数据**。**牺牲一致性**(重建完成前大家拿到的是旧值)**换可用性**(永远不用等、不阻塞)。

选哪个看业务能不能容忍短暂旧数据。

### ⭐ Q3.5 浏览量为什么不直接 `UPDATE view_count = view_count + 1`?

`UPDATE ... +1` 每次都要**对这一行加行锁**,高并发下大家抢同一行的锁,串行化、性能差,还可能死锁/锁等待。我的做法:每次访问只往 Redis 计数器 `INCR`(纯内存、原子、极快),再用 `@Scheduled` 定时任务把增量**批量合并**写回 MySQL,写完 `GETDEL` 清计数器。用一点"浏览量短暂不精确"换来了热点写的高吞吐。

### Q3.6 详情缓存里的 viewCount 和库里真实值不一致,凭什么说可以接受?换成库存呢?

浏览量是**展示型、容忍误差**的数据,少几个多几个用户根本无感,最终会被定时任务对齐,属于可接受的最终一致。**换成"库存数量"就绝对不行**——库存直接决定"能不能下单",不一致会导致超卖(把已经没货的卖出去),这种**涉及资金/交易正确性**的数据必须强一致,得用数据库行锁/乐观锁/`UPDATE ... WHERE stock>0` 这类保证。判断标准:**这个数不准会不会造成业务后果**。

### Q3.7 Redis 单线程为什么反而能扛高并发?

三点:① **纯内存操作**,没有磁盘 IO 瓶颈;② **单线程没有多线程的锁竞争和上下文切换开销**,命令一个个原子执行,简单又快;③ 网络层用 **IO 多路复用(epoll)**,一个线程就能高效管理海量连接。所以"单线程"指的是**命令执行**是单线程,不代表它慢。

### ⭐ Q3.8 排行榜为什么用 ZSet?底层跳表相比红黑树好在哪?

排行榜要"按分数排序 + 取 TopN + 范围查询",Redis 的 **ZSet(有序集合)** 天生支持,`ZINCRBY` 加分、`ZREVRANGE` 取 TopN 都是现成的。

底层是**跳表(skip list)**不是红黑树,原因:① **范围/区间查询**上跳表天然是"排好序的链表 + 多级索引",找到起点后**顺着链表往后遍历**就行,`ZRANGE` 这种区间操作复杂度和实现都简单;红黑树做区间遍历要中序遍历,复杂;② 跳表**实现简单得多**,增删改的平衡逻辑比红黑树好写好维护;性能上两者都是 O(logN),但工程上跳表更划算。

### ⭐ Q3.9 排行榜加分为什么用 `ZINCRBY`,不能"先 ZSCORE 查、再 ZADD 写回"?

因为"先查后写"是两步、**非原子**,并发下会**丢更新**:A 和 B 同时读到分数 5,各自 +1 算出 6,先后写回,最终是 6——**丢了一次**,应该是 7。`ZINCRBY`(对应 `incrementScore`)把"读-改-写"合成**一条原子命令**,并发再多也一次不丢。这和第 6 章限流用 `SET NX EX`、浏览量用 `INCR` 是**同一个"用单条原子命令替代读改写"的思想**。

### Q3.10 `answer_record` 表和 Redis ZSet 可能不一致,为什么可接受?要强一致怎么改?

`answer_record` 是**事实来源(source of truth)**:答对答错都插一行流水,永久保存。Redis ZSet 是**实时视图**,加分靠 `ZINCRBY`。可能的不一致:流水已经插了,但 Redis 刚好在两步之间挂了、丢了一次 `ZINCRBY`。这可接受,因为**榜单差一分无伤大雅,而且能靠 `answer_record` 重跑统计脚本把 ZSet 重建出来**——数据没有永久丢失。反过来只有 Redis 没有流水表,数据一丢就找不回。要强一致代价很高(两阶段提交),更现实的是**定时对账**:周期性用流水表校准 Redis。

### Q3.11 日榜 key 为什么"首次创建才设 TTL",不每次都 `EXPIRE`?

日榜 key 当天有效、第二天该过期。如果每次加分都无脑 `EXPIRE key 到今天结束`,逻辑上其实也对;但更严谨的是**只在首次创建时设 TTL**,避免"每次都重设过期时间"这种多余操作,也避免万一 TTL 算法有偏差时被反复刷新。这个场景下不判断不会引发功能 bug,但**"设置过期时间应该和 key 的生命周期绑定、而不是每次写都碰它"这个意识值得养成**——换个场景(比如会话上下文那种"每活跃一次就该续期"的)判断逻辑就完全相反,得想清楚"这个 key 到底该固定过期还是滑动续期"。

### Q3.12 排行榜查昵称,为什么先收集所有 userId 再查一次,不拿到一个查一个?

避免 **N+1 查询**。榜单 100 个名次,如果拿到一个 `userId` 就查一次昵称,就是 100 条 SQL;先把 100 个 id 收集起来发**一条 `IN` 批量查**,只 1 条 SQL。这和题库列表补标签、上下文补数据是同一个套路——**循环里绝不现查,收集 id 批量查再内存组装**(见 `docs/数据组装与转换专题.md`)。

## 第 4 章 · Spring AI 与大模型工程

### Q4.1 为什么能用 OpenAI 协议的客户端去调硅基流动的 DeepSeek?说明了什么?

因为很多厂商(硅基流动、DeepSeek、通义等)都**兼容 OpenAI 的 HTTP 接口协议**(请求/响应格式、endpoint 风格一致),只是 `base-url` 和 `api-key` 不同。所以 `spring-ai-starter-model-openai` 这个 starter 配上 DeepSeek 的 base-url 就能直接用。这说明 **OpenAI 的接口事实上成了行业标准**,也说明只要协议统一,换厂商几乎零成本。

### ⭐ Q4.2 Spring AI 里 Model / ChatClient / Advisor 三层抽象各负责什么?

- **Model**:最底层,直接和具体厂商 API 对接(拼 HTTP 请求、解析响应)。
- **ChatClient**:给业务代码用的**高层门面**,`prompt().system().user().call()` 这套流式 API 就是它,屏蔽了底层细节。
- **Advisor**:可插拔的**请求/响应拦截器**,能在调用前后统一织入逻辑(比如上下文裁剪、日志、审计),不侵入业务代码。

分层的好处见下一题。

### Q4.3 要把模型从"硅基流动 DeepSeek"换成另一个 OpenAI 兼容厂商,要改几处?说明什么?

基本只改**配置**(`base-url`、`api-key`、`model` 名),业务代码一行不动。因为业务代码只依赖 `ChatClient` 这个门面,不关心底层是哪家。这就是 Spring AI 这套抽象的价值:**把"业务逻辑"和"具体模型厂商"解耦**,厂商变化被隔离在配置层。

### ⭐ Q4.4 为什么"插入 session + 调用 AI"不能包在同一个数据库事务里?

因为 AI 调用是一次**耗时不可控的外部网络请求**(几秒甚至几十秒)。如果包在事务里,这个**数据库连接和事务会在整个 AI 调用期间一直被占着**——事务不提交、连接不释放。并发一上来,连接池很快被这些"陪着 AI 一起等"的连接占满,**数据库层面直接瘫痪**。所以我 `createInterview` 里先把 session 插库(短事务),然后**在事务外**调 AI。

如果非要"AI 失败就回滚 session":代价是要么强行把外部调用拉进事务(上面说的连接占用问题),要么改成**补偿模式**——先建 session、AI 失败后再单独发一个"删除/标记失败"的补偿操作(Saga 思路)。我项目权衡后选择"AI 失败不补偿、session 留着",因为一个空会话无害,不值得为它付出复杂度。

### ⭐ Q4.5 为什么大模型多轮对话每次都要把历史重发?和 Web 服务端存 session 有什么本质区别?

因为大模型 API 是**无状态**的:它不记得你上一轮说了什么,每次调用都是独立的。要让它"记住"上下文,只能**每一轮都把之前的完整历史(system + 历次问答)重新拼进请求发过去**。这跟传统 Web"服务端存 session、客户端只带个 sessionId"本质不同——那种是服务端**有状态**地替你记着;而大模型这边"记忆"是**每次现场重建、由调用方负责携带**的。

### ⭐ Q4.6 system prompt 和 user 消息分别放什么?"提出第一个问题"为什么不能写进 system prompt?

- **system prompt**:定**角色和长期行为约束**——"你是资深 Java 面试官、每次只问一个问题、根据回答质量调整深度"。它要**每一轮都原封不动带上**,因为模型每次调用都要被重新告知"你是谁"。
- **user 消息**:某一轮的**具体输入**。

"请提出第一个问题"是一句**一次性指令**,只在开场用一次。如果写进 system prompt,那它就会**每一轮都被重发**,模型每轮都被要求"提出第一个问题",行为就乱了(总想重新开头)。所以它应该作为开场那一次的 **user 消息**发,发完就不再出现。

### ⭐ Q4.7 面试消息为什么同时存 MySQL 和 Redis?各承担什么?

**双写架构**:

- **Redis(`interview:ctx:{sessionId}` List)**:热数据、当前对话上下文。每轮对话都要读最近 N 条拼 prompt,是**高频读**,放内存里快。
- **MySQL(`interview_message` 表)**:**事实来源**,全量历史永久保存。用于"查看历史详情"这种低频、要完整的场景,也是 Redis 数据丢失时**重建现场**的底本。

为什么不只用 Redis:内存库,重启/淘汰会丢,历史不能丢。为什么不只用 MySQL:每轮高频读都查库太慢。这个"热数据 Redis + 事实来源 MySQL"的设计本身就是道面试题。

### ⭐ Q4.8 Token 预算裁剪(滑动窗口)和摘要压缩,各自优缺点?为什么裁剪要"从最新往回"数?

- **滑动窗口(本项目)**:只保留最近若干轮(在 token 预算内),旧的直接丢。优点:实现简单、无额外成本、延迟低。缺点:丢掉的早期信息**彻底没了**,聊太久模型会忘掉最开头说的。
- **摘要压缩**:把旧对话**让模型总结成一段摘要**再保留。优点:用很少 token 保住早期关键信息。缺点:每次压缩要**额外调一次模型**(费钱、增加延迟),摘要还可能丢细节。

我选滑动窗口,因为够用、简单,而且**能讲清摘要压缩这个替代方案好在哪、贵在哪,比两个都实现更重要**。

**为什么从最新往回数**:要保留的是**最近**的对话(模型最该记得刚刚说的话)。如果写成正序、从最旧开始累加到预算满,留下的就是**最旧的几条**、丢掉刚说的——AI 会"记得你老早说的、忘了你刚说的",体验完全反了。实现上倒序遍历、用 `addFirst` 往前插,遍历完天然是正序。这个方向**极易写反且编译器查不出**,是个隐蔽考点。

### Q4.9 `interview:ctx` 的 TTL 为什么每次追加都重设,而日榜 key 只首次设?

因为两者生命周期语义相反。会话上下文是**"只要还在活跃聊,就该一直有效"**——每追加一条消息就是一次活跃,应当**续期**(滑动过期),所以每次都重设 TTL,避免聊到一半 key 过期。日榜是**"当天固定到期"**——不管今天被刷多少次,它都该在今天结束时过期,所以**固定过期、首次设置即可**。判断关键:这个 key 是"活跃就续命"还是"到点必死"。

### Q4.10 如果 Redis 上下文过期了,怎么保证 AI 还记得之前聊的?

靠 MySQL 兜底。`InterviewContextManager.load()` 的逻辑是:**先查 Redis,命中直接用;未命中就查 `interview_message` 表把全量历史读出来、重建上下文、回填 Redis、再返回**。这是"缓存未命中回源事实来源"的经典模式,我项目里第三次用它(前两次是详情缓存、排行榜)。所以哪怕 Redis 重启丢了数据,用户也不会发现 AI"失忆"。

### ⭐ Q4.11 "结构化输出"的本质是什么?为什么说模型没有真正"输出 Java 对象"的能力?

模型**永远只会输出文本**,它不可能直接吐一个 Java 对象。所谓结构化输出是两步"障眼法":① **请求发出前**,Spring AI 的 `BeanOutputConverter` 根据你的目标类型(如 `InterviewReportResult`)自动生成一段"请严格按这个 JSON schema 回答(含字段名、类型)"的指令,**偷偷追加到你的 prompt 后面**;② **拿到回复后**,模型返回的还是一段文本(只是因为被要求了格式,长得像 JSON),Spring AI 再用 **Jackson 把这段文本反序列化**成目标对象,解析失败就抛异常。所以"输出对象"= **提示词约束格式 + 事后解析**,模型本身只是被"哄"着输出了合法 JSON。

### ⭐ Q4.12 评委的 system prompt 为什么不能复用面试官的?"不要编造"防的是什么?

面试官的 prompt 是"你是面试官、每次只问一个问题、根据回答追问"——那是一套**"问问题"的行为约束**。生成报告时如果复用它,模型会顺着惯性**继续问下一个问题**,它甚至意识不到对话已经结束,根本不会切换到"点评"模式。所以评委要**单独一份 system prompt**:"你是资深评委,读完整场记录,输出分数/亮点/薄弱点"。同一个模型靠不同 system prompt 扮演不同角色,这就是 system prompt 的威力。

"不要编造候选人没说过的内容"防的是大模型的**幻觉(hallucination)**——它天生倾向于"编得像模像样",不加约束可能会夸候选人一些他根本没提过的技术点,导致报告失真。这句是给它划边界:**只依据对话里真实出现的内容打分**。

### ⭐ Q4.13 结束面试的状态机为什么要有中间态 1?0 直接跳 2 会怎样?

状态:0 进行中 → 1 已结束未评价 → 2 已评价。中间态 1 存在的意义:**"结束会话"和"生成报告成功"是两件事,后者可能失败(模型抽风、超时)**。我的流程是先把状态从 0 改成 1(表示"这场面试已经结束、不能再聊了"),**再**去调模型生成报告,成功了才置 2。

如果没有中间态、0 直接跳 2:一旦"改状态"和"生成报告"之间报告失败,就陷入两难——要么状态还停在 0(用户点了结束却还能继续聊,矛盾)、要么已经跳到 2 但报告根本没生成(状态说有报告、实际没有)。有了中间态 1,失败时状态**干净地停在 1**:面试确实结束了(不能再聊),报告没生成(用户可以重新点 finish 补上)。

### ⭐ Q4.14 幂等的"业务判断"和"唯一索引"分别防什么?为什么两个都要?

- **业务判断**(finish 里先查 status==2 就直接返回已有报告):防**正常的重复调用**——用户手滑点两次结束,第二次走短路,不重新生成。这是**主路径**、体验好(直接返回、不调模型)。
- **数据库唯一索引**(`interview_report.uk_session_id`):防**并发/极端竞态**——两个请求几乎同时通过了业务判断、都去插报告,靠唯一索引让第二条插入**失败**,保证一场会话最多一份报告。这是**兜底**。

少了业务判断:每次重复调用都白白调一次模型(费钱慢)。少了唯一索引:高并发下业务判断挡不住的竞态会插出两份报告。所以**双保险**:业务判断管高频正常场景、唯一索引管极端并发。

### Q4.15 report 表 `score` 单独成列、其余打包进 JSON 列,判断标准是什么?

标准:**要被数据库直接筛选/排序/计算的字段,拉成普通列;整存整取、不单独查询的部分,打包进 JSON 列。** `score` 以后很可能要 `ORDER BY`、算平均分、看趋势,普通列能直接建索引、直接排序;highlights/weaknesses/summary 只是"读出来整个渲染",不会拿单个去查库,塞进 MySQL 的 `JSON` 列整存整取即可(写时校验合法 JSON,读时也能 `JSON_EXTRACT`)。

### ⭐ Q4.16 finish 为什么必须和 chat 抢同一把锁?各用各的锁会怎样?

因为它们操作的是**同一场会话的同一份对话记录**,存在竞态:如果 finish 正在"读全量历史、生成报告",而用户同时 chat 又发了一条,chat 的最后一条回复可能**刚好没落库**,finish 拼记录稿时就漏了它,报告是基于**残缺对话**生成的。共用同一把 `interview:lock:{sessionId}` 会话锁,保证"结束"和"继续聊"**互斥**,不会同时发生。各用各的锁就锁不住彼此,该串行的操作并发了,数据就可能不一致。

## 第 5 章 · SSE 流式与异步编程

### ⭐ Q5.1 `SseEmitter` 为什么能"不占用 Tomcat 工作线程死等"?靠什么机制?

靠 **Servlet 3.0 的异步请求处理(Async Servlet)**。普通同步接口里,一个请求从头到尾占着一个 Tomcat 工作线程,响应没写完线程不释放。`SseEmitter` 内部帮你调了 `request.startAsync()`,把请求**挂起**、**立刻把工作线程还回线程池**;等真正有数据要推(模型吐出一个 delta)时,再通过 `AsyncContext` 把数据写回这条还没关闭的连接。所以流式响应持续几十秒,期间并不霸占一个工作线程——这是 `SseEmitter` 相对"手写阻塞式输出"的核心优势。

### ⭐ Q5.2 客户端流式进行到一半断开,不调 `subscription.dispose()` 会怎样?

`chatClient...stream()` 是个**响应式流,它默认不知道"客户端已经走了"**,会继续从模型那边消费 token、生成内容——只是这些内容再也发不出去(`emitter.send()` 抛 `IOException` 被悄悄吃掉)。结果就是**白白烧模型调用成本**。`Disposable`(subscribe 的返回值)是"取消订阅"的句柄,在 `onTimeout`/`onError`(连接生命周期结束的信号)回调里调它的 `dispose()`,能让响应式流**及时停止拉取模型输出**,止损。同一个回调里还要**释放会话锁**,否则锁要等 60 秒 TTL 才放。

### ⭐ Q5.3 SSE 报错为什么不能改 HTTP 状态码,只能发一个 data 事件?

因为 SSE 是**流式响应**:一旦开始流式输出,**HTTP 响应头(含状态码)早就已经发出去了**(200 OK),后面是持续不断的 body 数据。HTTP 状态码在响应头里、**只能在最开始设置一次、发出后不可更改**。所以流到一半出错,没法再把状态码改成 500 告诉客户端。唯一的办法是**在数据流里发一个约定好的错误事件**(我项目发 `data: {"type":"error",...}`),让前端在解析流的时候识别这个错误帧。这反映了 SSE 协议的约束:**错误也是数据流的一部分,而不是协议层的状态**。

### ⭐ Q5.4 `JwtInterceptor` 为什么要专门处理 `DispatcherType.ASYNC`?不处理会怎样?

异步请求在 Servlet 容器里会经历**两次**进入拦截器:第一次是原始请求(DispatcherType.REQUEST),第二次是异步任务完成后容器把请求**重新 dispatch** 回来收尾(DispatcherType.ASYNC)。第二次这个 ASYNC 分发里,**请求上下文可能已经不带原始 token 了 / ThreadLocal 已被第一次的 afterCompletion 清理了**,如果拦截器不加区分又跑一遍鉴权逻辑,就会因为"没有有效登录态"而**误拦这次异步收尾**,导致 SSE 响应异常/连接被打断。所以要在 `preHandle` 开头判断 `if (request.getDispatcherType() == DispatcherType.ASYNC) return true;`,对异步二次分发直接放行。验证方式:发一次 SSE chat,看异步收尾阶段是否被拦截器拦下。

### Q5.5 chat 用了响应式 Flux,其他接口是同步阻塞 MVC,两种模型混用有问题吗?

没有本质问题,是可控的**混合架构**。项目主体是同步阻塞的 Spring MVC(简单、够用),只有 chat 这一个"需要流式、长时间、边生成边推送"的接口,借助 `SseEmitter` + 响应式 `Flux` 来实现。关键在于**边界清晰**:响应式只用在"消费模型流"这一小段,通过 `SseEmitter` 这个桥把结果接回 Servlet 异步机制,不需要把整个项目改成 WebFlux。要注意的是响应式流跑在**另外的线程**上,所以别在它的回调里读 ThreadLocal(见下题),需要的值提前取出来传进闭包。

### ⭐ Q5.6 ThreadLocal 里的数据为什么不会自动"漂移"到处理同一请求的第二个线程?异步回调要用当前用户 id 怎么办?

因为 `ThreadLocal` 顾名思义是**"绑定在某个具体线程"**上的存储,它跟"线程"走,不跟"逻辑上的一次请求"走。一次请求如果中途切到另一个线程执行(比如 SSE 的响应式回调跑在 Reactor 调度线程上),新线程的 ThreadLocal 里**没有**原始线程 set 的用户信息(要么 null,要么线程池复用下是**别人**残留的脏数据)。

正确做法:在还处于**原始线程**时(进入 `.subscribe(...)` 之前)先 `Long userId = UserContext.getUserId();` 存成局部变量,再把这个变量**作为参数传进闭包**里用。绝不能在回调内部再调 `UserContext.getUserId()`。我项目 `onStreamComplete` 需要的 sessionId/lockKey 就是这么提前打包传进去的。注意区分两个概念:`afterCompletion` 清理 ThreadLocal 解决的是**线程复用**(下个请求别读到上个残留);这里说的是**线程切换**(同一请求内换线程执行),是两回事。

### Q5.7 那些"编译能过、运行时才炸"的冷路径 bug,你怎么防?

典型例子:新建的 Mapper,XML 的 `<select>` id 写成了结果类名、漏了 resultType。这类错**编译期查不出**——MyBatis 的接口↔XML 是运行时才解析绑定的。如果平时一直走 Redis 缓存命中的路径,这条"未命中回源 MySQL"的语句根本不被调用,bug 就**潜伏着不发作**,直到某天真触发了那条冷路径(比如第一次点"结束面试"、或 Redis key 恰好过期)才 `BindingException` 炸。

防法:**自测清单必须显式覆盖冷路径**——比如"手动 `redis-cli DEL` 掉上下文 key 再测一次"强制走回源分支、"专门测一次结束面试"走 report 的 Mapper。写完新 Mapper 一定对照检查"接口方法名 ↔ XML id 一字不差、有没有 resultType"。

## 第 6 章 · 健壮性与工程素养

### ⭐ Q6.1 为什么外部 API 调用必须显式设超时?不设最坏会怎样?

AI 调用是一次网络请求,如果对端卡住不返回、**又没设读超时**,处理这次请求的线程就会**永远阻塞在等待那一行,回不到线程池**。这样的"僵尸请求"越攒越多,把有限的线程池(比如 200)占满后,**连一个只查数据库、根本不碰 AI 的普通接口都会因为拿不到工作线程而被拖死**——一个外部依赖的慢,通过"共享线程池"这个通道**传染成整个服务不可用**。显式设超时(我项目 `AiConfig` 里 connect 10s / read 60s)就是画一条止损线:"最多等这么久,再不返回就放弃、把线程还回去",把故障**隔离**在这一次调用里。这是外部依赖故障隔离最基本、最不能省的一环。

### Q6.2 连接超时和读超时为什么设不同的值?

它们是两种不同性质的等待。**连接超时**(10s)是"建立 TCP 连接/握手"的等待,正常都是毫秒级,等 10 秒还连不上基本就是网络或对端挂了,没必要久等。**读超时**(60s)是"连上之后等对端返回数据"的等待,而大模型生成一大段回答本来就慢,得给足生成余量。用同一个值一刀切要么把正常的长回答误杀、要么给握手留了过多耐心。

### ⭐ Q6.3 限流为什么用 `SET NX EX` 一条命令,不能"先判断 key 在不在、不在再 set"?

"先判断再设置"是**两步、非原子**:用户连点两下,两个请求几乎同时到,都执行了判断、都发现 key 不存在,于是**都放行**,限流失效。`SET key value NX EX seconds`(对应 `setIfAbsent(key, val, ttl)`)把"key 不存在才写入"和"写入同时设过期"合成**一条原子命令**,Redis 单线程里执行,不给并发留缝隙。这和会话锁、`ZINCRBY`、`INCR` 是**同一个"用单条原子命令替代读改写"的道理**——只是会话锁是互斥、这里是冷却限流。

### ⭐ Q6.4 已经有"每会话"的会话锁,为什么还要"每用户"的限流?举个只有一个能拦住的例子。

两者维度正交,拦的东西不同:

- **会话锁**拦"同一会话、同一时刻的并发":A 会话上一轮还在流式吐字,你又对 A 发下一条,被锁挡住。但它**管不到你换 B、C、D 会话疯狂发**——每个会话有独立的锁。
- **每用户限流**拦"同一用户、跨会话的总频率":哪怕你在 3 个会话间来回切着发,10 秒内发第二条就被这个每用户的闸挡住。

**只有会话锁拦不住、限流能拦住的例子**:用户开了 3 个会话,在它们之间轮流发消息,每个会话都不触发自己的锁,但总频率极高——只有每用户限流能刹住。所以两个都要。

### Q6.5 限流 key 为什么必须带 userId?限流 key 为什么不能在 finally 里删?

- **必须带 userId**:限流的"维度"由 key 表达。如果 key 写成固定的 `zhimian:interview:rate` 不带用户,就变成**全局限流**——全站所有人 10 秒只能有一个人发消息,A 发了 B 就被拦,完全错了。"每用户限流"就必须 `rate:{userId}`。
- **不能在 finally 删**:限流 key 的语义是"这 10 秒冷却期必须完整走完",它靠 **TTL 自然过期**来结束冷却。如果处理完在 finally 里把它删了,冷却窗口直接归零,限流白做。这跟会话锁正好相反——会话锁必须在 finally 删(处理完就该放行下一轮),限流 key 设了就不管。

### ⭐ Q6.6 生成评价报告失败可以自动重试,流式对话为什么绝对不能?判断标准是什么?

- **报告可重试**:它是**幂等**的——输入是同一份完整对话记录,重试无非"用同样输入再算一遍分",没有副作用、重试前也没往库里写东西,失败悄悄再试对用户透明。我 `generateReportWithRetry` 就重试到第 2 次。
- **流式对话不能重试**:第一,它已经**一个字一个字推给客户端了**,推到一半失败没法"把吐出去的字收回来"重发;第二,重试会让模型**从头重新生成**,用户看到半句话后又重来一遍。所以流式失败就老实发 error 帧,让**用户自己决定**要不要重发,后端不偷偷重试。

**通用判断标准**:这次调用**是不是幂等、有没有已经产生对外可见的副作用**。幂等且无副作用 → 能重试;非幂等或已有副作用(已推流、已扣款、已发消息)→ 不能盲目重试。

### ⭐ Q6.7 四种限流算法对比?固定窗口的"临界问题"是什么?本项目为什么固定窗口够用?

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 固定窗口 | 每个时间窗内计数,超了拒 | 最简单(INCR+EXPIRE) | 临界问题 |
| 滑动窗口 | 大窗切小格滚动统计 | 消掉临界毛刺 | 实现更复杂 |
| 令牌桶 | 匀速发令牌,取到才放行 | 允许一定突发 | 参数要调 |
| 漏桶 | 请求匀速漏出处理 | 输出绝对平滑 | 不容忍突发 |

**临界问题**:限"每分钟 100 次",如果 100 个请求挤在第 1 分钟最后 1 秒、又 100 个挤在第 2 分钟最前 1 秒,从每个窗口看都没超,但**跨窗口那 2 秒实际放行了 200 次**,是限流值的两倍。滑动窗口就是为消掉这个边界毛刺而生。

**本项目为什么固定窗口够**:我的需求是"每用户 10 秒最多 1 次",配额是 1、窗口短,`SET NX EX` 实现的正是"固定窗口、配额为 1"这个最简形态,用户体感就是个 10 秒冷却,临界问题在配额=1 时几乎无实际影响。**限流算法按业务实际需要选,不是越高级越好**。

### Q6.8 如果配额改成"每分钟 5 次",`INCR`+`EXPIRE` 会踩什么坑?怎么解决?

配额>1 就得计数:`INCR key` 自增、第一次自增后 `EXPIRE key 60`,值超 5 就拒。坑在于 **`INCR` 和 `EXPIRE` 是两条命令、不原子**:如果第一次 `INCR` 之后、还没来得及 `EXPIRE`,进程刚好崩了,这个 key 就**永远没有过期时间**,该用户被**永久限流**。解决:用 **Lua 脚本**把 `INCR` +(首次)`EXPIRE` 打包成一个原子操作执行;或者像我们配额=1 的场景直接用 `SET NX EX`(天生原子,绕开了这个坑)。

### Q6.9 AI 相关异常为什么要统一收敛成 50001,不是笼统的 50000?

**错误码要如实反映"是哪一层出的问题"**。api-key 配错、对端 401/超时,本质是"AI 服务调不通",语义上就该是 `50001 AI 服务调用失败`。如果让底层 AI 异常裸奔到全局兜底 handler,会变成笼统的 `50000 系统内部异常`——运维看到 50001 能立刻判断"去查 AI 网关/key",看到 50000 只能从头一层层排查。我在 `GlobalExceptionHandler` 里加了专门接 `NonTransientAiException`/`TransientAiException`/`RestClientException` 的 handler 统一收敛成 50001,作为**防御纵深**:哪怕将来某个新接口忘了在调用处 try/catch,这张网也能兜住,不让它裸奔成 50000。

### Q6.10 降级预案你会怎么设计?(讲思路)

核心是**配置化的备用模型**:把主用模型和一个更便宜/更稳的备用模型都写进配置。当主模型**连续失败触发熔断阈值**时,熔断器开路,自动**切到备用模型**顶上,保证"服务降级但不中断"。落地一般用 Resilience4j 这类熔断器统计失败率、超阈值开路、提供 fallback 分支切模型。要点是想清楚这条链路:**配置备用模型 → 熔断触发切换 → 降级不等于不可用**。本项目不强制实现,能讲清思路即可。

### Q6.11 `@Scheduled` 定时任务(浏览量回写)如果部署两个实例会出什么问题?怎么解决?

`@Scheduled` 是**单机语义**——每个实例都会各自到点触发。两个实例同时跑同一个回写任务,会去抢同一批计数器 key 做 `GETDEL`。好在 `GETDEL` 本身原子,同一份增量不会被重复回写(谁先抢到谁拿走),但**这个任务被无意义地跑了两遍**,浪费资源、也可能造成回写时序混乱。解决:让"多个实例只有一个真正执行"——① 用**分布式锁**(执行前抢 Redis 锁,抢到才跑);② 用 **xxl-job / ElasticJob** 这类支持"只由一个节点抢到执行权"的分布式调度框架。

### Q6.12 构造器注入(`@RequiredArgsConstructor` + final)比字段注入 `@Autowired` 好在哪?

三点:① **依赖不可变**——`final` 保证注入后不会被改,线程安全;② **便于单测**——不依赖 Spring 容器,`new` 对象时直接把 mock 依赖传进构造器就行;③ **循环依赖在启动时就暴露**——构造器注入遇到循环依赖会直接启动失败报错,而字段注入会把问题藏到运行时。所以 Spring 官方也推荐构造器注入。

### Q6.13 你这个项目里反复出现的几个"设计模式/思想",能总结一下吗?

能,这也是这个项目最想训练的东西:

1. **缓存 + 事实来源双写,允许最终一致但不允许永久丢失**:上下文(Redis+MySQL)、排行榜(ZSet+answer_record)、浏览量都是这个结构。
2. **缓存未命中回源重建再回填**:详情缓存、排行榜、AI 上下文,同一套"查缓存→未命中查库→回填"。
3. **用单条原子命令替代"读-改-写"**:`INCR`(浏览量)、`ZINCRBY`(排行榜)、`SET NX EX`(锁/限流),都是为了并发不丢更新。
4. **收集 id 批量查 + 内存 Map 组装,消灭 N+1**:题库补标签、排行榜补昵称、上下文补数据。
5. **存储 ≠ 对外展示**:system 消息存但不返前端;viewCount 存但容忍不一致。
6. **外部依赖要隔离**:AI 调用不进事务、显式超时、限流、异常收敛、不盲目重试。

能把散落在各个任务里的这几条"思想主线"串起来讲,比单点回答某个八股更能体现你真的理解了这个项目。
