# 数据组装与转换专题:从"看得懂"到"自己敢下笔"

> 这篇不讲新技术,讲一个更基础的能力:拿到一个"把 A 数据变成 B 数据"的需求时,怎么一步步想清楚该写什么代码。例子全部来自你项目里已经写过、跑通了的代码(`QuestionServiceImpl`、`InterviewServiceImpl`、`AnswerServiceImpl`),不是新造的demo。

---

## 一、你卡住的到底是哪一步

先说清楚一个事实:**"看代码能懂"和"自己写不出来",不是因为你基础差,是因为看代码的时候,别人已经替你做完了三件事:**

1. 想清楚了**源数据长什么样**(是一个对象?一个列表?要不要额外查一张表?)
2. 想清楚了**目标数据长什么样**(接口约定的 VO/DTO 有哪些字段)
3. 想清楚了**源和目标之间怎么对应**(哪些字段直接抄,哪些字段要算,哪些字段要另外查一次)

你读代码的时候,这三样东西已经摆在你眼前了,你只是在"验证"这三件事对不对——这当然轻松。自己写的时候,这三样东西全部要你自己从一句需求描述里抠出来,懵是正常的,不是你笨。

**这篇文档要给你的,就是把这三件事拆成一套可以照着走的步骤**,替代"瞪着空白文件不知道从哪下手"的状态。

## 二、最基础的单对象转换:字段对字段

### 2.1 手动 set:最原始但最不会出错的写法

`QuestionServiceImpl.addQuestion`(DTO → Entity):

```java
public Long addQuestion(QuestionAddDTO dto) {
    Question question = new Question();
    question.setTitle(dto.getTitle());
    question.setContent(dto.getContent());
    question.setAnswer(dto.getAnswer());
    question.setDifficulty(dto.getDifficulty());
    question.setCategoryId(dto.getCategoryId());
    question.setCreateUserId(UserContext.getUserId());
    questionMapper.insert(question);
    ...
}
```

这是最笨也最直白的写法:**目标对象要哪个字段,就去源里找一个值塞进去**。注意最后一行 `setCreateUserId(UserContext.getUserId())`——它不是从 `dto` 里来的,是从当前登录用户上下文里来的。这提醒你一件事:**转换不总是"从一个源搬到一个目标",有时候某个字段的值根本不在你手上的这个源对象里,而是要从别的地方(当前用户、当前时间、常量)去补。**

### 2.2 `BeanUtils.copyProperties`:字段名对得上时的偷懒写法

`QuestionServiceImpl.buildDetailVO`(Entity → VO):

```java
private QuestionDetailVO buildDetailVO(Question question) {
    QuestionDetailVO vo = new QuestionDetailVO();
    BeanUtils.copyProperties(question, vo);   // Question 和 QuestionDetailVO 里同名的字段自动抄一遍
    Map<Long, String> categoryNameMap = ...;
    vo.setCategoryName(categoryNameMap.get(question.getCategoryId()));  // 抄不到的字段,手动补
    List<String> tags = ...;
    vo.setTags(tags);                                                   // 抄不到的字段,手动补
    return vo;
}
```

`BeanUtils.copyProperties(源, 目标)` 做的事很简单:**遍历目标对象的每个字段,如果源对象里有同名同类型的字段,就把值抄过去;抄不到的字段保持原样(基本类型是默认值,对象是 null)。**

它能不能用,就看一个问题:**目标 VO 里的字段,是不是大部分都能在源 Entity 里找到"同名同类型"的对应字段?**

- `QuestionDetailVO` 的 `id/title/content/answer/difficulty/categoryId/viewCount/createTime`,`Question` 实体里全都有同名字段 → 这部分交给 `BeanUtils` 一行搞定。
- `categoryName`(要查 `Category` 表)、`tags`(要查关联表)—— `Question` 实体里根本没有这两个字段,`BeanUtils` 当然抄不出来,必须手动补。

**判断口诀:`BeanUtils` 只负责"字段名对得上、值不用算"的那一部分,剩下的永远要手写。它是省力气的工具,不是能自动理解业务逻辑的工具。**

### 2.3 字段对不上时,`BeanUtils` 反而会害你——只能手写

`InterviewServiceImpl.createInterview` 里组装 `InterviewSessionVO` 的这段,**没有用** `BeanUtils`:

```java
InterviewSessionVO vo = new InterviewSessionVO();
vo.setId(session.getId());
vo.setDirection(direction.getCode());
vo.setOpeningMessage(openingMessage);
return vo;
```

为什么不用 `BeanUtils.copyProperties(session, vo)`?因为 `InterviewSession`(数据库实体)和 `InterviewSessionVO`(返回给前端的对象)长得完全不像:

| `InterviewSessionVO` 需要的字段 | 从哪来 |
|---|---|
| `id` | `session.getId()`,是同名字段 |
| `direction` | `direction.getCode()`——**这是从枚举对象取出来的,不是从 `session` 实体抄的**,虽然 `session` 里也有个 `direction` 字段,但那是刚 set 进去的原始 code,这里用局部变量 `direction` 枚举对象取更直接 |
| `openingMessage` | 调用 AI 之后**才产生的**结果,`session` 实体里根本没有这个字段(开场白是消息表里的一条记录,不是会话表的字段) |

**这里的判断标准是:一旦目标对象里有任何一个字段,要么名字对不上、要么值来自"计算/另一次调用/另一张表",就不要图省事硬套 `BeanUtils`——三个字段全手写,比"两行 `BeanUtils` + 一行手动补漏"更清楚,也更不容易漏改。** 这是个工程判断,没有绝对对错,但优先级是:**先想清楚有几个字段对得上,只有"大多数字段都对得上、只差一两个"的情况才值得用 `BeanUtils` 省事。**

## 三、集合转换:一个个搬,还是 `stream`?

### 3.1 for 循环:先用这个想清楚逻辑

`InterviewServiceImpl.toSpringAiMessages`(`List<InterviewMessage>` → `List<Message>`):

```java
private List<Message> toSpringAiMessages(List<InterviewMessage> history) {
    List<Message> messages = new ArrayList<>();
    for (InterviewMessage m : history) {
        switch (m.getRole()) {
            case "system" -> messages.add(new SystemMessage(m.getContent()));
            case "user" -> messages.add(new UserMessage(m.getContent()));
            case "assistant" -> messages.add(new AssistantMessage(m.getContent()));
            default -> throw new IllegalStateException("未知的消息角色:" + m.getRole());
        }
    }
    return messages;
}
```

这里**故意没用** `stream().map(...)`,因为每一条消息要 `new` 出**不同的类**(`SystemMessage`/`UserMessage`/`AssistantMessage`),中间还有一个"角色不认识就报错"的分支——这种"看内容决定分支逻辑"的转换,用 `for` + `switch` 写出来比硬拗成一行 `stream` 表达式清楚得多。

### 3.2 stream:纯粹的"每个元素都做同一件事"才用

`QuestionServiceImpl.enrichToListVO` 现在写的是 `for` 循环:

```java
List<QuestionListVO> voList = new ArrayList<>();
for (Question q : records) {
    QuestionListVO vo = new QuestionListVO();
    BeanUtils.copyProperties(q, vo);
    vo.setCategoryName(categoryNameMap.get(q.getCategoryId()));
    vo.setTags(tagMap.getOrDefault(q.getId(), List.of()));
    voList.add(vo);
}
```

如果改成 `stream`,长这样:

```java
List<QuestionListVO> voList = records.stream()
        .map(q -> {
            QuestionListVO vo = new QuestionListVO();
            BeanUtils.copyProperties(q, vo);
            vo.setCategoryName(categoryNameMap.get(q.getCategoryId()));
            vo.setTags(tagMap.getOrDefault(q.getId(), List.of()));
            return vo;
        })
        .collect(Collectors.toList());
```

两种写法做的事完全一样,`stream` 版本只是把"造一个新列表、往里面塞转换后的元素"这个套路用标准 API 表达了一遍。**这两种写法在这个项目里都合理,选哪个纯粹是风格问题**——但给你一个建议:**自己写的时候,先用 `for` 循环写出来、跑通、想清楚每一步在干什么;写顺手了之后,再考虑要不要为了简洁改成 `stream`。不要一上来就对着 `stream` 的链式 API 抠语法,那会把"组装数据的逻辑"和"记 API 写法"这两件事混在一起,更容易卡壳。**

## 四、核心技巧:先建索引表,再补字段(避免 N+1)

这是这个项目里**出现次数最多、也是你最该练熟的模式**——`pageQuestions`、`enrichToListVO`、`getRank` 三处都用了同一套思路。单独拎出来讲。

### 4.1 反面写法(不要这么写,但要知道为什么不能这么写)

假设你要给一页 20 道题,每道题都补上分类名和标签,直觉写法可能是:

```java
for (Question q : records) {
    Category category = categoryMapper.selectById(q.getCategoryId());   // 每道题查一次分类表
    List<String> tags = questionTagMapper.selectTagNamesByQuestionId(q.getId()); // 每道题查一次标签表
    ...
}
```

20 道题 = 1 次查题目列表 + 20 次查分类 + 20 次查标签 = **41 次数据库查询**。这就是经典的 **N+1 查询问题**:主查询 1 次,但为了补全每一条记录的关联数据,又对每一条记录单独发一次查询,数据量一大直接拖垮数据库。

### 4.2 项目里的正确写法:三步走

`QuestionServiceImpl.enrichToListVO` 实际是这么做的:

```java
// 第一步:批量查出所有分类,建一个「分类id -> 分类名」的索引表
Map<Long, String> categoryNameMap = new HashMap<>();
for (Category c : categoryMapper.selectAll()) {
    categoryNameMap.put(c.getId(), c.getName());
}

// 第二步:把这一页题目的 id 收集起来,一次 IN 查询查出所有相关标签
List<Long> questionIds = new ArrayList<>();
for (Question q : records) {
    questionIds.add(q.getId());
}
Map<Long, List<String>> tagMap = new HashMap<>();
for (QuestionTagName row : questionTagMapper.selectTagNamesByQuestionIds(questionIds)) {
    tagMap.computeIfAbsent(row.getQuestionId(), k -> new ArrayList<>()).add(row.getName());
}

// 第三步:遍历主数据,从索引表里"查内存 Map"而不是"查数据库"来补字段
List<QuestionListVO> voList = new ArrayList<>();
for (Question q : records) {
    QuestionListVO vo = new QuestionListVO();
    BeanUtils.copyProperties(q, vo);
    vo.setCategoryName(categoryNameMap.get(q.getCategoryId()));
    vo.setTags(tagMap.getOrDefault(q.getId(), List.of()));
    voList.add(vo);
}
```

20 道题 = 1 次查题目 + 1 次查全部分类 + 1 次按 id 批量查标签 = **3 次数据库查询**,不管这一页是 20 道题还是 200 道题,查询次数都不会涨。

**通用模板,记住这三步:**

1. **先批量查出"主数据"列表**(这一页的题目、这次要处理的会话……)
2. **收集主数据的 id,批量查出"关联数据"**(一次 `IN` 查询,不要在循环里一条条查)
3. **把关联数据在内存里建成 `Map<id, value>` 索引**,再遍历主数据时从这个 Map 里取值补字段

第 3 步里有个细节要认准:**一个主数据对应几条关联数据?**

- **一对一**(比如 `分类id -> 分类名`):`Map<Long, String>`,直接 `put`。
- **一对多**(比如 `题目id -> 多个标签名`):`Map<Long, List<String>>`,要用 `computeIfAbsent(key, k -> new ArrayList<>()).add(value)`——这句的意思是"这个 key 第一次出现就新建一个空列表放进 Map,不管是不是第一次出现,都往列表里加一个元素"。这是**处理"一对多分组"的标准写法**,自己写代码遇到"同一个 id 可能对应多条记录,要把它们收集到一起"的场景,直接照抄这个套路。

## 五、保序拼装:排行榜的例子

`AnswerServiceImpl.getRank`:

```java
Set<ZSetOperations.TypedTuple<String>> tuples = redisTemplate.opsForZSet()
        .reverseRangeWithScores(key, 0, limit - 1);   // Redis 已经按分数从高到低排好序了

List<Long> userIds = new ArrayList<>();
for (ZSetOperations.TypedTuple<String> tuple : tuples) {
    userIds.add(Long.valueOf(tuple.getValue()));
}
Map<Long, String> nicknameMap = new HashMap<>();
for (User u : userMapper.selectByIds(userIds)) {
    nicknameMap.put(u.getId(), u.getNickname());
}

List<RankVO> result = new ArrayList<>();
int rank = 1;
for (ZSetOperations.TypedTuple<String> tuple : tuples) {   // 注意:外层遍历的还是 tuples,不是 nicknameMap
    Long userId = Long.valueOf(tuple.getValue());
    RankVO vo = new RankVO();
    vo.setRank(rank++);
    vo.setUserId(userId);
    vo.setNickname(nicknameMap.get(userId));   // 只是从 Map 里查一下,不是拿 Map 当主线
    vo.setCount(tuple.getScore().intValue());
    result.add(vo);
}
```

这里和第四节的模式看着很像(也是先批量查、建 Map、再补字段),但有一个关键区别值得单独拎出来讲:**`HashMap` 是不保证顺序的**。如果你偷懒把最后一步的外层遍历从 `tuples` 换成 `nicknameMap.entrySet()`,排行榜的名次顺序就乱了——第一名可能被排到第三名。

**判断标准:谁是"骨架"(决定最终顺序/结构的那个集合),谁是"配角"(只是被查一下、贡献个别字段的值)。外层遍历永远用骨架,配角只用来在内层"查一下"。** 这个项目里,`tuples`(Redis 已排好序的结果)是骨架,`nicknameMap` 是配角。

## 六、类型转换里容易踩的坑

### 6.1 List 缓存要用 `TypeReference` 反序列化,不能直接写 `.class`

`QuestionServiceImpl.deserializeList`:

```java
private List<QuestionListVO> deserializeList(String json) {
    return objectMapper.readValue(json, new TypeReference<List<QuestionListVO>>() {});
}
```

如果写成 `objectMapper.readValue(json, List.class)`,能编译、能跑,但反序列化出来的每个元素只是一堆 `LinkedHashMap`,不是 `QuestionListVO`——因为 Java 的泛型信息在编译后会被"擦除",运行时 `List.class` 只知道"这是个 List",不知道里面装的是什么。`TypeReference` 借助一个匿名内部类的技巧,把完整的泛型信息保留到运行时,`ObjectMapper` 才能正确还原类型。**记住结论就行:反序列化任何带泛型的集合类型(`List<T>`、`Map<K,V>`),都要用 `new TypeReference<...>() {}`,不要直接写 `.class`。**

### 6.2 枚举 ↔ 字符串:`code` 是"数据库/前端认识的样子",枚举对象是"代码里认识的样子"

`InterviewDirection.fromCode(dto.getDirection())` 把前端传来的字符串转成枚举对象,`direction.getCode()` 再把枚举对象转回字符串存库/传给前端。**为什么不直接存枚举本身?** 因为数据库字段和 JSON 字段本质上只能存"字符串/数字"这种基础类型,枚举是 Java 语言层面的概念,跨进程(存库、传 HTTP)的时候必须先"降级"成字符串,读回来的时候再"升级"回枚举——这一去一回就是 `getCode()` / `fromCode()` 这一对方法存在的意义。

### 6.3 Map 里查不到,不要让 `null` 一路传下去

```java
vo.setTags(tagMap.getOrDefault(q.getId(), List.of()));
```

如果这道题恰好没有任何标签,`tagMap.get(q.getId())` 会返回 `null`。如果直接 `vo.setTags(tagMap.get(q.getId()))`,前端拿到的 `tags` 字段就是 `null`,前端如果没做判空直接 `tags.map(...)` 就会报错。**用 `getOrDefault(key, 空的默认值)` 在组装的这一步就把 `null` 挡掉,比指望前端或者后面每个用到这个字段的地方都记得判空更可靠。**

## 七、自己写的时候,按这张清单过一遍

这是给你写代码时用的**思考顺序**,不是要你背下来,是让你卡壳的时候有个"下一步该问自己什么"的抓手:

1. **先不写代码,把目标对象(VO/DTO)的字段一个个列出来。**——不管是写在注释里还是脑子里过一遍都行,重点是先把"我要凑出哪些字段"想清楚,再想怎么凑。
2. **逐个字段问三个问题里的哪一种:**
   - **直抄**:源对象里有同名字段,值不用算 → 这部分字段留给 `BeanUtils.copyProperties`(如果大多数字段都是这种,才值得用它;只有一两个字段是这种,手写更清楚)。
   - **计算**:值需要从源对象的某个字段"变换"一下才能得到(枚举转文字、拼字符串、算次数)→ 手写一行 `set`。
   - **外查**:这个字段的值不在手上的源对象里,要另外查一张表/调一个方法 → 想清楚是**一对一**还是**一对多**,决定用 `Map<id, value>` 还是 `Map<id, List<value>>`。
3. **涉及集合(要转换一整个列表)时,再多问两个问题:**
   - **要不要保序?**——如果最终结果的顺序有业务含义(排行榜、最近浏览),外层遍历必须用"已经排好序的那个集合",索引 Map 只能是配角。
   - **空列表要不要提前 return?**——比如 `pageQuestions` 一开始就判断 `total == 0` 直接返回空结果,不用往下走"建索引、查关联"这一整套,省一次无意义的空 `IN` 查询。
4. **涉及"外查"字段、且列表可能有多个元素时,默认按第四节的三步模板走**:先批量查主数据 → 收集 id 批量查关联数据 → 建 Map 索引 → 遍历主数据补字段。不要在循环里现查——写出"for 循环里调 mapper 方法"这行代码之前,先想一下这一步是不是能挪到循环外面批量查。
5. **写完之后,自己在脑子里(或者真的造几条假数据)走一遍两种边界情况**:
   - 列表是空的,会不会报错?
   - Map 里查某个 id 查不到(返回 `null`),会不会导致 NPE 或者把 `null` 传给前端?

## 八、练习建议

看懂这篇文档不代表你已经会了——**这个能力必须靠自己写出来才能长住**。建议挑一个你已经读过的组装场景(比如 `enrichToListVO`、`toSpringAiMessages`、`getRank` 任选一个),合上代码,只看"输入是什么、输出要什么样"这两头,自己重新写一遍,写完再跟原文件 diff 对比差异——**看哪里想漏了,比看哪里写对了更值钱**。
