# 智面前端阶段代码 · 学习路线

这组文档是智面 Vue 3 前端的系统练习路线。请结合 `frontend/src` 里的真实代码，**自己把每个任务敲进项目**，不要整段复制粘贴。敲完一个任务后先运行构建，再把代码发给导师 review。

本阶段只关注前端技术链路：Vue 3 Composition API、TypeScript、Axios、Pinia、Vue Router、组件通信、分页、状态机、SSE 流式读取和前后端联调。CSS 只要求能读懂模板中的 class，不把视觉调整作为验收重点。

## 一、当前前端地图

```text
frontend/src/
├── api/              # 一组后端接口对应一个模块，页面不直接写 axios
│   ├── http.ts       # Axios 实例、token 注入、统一拆包、错误处理
│   ├── auth.ts       # 登录
│   ├── question.ts   # 题目分页、题目详情
│   ├── category.ts   # 分类树
│   ├── dashboard.ts  # 仪表盘
│   ├── rank.ts       # 排行榜
│   └── interview.ts  # 面试接口与 SSE
├── types/            # 与后端 DTO/VO 对齐的 TypeScript 类型
├── stores/           # Pinia 全局状态，目前主要是登录态
├── router/           # 路由表和登录守卫
├── components/       # 可复用的业务组件
├── views/            # 路由页面，负责组织状态和页面流程
├── utils/            # 与业务无关的小工具
├── styles/           # 设计 token、全局样式和 Element Plus 覆盖
├── App.vue           # 应用根组件
└── main.ts           # 创建 Vue 应用并注册插件
```

## 三、每个任务的统一完成标准

1. 能说清楚数据从页面事件到 API，再从 API 回到页面的路径。
2. 页面不直接 import axios；请求集中放在 `src/api`。
3. 后端返回的字段有对应 TypeScript 类型，不用 `any` 糊过去。
4. 至少处理 loading、空数据、请求失败三种状态。
5. 页面卸载时清理定时器、流读取或其他异步资源。
6. 每完成一个任务运行一次 `npm run build`，避免最后才发现类型错误堆在一起。

## 四、启动方式

在 `frontend` 目录执行：

```bash
npm install
npm run dev
```

生产构建：

```bash
npm run build
```

Vite 开发代理配置在 `frontend/vite.config.ts`。浏览器请求写 `/api/...`，开发服务器会把它转给后端，不要在页面里到处写 `http://localhost:8080`。

## 五、学习纪律

- 先读任务文档中的接口契约，再看现有相似页面。
- 先让接口请求成功，再补页面展示；先处理主流程，再补异常和体验状态。
- 代码中的中文注释只保留“为什么这样做”的解释，不给每一行翻译。
- CSS 可以先沿用现有 class，等功能链路稳定后再单独做视觉优化。

## 六、初学者学习方法

如果你以前主要写后端，第一次看 Vue 时最容易产生一个错觉：文件里有很多标签、箭头函数和 `.value`，好像每个地方都在“魔法更新”。其实可以把页面先理解成三个部分：

```text
状态 state       用户当前看到和操作的数据
模板 template    状态应该怎样显示
副作用 effect    什么时候请求接口、监听变化、清理资源
```

例如题库页：

```text
pageNum、questions、loading       state
v-for、v-if、el-pagination         template
onMounted、watch、loadQuestions    effect
```

每次写一个页面，都先问自己三个问题：

1. 页面需要保存哪些状态？类型是什么？初始值是什么？
2. 哪些内容是由状态计算出来的，而不是单独保存的？
3. 哪些事情属于副作用，应该在 mounted、watch 或点击事件中执行？

## 七、后端开发者必须先掌握的对应关系

| 后端概念 | Vue 前端中的相近概念 |
|---|---|
| Controller 接收 HTTP 请求 | `src/api/*.ts` 封装请求方法 |
| DTO 请求参数 | API 函数的参数类型 |
| VO 响应对象 | `src/types/*.ts` 的返回类型 |
| Service 业务编排 | 页面函数或 composable 中的流程编排 |
| Redis/数据库状态 | Pinia 或页面中的响应式状态 |
| 全局异常处理 | Axios 响应拦截器和页面 `catch` |
| 拦截器 | Axios request/response interceptor |
| 定时任务 | `setInterval`，并在组件卸载时清理 |

这不是说两端完全一样，而是帮助你把已有的后端思维迁移到浏览器运行环境。前端还有一个后端没有那么明显的维度：用户每点击一次、输入一个字符、切换一次路由，页面状态都会变化。

## 八、每个任务的敲代码流程

1. 先读“本任务要实现什么”，用自己的话写出输入、输出和状态变化。
2. 再读“涉及的文件”，先打开现有相似代码，不要直接新建抽象。
3. 先写类型，再写 API，再写页面状态，最后写模板。
4. 每写完一小步就运行 `npm run build`，错误出现在哪里就在哪里解决。
5. 打开浏览器 Network 和 Console，确认请求、参数、响应和页面状态。
6. 把文档里的自测问题逐条回答，回答不了的地方就是需要继续学习的地方。

## 九、每个任务完成后要留下的学习记录

建议在自己的笔记里固定写四行：

```text
本任务的入口文件：
一次请求经过哪些文件：
我今天遇到的第一个错误：
这个错误最终为什么发生：
```

这样做的目的不是写形式化日报，而是训练你从“看起来能跑”走到“我能解释它为什么能跑”。面试时真正有价值的也是后者。
