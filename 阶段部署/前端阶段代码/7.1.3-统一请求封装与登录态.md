# 任务 7.1.3 · 统一请求封装与登录态

> 本任务是前端接后端的核心。完成后，页面只调用 `api` 函数，不直接写 Axios 细节。

## 一、本任务要实现什么

统一处理四件事：

1. 所有普通请求使用一个 Axios 实例。
2. 请求自动带上 `Authorization: Bearer token`。
3. 后端 `{ code, message, data }` 成功时，调用方直接拿到 `data`。
4. 登录过期时清理 Pinia 和 `localStorage` 中的登录态。

## 三、分步实现

### Step 1：创建 Axios 实例

当前项目的核心配置：

```ts
const http = axios.create({
  baseURL: '/api',
  timeout: 10000,
})
```

页面只写：

```ts
get<QuestionDetail>(`/questions/${id}`)
```

最终请求地址是 `/api/questions/${id}`。`baseURL` 集中管理前缀，后续切换部署地址时不需要全项目搜索替换。

### Step 2：请求拦截器注入 token

```ts
http.interceptors.request.use((config) => {
  const token = localStorage.getItem('zm-token')
  if (token) {
    config.headers.Authorization = `Bearer ${token}`
  }
  return config
})
```

这里直接从 `localStorage` 取 token，是为了避免 `http.ts → auth store → auth API → http.ts` 的循环依赖。Pinia 负责响应式状态，`localStorage` 是刷新页面后仍能读取的持久化来源。

### Step 3：响应拦截器拆包

后端成功响应类似：

```json
{ "code": 0, "message": "ok", "data": { "id": 1 } }
```

当前拦截器在成功时返回 `body.data`，因此 API 函数可以写：

```ts
export function fetchDashboard(): Promise<DashboardStats> {
  return get<DashboardStats>('/dashboard')
}
```

页面拿到的就是 `DashboardStats`，而不是再写 `response.data.data`。统一拆包是一个项目约定，不能一部分接口拆包、一部分接口不拆包。

### Step 4：错误处理和 401

业务失败时，拦截器显示 `message` 并 reject。`40100`、`40101` 表示登录失效，需要同时清理：

```ts
token.value = null
user.value = null
localStorage.removeItem(TOKEN_KEY)
localStorage.removeItem(USER_KEY)
```

只删 localStorage、不调用 store 的 `logout()`，会导致界面仍然认为用户已登录；只改 store、不删 localStorage，刷新后又会恢复旧 token。

### Step 5：封装一个模块 API

以题目接口为例：

```ts
export interface QuestionPageParams {
  pageNum: number
  pageSize: number
  categoryId?: number
  difficulty?: number
  keyword?: string
}

export function fetchQuestionPage(
  params: QuestionPageParams,
): Promise<PageResult<QuestionListItem>> {
  return get<PageResult<QuestionListItem>>('/questions', { params })
}
```

注意：

- API 文件负责 URL、HTTP 方法、参数类型和返回类型。
- API 文件不负责弹窗、路由跳转和页面 loading。
- 页面负责何时调用，API 文件负责“怎么调用后端”。

### Step 6：理解 Pinia 登录流程

登录完整链路：

```text
LoginDialog 表单
  → auth.login(username, password)
  → api/auth.ts 的 login()
  → http.ts POST /api/auth/login
  → 返回 token + user
  → auth store 更新 ref
  → 写入 localStorage
  → 依赖 auth.user/auth.token 的组件自动更新
```

登录按钮不应该自己改 `localStorage`，否则状态会分散。所有登录态变化集中进入 store。

## 四、为什么 SSE 不走这里

普通 Axios 拦截器适合“请求发出，等待一个 JSON 响应”。AI 面试的 chat 接口返回 `text/event-stream`，需要逐段读取 `ReadableStream`，所以当前 `api/interview.ts` 使用 `fetch`，并手动补充 token 和失效处理。详见 7.1.7。

## 六、初学者课堂：一次普通请求的完整生命周期

以 `fetchQuestionDetail(7)` 为例：

```text
QuestionBank.vue 调用 fetchQuestionDetail(7)
        ↓
question.ts 组织 URL /questions/7
        ↓
http.ts 的 get<T>() 调用 Axios
        ↓
request interceptor 读取 localStorage 并加 Authorization
        ↓
浏览器发送 GET /api/questions/7
        ↓
后端返回 { code, message, data }
        ↓
response interceptor 判断 code
        ↓
成功返回 data，失败 reject Promise
        ↓
页面 await 得到 QuestionDetail
```

你在页面里看到的 `await fetchQuestionDetail(id)` 只是这条链路的最后一小段。理解链路后，遇到问题就能判断应该查 API 文件、拦截器、Network 还是页面状态。

## 七、Promise 和 async/await 的入门解释

网络请求不是立刻得到结果，而是先得到一个“将来会有结果的 Promise”：

```ts
const promise = fetchQuestionDetail(7)
```

`await` 会让当前异步函数暂停到结果回来，但不会冻结整个浏览器页面：

```ts
try {
  const detail = await fetchQuestionDetail(7)
  activeQuestion.value = detail
} catch (error) {
  // 请求失败
} finally {
  loading.value = false
}
```

只有标记为 `async` 的函数内部才能使用 `await`。`try/catch/finally` 对应成功、失败、无论如何执行三个路径，是页面请求 loading 的标准结构。

## 八、为什么 API 文件不弹提示

如果每个 API 函数都这样写：

```ts
export async function fetchSomething() {
  try {
    return await get('/something')
  } catch {
    ElMessage.error('失败')
  }
}
```

会出现三个问题：页面无法判断请求失败还是返回了 `undefined`；同一个错误可能被 API 和页面重复提示；请求层和 UI 组件耦合。当前项目把通用错误提示放在 `http.ts`，页面只决定是否需要额外展示重试按钮或局部错误。

## 九、登录态为什么要放 Pinia

登录态会被多个组件使用：

```text
AppShell       显示昵称、退出按钮
Router         判断是否允许进入页面
LoginDialog    执行登录
Interview      判断是否可以开始面试
History        未登录时显示登录引导
```

如果每个组件自己读写 localStorage，它们不会自动互相通知。Pinia 的 `ref` 是响应式的：store 变化后依赖它的组件会更新；localStorage 负责刷新页面后的持久化。两者职责不同，不能互相替代。

## 十、一个容易忽略的错误

`JSON.parse(rawUser)` 可能因为 localStorage 被手动写入非法 JSON 而抛异常。学习阶段可以先保持当前实现；后续增强时，可以用 try/catch 恢复为空用户。这个问题属于“外部持久化数据不可信”，和后端解析请求体的思想是一样的。

## 十一、接口封装练习

新增 `api/favorite.ts` 时按这个顺序：

1. 先写 `FavoriteQuery` 和 `FavoriteQuestionItem` 类型。
2. 再写 `fetchFavorites`，只负责 GET 参数和返回类型。
3. 再写 `addFavorite`、`removeFavorite`、`checkFavorite`。
4. 最后在页面中调用它们，不要在页面中拼 `/api` 或手写 Authorization。

完成后用浏览器 Network 验证请求 URL 是否刚好是后端 Controller 定义的路径。
