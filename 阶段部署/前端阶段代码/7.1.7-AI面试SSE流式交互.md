# 任务 7.1.7 · AI 面试 SSE 流式交互

> 本任务是前端阶段的核心难点。先理解普通 JSON 请求和流式请求的差别，再敲 `api/interview.ts` 和 `views/InterviewCabin.vue`。

## 一、本任务要实现什么

用户发送回答后，页面要做到：

```text
提交回答
  → 立即显示用户气泡
  → 显示 AI 正在思考
  → 收到 delta 就追加到 AI 气泡
  → 收到 done 结束等待
  → 收到 error 保留/标记失败并允许重试
```

后端事件格式：

```text
data: {"type":"delta","content":"线程池"}

data: {"type":"done","messageId":88}

data: {"type":"error","message":"AI 服务异常"}
```

## 二、为什么不能继续用 Axios

Axios 普通调用通常等整个响应体收完才交给你；SSE 需要在响应尚未结束时不断读取字节。当前实现使用浏览器原生 `fetch`：

```ts
const resp = await fetch(`/api/interviews/${sessionId}/chat`, {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    ...(token ? { Authorization: `Bearer ${token}` } : {}),
  },
  body: JSON.stringify({ content }),
})
```

这条请求绕过了 `http.ts`，所以 token 注入、登录失效处理也必须在这个函数里单独补上。

## 三、分步实现 SSE API

### Step 1：定义事件类型和回调

```ts
export interface ChatStreamHandlers {
  onDelta: (content: string) => void
  onDone: (messageId: number) => void
  onError: (message: string) => void
}
```

API 层只负责解析协议，然后通过回调通知页面，不直接修改页面的 `transcript`。这样 API 函数与具体页面解耦。

### Step 2：先判断是不是 SSE

```ts
const contentType = resp.headers.get('content-type') ?? ''
if (!contentType.includes('text/event-stream')) {
  const body = await resp.json().catch(() => null)
  handlers.onError(body?.message || '请求失败')
  return
}
```

同步阶段如果会话不存在、未登录或上一轮还在处理中，后端可能返回普通 JSON 错误，而不是 SSE。不能直接把 JSON 当流解析。

### Step 3：读取字节流并解码

```ts
if (!resp.body) {
  handlers.onError('当前浏览器不支持读取流式响应')
  return
}

const reader = resp.body.getReader()
const decoder = new TextDecoder('utf-8')
let buffer = ''

while (true) {
  const { done, value } = await reader.read()
  if (done) break
  buffer += decoder.decode(value, { stream: true })
  // 下一步在这里拆 SSE 帧
}
```

一次 `reader.read()` 不等于一次 SSE 事件：一个事件可能被拆成多个 read，多条事件也可能合并进一个 read，所以一定要有 `buffer`。

### Step 4：按空行拆帧

```ts
let separatorIndex: number
while ((separatorIndex = buffer.indexOf('\n\n')) !== -1) {
  const rawFrame = buffer.slice(0, separatorIndex)
  buffer = buffer.slice(separatorIndex + 2)

  const dataLine = rawFrame
    .split('\n')
    .find((line) => line.startsWith('data:'))
  if (!dataLine) continue

  const payload: ChatStreamEvent = JSON.parse(dataLine.slice(5).trim())
  if (payload.type === 'delta') {
    handlers.onDelta(payload.content ?? '')
  } else if (payload.type === 'done') {
    handlers.onDone(payload.messageId ?? 0)
  } else if (payload.type === 'error') {
    handlers.onError(payload.message ?? 'AI 服务异常，请稍后重试')
  }
}
```

处理完完整帧后，未形成 `\n\n` 的残片留在 `buffer`，等待下一次读取。这里是流式解析最容易漏掉的边界。

## 四、页面状态机

当前页面使用：

```ts
const phase = ref<
  'picking' | 'chatting' | 'generating-report' | 'report'
>('picking')
const waitingReply = ref(false)
const transcript = ref<ChatTurn[]>([])
```

发送回答的逻辑顺序：

```ts
async function sendAnswer() {
  const content = answer.value.trim()
  if (!content || waitingReply.value || !sessionId.value) return

  answer.value = ''
  transcript.value.push({ role: 'user', content })
  transcript.value.push({ role: 'assistant', content: '', pending: true })
  waitingReply.value = true

  await chatInterviewStream(sessionId.value, content, {
    onDelta(delta) {
      const last = transcript.value.at(-1)
      if (last?.role === 'assistant') {
        last.content += delta
        last.pending = false
      }
    },
    onDone() {
      waitingReply.value = false
    },
    onError(message) {
      waitingReply.value = false
      ElMessage.error(message)
    },
  })
}
```

`waitingReply` 是交互锁：发送期间禁用提交按钮，避免同一会话并发发起两条 AI 请求。后端也有 Redis 锁，但前端提前阻止重复点击可以减少无效请求和错误提示。

## 五、失败和卸载

网络失败时不能让 `waitingReply` 永远为 true。所有结束路径都要恢复它：正常完成、协议 error、fetch 抛异常。

页面有轮询或其他资源时，在 `onUnmounted` 中清理；如果后续给 SSE 加 `AbortController`，也要在卸载时 `controller.abort()`。不要把仍在运行的异步任务留给已经离开的页面。

## 六、自测清单

- 每收到一条 `delta`，AI 气泡都会追加，而不是覆盖前一段。
- 把一个 SSE 帧拆成两次网络读取时，仍能正确解析。
- 一次读取包含多条 SSE 帧时，能全部处理。
- 同步错误 JSON 能显示后端 message，不会触发 JSON.parse 流解析异常。
- AI 回复期间不能重复发送。
- 正常完成、错误、网络异常后，输入框都能再次使用。
- 刷新带 `sessionId` 的地址，页面能调用详情接口恢复对话。

## 七、初学者课堂：SSE 的数据不是一次性到达的

普通 JSON 请求像这样：

```text
请求 ─────────────────────→ 等待完整 JSON
响应 {"data":"完整答案"} ← 一次性收到
```

SSE 更像一条持续打开的水管：

```text
请求 ─────────────────────→ 连接保持打开
响应 data: delta 1         ← 先到一段
响应 data: delta 2         ← 再到一段
响应 data: done             ← 最后结束
```

浏览器的 `fetch()` 先返回 `Response`，并不代表所有正文已经到达。`resp.body.getReader()` 才是读取正文的入口；每次 `reader.read()` 得到的 `value` 是一小段二进制数据。

## 八、为什么必须使用 TextDecoder 和 buffer

网络传输的是字节，不保证一次正好传完一个中文字符，也不保证一次正好传完一条 SSE 消息。`TextDecoder('utf-8')` 负责把字节还原成文字，`buffer` 负责暂存不完整的文本。

例如服务端发送：

```text
data: {"type":"del
ta","content":"线程"}\n\n
```

第一次 read 可能拿到前半段，第二次 read 拿到后半段。如果你每次 read 都立即 `JSON.parse`，第一次必然报错。正确做法是拼进 buffer，只有找到完整的 `\n\n` 才拆出来。

## 九、SSE 解析代码逐行解释

```ts
const reader = resp.body.getReader()
const decoder = new TextDecoder('utf-8')
let buffer = ''
```

- `reader`：从响应体持续取数据。
- `decoder`：把 Uint8Array 转成 UTF-8 字符串。
- `buffer`：跨多次 read 保存残片。

```ts
const { done, value } = await reader.read()
if (done) break
buffer += decoder.decode(value, { stream: true })
```

`done=true` 表示服务端关闭了响应流；`stream:true` 告诉解码器后面可能还有字节，不要把当前片段当成完整输入处理。

```ts
const rawFrame = buffer.slice(0, separatorIndex)
buffer = buffer.slice(separatorIndex + 2)
```

先取出完整帧，再把已经消费的部分从 buffer 移除。顺序反了会导致重复处理同一条消息。

## 十、SSE 事件和页面事件的边界

`api/interview.ts` 只做协议工作：

```text
服务器文字帧 → 解析 JSON → 判断 type → 调用 onDelta/onDone/onError
```

`InterviewCabin.vue` 只做页面工作：

```text
onDelta → 找到正在生成的 assistant 气泡并追加 content
onDone  → waitingReply=false
onError → waitingReply=false，显示错误，允许重试
```

如果 API 层直接修改 Vue 的 `transcript`，它就和具体页面绑定；以后换成别的流式页面会很难复用。

## 十一、为什么要先插入空的 assistant 气泡

发送用户回答时先加入两条本地记录：

```ts
transcript.value.push({ role: 'user', content })
transcript.value.push({ role: 'assistant', content: '', pending: true })
```

这样用户马上看到自己的回答，页面也有一个确定的目标去接收后续 delta。若等第一段 delta 到达后才创建气泡，首段和慢网速下的 loading 状态会更难处理。

## 十二、异常路径必须逐一走通

### 1. 请求还没建立就失败

例如会话不存在、token 失效。后端返回普通 JSON，调用 `handlers.onError`。

### 2. 已经开始流式，模型中途失败

响应头已经发出，不能再把 HTTP 状态码改成 500，只能接收 `type=error` 或流异常，页面显示错误。

### 3. 用户关闭页面

前端应停止 reader 或 abort fetch，后端也应释放会话锁。否则模型可能继续生成无用内容。

### 4. 收到 done 但 messageId 缺失

要使用 `?? 0` 等默认值保护页面，之后再通过日志排查后端契约问题；不要让一个缺字段导致整个页面运行时崩溃。
