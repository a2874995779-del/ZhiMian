# 任务 7.1.4 · 路由、布局与组件通信

> 本任务解决“页面怎么进入、谁负责登录拦截、父子组件怎么传数据”三个问题。

## 二、路由守卫

当前路由通过 meta 标记需要登录的页面：

```ts
{
  path: '/interview',
  component: () => import('../views/InterviewCabin.vue'),
  meta: { label: '模拟面试舱', requiresAuth: true },
}
```

守卫的决策可以概括为：

```ts
router.beforeEach((to) => {
  if (!to.meta.requiresAuth || localStorage.getItem('zm-token')) {
    return true
  }

  return {
    path: '/questions',
    query: { login: '1', redirect: to.fullPath },
  }
})
```

公开页面直接放行；受保护页面没有 token 时，先跳到公开页面并把原目标放进 `redirect`。登录成功后 `AppShell` 读取这个 query，再跳回原页面。

这里的 `redirect` 只能接受站内路径，当前代码检查了 `startsWith('/')`，这是为了避免把登录后的跳转变成任意外部地址。

## 三、布局组件的职责

`App.vue` 只渲染：

```vue
<AppShell />
```

`AppShell` 负责：

- 侧边栏和顶部栏；
- 根据路由表生成导航；
- 显示登录按钮或当前用户；
- 主题偏好；
- 监听登录 query，打开登录弹窗；
- 在 `<RouterView>` 中渲染当前页面。

它不应该负责题目分页或 AI 对话，这些属于具体页面。

## 四、父子组件传值

### 1. 父传子：props

`QuestionCard` 接收一个题目：

```ts
const props = defineProps<{
  question: QuestionListItem
}>()
```

父组件使用：

```vue
<QuestionCard :question="q" />
```

props 是只读输入。子组件不要直接修改 `props.question.title`，需要修改时应发事件让父组件处理。

### 2. 子传父：emit

```ts
const emit = defineEmits<{
  open: [id: number]
}>()

function openDetail() {
  emit('open', props.question.id)
}
```

父组件监听：

```vue
<QuestionCard @open="openDetail" />
```

卡片只报告“用户点击了哪道题”，详情请求由页面完成，组件边界更清楚。

### 3. 双向绑定：`defineModel`

登录弹窗：

```ts
const visible = defineModel<boolean>({ default: false })
```

父组件：

```vue
<LoginDialog v-model="loginDialogVisible" />
```

这相当于父子之间约定了一个 `modelValue` 输入和 `update:modelValue` 更新事件。适合“显示/隐藏”这种通用状态，不适合把整个页面业务状态都塞进子组件双向修改。

## 五、生命周期与监听

```ts
onMounted(loadQuestions)
watch(pageNum, loadQuestions)
onUnmounted(stopTimer)
```

- `onMounted`：组件进入 DOM 后执行初次加载。
- `watch`：某个响应式值变化后执行副作用，例如换页重新请求。
- `onUnmounted`：页面离开时清理定时器、事件监听、流连接。

不要在 `watch` 中无条件修改它正在监听的值，否则很容易形成循环更新。

## 六、自测清单

- 未登录访问 `/interview` 会回到题库并弹出登录框。
- 登录成功后能回到原先想访问的地址。
- 能解释 props、emit、v-model 三种通信方式各自适合什么场景。
- 题目卡片只负责展示和发事件，题目详情请求由页面负责。
- 给路由新增“错题本”和“收藏夹”时，能决定它们是否需要 `requiresAuth: true`。

## 七、初学者课堂：路由和页面不是一回事

路由是一张“地址 → 组件”的映射表。它不等于页面本身，也不负责调用题目接口：

```ts
{
  path: '/questions',
  component: () => import('../views/QuestionBank.vue'),
}
```

当地址变化为 `/questions` 时，Router 找到 `QuestionBank.vue` 并把它放进 `RouterView`。真正的 `fetchQuestionPage()` 仍然由页面组件在 `onMounted` 或用户操作中调用。

这样分工的好处是：路由只关心“去哪里”，页面只关心“这个地方展示什么和怎么交互”。

## 八、登录守卫的执行时机

访问受保护地址时，执行顺序可以理解为：

```text
用户访问 /interview
  → beforeEach 收到目标路由 to
  → 检查 to.meta.requiresAuth
  → 检查 localStorage 中是否有 token
  → 有 token：return true，进入页面
  → 无 token：返回重定向对象，进入 /questions?login=1&redirect=...
```

守卫返回 `true` 表示继续；返回一个路由对象表示改去另一个地址。它不是后端鉴权的替代品，真正的权限仍然必须由后端 JWT 拦截器校验。前端守卫主要是改善体验，避免用户进入后才看到一个接口错误。

## 九、`route`、`router` 和 `RouterLink`

```ts
const route = useRoute()   // 读取当前路由、query、params
const router = useRouter() // 编程式跳转
```

```vue
<RouterLink to="/questions">题库</RouterLink>
```

```ts
router.push({ path: '/interview', query: { sessionId: String(id) } })
```

`RouterLink` 适合模板中的导航；`router.push` 适合点击后需要先判断、组装参数或执行业务逻辑的场景；`route` 只是当前信息，不要用它调用跳转。

## 十、组件通信的单向数据流

推荐把数据流记成：

```text
父组件 state
   ↓ props
子组件展示
   ↑ emit 事件
父组件执行请求或修改 state
```

例如题目卡片：父组件拥有题目列表，子组件展示一张卡片；用户点击卡片时，子组件 emit 题目 id；父组件收到后调用详情 API。子组件不需要知道后端 URL，也不需要管理抽屉是否打开。

## 十一、为什么不能到处使用全局 store

Pinia 适合跨页面共享的状态，例如登录用户、主题、全局通知。题库当前页、某个抽屉是否打开、某个按钮是否 loading，只属于题库页面，就留在页面的 `ref` 中。把所有状态都塞进 store 会让数据生命周期变长，页面离开后旧状态还可能残留。

## 十二、组件练习

把 `PracticeSandbox.vue` 拆成：

```text
PracticeSandbox.vue      保存 count 和 visible
CounterButton.vue        接收 count，emit increase
VisibilityMessage.vue    接收 visible，负责展示
```

练习目标不是为了拆得越细越好，而是体验一次 props 和 emit 的边界。只有当组件具有独立展示逻辑、重复使用价值或明显降低页面复杂度时，才值得拆出来。
