## 一、本任务要实现什么

任务 2.2 只做到了"创建会话 + 生成第一句开场白",这次要补上真正的"对话"能力:用户针对开场白/上一个问题给出回答,AI 结合**完整的历史对话**生成下一个问题。

先说清楚这次任务的**边界**:开发文档的思路提示明确写了"先在非流式接口上验证整个链路"——也就是说,这次先把"上下文怎么存、怎么取、怎么裁剪"这件事用一个**普通的、一次性返回完整结果**的接口验证正确,不掺和"流式输出"的复杂度。流式化是下一个任务(2.4)的事,到时候只需要把这次写好的"取上下文 → 调模型 → 存回结果"这条链路,从"等它跑完再一次性返回"换成"边跑边往外吐",核心逻辑不用大改。**这是一种很实用的开发节奏:先保证逻辑对,再解决传输方式的复杂度,不要两个难点一起啃。**

### 这次要解决的核心矛盾:大模型没有"记忆"

之前讲过(见 `docs/spring-ai初学.md`),大模型是无状态的,每次调用都不记得上一次说了什么。"多轮对话"这个体验,全靠**你自己每次把完整的历史消息重新发一遍**给它。这就带来两个新问题:

1. **历史存在哪、怎么取**——任务 2.2 已经把每条消息写进了 Redis List(`zhimian:interview:ctx:{sessionId}`)和 MySQL,这次要把"取"这件事也做完整,包括 Redis 缓存失效时的兜底。
2. **历史发多少合适**——聊得越久,历史消息越长,而大模型的每次调用都有**上下文窗口上限**(能接收的最大 token 数)和**按 token 计费**这两个硬约束。发太多会超限报错或者花冤枉钱,所以要在"发送前"就把历史裁剪到一个合理的预算内。

---

## 二、几个新概念

### 1. Token 是什么,为什么要按它算预算

Token 是大模型处理文本的最小单位,不完全等于"一个字"——英文大概 4 个字符≈1 个 token,中文大概 1~2 个字≈1 个 token(不同模型的分词器不完全一样)。**模型的收费和"能记住多少上下文"都是按 token 数算的,不是按字符数**,所以做上下文管理躲不开"预估这段文字大概是多少 token"这件事。

**这次不追求精确分词**,开发文档给的思路是粗算:中文字符数 / 2 大致估一个数量级就够用了。真要精确计算需要引入模型对应的分词器(比如 OpenAI 家族常用 `tiktoken`),这个精度对"防止超限"这个目的来说没必要,**先用便宜的方法解决 80% 的问题,这是工程上常见的取舍**。

### 2. 上下文裁剪的两种主流策略

- **滑动窗口(本项目用这个)**:只保留最近 N 轮对话(或者最近 M 个 token 预算内的消息),超出的直接丢弃。简单、可预测,缺点是"很早以前聊过的内容"会被彻底忘记。
- **摘要压缩**:被丢弃的历史不是直接扔掉,而是先用模型把它们总结成一段摘要,后续对话把"摘要 + 最近几轮原文"一起发给模型,相当于"模糊地记得早期聊了什么,但记得住最近的细节"。效果更好,但要多一次模型调用(生成摘要本身也要花 token 和时间),复杂度高不少。

这次选滑动窗口,原因是"够用、简单、面试也考得到点子上"——**能讲出摘要压缩这个替代方案、以及它比滑动窗口好在哪、贵在哪,比直接把两种方案都写出来更重要**,这是本任务的一个预告问题。

### 3. 缓存重建模式:你已经很熟悉这个套路了

Redis 上下文缓存有 TTL(任务 2.2 里定过 2 小时),一旦过期(用户中途去干别的事,超过 2 小时才回来继续聊),缓存读出来是空的——这次要处理这个场景:**Redis 未命中时,从 MySQL 把这场会话的全部历史查出来,重新灌回 Redis,再走正常的裁剪逻辑**。这和你在**任务 1.9(缓存穿透/雪崩/击穿)**、**任务 1.10(排行榜的 answer_record 兜底)**里已经用过的"数据库是事实来源,缓存没命中就回源重建"是同一个模式的第三次应用——这次你应该已经能一眼看出该怎么写了。

## 四、分步实现

### Step 1:把上下文管理抽成独立组件 `InterviewContextManager`

任务 2.2 里,"往 Redis 追加一条消息"这个逻辑(`appendToContext`)是写在 `InterviewServiceImpl` 里的私有方法。这次要新增"读取 + 裁剪 + 缓存重建"的逻辑,如果继续堆在 `InterviewServiceImpl` 里,这个类会越来越臃肿,而且以后**任务 2.6(结束面试生成报告)也要读完整对话历史**,到时候又要重复"读 Redis、未命中查 MySQL"这一整套。**上下文管理是一个独立的、会被多处复用的关注点,值得单独抽成一个类**——这和你在任务 1.9 把"补分类名+标签"抽成 `enrichToListVO` 是同一个道理(第二次被用到就该抽,不用等第三次)。

`ai/InterviewContextManager.java`(这是项目第一次用到 `ai` 这个包,专门存放和"面试官对话"这个业务强相关、但又不是纯 CRUD 的逻辑):

```java
package com.zhimian.ai;

import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.core.type.TypeReference;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.zhimian.mapper.InterviewMessageMapper;
import com.zhimian.model.entity.InterviewMessage;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;

import java.util.ArrayList;
import java.util.LinkedList;
import java.util.List;
import java.util.concurrent.TimeUnit;

@Slf4j
@Component
@RequiredArgsConstructor
public class InterviewContextManager {

    private static final String CTX_KEY_PREFIX = "zhimian:interview:ctx:";
    private static final long CTX_TTL_HOURS = 2;
    // 粗算 token 预算:中文字符数/2 估一个数量级,不追求精确
    private static final int TOKEN_BUDGET = 2000;

    private final StringRedisTemplate redisTemplate;
    private final InterviewMessageMapper interviewMessageMapper;
    private final ObjectMapper objectMapper;

    /**
     * 追加一条消息:写入 Redis List 并续期。
     * 只要这场对话还在继续,TTL 就应该一直被打回 2 小时,不会中途过期。
     */
    public void append(Long sessionId, InterviewMessage message) {
        String key = ctxKey(sessionId);
        redisTemplate.opsForList().rightPush(key, serialize(message));
        redisTemplate.expire(key, CTX_TTL_HOURS, TimeUnit.HOURS);
    }

    /**
     * 加载这场会话"要发给模型"的消息列表:Redis 未命中就从 MySQL 重建,
     * 最后统一按 token 预算裁剪(system prompt 永远保留)。
     */
    public List<InterviewMessage> load(Long sessionId) {
        String key = ctxKey(sessionId);
        List<String> raw = redisTemplate.opsForList().range(key, 0, -1);

        List<InterviewMessage> messages;
        if (raw == null || raw.isEmpty()) {
            log.info("会话 {} 的 Redis 上下文未命中,从 MySQL 重建", sessionId);
            messages = interviewMessageMapper.selectBySessionId(sessionId);
            rebuildRedis(sessionId, messages);
        } else {
            messages = raw.stream().map(this::deserialize).toList();
        }
        return trim(messages);
    }

    private void rebuildRedis(Long sessionId, List<InterviewMessage> messages) {
        if (messages.isEmpty()) {
            return;
        }
        String key = ctxKey(sessionId);
        for (InterviewMessage m : messages) {
            redisTemplate.opsForList().rightPush(key, serialize(m));
        }
        redisTemplate.expire(key, CTX_TTL_HOURS, TimeUnit.HOURS);
    }

    /**
     * 按 token 预算从最新往回裁剪:system prompt 永远保留,
     * 其余消息从最后一条往前累加 token 数,超预算就停,保证留下的是"最近的"。
     */
    private List<InterviewMessage> trim(List<InterviewMessage> messages) {
        InterviewMessage systemMsg = messages.stream()
                .filter(m -> "system".equals(m.getRole()))
                .findFirst()
                .orElse(null);
        List<InterviewMessage> others = messages.stream()
                .filter(m -> !"system".equals(m.getRole()))
                .toList();

        int used = systemMsg != null ? estimateTokens(systemMsg.getContent()) : 0;
        LinkedList<InterviewMessage> kept = new LinkedList<>();
        for (int i = others.size() - 1; i >= 0; i--) {
            InterviewMessage m = others.get(i);
            int tokens = estimateTokens(m.getContent());
            if (used + tokens > TOKEN_BUDGET) {
                break;
            }
            kept.addFirst(m);
            used += tokens;
        }

        List<InterviewMessage> result = new ArrayList<>();
        if (systemMsg != null) {
            result.add(systemMsg);
        }
        result.addAll(kept);
        log.info("会话上下文裁剪完成:原始 {} 条,保留 {} 条,预估 token {}", messages.size(), result.size(), used);
        return result;
    }

    private int estimateTokens(String text) {
        return text.length() / 2;
    }

    private String ctxKey(Long sessionId) {
        return CTX_KEY_PREFIX + sessionId;
    }

    private String serialize(InterviewMessage message) {
        try {
            return objectMapper.writeValueAsString(message);
        } catch (JsonProcessingException e) {
            throw new RuntimeException(e);
        }
    }

    private InterviewMessage deserialize(String json) {
        try {
            return objectMapper.readValue(json, InterviewMessage.class);
        } catch (JsonProcessingException e) {
            throw new RuntimeException(e);
        }
    }
}
```

【讲解,这是本任务最核心的部分】

- **为什么按 `role` 找 system 消息,而不是假设它一定是列表第 0 条?** 虽然目前的写入顺序确实保证了 system 永远最先插入,但**代码不应该依赖"隐含的顺序约定"去判断一条数据的身份**——万一以后哪个环节改了插入顺序,或者从 MySQL 查出来的顺序因为某种原因变了,"assume 第 0 条是 system"这种写法会悄悄读错数据,而且不会报错,是那种最难排查的 bug。用 `role` 字段直接过滤,语义清晰,也不受顺序变化影响。
- **裁剪为什么要"从最新往回"数,而不是"从最旧往前"数到预算就切?** 想清楚这次任务的目标:**保留的应该是离现在最近的对话**,越早聊过的内容优先级越低。所以要**倒序遍历**(`for (int i = others.size() - 1; i >= 0; i--)`),从最后一条开始往前累加 token,一旦发现"再往前加一条就要超预算了"就停手。这里如果不小心写成正序遍历、从预算里扣,会导致留下的是**最旧的**几条、丢掉的是**最新的**几条——这正是开发文档"易踩的坑"里点名的"裁剪方向搞反",效果是 AI 记得住你老早以前说的话,却不记得你刚刚才说过什么,体验完全是反的。
- **`LinkedList` + `addFirst`**:倒序遍历、但要保持"最终结果里消息顺序是从旧到新",用 `LinkedList.addFirst` 每次把新决定要保留的消息插到已保留列表的最前面,遍历完之后这个链表天然就是正序的,不需要额外反转一次。
- **`Redis` 未命中时的重建,不只是查出来就完了,还要把它重新写回 `Redis`**:如果只读 MySQL 不回填,那这次调用是快了,但下一次同一个会话再来对话,Redis 还是空的,又要查一次 MySQL——**缓存重建之后一定要把数据放回缓存,不然这个"缓存"形同虚设**,这是缓存设计的基本要求,任务 1.9 讲穿透防护时其实也讲过同一个道理(查不到也要缓存"没有"这个事实)。

`service/impl/InterviewServiceImpl.java`,这次改动比较大,完整贴出核心部分(`createInterview` 方法本身不用大改,只是把原来内嵌的 `appendToContext`/`serialize` 私有方法删掉,换成调用 `InterviewContextManager`):

```java
@Service
@RequiredArgsConstructor
public class InterviewServiceImpl implements InterviewService {
    private static final int MAX_ACTIVE_SESSIONS = 3;
    private static final String LOCK_PREFIX = "zhimian:interview:lock:";
    private static final long LOCK_TTL_SECONDS = 60;

    private final InterviewMessageMapper interviewMessageMapper;
    private final InterviewSessionMapper interviewSessionMapper;
    private final ChatClient chatClient;
    private final StringRedisTemplate stringRedisTemplate;
    private final InterviewContextManager contextManager;

    @Override
    public InterviewSessionVO createInterview(CreateInterviewDTO dto) {
        // ……方向校验、会话数限制、插库、生成开场白,这部分逻辑不变(见任务 2.2)……

        InterviewMessage systemMsg = buildMessage(session.getId(), "system", systemPrompt);
        InterviewMessage assistantMsg = buildMessage(session.getId(), "assistant", openingMessage);
        interviewMessageMapper.insert(systemMsg);
        interviewMessageMapper.insert(assistantMsg);
        contextManager.append(session.getId(), systemMsg);
        contextManager.append(session.getId(), assistantMsg);

        // ……组装并返回 InterviewSessionVO,不变……
    }

    @Override
    public ChatReplyVO chat(Long sessionId, ChatMessageDTO dto) {
        InterviewSession session = mustFindSession(sessionId);
        if (session.getStatus() != 0) {
            throw new BusinessException(ErrorCode.CONFLICT, "会话已结束,无法继续对话");
        }

        String lockKey = LOCK_PREFIX + sessionId;
        Boolean locked = stringRedisTemplate.opsForValue().setIfAbsent(lockKey, "1", LOCK_TTL_SECONDS, TimeUnit.SECONDS);
        if (!Boolean.TRUE.equals(locked)) {
            throw new BusinessException(ErrorCode.TOO_MANY_REQUESTS, "上一轮对话还在处理中,请稍候");
        }

        try {
            List<InterviewMessage> history = contextManager.load(sessionId);

            InterviewMessage userMsg = buildMessage(sessionId, "user", dto.getContent());
            interviewMessageMapper.insert(userMsg);
            contextManager.append(sessionId, userMsg);

            List<Message> springAiMessages = toSpringAiMessages(history);
            springAiMessages.add(new UserMessage(dto.getContent()));

            String reply = chatClient.prompt(new Prompt(springAiMessages))
                    .call()
                    .content();

            InterviewMessage assistantMsg = buildMessage(sessionId, "assistant", reply);
            interviewMessageMapper.insert(assistantMsg);
            contextManager.append(sessionId, assistantMsg);

            ChatReplyVO vo = new ChatReplyVO();
            vo.setMessageId(assistantMsg.getId());
            vo.setContent(reply);
            return vo;
        } finally {
            stringRedisTemplate.delete(lockKey);
        }
    }

    private InterviewSession mustFindSession(Long sessionId) {
        InterviewSession session = interviewSessionMapper.selectById(sessionId);
        if (session == null) {
            throw new BusinessException(ErrorCode.NOT_FOUND, "面试会话不存在");
        }
        return session;
    }

    private List<Message> toSpringAiMessages(List<InterviewMessage> history) {
        List<Message> messages = new ArrayList<>();
        for (InterviewMessage m : history) {
            switch (m.getRole()) {
                case "system" -> messages.add(new SystemMessage(m.getContent()));
                case "user" -> messages.add(new UserMessage(m.getContent()));
                case "assistant" -> messages.add(new AssistantMessage(m.getContent()));
                default -> throw new IllegalStateException("未知的消息角色: " + m.getRole());
            }
        }
        return messages;
    }

    // buildMessage 不变(见任务 2.2)
}
```

新增的 import:`org.springframework.ai.chat.messages.Message`、`SystemMessage`、`UserMessage`、`AssistantMessage`、`org.springframework.ai.chat.prompt.Prompt`。

【讲解】

- **`mustFindSession` 目前只校验了"会话存不存在",没有校验"这场会话是不是当前登录用户自己的"**——水平越权(拿别人的会话 id 来对话)这个安全点,开发文档把它作为**任务 2.5 的核心知识点**专门讲,这次先不做也不算超纲,但如果你手痒想现在就加一行 `if (!session.getUserId().equals(UserContext.getUserId())) throw ...`,完全可以,不会和后面的任务冲突。我建议你**跟着任务节奏走**,2.5 会系统性地把"每个按 id 查的接口都要校验归属"这件事讲透。
- **`session.getStatus() != 0` 用 `ErrorCode.CONFLICT`(40900)而不是 `PARAMS_ERROR`**:这次请求本身格式没问题,问题出在"这个会话现在的状态不允许做这个操作"——这是**资源状态冲突**的语义,`CONFLICT` 比 `PARAMS_ERROR` 更贴切。
- **`interview:lock:{sessionId}` 这把互斥锁在干什么**:如果同一个会话被并发发起两次 `chat` 请求(比如用户手抖点了两次提交,或者两个浏览器标签页开着同一个会话),两次请求都会去读同一份上下文、各自往里追加消息、各自调用模型——历史消息的顺序会被打乱(所谓"上下文交错"),AI 收到的对话历史可能是错位的。用 `SET NX EX` 抢一把会话级的锁,抢不到的请求直接返回"上一轮还在处理中",而不是让两次调用的结果互相踩踏。这个模式你在**任务 1.9(详情缓存击穿防护)**里已经写过一次,这里是同一个思路换了个业务场景。**注意这次锁的粒度是"整个会话",不是"整个接口"**——不同会话之间可以完全并发,不受影响。
- **`toSpringAiMessages` 在把项目自己的 `InterviewMessage`(数据库实体)转换成 Spring AI 认识的 `Message` 接口的具体实现**——这是两套"消息"概念的转换:一套是你自己的持久化模型(有 `id`、`sessionId`、`tokens` 这些数据库相关字段),一套是 Spring AI 用来构建请求的领域模型(只关心角色和内容)。这种"内部模型不直接暴露给第三方库,而是转换成对方认识的类型"是很常见的做法,好处是以后如果 Spring AI 的 `Message` 接口变了,只需要改这一个转换方法,不用动 `InterviewMessage` 这个数据库实体。
- **`chatClient.prompt(new Prompt(springAiMessages))`**:和任务 2.2 里 `.system(...).user(...)` 这种"逐条设置"的写法不同,这次是**直接把一整份消息列表**(已经从 `InterviewContextManager` 拿到、裁剪好的历史 + 这一轮新的用户消息)打包成一个 `Prompt` 对象传进去。这才是"多轮对话"的真正实现方式——不是"模型自己记得",而是**每次调用你都把完整的、你认为它该看到的历史,重新摆在它面前**。
