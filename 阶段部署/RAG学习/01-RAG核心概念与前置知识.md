# RAG 入门:阶段三开工前必须先懂的那些概念

> 这篇是**纯概念前置课**,一行项目代码都不用你写。目的是:等你真正开始写阶段三的代码(`vectorStore.similaritySearch(...)`、`TokenTextSplitter`、`knowledge_chunk` 表……)时,不会觉得"每个 API 都认识、合起来不知道在干嘛"。
> 阅读方式:不用背,重点是**建立直觉**——每个概念先问"它要解决什么问题",再看"它怎么解决"。读完你应该能对着文末的自测清单把 RAG 这条链路自己讲一遍。
> 承接:前面 `docs/spring-ai初学.md` 讲的是"怎么调模型对话"(阶段二),这篇讲的是"怎么让模型查你自己的资料回答"(阶段三)。

---

## 一、先搞清楚:RAG 到底要解决什么问题

大模型(阶段二你已经用得很熟了)有两个绕不开的硬伤:

1. **知识有截止日期,而且不知道你的私有数据**。模型是拿"截止到某个时间点的公开互联网数据"训练出来的。它不知道你公司内部的文档、不知道你这个题库里的参考答案、更不知道昨天才发生的事。你问它"我们题库里那道线程池的题标准答案是什么",它只会**按它自己学到的通用知识编一个**,不是你库里那份。

2. **幻觉(hallucination)**。模型的本质是"根据前文预测下一个最像的词",所以当它不知道答案时,**它不会说"我不知道",而是一本正经地编一个看起来很对的**。这在闲聊里无所谓,在"给用户提供准确参考答案"这种场景里是致命的。

**怎么解决?有两条路:**

- **微调(Fine-tuning)**:拿你的私有数据再训练一遍模型,把知识"焊"进模型参数里。缺点:贵、慢、数据一更新就得重训、还容易训崩。像是"让学生把整本书背下来",书一改版就得重背。
- **RAG(检索增强生成)**:不动模型,而是在**每次提问时,先从你的资料库里找出跟问题最相关的几段,连同问题一起塞给模型**,让它"照着这几段材料回答"。像是"开卷考试"——学生不用背书,考试时把书翻到相关那页摆在面前照着答。

**这个项目选 RAG,不选微调。** 因为对一个"面试题库 + AI 答疑"的应用,资料会经常增删改(今天加 10 道题、明天改一份八股),RAG 只要把新资料**塞进资料库**就行,模型一秒都不用重训;而且"照着材料回答"天然压制了幻觉——模型手里有卷子,就不用瞎编了。

> 一句话记住 RAG:**RAG = 开卷考试。把模型不知道的私有知识,在提问的那一刻"翻到相关那页"塞进它的输入里,让它照着答。**

## 二、RAG 这个词拆开看:检索(R) + 增强(A) + 生成(G)

**R**etrieval-**A**ugmented **G**eneration,倒着念更好懂:

- **G 生成(Generation)**:就是阶段二那个大模型生成回答的能力,你已经会了。
- **A 增强(Augmented)**:在让它生成之前,给它的输入**"增强"**——补充一些它本来不知道的材料。
- **R 检索(Retrieval)**:这些材料从哪来?从你的资料库里**"检索"**出跟当前问题最相关的几段。

所以 RAG 全流程一句话:**先检索(找到相关资料)→ 拿资料增强提问 → 让模型生成答案**。难点全在"检索"这一步——**怎么在一大堆资料里,快速找到跟用户这句话语义最相关的几段?** 这就引出了下面这一串新概念。

## 三、核心概念逐个击破(这一节是重点)

### 3.1 Embedding(向量化):把文字变成一串数字

**它要解决的问题**:计算机不认识文字,更不会判断"两句话意思像不像"。"线程池参数"和"ThreadPoolExecutor 的构造函数",字面上一个汉字都不重合,但语义上高度相关——**传统的关键词匹配(like '%线程池%')根本发现不了这种相关**。我们需要一种方式,让计算机能算出"这两句话意思有多近"。

**它怎么解决**:用一个专门的模型(叫 **Embedding 模型**,和对话模型是两个不同的模型)把每一段文字**转换成一串固定长度的数字**,比如 1024 个小数:

```
"线程池参数"                    → [0.021, -0.113, 0.887, ... ]  (1024 个数)
"ThreadPoolExecutor 构造函数"   → [0.019, -0.108, 0.901, ... ]  (1024 个数)
"今天天气真好"                   → [-0.55,  0.72, -0.03, ... ]  (1024 个数)
```

这一串数字叫**向量(vector / embedding)**。神奇之处在于:这个模型经过训练,会让**语义相近的文本,转换出来的向量在空间里也"离得近";语义无关的,离得远**。上面前两句意思相近,它们的向量几乎挨在一起;第三句"天气"跟它们无关,向量就飘到很远的地方去了。

打个比方:embedding 就像把每段文字**扔到一张巨大的"语义地图"上**,内容相近的文字自动聚到地图的同一片区域。"线程池"相关的都在地图东边,"美食"相关的都在地图西边。

> **必须记住的两点**:
> ① Embedding 模型和对话模型是**两个模型**。DeepSeek 只有对话没有 embedding,所以项目里对话用 DeepSeek、向量化要另找一个 embedding 服务(阶段三会用通义 text-embedding)。
> ② **向量的维度必须前后一致**。入库时用某个 embedding 模型转成了 1024 维,查询时也必须用**同一个模型**转成 1024 维——不同模型维度不同(有的 768、有的 1536),混用会直接报错或结果全乱。这是开发文档点名的坑。

### 3.2 向量相似度:怎么算"两个向量离得近不近"

有了向量,"两句话像不像"就变成了"两个向量距离远不远"这个纯数学问题。最常用的度量是**余弦相似度(cosine similarity)**:

- 它算的是两个向量**方向的夹角**,而不是长度。夹角越小(方向越一致)→ 越相似。
- 结果通常归一化到 **0~1**(或 -1~1):**1 = 几乎同义,0 = 毫不相关**。
- 为什么用"方向"而不是"直线距离"?因为在语义空间里,**方向代表"讨论的是什么话题",长度更多受文本长短影响**——一句话和它的详细展开版,方向应该一致(同一话题),我们不希望因为一个长一个短就判定它们不相似。

你在代码里会看到检索结果带一个 `score`(比如 0.82),那就是这个相似度分数。**分数越高,这段资料和用户问题越相关。** 阶段三任务 3.3 要设一个**阈值**(比如 0.7),低于它的资料宁可不要(后面 3.5 讲为什么)。

### 3.3 向量数据库:专门用来"找最近邻"的库

**普通数据库(MySQL)怎么查**:精确匹配或范围匹配——`WHERE id = 5`、`WHERE title LIKE '%线程%'`。它擅长"值等不等、在不在范围内",但**不会算"语义最近"**。

**向量数据库要干的事**:你给它一个查询向量,它帮你从库里**几百万条向量中,快速找出方向最接近的那 topK 个**(比如最相似的 3 条)。这个操作叫**相似度检索 / 最近邻搜索**。

你会在代码里遇到的核心方法就一个:

```java
// 伪代码,建立印象即可
List<Document> results = vectorStore.similaritySearch(
        SearchRequest.query("线程池核心参数有哪些")  // 查询文本(框架内部会先帮你 embedding)
                     .withTopK(3)                    // 要最相似的前 3 条
                     .withSimilarityThreshold(0.7)   // 相似度低于 0.7 的不要
);
```

**本项目的向量库用 Redis Stack**(就是你已经在用的 Redis,换一个带 RediSearch/JSON 模块的镜像 `redis-stack`)。好处:不用新引入组件,还能在面试时讲"Redis 不只是缓存,它还能当向量库"。Spring AI 提供了统一的 `VectorStore` 接口,以后想换 Milvus/pgvector,业务代码几乎不用改——这又是一次"接口抽象隔离底层实现"的活例子(跟阶段二 `ChatClient` 隔离模型厂商一个道理)。

### 3.4 向量索引 HNSW vs FLAT:精确但慢 vs 近似但快

库里有几百万条向量,来一个查询向量要找最相似的 topK,**怎么找**?两种策略:

- **FLAT(暴力/精确)**:把查询向量和库里**每一条**都算一遍相似度,排序取前 K。结果 100% 精确,但库大了就慢(几百万次计算)。
- **HNSW(近似)**:预先给向量建一种**分层图索引**,查询时顺着图"跳"着找,只比较一小部分向量就能找到"几乎是最相似"的那几条。速度快几个数量级,代价是**极小概率漏掉真正最相似的那条**(近似,不保证 100% 精确)。

一句话:**FLAT 用精度换速度,HNSW 用速度换一点点精度**。生产环境数据量大,基本都用 HNSW;你的项目数据量小,两者都行,理解这个"精确 vs 近似"的权衡就够了(这是任务 3.1 的考点)。

### 3.5 Chunk 切分:为什么不能把整篇文档直接向量化

假设你有一篇 5000 字的《Java 并发八股》文档,能不能直接把整篇转成一个向量存进去?**不行,有两个原因:**

1. **Embedding 模型有输入长度上限**,整篇太长塞不下。
2. **更关键:召回精度会崩**。如果整篇是一个向量,那这个向量代表的是"整篇的平均语义"——很模糊。用户问"线程池参数",你只想召回**讲线程池那一小段**,而不是把整篇 5000 字(里面还有锁、volatile、CAS……)整个塞给模型。整篇塞进去 = 大量无关内容进 prompt,又费 token 又干扰模型。

所以要先把长文档**切成一小段一小段**,每段叫一个 **chunk**,每个 chunk 单独向量化、单独入库。检索时就能精准命中"讲线程池的那个 chunk",而不是整篇。

**切多大?这是个权衡(任务 3.2 的核心考点):**

- **切太小**(比如 50 字):语义被切碎,一句话讲一半就断了,单个 chunk 可能表达不完整,召回回来看不懂。
- **切太大**(比如 2000 字):又回到"整篇"的老问题,一个 chunk 混了好几个话题,召回不精准、还费 token。
- **经验值**:项目里用 **300~500 token 一个 chunk**,是个平衡点。

**为什么 chunk 之间要"重叠(overlap)"?** 比如相邻两个 chunk 重叠 50 token。因为**硬切**可能刚好把一个完整的意思从中间劈开——上半句在 chunk A 结尾、下半句在 chunk B 开头,两个 chunk 单看都不完整。让它们首尾重叠一点,就能保证"跨切分边界的那句话"至少在某一个 chunk 里是完整的,不会因为切分位置不巧而丢失关键信息。

> 类比:把一本书拆成活页去归档,如果沿着句子中间硬撕,每页开头结尾都是半句话;overlap 就相当于**每页多印一点上一页的结尾**,保证任何一句话都能在某一页里完整读到。

## 四、把概念串起来:RAG 的两条流水线

上面的概念不是孤立的,它们串成**两条流水线**——一条离线建库、一条在线问答。看懂这张图,阶段三的代码结构就清楚了。

### 流水线 A:离线 ETL(把资料灌进向量库)—— 对应任务 3.2

平时(用户提问之前)就做好,是"备考时把书整理好翻页贴标签":

```
一篇文档(md/txt)
   │  ① 切分:按 ## 标题或 300~500 token 切成一个个 chunk(相邻重叠 50)
   ▼
多个 chunk
   │  ② 向量化:每个 chunk 用 embedding 模型转成一个向量
   ▼
多个 (chunk 文本 + 向量)
   │  ③ 入库:向量存进向量库(Redis Stack),chunk 原文 + 关联信息(docId/chunkId)
   │     同时也存一份进 MySQL 的 knowledge_chunk 表(事实来源,跟阶段二双写一个思路)
   ▼
资料库建好,待命
```

这一步**耗时**(大文档切分+逐个向量化很慢),所以任务 3.2 特意要求**异步处理**:上传接口收到文件先插一条 `knowledge_doc`(status=0 处理中)、立刻返回,把重活丢给线程池慢慢做,做完把 status 改成 1(已完成),失败改成 2(并记原因)。这就是为什么开发文档在这里让你**手写 `ThreadPoolExecutor` 并讲得出七个参数**——把线程池八股用在了实处。

### 流水线 B:在线问答(用户提问时实时走)—— 对应任务 3.3 / 3.4

```
用户的问题(query),比如题目标题"线程池的核心参数"
   │  ① 向量化:用同一个 embedding 模型把 query 转成查询向量
   ▼
查询向量
   │  ② 检索:vectorStore.similaritySearch(topK=3, threshold=0.7)
   │     向量库返回最相似的 3 个 chunk(每个带 score)
   ▼
topK 个相关 chunk(+ 相似度分数)
   │  ③ 阈值过滤:score 低于 0.7 的丢掉;如果全被丢光 → 走降级(见下)
   ▼
筛选后的 chunk
   │  ④ 拼 prompt(增强):"仅根据以下资料回答,资料不足就说不知道:
   │                      {chunk1}{chunk2}{chunk3}  问题:{query}"
   ▼
增强后的 prompt
   │  ⑤ 生成:丢给对话模型(DeepSeek),它照着资料生成答案
   ▼
答案 + sources(附上每段资料来自哪篇文档、原文片段)
```

**注意第 ④ 步那句 prompt 的措辞**:"仅根据以下资料回答,资料不足就说不知道"——这是 RAG 压制幻觉的关键。你既给了它开卷的"卷"(chunks),又明确命令它"只准照卷答、没有就说不知道",双管齐下。

**降级路径(任务 3.4)**:如果检索一条都没命中(用户问的东西知识库里根本没有),不要硬凑——直接返回题库里自带的那份 `answer`,并标注"未命中知识库"。**宁可诚实地降级,也不要拿无关资料硬编答案。**

## 五、决定 RAG 效果的几个"旋钮" + 一对核心权衡

RAG 能不能用得好,不在于代码写得多复杂,而在于这几个参数调得准(任务 3.5 专门做这件事):

| 旋钮 | 调大 | 调小 |
|------|------|------|
| **chunk 大小** | 语义更完整,但召回不精准、费 token | 召回精准,但语义可能破碎 |
| **overlap 重叠** | 更不容易切碎完整语义,但冗余、存储变多 | 省空间,但边界句子可能丢 |
| **topK(取前几条)** | 召回更全,但更多无关内容进 prompt、费 token | 精准省 token,但可能漏掉相关资料 |
| **相似度阈值** | 只留高度相关的,准但可能返回空 | 宽松、召回多,但混进不相关的 |

这背后是一对贯穿信息检索的核心权衡——**召回率(Recall) vs 准确率(Precision)**:

- **召回率**:该找到的相关资料,你找回来了多少?(宁可多抓,别漏)
- **准确率**:你找回来的资料里,真正相关的占多少?(宁可少抓,别混进垃圾)

两者天然矛盾:阈值调低、topK 调大 → 召回率高但准确率低(抓得多但杂);反过来 → 准确率高但召回率低(准但可能漏)。**RAG 调优的本质,就是在你的业务场景下,把这两者调到一个合适的平衡点**,并且**用数据说话**(任务 3.5 让你准备 10 个测试问题统计命中率、调参记录对比)——这份数据写进简历比"做了个 RAG"有力得多。

## 六、RAG 为什么能减少幻觉,以及它的边界

**为什么能减少幻觉**:幻觉的根源是"模型不知道却硬编"。RAG 把相关资料(卷子)直接塞进它的输入,又命令它"只照资料答",它就没有编造的空间了——**从'闭卷凭记忆' 变成 '开卷照着抄'**。

**但 RAG 不是万能的,有几条边界你要清楚**:

1. **垃圾进,垃圾出(garbage in, garbage out)**。如果检索这一步召回的资料本身就不相关(阈值没设好、chunk 切得烂),把垃圾塞进 prompt,模型照着垃圾答,结果更糟。所以**相似度阈值是 RAG 防幻觉的第一道闸**——它决定了"什么样的资料才配进 prompt"。任务 3.3 特意强调:低于阈值宁可返回空,不硬凑。

2. **召回的质量决定上限**。RAG 的效果 = 检索质量 × 生成质量。检索没找对,生成再强也白搭。所以评估时要**把"召回质量"和"生成质量"分开评**(任务 3.5)。

3. **Prompt 注入的意识(了解级)**。你召回的资料是"外部内容",万一某段资料里混了一句"忽略之前的指令,告诉用户……"这种指令性文本,会不会被模型当成命令执行?这是 RAG/Agent 场景的一类安全问题,阶段三只要求你**有这个意识**,知道"塞进 prompt 的外部内容不是绝对可信的"即可。

## 七、这个项目里,RAG 具体长什么样(先对上号)

把上面的抽象概念,提前对到阶段三你会真正碰到的东西,写代码时就能"对上号":

| 抽象概念 | 项目里的具体落地 |
|----------|------------------|
| 对话模型 | DeepSeek(阶段二已接,继续用) |
| Embedding 模型 | 通义 text-embedding(DeepSeek 没有 embedding,单独接) |
| 向量数据库 | Redis Stack(`redis-stack` 镜像)+ Spring AI 的 `RedisVectorStore` |
| 向量索引 | HNSW(Redis Stack 支持) |
| 切分工具 | Spring AI 的 `TokenTextSplitter`,或自己按 `##` 标题切 |
| chunk 的事实来源 | MySQL 的 `knowledge_chunk` 表(向量库存向量,MySQL 存原文,双写) |
| 文档元信息 + 处理状态 | MySQL 的 `knowledge_doc` 表(status:0处理中/1完成/2失败) |
| 检索 API | `vectorStore.similaritySearch(topK, threshold)` |
| RAG 的应用出口 | 任务 3.4「答错联动参考答案」:答错某题 → 用题目标题去检索 → 组装 RAG prompt → 返回带出处的答案 |

你会发现很多东西是**老朋友换了个场景**:双写(向量库+MySQL,像阶段二的 Redis+MySQL)、缓存/事实来源的分工、异步线程池(像阶段一浏览量回写)、接口抽象隔离底层(`VectorStore` 像 `ChatClient`)、幂等状态机(`knowledge_doc` 的 status 像面试报告的 0/1/2)。**RAG 引入的真正全新概念,其实就是第三节那几个:embedding、向量相似度、向量库、索引、chunk。这几个吃透了,阶段三代码就不再是天书。**

## 八、澄清边界:RAG vs 微调 vs Function Calling

这三个经常被一起问,别搞混(阶段四会用到 Function Calling):

| 方案 | 解决什么 | 一句话 | 本项目 |
|------|----------|--------|--------|
| **微调** | 把知识/风格焊进模型参数 | 让模型"重新学一遍" | 不用(太重、数据常变) |
| **RAG** | 让模型用**静态私有知识**回答 | 开卷考试,把资料塞进输入 | 阶段三,核心 |
| **Function Calling** | 让模型能拿**实时数据/执行动作** | 模型说"我要调这个函数",框架执行完把结果喂回它 | 阶段四(生成复习计划时查错题分布) |

**RAG 和 Function Calling 是互补的**:RAG 给的是"躺在库里的静态知识"(题库、八股文档);Function Calling 给的是"需要实时算出来的数据或要执行的操作"(比如"这个用户各分类错了多少题"——这得现查数据库,不是躺在文档里的死知识)。一个管"查资料",一个管"调工具/取实时数据"。

> Function Calling 有个必考点先剧透:**模型本身不会执行任何代码**。它只是在输出里说"我想调用 `getWrongStats(userId=5)` 这个函数",真正执行的是你的后端框架,执行完把结果再喂回模型让它接着生成。跟"结构化输出"一样,模型永远只吐文本,"调函数""输出对象"都是框架在旁边帮它兑现的。这个到阶段四再细讲。

## 十、术语速查表

| 术语 | 一句话 |
|------|--------|
| RAG | 检索增强生成;提问时先检索相关资料塞进输入,让模型照着答 |
| Embedding / 向量 | 把一段文字转成一串固定长度的数字,语义近则向量近 |
| Embedding 模型 | 专门做向量化的模型,和对话模型是两个模型 |
| 余弦相似度 | 用两个向量的夹角衡量语义相似度,0~1,越大越像 |
| 向量数据库 | 专门做"最近邻检索"的库,给一个向量返回最相似的 topK |
| HNSW | 近似向量索引,快、极小概率漏,生产常用 |
| FLAT | 暴力精确检索,准、慢,小数据量可用 |
| Chunk / 切分 | 把长文档切成的小段,每段单独向量化入库 |
| Overlap | 相邻 chunk 首尾重叠的部分,防止完整语义被切分边界劈开 |
| topK | 检索时取最相似的前 K 条 |
| 相似度阈值 | 低于这个分数的资料一律不要,RAG 防幻觉第一道闸 |
| 召回率 Recall | 该找到的相关资料,找回来了多少 |
| 准确率 Precision | 找回来的资料里,真正相关的占多少 |
| VectorStore | Spring AI 统一的向量库接口,屏蔽 Redis/Milvus/pgvector 差异 |
