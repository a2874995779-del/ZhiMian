## 二、07 和前面六个阶段是什么关系

把整个过程想成图书馆：

```text
04：设计书库登记表
        ↓
05：把整本书整理成可阅读的小节
        ↓
06：把小节可靠地放进书架和索引系统
        ↓
07：用户提问时，找到最相关的小节，并证明找得准
        ↓
08：让 ChatModel 阅读这些小节后组织答案
```

第 06 阶段结束时，我们已经拥有：

```text
自然语言知识
    ↓ KnowledgeTextCleaner
干净文本
    ↓ MarkdownSectionParser
有标题路径的章节
    ↓ TokenWindowSplitter
KnowledgeChunk
    ├── MySQL：事实来源
    └── Redis Stack：向量检索索引
```

第 07 阶段要完成反方向的数据流：

```text
用户自然语言问题
    ↓ EmbeddingModel
查询向量
    ↓ Redis VectorStore
相似向量候选
    ↓ metadata.chunkId
MySQL 批量回表校验
    ↓ 去重、恢复排序、截断 TopK
可信的知识命中结果
```

注意“Redis 命中以后还要回 MySQL”。原因是：

- MySQL 是知识数据的事实来源；
- Redis 是可以重建的派生索引；
- Redis 中可能短暂残留已经删除或状态失效的向量；
- 返回给业务的正文应该使用 MySQL 当前有效版本；
- 不能只相信 Redis metadata 中的状态。

这就是第 06 阶段“最终一致性”思想在检索方向上的继续应用。

## 三、先理解 Retrieval 的输入和输出

### 3.1 输入

检索服务最小输入是：

```text
query：用户自然语言问题
topK：最终最多返回多少条结果
similarityThreshold：最低相似度阈值
```

例如：

```text
query = "热点缓存刚好失效时，大量请求同时访问数据库叫什么？"
topK = 5
similarityThreshold = 0.70
```

### 3.2 输出

每一条命中至少要包含：

```text
chunkId
documentId
documentTitle
chunkIndex
headingPath
content
score
```

输出示例：

```json
{
  "query": "热点缓存刚好失效时，大量请求同时访问数据库叫什么？",
  "topK": 5,
  "similarityThreshold": 0.7,
  "hitCount": 1,
  "hits": [
    {
      "chunkId": 13,
      "documentId": 15,
      "documentTitle": "测试样例-Java并发与Redis缓存",
      "chunkIndex": 4,
      "headingPath": "智面 RAG 测试资料：Java 并发与 Redis 缓存 > 2. Redis 缓存的三个常见问题 > 2.2 缓存击穿",
      "content": "缓存击穿通常发生在某个热点键过期的一瞬间……",
      "score": 0.86
    }
  ]
}
```

### 3.3 检索服务不负责什么

检索服务不负责：

- 把多个片段写成通顺答案；
- 判断用户回答是否正确；
- 流式输出；
- 维护聊天记忆；
- 自动把检索内容拼进面试 Prompt；
- 在失败时偷偷使用模型常识伪装成知识库结果。

这些职责一旦混在同一个方法中，就无法判断错误来自检索还是生成。

## 四、TopK、候选数量和阈值到底是什么

### 4.1 TopK

`topK = 5` 表示最终最多返回 5 条结果，不代表一定返回 5 条。

如果只有 2 条结果超过阈值，就应该只返回 2 条。如果没有任何结果超过阈值，应该返回空列表。

TopK 太小：

- 可能漏掉真正相关的片段；
- 长问题涉及多个知识点时上下文不足。

TopK 太大：

- 容易引入无关内容；
- 第 08 阶段 Prompt 更长；
- ChatModel 更容易被干扰；
- Token 成本和响应时间增加。

智面当前默认值为：

```yaml
zhimian:
  rag:
    top-k: 5
```

它只是初始值，不是永远正确的答案。

### 4.2 为什么检索候选数要大于最终 TopK

Redis 返回的结果还要经过：

- 无效 metadata 过滤；
- 重复 chunk 过滤；
- MySQL 有效状态过滤；
- 完全重复正文过滤。

如果只从 Redis 请求 5 条，其中 2 条已失效，最终只剩 3 条。

因此第一版采用：

```text
candidateK = min(topK × 3, 50)
```

例如最终需要 5 条，先向 Redis 请求 15 条候选，回表和去重后再截断为 5 条。

这叫“过量召回后再过滤”，不是把最终 TopK 改成 15。

### 4.3 similarityThreshold

`similarityThreshold = 0.70` 表示只接受相似度达到 0.70 的结果。

阈值太低：

- 返回结果更多；
- 召回率可能提高；
- 噪声也会增加。

阈值太高：

- 结果更保守；
- 可能找不到措辞差异较大的正确知识。

阈值必须通过评估集确定，不能凭感觉选择。

### 4.4 score 不能跨模型直接比较

当前 Embedding 模型是 `BAAI/bge-m3`，Redis 使用 COSINE 距离并由 Spring AI 转换为相似度分数。

以后如果更换：

- Embedding 模型；
- 向量维度；
- 距离算法；
- 文本清洗方式；
- 标题拼接方式；

旧评估分数和阈值都需要重新测量。不能认为“0.70 对所有模型都合适”。

## 五、当前 Redis metadata 的真实情况

第 06 阶段写入的 Redis JSON 包含：

```text
sourceType
documentId
embedding
chunkIndex
documentTitle
chunkId
headingPath
content
```

这说明 metadata 已经保存成功。

但是当前 `FT.INFO zhimian-rag-index` 中真正建立索引的字段只有：

```text
$.content   → TEXT
$.embedding → VECTOR
```

`documentId`、`sourceType` 等字段存在于 JSON 中，但没有注册为 Redis Search 的 TAG/NUMERIC 字段。

真实联调还验证了一个容易忽略的细节：Spring AI 1.0.0 的 Redis VectorStore 在当前 Schema 下执行检索时，返回的 `Document` 只保证带回稳定向量 ID、正文和 score，并不会把未注册的 JSON metadata 全部恢复到 `Document.metadata`。因此 Redis JSON 中看得到 `chunkId`，不代表 Java 检索结果的 metadata 中一定取得到它。

因此现在不要直接写：

```java
SearchRequest.builder()
        .filterExpression("documentId == '15'")
        .build();
```

字段没有建索引时，这段代码不会获得你想象中的稳定过滤效果。

### 5.1 第一版如何保证结果有效

第一版策略是：

```text
Redis 做语义召回
        ↓
读取 metadata.chunkId
        ↓
MySQL JOIN knowledge_document 批量回表
        ↓
只保留：
  chunk.is_deleted = 0
  chunk.vector_status = 1
  document.is_deleted = 0
  document.status = 2
```

这是当前项目最清晰、最容易验证的实现。

### 5.2 什么时候再做 metadata filter

当后续需要：

- 只检索某个知识包；
- 只检索 Java 分类；
- 只检索某家公司面试资料；
- 按来源类型过滤；

再显式创建 `RedisVectorStore`，通过 `metadataFields(...)` 注册字段，并重建整个索引。

Spring AI 1.0.0 可使用：

```java
RedisVectorStore.MetadataField.tag("documentId")
RedisVectorStore.MetadataField.tag("sourceType")
RedisVectorStore.MetadataField.numeric("chunkIndex")
```

注意：给已有 JSON 增加 metadata 不等于修改了 Redis Search Schema。Schema 变化后通常要删除并重建索引，再重新导入向量。

本篇先不改 VectorStore Bean，避免把“基础检索是否准确”和“高级过滤配置”两个未知问题同时引入。

## 八、检查点 B：增加 MySQL 批量回表查询

### 8.1 为什么不能循环调用 selectById

错误写法：

```java
for (Document document : vectorHits) {
    chunkMapper.selectById(readChunkId(document));
}
```

如果 Redis 返回 15 条候选，就会执行 15 次 SQL，这就是典型 N+1 查询。

正确方向是：

```text
一次收集所有 chunkId
        ↓
一条 WHERE id IN (...) 查询
        ↓
在 Java 内存中恢复 Redis 原始排序
```

### 8.2 创建回表对象

### 8.4 修改 Mapper XML

在 `KnowledgeChunkMapper.xml` 中增加：

```xml
<select id="selectSearchableByIds"
        resultType="com.zhimian.rag.retrieval.KnowledgeSearchRow">
    SELECT
        c.id AS chunk_id,
        c.document_id,
        d.title AS document_title,
        d.source_type,
        c.chunk_index,
        c.heading_path,
        c.content,
        c.content_hash,
        c.token_count
    FROM knowledge_chunk c
    INNER JOIN knowledge_document d
        ON d.id = c.document_id
    WHERE c.id IN
    <foreach collection="ids" item="id"
             open="(" separator="," close=")">
        #{id}
    </foreach>
      AND c.vector_status = 1
      AND c.is_deleted = 0
      AND d.status = 2
      AND d.is_deleted = 0
</select>
```

这里的状态码含义必须与你现有枚举一致：

```text
c.vector_status = 1 → INDEXED
d.status = 2        → COMPLETED
```

SQL 不会自动知道 Java 枚举，所以数据库状态码必须有稳定约定。

### 8.5 为什么 SQL 不写 ORDER BY

`WHERE id IN (...)` 不保证按照传入 ID 顺序返回。

真正的相关度排序来自 Redis score，因此后面会：

1. 把 MySQL 行转成 `Map<chunkId, row>`；
2. 再按照 Redis 候选顺序遍历；
3. 从 Map 中取出事实数据。

不要尝试使用 MySQL 的默认返回顺序代替相似度排序。

### 8.6 Mapper 集成测试要检查什么

在现有 `KnowledgeMapperIntegrationTest` 中增加一个用例，至少验证：

- 有效且 INDEXED 的 chunk 可以查到；
- `vector_status != 1` 的 chunk 查不到；
- 已软删除 chunk 查不到；
- 文档不是 COMPLETED 时查不到；
- 返回值包含文档标题和 chunk 正文。

不要只 Mock Mapper 来证明 SQL 正确。XML 动态 SQL 必须至少有一个真实 MySQL 集成测试。

```java
import java.util.HashSet;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Set;

@Service
@RequiredArgsConstructor
public class KnowledgeRetrievalServiceImpl
        implements KnowledgeRetrievalService {

    private static final String VECTOR_ID_PREFIX = "knowledge-chunk:";
    private static final int MAX_QUERY_LENGTH = 500;
    private static final int MAX_TOP_K = 20;
    private static final int MAX_CANDIDATE_K = 50;

    private final VectorStore vectorStore;
    private final KnowledgeChunkMapper chunkMapper;
    private final RagProperties ragProperties;

    @Override
    public KnowledgeSearchResult search(
            String query,
            Integer requestedTopK,
            Double requestedThreshold) {

        String normalizedQuery = normalizeQuery(query);
        int topK = resolveTopK(requestedTopK);
        double threshold = resolveThreshold(requestedThreshold);
        int candidateK = Math.min(MAX_CANDIDATE_K, topK * 3);

        SearchRequest request = SearchRequest.builder()
                .query(normalizedQuery)
                .topK(candidateK)
                .similarityThreshold(threshold)
                .build();

        List<Document> vectorHits =
                vectorStore.similaritySearch(request);

        if (vectorHits == null || vectorHits.isEmpty()) {
            return emptyResult(normalizedQuery, topK, threshold);
        }

        LinkedHashMap<Long, ScoredCandidate> candidates =
                collectCandidates(vectorHits, threshold);

        if (candidates.isEmpty()) {
            return emptyResult(normalizedQuery, topK, threshold);
        }

        List<KnowledgeSearchRow> rows =
                chunkMapper.selectSearchableByIds(
                        new ArrayList<>(candidates.keySet()));

        Map<Long, KnowledgeSearchRow> rowByChunkId = new HashMap<>();
        for (KnowledgeSearchRow row : rows) {
            rowByChunkId.put(row.getChunkId(), row);
        }

        List<KnowledgeSearchHit> hits = new ArrayList<>();
        Set<String> seenContents = new HashSet<>();

        for (ScoredCandidate candidate : candidates.values()) {
            KnowledgeSearchRow row =
                    rowByChunkId.get(candidate.chunkId());
            if (row == null) {
                continue;
            }
            if (!seenContents.add(row.getContent())) {
                continue;
            }

            hits.add(new KnowledgeSearchHit(
                    row.getChunkId(),
                    row.getDocumentId(),
                    row.getDocumentTitle(),
                    row.getChunkIndex(),
                    row.getHeadingPath(),
                    row.getContent(),
                    candidate.score()
            ));

            if (hits.size() >= topK) {
                break;
            }
        }

        return new KnowledgeSearchResult(
                normalizedQuery,
                topK,
                threshold,
                hits
        );
    }

    private LinkedHashMap<Long, ScoredCandidate> collectCandidates(
            List<Document> vectorHits,
            double threshold) {
        LinkedHashMap<Long, ScoredCandidate> candidates =
                new LinkedHashMap<>();

        for (Document document : vectorHits) {
            Long chunkId = readChunkId(document);
            Double score = document.getScore();

            if (chunkId == null || score == null || score < threshold) {
                continue;
            }

            ScoredCandidate current = candidates.get(chunkId);
            if (current == null || score > current.score()) {
                candidates.put(
                        chunkId,
                        new ScoredCandidate(chunkId, score)
                );
            }
        }
        return candidates;
    }

    private Long readChunkId(Document document) {
        Object rawValue = document.getMetadata().get("chunkId");
        Long metadataChunkId = parseLong(rawValue);
        if (metadataChunkId != null) {
            return metadataChunkId;
        }

        String vectorId = document.getId();
        if (!StringUtils.hasText(vectorId)
                || !vectorId.startsWith(VECTOR_ID_PREFIX)) {
            return null;
        }
        return parseLong(vectorId.substring(VECTOR_ID_PREFIX.length()));
    }

    private Long parseLong(Object rawValue) {
        if (rawValue == null) {
            return null;
        }
        if (rawValue instanceof Number number) {
            return number.longValue();
        }
        try {
            return Long.valueOf(rawValue.toString().strip());
        }
        catch (NumberFormatException exception) {
            return null;
        }
    }

    private String normalizeQuery(String query) {
        if (!StringUtils.hasText(query)) {
            throw new BusinessException(
                    ErrorCode.PARAMS_ERROR,
                    "检索问题不能为空");
        }
        String normalized = query.strip();
        if (normalized.length() > MAX_QUERY_LENGTH) {
            throw new BusinessException(
                    ErrorCode.PARAMS_ERROR,
                    "检索问题最多 500 个字符");
        }
        return normalized;
    }

    private int resolveTopK(Integer requestedTopK) {
        int topK = requestedTopK == null
                ? ragProperties.getTopK()
                : requestedTopK;
        if (topK < 1 || topK > MAX_TOP_K) {
            throw new BusinessException(
                    ErrorCode.PARAMS_ERROR,
                    "topK 必须在 1 到 20 之间");
        }
        return topK;
    }

    private double resolveThreshold(Double requestedThreshold) {
        double threshold = requestedThreshold == null
                ? ragProperties.getSimilarityThreshold()
                : requestedThreshold;
        if (!Double.isFinite(threshold)
                || threshold < 0.0
                || threshold > 1.0) {
            throw new BusinessException(
                    ErrorCode.PARAMS_ERROR,
                    "相似度阈值必须在 0 到 1 之间");
        }
        return threshold;
    }

    private KnowledgeSearchResult emptyResult(
            String query,
            int topK,
            double threshold) {
        return new KnowledgeSearchResult(
                query,
                topK,
                threshold,
                List.of()
        );
    }

    private record ScoredCandidate(Long chunkId, Double score) {
    }
}
```

### 9.3 按执行顺序理解这个方法

```text
1. normalizeQuery
   校验并去掉问题首尾空白

2. resolveTopK / resolveThreshold
   请求没有传值时使用配置文件默认值

3. 构造 SearchRequest
   candidateK 是候选数量，不是最终返回数量

4. vectorStore.similaritySearch
   内部先调用 Embedding API 得到查询向量
   再到 Redis Stack 做 HNSW 相似度检索

5. collectCandidates
   优先从 metadata 读取 chunkId
   metadata 未回传时从稳定向量 ID `knowledge-chunk:{chunkId}` 解析
   丢弃无 ID、无 score、低于阈值和重复 ID 的结果

6. selectSearchableByIds
   一次 SQL 回 MySQL 校验真实有效状态

7. rowByChunkId
   将无序 SQL 结果变成可按 ID 读取的 Map

8. 按 Redis 候选顺序组装 KnowledgeSearchHit
   保留相关度排序
   去掉完全相同正文
   最终截断到 topK

9. 返回 KnowledgeSearchResult
```

### 9.4 为什么这里暂时不 catch VectorStore 异常

第 07 阶段的 API 是管理员检索诊断工具。Redis 或 Embedding 服务失败时，必须明确暴露失败，不能返回空数组伪装成“没有相关知识”。

第 08 阶段接入错题讲解时，会在业务编排层区分：

```text
检索成功但没有命中 → 正常空结果
检索服务异常       → 降级到题库原答案，并记录告警
```

严格检索服务与业务降级不是同一层职责。

### 11.2 还必须写的用例

1. `returnsEmptyWhenVectorStoreHasNoHits`
   - VectorStore 返回空列表；
   - Mapper 不应该被调用；
   - 结果 hits 为空。

2. `ignoresInvalidAndDuplicateChunkMetadata`
   - 一个结果没有 `chunkId`；
   - 一个 `chunkId` 不是数字；
   - 同一 chunkId 出现两次；
   - 最终只回表一次。

3. `fallsBackToStableVectorIdWhenMetadataIsNotReturned`
   - 模拟 Spring AI 检索结果中没有 `metadata.chunkId`；
   - `Document.id` 为 `knowledge-chunk:10`；
   - 服务仍能解析出 MySQL chunkId 10；
   - 这是当前 Redis 自动配置下必须保留的回归测试。

4. `filtersRowsRejectedByMysqlTruth`
   - Redis 返回两个 ID；
   - Mapper 只返回一个有效行；
   - 最终只返回一个命中。

5. `removesExactDuplicateContent`
   - 两个不同 chunkId 的 MySQL 正文完全相同；
   - 最终只保留分数更靠前的一条。

6. `rejectsBlankQuery`
   - 空字符串、空格字符串都抛 `BusinessException`。

7. `rejectsInvalidTopKAndThreshold`
   - topK 为 0 或 21；
   - threshold 为负数、大于 1、NaN 或 Infinity。

## 十三、为什么只看几个回答不算效果评估

你手工问一句：

```text
Lua 为什么能保证原子性？
```

系统正好返回正确片段，这只能说明一个样例成功，不能证明整体检索可靠。

可靠评估必须满足：

- 使用一组固定问题；
- 每个问题有明确的相关结果定义；
- 每次改模型、切片或阈值后重复执行同一组问题；
- 使用统一指标比较前后变化；
- 保存失败样例，而不是只展示成功样例。

这组固定数据叫 Retrieval Evaluation Dataset，也就是检索评估集。

## 十四、Hit@K 和 MRR

### 14.1 Hit@K

一个问题的正确片段只要出现在前 K 名，就记为命中。

```text
Hit@K = 命中的问题数量 / 全部问题数量
```

例如 10 个问题中，8 个问题的正确片段出现在前 5 名：

```text
Hit@5 = 8 / 10 = 0.80
```

Hit@K 只关心“有没有进入前 K”，不关心排在第 1 还是第 5。

### 14.2 MRR

MRR 全称 Mean Reciprocal Rank，平均倒数排名。

单个问题：

```text
正确结果第 1 名 → RR = 1 / 1 = 1.00
正确结果第 2 名 → RR = 1 / 2 = 0.50
正确结果第 4 名 → RR = 1 / 4 = 0.25
前 K 没有正确结果 → RR = 0
```

全部问题取平均就是 MRR。

MRR 可以区分：

- 两套方案 Hit@5 都是 100%；
- 方案 A 正确结果大多第 1；
- 方案 B 正确结果大多第 4、5；
- 方案 A 的 MRR 会更高。

### 14.3 为什么暂时不用“模型判断相关性”

初学阶段先使用确定性规则：

```text
headingPath 是否包含预期章节关键词
content 是否包含预期唯一事实
```

不要马上让另一个大模型判断检索结果是否相关，否则又引入：

- 模型成本；
- 评分不稳定；
- Prompt 设计误差；
- 评估模型自身偏差。

先建立可重复的基础评估，再研究 LLM-as-a-Judge。

```java
import com.zhimian.ZhiMianApplication;
import com.fasterxml.jackson.core.type.TypeReference;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.condition.EnabledIfEnvironmentVariable;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;

import java.io.InputStream;
import java.util.List;

import static org.assertj.core.api.Assertions.assertThat;

@SpringBootTest(classes = ZhiMianApplication.class)
@EnabledIfEnvironmentVariable(
        named = "RUN_RAG_EVALUATION_TESTS",
        matches = "true")
class KnowledgeRetrievalEvaluationTest {

    @Autowired
    private KnowledgeRetrievalService retrievalService;

    @Autowired
    private ObjectMapper objectMapper;

    @Test
    void importedKnowledgeShouldMeetRetrievalBaseline()
            throws Exception {
        List<EvaluationCase> cases = loadCases();

        int hitCount = 0;
        double reciprocalRankSum = 0.0;

        for (EvaluationCase evaluationCase : cases) {
            KnowledgeSearchResult result = retrievalService.search(
                    evaluationCase.query(),
                    5,
                    0.50
            );

            int rank = firstRelevantRank(
                    result.hits(),
                    evaluationCase.expectedHeadingContains()
            );

            if (rank > 0) {
                hitCount++;
                reciprocalRankSum += 1.0 / rank;
            }

            System.out.printf(
                    "case=%s rank=%d top=%s%n",
                    evaluationCase.id(),
                    rank,
                    result.hits().isEmpty()
                            ? "NONE"
                            : result.hits().get(0).headingPath()
            );
        }

        double hitAt5 = (double) hitCount / cases.size();
        double mrr = reciprocalRankSum / cases.size();

        System.out.printf(
                "Retrieval baseline: Hit@5=%.3f, MRR=%.3f%n",
                hitAt5,
                mrr
        );

        assertThat(hitAt5).isGreaterThanOrEqualTo(0.80);
        assertThat(mrr).isGreaterThanOrEqualTo(0.60);
    }

    private List<EvaluationCase> loadCases() throws Exception {
        try (InputStream input = getClass().getResourceAsStream(

                    .as("检索评估集必须存在")
                    .isNotNull();
            return objectMapper.readValue(
                    input,
                    new TypeReference<>() {
                    }
            );
        }
    }

    private int firstRelevantRank(
            List<KnowledgeSearchHit> hits,
            String expectedHeadingContains) {
        for (int index = 0; index < hits.size(); index++) {
            if (hits.get(index).headingPath()
                    .contains(expectedHeadingContains)) {
                return index + 1;
            }
        }
        return 0;
    }

    private record EvaluationCase(
            String id,
            String query,
            String expectedHeadingContains
    ) {
    }
}
```

## 十七、怎样做阈值实验

固定同一份评估集，分别执行：

```text
threshold = 0.40
threshold = 0.50
threshold = 0.60
threshold = 0.70
threshold = 0.75
threshold = 0.80
```

记录表：

| threshold | Hit@5 | MRR | 平均返回数 | 明显噪声数 |
|---:|---:|---:|---:|---:|
| 0.40 | 待测 | 待测 | 待测 | 待测 |
| 0.50 | 待测 | 待测 | 待测 | 待测 |
| 0.60 | 待测 | 待测 | 待测 | 待测 |
| 0.70 | 待测 | 待测 | 待测 | 待测 |
| 0.75 | 待测 | 待测 | 待测 | 待测 |
| 0.80 | 待测 | 待测 | 待测 | 待测 |

选择阈值时优先满足：

```text
正确片段不被过滤
        ↓
正确片段尽量靠前
        ↓
再减少无关结果
```

RAG 中“完全不返回”通常比“返回一个低质量片段并强迫模型引用”更诚实。第 08 阶段应允许无命中降级。

## 十八、相邻 Chunk 合并该放在哪里

假设第 1 名命中 chunk 5，但它的定义在 chunk 4，示例在 chunk 6。只返回 chunk 5 可能缺上下文。

一种常见做法是：

```text
向量检索得到锚点 chunk 5
        ↓
按 documentId + chunkIndex 查询相邻 chunk 4、6
        ↓
控制总 Token 数后组装上下文
```

但是要区分两个概念：

- Retrieval Hit：真正被语义检索命中的锚点；
- Context Expansion：为了让模型理解完整而补充的邻居。

邻居不能继承锚点的 score，也不能在 Hit@K 中冒充语义命中。

本篇第一版 API 只返回 Retrieval Hit。第 08 阶段构造 Prompt Context 时再新增 `KnowledgeContextAssembler`，进行：

- 相邻 chunk 扩展；
- 相同文档排序；
- Token 总预算限制；
- 重复段落消除。

这样评估检索时不会被上下文组装逻辑干扰。

## 十九、常见错误与排查顺序

### 19.1 返回空列表

按顺序检查：

1. `knowledge_document.status` 是否为 2；
2. `knowledge_chunk.vector_status` 是否全部为 1；
3. `FT.INFO` 的 `num_docs` 是否大于 0；
4. Embedding API 是否可用；
5. threshold 是否过高；
6. metadata 是否有 `chunkId`；
7. MySQL 回表 SQL 是否把结果过滤掉。

先把 threshold 临时降到 0.0 观察原始排序。如果仍为空，通常不是阈值问题。

### 19.2 Redis 有结果，最终 API 没结果

重点检查 MySQL 回表条件：

```sql
SELECT
    c.id,
    c.vector_status,
    c.is_deleted,
    d.status,
    d.is_deleted
FROM knowledge_chunk c
JOIN knowledge_document d ON d.id = c.document_id
WHERE c.id IN (...);
```

也要打印 Redis metadata 中的 `chunkId`，确认它与 MySQL 主键一致。

### 19.3 正确结果有时第一、有时很后

检查：

- 是否更换了 Embedding 模型；
- 文档是否重新切片导致内容变化；
- Redis 中是否混入重复测试数据；
- 查询中是否包含大量无关上下文；
- 是否错误使用 MySQL 返回顺序覆盖 Redis 排序。

### 19.4 相似概念互相混淆

例如缓存穿透、击穿、雪崩容易互相召回。优化顺序：

1. 增加区分明显的标题和定义；
2. 增加包含典型触发条件的评估问题；
3. 观察正确结果排名和 score 差距；
4. 调整 chunk 边界；
5. 再考虑关键词混合检索或重排序。

不要只通过调高阈值解决，因为错误结果和正确结果可能同时被过滤。

### 19.5 API 调用很慢

一次检索通常包含：

```text
一次远程 Embedding API
一次 Redis 向量查询
一次 MySQL 回表
```

先分别记录三段耗时，再优化。不要看到总耗时就直接给整个方法加缓存。

```text
        ↓
```

## 二十三、与第 08 阶段的关系

07 完成后，系统会拥有一个可证明质量的能力：

```text
问题
  ↓
KnowledgeRetrievalService
  ↓
可信 KnowledgeSearchHit 列表
```

第 08 阶段才会在它上面增加：

```text
可信命中列表
  ↓ KnowledgeContextAssembler
相邻片段扩展 + Token 预算 + 引用编号
  ↓ RagPromptBuilder
明确要求“只能基于资料回答”的增强 Prompt
  ↓ ChatModel
错题知识讲解
  ↓
答案 + 引用来源 + 是否降级
```

如果 07 的检索不稳定，第 08 阶段无论 Prompt 写得多漂亮，都只是让模型更自然地引用错误资料。

因此当前唯一目标是：

> 用固定问题、固定数据和固定指标，证明智面能够稳定找到正确知识片段。
