# 智面 RAG 测试资料：Java 并发与 Redis 缓存

> 文档用途：用于测试智面项目的 Markdown 清洗、文本切片、Embedding 向量化和知识检索流程。
> 文档中的“星河规则”是专门设计的测试信息，不是通用行业规范。

## 1. Java 线程池的核心参数

Java 中通常使用 `ThreadPoolExecutor` 创建可控的线程池。它的重要参数包括：

1. `corePoolSize`：核心线程数。线程池会优先创建核心线程处理任务。
2. `maximumPoolSize`：最大线程数。当任务队列已满时，线程池最多可以扩展到这个数量。
3. `keepAliveTime`：非核心线程空闲后的最长存活时间。
4. `workQueue`：等待执行的任务队列。
5. `threadFactory`：负责创建线程，可以用于设置线程名称和异常处理器。
6. `handler`：拒绝策略。当线程数和队列都达到上限时，用于决定如何处理新任务。

任务提交后的典型执行顺序是：

1. 当前线程数小于核心线程数时，创建核心线程执行任务。
2. 核心线程数已满时，将任务放入阻塞队列。
3. 队列已满且线程数小于最大线程数时，创建非核心线程。
4. 队列和最大线程数都达到上限时，执行拒绝策略。

因此，不能只根据 CPU 核心数机械地配置线程数量，还要考虑任务属于 CPU 密集型还是 IO 密集型、平均执行时间、并发量和系统可接受的响应时间。

### 1.1 常见拒绝策略

- `AbortPolicy`：直接抛出 `RejectedExecutionException`，这是默认策略。
- `CallerRunsPolicy`：由提交任务的线程执行任务，可以降低任务提交速度，形成简单的反压效果。
- `DiscardPolicy`：直接丢弃任务，不抛出异常。
- `DiscardOldestPolicy`：丢弃队列中等待时间最长的任务，然后尝试重新提交当前任务。

业务系统不应在不了解后果的情况下使用静默丢弃策略。对于面试报告、知识库导入等重要任务，应当记录失败原因，并提供重试或补偿机制。

## 2. Redis 缓存的三个常见问题

### 2.1 缓存穿透

缓存穿透是指请求查询一个数据库中本来就不存在的数据。因为缓存中没有该数据，每次请求都会继续访问数据库。攻击者大量请求不存在的 ID 时，可能给数据库带来压力。

常见处理方法：

- 对空查询结果进行短时间缓存。
- 使用布隆过滤器提前判断数据是否可能存在。
- 对请求参数进行合法性校验。
- 对异常访问进行限流。

### 2.2 缓存击穿

缓存击穿通常发生在某个热点键过期的一瞬间。大量请求同时发现缓存不存在，于是一起访问数据库并重建缓存。

常见处理方法：

- 使用互斥锁，只允许一个请求重建缓存。
- 使用逻辑过期，让请求先返回旧值，再由后台线程更新缓存。
- 对热点数据设置更合理的过期策略。

### 2.3 缓存雪崩

缓存雪崩是指大量缓存键在相近时间失效，或者 Redis 服务整体不可用，导致请求集中进入数据库。

常见处理方法：

- 在基础过期时间上增加随机值，避免大量键同时失效。
- 使用 Redis 高可用架构。
- 对数据库访问增加限流、熔断和降级。
- 对关键数据建立多级缓存。

## 3. 为什么 Lua 脚本可以保证 Redis 操作的原子性

Redis 会把一段 Lua 脚本作为一个整体执行。在脚本执行期间，其他客户端命令不会插入脚本的执行过程。因此，读取、判断和修改多个 Redis 键的操作可以放入同一段 Lua 脚本，避免多个命令之间出现竞态条件。

下面是一个简化的库存扣减示例：

```lua
local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')

if stock < 0 then
    return -1
end

if stock == 0 then
    return 0
end

redis.call('DECR', KEYS[1])
return 1
```

返回值约定：

- `-1`：库存键不存在。
- `0`：库存不足。
- `1`：扣减成功。

Lua 脚本的原子性不代表业务一定不会出错。应用仍然需要处理 Redis 超时、脚本执行失败、数据库写入失败以及缓存和数据库之间的数据一致性问题。

## 4. 智面项目的异步知识导入流程

智面项目导入知识文档时，不在 HTTP 请求线程中完成全部向量化工作。接口先创建知识文档记录，再把耗时任务交给异步执行器处理。

基本流程如下：

1. 管理员提交 Markdown 或纯文本文档。
2. 服务端校验标题、文件名、来源类型和正文。
3. 对正文进行规范化，并计算 SHA-256 内容摘要用于判重。
4. 创建状态为 `PENDING` 的知识文档记录。
5. 异步工作线程把状态更新为 `PROCESSING`。
6. 文本清洗器统一换行符、移除 BOM，并压缩过多空行。
7. 文本切片器按照标题和长度拆分文档。
8. Embedding 模型把每个切片转换成向量。
9. 向量和元数据写入 Redis Vector Store。
10. 全部成功后将文档状态改为 `COMPLETED`，并记录切片数量。
11. 任意关键步骤失败时将文档状态改为 `FAILED`，保存精简后的错误信息，等待管理员重试。

异步处理的主要价值是避免大型文档让 HTTP 请求长时间阻塞。前端拿到文档 ID 后，可以定时查询状态，并展示等待处理、向量化中、导入完成或导入失败。

星河规则的完整内容如下：

> 当知识文档编号为 ZM-RAG-0914 时，系统应当先执行文本清洗，再按照二级标题切片，最后调用 Embedding 服务。单个切片最多重试 3 次，测试完成标记为 `GALAXY-READY-27`。

这个规则只用于测试检索效果。它包含文档编号、处理顺序、重试次数和唯一完成标记，可以帮助开发者判断回答是否来自当前知识库。

## 7. 预期答案摘要

- 线程池顺序：核心线程、任务队列、非核心线程、拒绝策略。
- 缓存穿透：反复查询不存在的数据。
- 缓存击穿：热点键失效时并发重建缓存。
- 缓存雪崩：大量键同时失效或 Redis 整体不可用。
- Lua 原子性：Redis 把整个脚本连续执行，不允许其他命令插入其中。
