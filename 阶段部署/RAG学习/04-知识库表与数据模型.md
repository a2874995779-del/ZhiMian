## 一、本阶段解决什么问题

03 阶段已经证明了下面这条技术链路可以工作：

```text
中文文本
    ↓
BAAI/bge-m3
    ↓
1024 维向量
    ↓
Redis Stack
    ↓
语义相似度检索
```

但现在 Redis 里只有测试数据，系统还不知道：

- 这段向量来自哪一份文档；
- 一份文档被切成了多少段；
- 文档是否处理完成；
- 处理失败后应该怎样重试；
- 删除文档时应该删除哪些向量；
- 同一份文档是否被重复上传；
- 更换 Embedding 模型后哪些数据需要重建。

因此，本阶段要先建立知识库的数据骨架：

```text
knowledge_document：管理整份知识文档
knowledge_chunk：管理文档切分后的知识片段
Redis VectorStore：下一阶段保存每个 chunk 的向量
```

完成后，项目中应该形成下面的关系：

```text
knowledge_document 1 ────── N knowledge_chunk
                                   │
                                   │ chunk.id
                                   ↓
                         Redis Document.id
```

这一阶段只搭建“知识档案管理系统”，还不进行真正的文档切片和向量化。

## 二、先理解 MySQL 与 Redis 的分工

### 2.1 MySQL 是事实来源

MySQL 保存：

- 文档标题和原始内容；
- 文档处理状态；
- 每一个 chunk 的原文；
- 文档与 chunk 的对应关系；
- 使用的 Embedding 模型和向量维度；
- 失败原因、创建人和时间。

即使 Redis 中的向量全部丢失，只要 MySQL 数据还在，我们就可以重新生成向量。

### 2.2 Redis 是可重建的检索索引

Redis Stack 保存：

- chunk 对应的 1024 维向量；
- 检索需要的 metadata；
- 用于快速语义搜索的向量索引。

Redis 中的数据不是唯一事实来源。它更像 MySQL 普通索引的加强版：丢失后会影响搜索，但可以根据 MySQL 重新构建。

### 2.3 为什么不只使用 Redis

如果只把原文和向量放进 Redis，会遇到：

- 文档处理到一半时难以记录状态；
- 管理员很难查看失败原因；
- 更新、删除和重新导入不容易管理；
- 无法方便地做后台分页和审计；
- Redis 数据丢失后缺少可靠的重建来源。

因此，智面的设计原则是：

```text
MySQL 管事实和状态
Redis 管向量和检索
```

这叫做“事实数据与派生索引分离”。

## 三、为什么需要两张表

假设管理员上传了一份文档：

```text
Java线程池完整指南.md
```

它是一份完整文档，对应一条 `knowledge_document`：

```text
id = 10
title = Java线程池完整指南
status = COMPLETED
chunk_count = 4
```

文档经过切片后产生四个片段，对应四条 `knowledge_chunk`：

```text
chunk 1：线程池核心参数
chunk 2：任务提交与执行流程
chunk 3：四种拒绝策略
chunk 4：shutdown 与 shutdownNow
```

不能把四段内容直接塞进文档表的一个 JSON 字段，因为后续需要：

- 单独向量化每一个片段；
- 单独搜索每一个片段；
- 单独删除失败的向量；
- 知道命中的片段属于哪个标题；
- 根据 chunk ID 回到 MySQL 查询完整原文。

所以是标准的一对多关系：

```text
一份文档拥有多个 chunk
一个 chunk 只能属于一份文档
```

## 四、状态机设计

### 4.1 文档状态

定义五种状态：

| 状态码 | 常量 | 含义 |
|---:|---|---|
| 0 | `PENDING` | 文档已创建，等待处理 |
| 1 | `PROCESSING` | 正在清洗、切片或向量化 |
| 2 | `COMPLETED` | 所有 chunk 已成功入库 |
| 3 | `FAILED` | 处理失败，可以重试 |
| 4 | `DELETING` | 正在删除 MySQL 数据和 Redis 向量 |

允许的状态变化：

```text
PENDING ──────→ PROCESSING ──────→ COMPLETED
                    │
                    └────────────→ FAILED
                                      │
                                      └────→ PROCESSING

PENDING / COMPLETED / FAILED ────────→ DELETING
```

不允许：

```text
COMPLETED → PENDING
DELETING → PROCESSING
PENDING → COMPLETED
```

为什么不能直接修改状态？

如果两个线程同时处理同一份文档：

```text
线程 A 读取 status = PENDING
线程 B 读取 status = PENDING
线程 A 开始向量化
线程 B 也开始向量化
```

最终会产生重复 chunk 和重复向量。

正确做法是使用条件更新：

```sql
UPDATE knowledge_document
SET status = 1
WHERE id = #{id}
  AND status IN (0, 3)
  AND is_deleted = 0;
```

只有一个线程能更新成功。返回值为 `1` 的线程获得处理权，返回值为 `0` 的线程必须停止。

这是一种基于数据库条件更新的 CAS 思想：

```text
Compare：确认当前状态是 PENDING 或 FAILED
And Set：将状态修改为 PROCESSING
```

### 4.2 Chunk 向量状态

每个 chunk 也需要记录向量状态：

| 状态码 | 常量 | 含义 |
|---:|---|---|
| 0 | `PENDING` | chunk 已保存，尚未写入向量库 |
| 1 | `INDEXED` | 向量已经写入 Redis |
| 2 | `FAILED` | 该 chunk 向量化失败 |

文档只有在全部 chunk 都是 `INDEXED` 后才能变为 `COMPLETED`。

```sql
USE zhimian;

CREATE TABLE IF NOT EXISTS `knowledge_document` (
  `id` BIGINT NOT NULL AUTO_INCREMENT,
  `title` VARCHAR(200) NOT NULL COMMENT '知识文档标题',
  `original_filename` VARCHAR(255) NOT NULL COMMENT '上传时的原始文件名',
  `source_type` VARCHAR(16) NOT NULL COMMENT '来源类型：MARKDOWN/TEXT',
  `content` MEDIUMTEXT NOT NULL COMMENT '规范化后的完整原文',
  `content_hash` CHAR(64) NOT NULL COMMENT '规范化原文的SHA-256',
  `status` TINYINT NOT NULL DEFAULT 0 COMMENT '0-待处理 1-处理中 2-已完成 3-失败 4-删除中',
  `chunk_count` INT NOT NULL DEFAULT 0 COMMENT '切片数量',
  `embedding_model` VARCHAR(128) DEFAULT NULL COMMENT '实际使用的Embedding模型',
  `vector_dimension` INT DEFAULT NULL COMMENT '实际向量维度',
  `error_message` VARCHAR(500) DEFAULT NULL COMMENT '最近一次失败原因',
  `created_by` BIGINT NOT NULL COMMENT '创建人用户id',
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `is_deleted` TINYINT NOT NULL DEFAULT 0 COMMENT '0-正常 1-已删除',
  `active_content_hash` CHAR(64)
    GENERATED ALWAYS AS (
      CASE WHEN `is_deleted` = 0 THEN `content_hash` ELSE NULL END
    ) STORED COMMENT '只约束未删除文档的内容Hash',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_active_content_hash` (`active_content_hash`),
  KEY `idx_status_time` (`status`, `create_time`),
  KEY `idx_created_by_time` (`created_by`, `create_time`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT 'RAG知识文档';

CREATE TABLE IF NOT EXISTS `knowledge_chunk` (
  `id` BIGINT NOT NULL AUTO_INCREMENT,
  `document_id` BIGINT NOT NULL COMMENT '所属知识文档id',
  `chunk_index` INT NOT NULL COMMENT '片段在文档中的顺序，从0开始',
  `heading_path` VARCHAR(500) DEFAULT NULL COMMENT 'Markdown标题路径',
  `content` TEXT NOT NULL COMMENT '片段原文',
  `content_hash` CHAR(64) NOT NULL COMMENT '片段原文SHA-256',
  `token_count` INT NOT NULL DEFAULT 0 COMMENT '片段Token数量',
  `vector_status` TINYINT NOT NULL DEFAULT 0 COMMENT '0-待向量化 1-已索引 2-失败',
  `error_message` VARCHAR(500) DEFAULT NULL COMMENT '向量化失败原因',
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `is_deleted` TINYINT NOT NULL DEFAULT 0 COMMENT '0-正常 1-已删除',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_document_chunk_index` (`document_id`, `chunk_index`),
  KEY `idx_document_status` (`document_id`, `vector_status`),
  KEY `idx_content_hash` (`content_hash`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT 'RAG知识片段';
```

### 5.1 为什么原文使用 `MEDIUMTEXT`

MySQL 的 `TEXT` 最大约 64 KB，一整份 Markdown 文档可能超过这个限制。`MEDIUMTEXT`可以保存更大的原始文档。

Chunk经过切分后应该比较短，所以`knowledge_chunk.content`使用`TEXT`已经足够。

### 5.2 为什么没有物理外键

`document_id`是逻辑外键，但脚本暂时不创建数据库物理外键，原因是当前智面项目其他业务表也主要依靠应用层维护关系，保持项目风格一致。

这不代表可以忽略关系。删除文档时，Service必须同步处理对应chunk。

### 5.3 `active_content_hash`是什么

如果直接给`content_hash`建立唯一索引：

```sql
UNIQUE KEY uk_content_hash (content_hash)
```

那么文档软删除后，相同内容永远不能重新上传。

`active_content_hash`是生成列：

```text
is_deleted = 0 → active_content_hash = content_hash
is_deleted = 1 → active_content_hash = NULL
```

MySQL唯一索引允许出现多个`NULL`，所以它只限制未删除文档不能重复。

这是“只约束有效数据唯一”的一种实现方式。

### 5.4 为什么chunk序号从0开始

Java集合下标从0开始，切片代码通常使用：

```java
for (int i = 0; i < chunks.size(); i++) {
    chunk.setChunkIndex(i);
}
```

数据库与Java保持一致，可以减少`i + 1`造成的边界错误。前端展示时再加1。

### 5.5 为什么不单独保存`vector_id`

本项目规定：

```text
Redis Document.id = String.valueOf(knowledge_chunk.id)
```

例如：

```text
knowledge_chunk.id = 208
Redis Document.id = "208"
```

两边使用同一个ID，就不需要再维护一列重复的`vector_id`。

## 十、步骤6：实现内容Hash工具

### 10.1 为什么需要Hash

直接比较两份长文档代价较高：

```sql
WHERE content = ?
```

SHA-256会把任意长度内容转换成固定64位十六进制字符串：

```text
原文 → 9f86d081884c7d659a2feaa0c55ad015...
```

内容相同，Hash相同；内容发生变化，Hash通常也会改变。

### 10.2 为什么Hash前要规范化换行

Windows通常使用：

```text
\r\n
```

Linux通常使用：

```text
\n
```

肉眼看起来完全相同的文档，在不同系统上原始字节可能不同。如果直接计算Hash，会被误判为两份文档。

新建：

```text
src/main/java/com/zhimian/util/KnowledgeContentHasher.java
```

```java
package com.zhimian.util;

import org.springframework.stereotype.Component;
import org.springframework.util.StringUtils;

import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.HexFormat;

@Component
public class KnowledgeContentHasher {

    public String normalize(String content) {
        if (!StringUtils.hasText(content)) {
            return "";
        }
        return content
                .replace("\r\n", "\n")
                .replace('\r', '\n')
                .strip();
    }

    public String sha256(String content) {
        String normalized = normalize(content);
        try {
            MessageDigest digest = MessageDigest.getInstance("SHA-256");
            byte[] hash = digest.digest(
                    normalized.getBytes(StandardCharsets.UTF_8)
            );
            return HexFormat.of().formatHex(hash);
        }
        catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException("当前JDK不支持SHA-256", e);
        }
    }
}
```

### 10.3 逐段理解

```java
MessageDigest.getInstance("SHA-256")
```

获得JDK内置的SHA-256摘要计算器。

```java
normalized.getBytes(StandardCharsets.UTF_8)
```

Hash计算的是字节，不是Java字符串，所以先固定使用UTF-8编码。

```java
digest.digest(...)
```

得到32字节的二进制Hash。

```java
HexFormat.of().formatHex(hash)
```

一个字节转换成两个十六进制字符，所以最终是64个字符，对应数据库的`CHAR(64)`。

Hash用于防止完全相同的内容重复上传，但它不能代替Embedding语义去重：

```text
Hash：文本必须基本完全一致
Embedding：文字不同但意思接近也能识别
```

本阶段只做Hash精确去重。

```xml
            error_message = #{errorMessage},
            update_time = NOW()
        WHERE id = #{id}
          AND status = 1
          AND is_deleted = 0
    </update>

    <update id="markDeleting">
        UPDATE knowledge_document
        SET status = 4,
            update_time = NOW()
        WHERE id = #{id}
          AND status IN (0, 2, 3)
          AND is_deleted = 0
    </update>

    <update id="softDelete">
        UPDATE knowledge_document
        SET is_deleted = 1,
            update_time = NOW()
        WHERE id = #{id}
          AND status = 4
          AND is_deleted = 0
    </update>

</mapper>
```

### 11.1 为什么更新方法返回`int`

MyBatis更新返回受影响行数：

```text
1：状态符合预期，更新成功
0：数据不存在、已删除或状态已经变化
```

Service必须检查返回值，不能无视：

```java
if (documentMapper.markProcessing(id, model, dimension) == 0) {
    throw new BusinessException(
            ErrorCode.CONFLICT,
            "文档状态已变化，请刷新后重试"
    );
}
```

### 11.2 为什么不先查状态再无条件更新

错误写法：

```java
KnowledgeDocument document = mapper.selectById(id);
if (document.getStatus() == 0) {
    mapper.updateStatus(id, 1);
}
```

查询和更新之间存在时间窗口，另一个线程可能已经修改状态。

条件必须写进同一条`UPDATE`，才能依赖数据库保证原子性。

业务删除需要保留记录，失败补偿产生的临时数据可以物理清理。

```java
package com.zhimian.service.impl;

import com.zhimian.common.ErrorCode;
import com.zhimian.exception.BusinessException;
import com.zhimian.mapper.KnowledgeDocumentMapper;
import com.zhimian.model.dto.KnowledgeDocumentCreateDTO;
import com.zhimian.model.entity.KnowledgeDocument;
import com.zhimian.model.enums.KnowledgeDocumentStatus;
import com.zhimian.service.KnowledgeDocumentService;
import com.zhimian.util.KnowledgeContentHasher;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.util.StringUtils;

import java.util.Locale;

@Service
@RequiredArgsConstructor
public class KnowledgeDocumentServiceImpl
        implements KnowledgeDocumentService {

    private static final int MAX_ERROR_MESSAGE_LENGTH = 500;

    private final KnowledgeDocumentMapper documentMapper;
    private final KnowledgeContentHasher contentHasher;

    @Override
    public Long createPending(KnowledgeDocumentCreateDTO dto) {
        validateCreateDTO(dto);

        String normalizedContent = contentHasher.normalize(dto.getContent());
        String contentHash = contentHasher.sha256(normalizedContent);

        KnowledgeDocument existing =
                documentMapper.selectActiveByContentHash(contentHash);
        if (existing != null) {
            throw new BusinessException(
                    ErrorCode.CONFLICT,
                    "相同内容的知识文档已经存在"
            );
        }

        KnowledgeDocument document = new KnowledgeDocument();
        document.setTitle(dto.getTitle().strip());
        document.setOriginalFilename(dto.getOriginalFilename().strip());
        document.setSourceType(dto.getSourceType().strip().toUpperCase(Locale.ROOT));
        document.setContent(normalizedContent);
        document.setContentHash(contentHash);
        document.setStatus(KnowledgeDocumentStatus.PENDING.getCode());
        document.setChunkCount(0);
        document.setCreatedBy(dto.getCreatedBy());

        if (documentMapper.insert(document) != 1 || document.getId() == null) {
            throw new IllegalStateException("知识文档创建失败");
        }
        return document.getId();
    }

    @Override
    public KnowledgeDocument getById(Long id) {
        KnowledgeDocument document = documentMapper.selectById(id);
        if (document == null) {
            throw new BusinessException(ErrorCode.NOT_FOUND, "知识文档不存在");
        }
        return document;
    }

    @Override
    public void startProcessing(Long id,
                                String embeddingModel,
                                int vectorDimension) {
        getById(id);
        if (!StringUtils.hasText(embeddingModel) || vectorDimension <= 0) {
            throw new BusinessException(
                    ErrorCode.PARAMS_ERROR,
                    "Embedding模型和向量维度不能为空"
            );
        }
        if (documentMapper.markProcessing(
                id, embeddingModel.strip(), vectorDimension
        ) == 0) {
            throw stateConflict();
        }
    }

    @Override
    public void complete(Long id, int chunkCount) {
        if (chunkCount <= 0) {
            throw new BusinessException(
                    ErrorCode.PARAMS_ERROR,
                    "完成处理时chunk数量必须大于0"
            );
        }
        if (documentMapper.markCompleted(id, chunkCount) == 0) {
            throw stateConflict();
        }
    }

    @Override
    public void fail(Long id, String errorMessage) {
        String safeMessage = truncateErrorMessage(errorMessage);
        if (documentMapper.markFailed(id, safeMessage) == 0) {
            throw stateConflict();
        }
    }

    @Override
    public void beginDelete(Long id) {
        getById(id);
        if (documentMapper.markDeleting(id) == 0) {
            throw stateConflict();
        }
    }

    private void validateCreateDTO(KnowledgeDocumentCreateDTO dto) {
        if (dto == null
                || !StringUtils.hasText(dto.getTitle())
                || !StringUtils.hasText(dto.getOriginalFilename())
                || !StringUtils.hasText(dto.getSourceType())
                || !StringUtils.hasText(dto.getContent())
                || dto.getCreatedBy() == null) {
            throw new BusinessException(
                    ErrorCode.PARAMS_ERROR,
                    "知识文档参数不完整"
            );
        }

        String sourceType = dto.getSourceType().strip().toUpperCase(Locale.ROOT);
        if (!sourceType.equals("MARKDOWN") && !sourceType.equals("TEXT")) {
            throw new BusinessException(
                    ErrorCode.PARAMS_ERROR,
                    "当前只支持MARKDOWN和TEXT文档"
            );
        }
    }

    private String truncateErrorMessage(String errorMessage) {
        if (!StringUtils.hasText(errorMessage)) {
            return "未知处理异常";
        }
        String stripped = errorMessage.strip();
        return stripped.length() <= MAX_ERROR_MESSAGE_LENGTH
                ? stripped
                : stripped.substring(0, MAX_ERROR_MESSAGE_LENGTH);
    }

    private BusinessException stateConflict() {
        return new BusinessException(
                ErrorCode.CONFLICT,
                "知识文档状态已变化，请刷新后重试"
        );
    }
}
```

### 13.1 为什么`createPending`不直接开始向量化

创建数据库记录与调用外部Embedding服务是两件事：

```text
第一步：可靠地保存任务
第二步：异步处理任务
```

如果在同一个请求中直接向量化：

- 上传请求会等待很久；
- API超时后不知道任务是否成功；
- 外部服务失败时难以重试；
- 大文档容易占用Web线程。

所以本阶段只保存`PENDING`任务。06阶段再实现异步处理。

### 13.2 为什么失败信息要截断

数据库字段只有500字符，而第三方API异常堆栈可能很长。如果直接保存，可能再次触发数据库字段超长异常，导致原始失败状态也无法记录。

数据库只保存适合管理员查看的摘要，完整堆栈写入日志。

### 13.3 并发重复上传还需要数据库唯一索引

Service中的先查询再插入：

```text
selectActiveByContentHash
        ↓
insert
```

只能改善用户提示，不能完全解决并发。

两个请求可能同时查询到不存在，然后同时插入。最终仍然要依赖：

```sql
UNIQUE KEY uk_active_content_hash
```

数据库是并发场景下最后的唯一性防线。

后续可以捕获`DuplicateKeyException`并转换成`BusinessException(CONFLICT)`，这是本阶段Code Review时需要重点检查的内容。

## 十九、常见错误与排查

### 19.1 `Duplicate entry`错误

说明相同内容的未删除文档已经存在。

检查：

```sql
SELECT id, title, content_hash, status, is_deleted
FROM knowledge_document
WHERE content_hash = '报错中的Hash';
```

Service应当把`DuplicateKeyException`转换为业务冲突，而不是直接把数据库异常返回给前端。

### 19.2 `Data too long for column error_message`

检查是否对第三方异常信息做了500字符截断。

### 19.3 `markProcessing`总是返回0

检查：

```sql
SELECT id, status, is_deleted
FROM knowledge_document
WHERE id = ?;
```

只有`PENDING`或`FAILED`可以进入`PROCESSING`。

### 19.4 为什么批量插入不依赖主键回填

不同MySQL驱动和MyBatis版本对批量主键回填行为可能不同。当前`batchInsert`不声明`useGeneratedKeys`，避免代码错误地认为传入的每个对象都已经获得ID。

06阶段需要chunk ID写入Redis时，采用明确流程：

```text
batchInsert(chunks)
        ↓
selectByDocumentId(documentId)
        ↓
获得数据库真实生成的chunk ID
        ↓
使用chunk ID作为Redis Document ID
```

多执行一次查询换来明确、可测试的行为，适合当前项目阶段。未来确认驱动支持批量主键回填后，再通过集成测试决定是否优化。

### 19.5 删除文档后仍然不能重新上传

检查：

```sql
SHOW CREATE TABLE knowledge_document;
```

确认唯一索引建立在`active_content_hash`，而不是直接建立在`content_hash`。

### 19.6 Java字段一直是`null`

检查：

- SQL是否选择了该列；
- `documentColumns`是否包含该列；
- 驼峰映射是否启用；
- 字段名称是否拼错；
- Mapper XML是否被`classpath:mapper/*.xml`加载。

## 二十、本阶段必须理解的编程思想

### 20.1 状态机不是一个status字段

只增加一个`status`字段不等于实现状态机。

真正的状态机包含：

```text
有哪些状态
每个状态代表什么
允许怎样变化
谁有权推动变化
并发时怎样保证只变化一次
失败以后怎样恢复
```

### 20.2 幂等不是简单查重

幂等表示同一个操作执行多次，最终结果与执行一次相同。

知识文档入库未来至少有三层幂等保护：

```text
content_hash：防止同内容重复创建
状态条件更新：防止同任务重复执行
固定chunk ID：防止同片段重复写入Redis
```

### 20.3 数据库唯一索引是最后防线

Java中的“先查再插”无法完全抵抗并发。数据库唯一索引才是最终保证。

正确思维是：

```text
Service查询：提供友好提示
数据库约束：保证绝不重复
异常转换：把数据库冲突变成业务错误
```

### 20.4 派生数据应该能够重建

向量是通过下面的过程产生的：

```text
chunk原文 + Embedding模型 = 向量
```

只要保存：

- chunk原文；
- 模型名称；
- 向量维度；

Redis向量就可以重建。因此不要把Redis向量当成唯一事实数据。

### 20.5 不要让跨系统操作假装成一个本地事务

后面会同时操作：

```text
MySQL
Redis Stack
Embedding HTTP API
```

`@Transactional`只能可靠管理同一个MySQL事务，不能让第三方HTTP接口和Redis自动一起回滚。

后续要使用：

```text
状态机 + 幂等 + 重试 + 补偿
```

这也是06阶段的核心学习内容。
