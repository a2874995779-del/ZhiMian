## 一、本任务要实现什么

一个接口:`POST /api/interviews`,请求体 `{ "direction": "java_concurrency" }`,创建一场模拟面试并返回 AI 面试官的开场白。

完整链路:

```
校验 direction 合法(枚举)
  → 查当前用户"进行中"的会话数,超过上限(3 个)拒绝
  → 插入 interview_session(status=0)
  → 按 direction 组装 system prompt(面试官人设)
  → 调用 ChatClient 生成开场白
  → system 消息 + 开场白(assistant 消息)两条,同时写入 MySQL(interview_message)和 Redis List(上下文缓存)
  → 返回会话 id + 开场白
```

先把这次的两个设计难点说清楚:

**难点一:为什么 system prompt 也要存进 `interview_message` 表,不是只留在内存里拼一次就算了?** 因为任务 2.3 要做"多轮对话上下文管理"——每一轮新的提问,都要把**完整的历史消息(包括 system)**重新拼给模型(这是所有无状态 LLM 接口的通用玩法:模型自己不记得上一轮说了什么,每次都要你把历史一起发过去)。如果 Redis 里的上下文缓存过期或者被清空,程序要能从 MySQL 里把这场面试完整地重建出来,重建出来的第一条必须是 system prompt,不然 AI 人设就丢了。所以 system prompt 从创建会话这一刻起,就要当成一条正式的消息持久化,不是"临时拼接用完即丢"的东西。

**难点二:为什么不能把"插入 session + 调用 AI 生成开场白"整个包在一个 `@Transactional` 事务里?** 这是本任务开发文档明确点出来的坑,也是一个经典面试考点——**数据库事务的本质是"占着连接、等着提交或回滚",事务开的时间越长,这条数据库连接被占用的时间就越长**。而调用 AI 接口是一次跨网络的外部请求,慢的时候要几秒甚至更久,如果把这次调用也包进事务里,相当于让一条数据库连接白白空等几秒钟什么都不干,高并发场景下连接池会被迅速占满,拖垮整个系统——这就是"长事务陷阱"。正确做法是:**先把 `interview_session` 插库这一步做完(这一步本身很快,可以是一个短事务或者不需要事务),再在事务外调用 AI**。如果 AI 调用失败了呢?——**允许这个会话就这样"晾"在那里,没有开场白**,这次任务不需要做"失败自动回滚删除 session"这种复杂处理,想清楚"外部调用绝不能拖着数据库事务"这个原则就够了。

```sql
CREATE TABLE `interview_session` (
  `id`          BIGINT      NOT NULL AUTO_INCREMENT,
  `user_id`     BIGINT      NOT NULL COMMENT '所属用户',
  `direction`   VARCHAR(32) NOT NULL COMMENT '面试方向:java_concurrency/mysql/redis...',
  `title`       VARCHAR(128) DEFAULT NULL COMMENT '会话标题(默认取方向+日期)',

  `is_deleted`  TINYINT     NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  KEY `idx_user_id` (`user_id`, `create_time`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT 'AI 面试会话表';

-- 面试消息表
CREATE TABLE `interview_message` (
  `id`          BIGINT     NOT NULL AUTO_INCREMENT,
  `session_id`  BIGINT     NOT NULL COMMENT '会话 id',
  `role`        VARCHAR(16) NOT NULL COMMENT 'user/assistant/system',
  `content`     MEDIUMTEXT NOT NULL COMMENT '消息内容',
  `tokens`      INT        DEFAULT NULL COMMENT '该消息估算 token 数',
  `create_time` DATETIME   NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_session_id` (`session_id`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT '面试消息表';
```

### Step 2:面试方向枚举 `model/enums/InterviewDirection.java`

```java
package com.zhimian.model.enums;

public enum InterviewDirection {
    JAVA_CONCURRENCY("java_concurrency", "Java 并发", "线程池、锁机制、CAS、AQS、并发容器、线程协作工具"),
    JVM("jvm", "JVM", "内存区域划分、垃圾回收算法与收集器、类加载机制、常见调优场景"),
    MYSQL("mysql", "MySQL", "索引原理、事务隔离级别与 MVCC、锁机制、SQL 优化与索引失效场景"),
    REDIS("redis", "Redis", "常用数据结构与使用场景、持久化机制、缓存穿透雪崩击穿、分布式锁"),
    SYSTEM_DESIGN("system_design", "系统设计", "高并发架构设计思路、限流降级、缓存与数据库一致性、常见系统的设计权衡");

    private final String code;
    private final String label;
    private final String focus;

    InterviewDirection(String code, String label, String focus) {
        this.code = code;
        this.label = label;
        this.focus = focus;
    }

    public String getCode() {
        return code;
    }

    public String getLabel() {
        return label;
    }

    public String getFocus() {
        return focus;
    }

    public static InterviewDirection fromCode(String code) {
        for (InterviewDirection d : values()) {
            if (d.code.equals(code)) {
                return d;
            }
        }
        return null;
    }
}
```

【讲解】

- **这是项目里第一次出现 `model/enums` 这个新包**,之前的 `ErrorCode` 放在 `common/` 下,是因为它是全局通用的基础设施;`InterviewDirection` 是面试模块自己的业务概念,不适合塞进 `common`,单独开一个 `enums` 包存放业务枚举,以后如果还有别的枚举(比如报告状态)也放这里。
- **`focus` 字段不是随便加的**:它会被拼进 system prompt 里,告诉模型"这场面试重点考察什么"——枚举不只是用来做值校验的,也可以承载和这个值强相关的业务素材,这样 `buildSystemPrompt` 方法就不需要写一个 `switch` 分支去对应每个方向的考察重点,直接从枚举实例上取就行。
- **五个方向和前端展示的技能雷达维度(并发编程/JVM/Redis/MySQL/系统设计)刻意保持一致**,以后要接真实数据时,后端的 `direction` 枚举值可以直接映射到雷达图的五个轴,不用再建一套新的映射关系。

### Step 6:核心业务逻辑 `InterviewService`

`service/impl/InterviewServiceImpl.java`:

```java
package com.zhimian.service.impl;

import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.zhimian.common.ErrorCode;
import com.zhimian.common.UserContext;
import com.zhimian.exception.BusinessException;
import com.zhimian.mapper.InterviewMessageMapper;
import com.zhimian.mapper.InterviewSessionMapper;
import com.zhimian.model.dto.CreateInterviewDTO;
import com.zhimian.model.entity.InterviewMessage;
import com.zhimian.model.entity.InterviewSession;
import com.zhimian.model.enums.InterviewDirection;
import com.zhimian.model.vo.InterviewSessionVO;
import com.zhimian.service.InterviewService;
import lombok.RequiredArgsConstructor;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;

import java.time.LocalDate;
import java.util.concurrent.TimeUnit;

@Service
@RequiredArgsConstructor
public class InterviewServiceImpl implements InterviewService {

    private static final int MAX_ACTIVE_SESSIONS = 3;
    private static final String CTX_KEY_PREFIX = "zhimian:interview:ctx:";
    private static final long CTX_TTL_HOURS = 2;

    private final InterviewSessionMapper interviewSessionMapper;
    private final InterviewMessageMapper interviewMessageMapper;
    private final ChatClient chatClient;
    private final StringRedisTemplate redisTemplate;
    private final ObjectMapper objectMapper;

    @Override
    public InterviewSessionVO createInterview(CreateInterviewDTO dto) {
        InterviewDirection direction = InterviewDirection.fromCode(dto.getDirection());
        if (direction == null) {
            throw new BusinessException(ErrorCode.PARAMS_ERROR, "不支持的面试方向");
        }

        Long userId = UserContext.getUserId();
        long activeCount = interviewSessionMapper.countInProgress(userId);
        if (activeCount >= MAX_ACTIVE_SESSIONS) {
            throw new BusinessException(ErrorCode.TOO_MANY_REQUESTS, "进行中的面试会话已达上限,请先结束现有会话");
        }

        InterviewSession session = new InterviewSession();
        session.setUserId(userId);
        session.setDirection(direction.getCode());
        session.setTitle(direction.getLabel() + " · " + LocalDate.now());
        session.setStatus(0);
        interviewSessionMapper.insert(session);
        // 到这里,插库已经完成。下面调用 AI 是一次不可控耗时的外部请求,
        // 整个方法没有加 @Transactional,就是不想让数据库连接陪着这次外部调用一起等

        String systemPrompt = buildSystemPrompt(direction);
        String openingMessage;
        try {
            openingMessage = chatClient.prompt()
                    .system(systemPrompt)
                    .user("请开始这场模拟面试:先用一两句话做简短的自我介绍,然后直接提出第一个问题。")
                    .call()
                    .content();
        } catch (Exception e) {
            // session 已经建好了,这里选择不做任何补偿(不删 session、不标记失败状态)。
            // 这次任务的验收范围到这里就够了:知道"为什么不能在事务里调 AI"是重点,
            // "开场白生成失败要不要提供重试接口"留给后面任务或者你自己课后思考
            throw new BusinessException(ErrorCode.AI_SERVICE_ERROR, "开场白生成失败,请稍后重试");
        }

        InterviewMessage systemMsg = buildMessage(session.getId(), "system", systemPrompt);
        InterviewMessage assistantMsg = buildMessage(session.getId(), "assistant", openingMessage);
        interviewMessageMapper.insert(systemMsg);
        interviewMessageMapper.insert(assistantMsg);
        appendToContext(session.getId(), systemMsg);
        appendToContext(session.getId(), assistantMsg);

        InterviewSessionVO vo = new InterviewSessionVO();
        vo.setId(session.getId());
        vo.setDirection(direction.getCode());
        vo.setOpeningMessage(openingMessage);
        return vo;
    }

    /**
     * 面试官人设 + 对话风格约束。注意这里不包含"请提出第一个问题"这类一次性指令——
     * 这段 prompt 之后每一轮对话都要原样复用(任务 2.3),一次性指令应该放在 user 消息里,
     * 混进 system prompt 会导致模型每一轮都以为自己是"刚开始",重复自我介绍
     */
    private String buildSystemPrompt(InterviewDirection direction) {
        return """
                你是一位经验丰富的 Java 后端资深面试官,正在对候选人进行一场专注于「%s」方向的技术面试。

                面试风格要求:
                1. 每次只问一个问题,不要一次性抛出多个问题。
                2. 根据候选人上一轮回答的质量动态调整下一个问题的深度——回答得好就继续追问细节,回答得含糊就换个角度重新问或给出提示。
                3. 语气专业、简洁,像真实面试官一样自然对话,不要用"好的,我们开始吧"这类机械化开场白,也不要每句话都用 Markdown 列表排版。
                4. 这场面试重点考察方向:%s。
                """.formatted(direction.getLabel(), direction.getFocus());
    }

    private InterviewMessage buildMessage(Long sessionId, String role, String content) {
        InterviewMessage message = new InterviewMessage();
        message.setSessionId(sessionId);
        message.setRole(role);
        message.setContent(content);
        return message;
    }

    private void appendToContext(Long sessionId, InterviewMessage message) {
        String key = CTX_KEY_PREFIX + sessionId;
        redisTemplate.opsForList().rightPush(key, serialize(message));
        redisTemplate.expire(key, CTX_TTL_HOURS, TimeUnit.HOURS);
    }

    private String serialize(InterviewMessage message) {
        try {
            return objectMapper.writeValueAsString(message);
        } catch (JsonProcessingException e) {
            throw new RuntimeException(e);
        }
    }
}
```

【讲解,这是本任务最重要的部分】

- **`InterviewDirection.fromCode` 返回 `null` 而不是直接抛异常**:让调用方(这里是 `createInterview`)自己决定"找不到对应方向"意味着什么业务含义、该抛什么错误码——枚举类只负责"查找"这个纯粹的事,不掺和业务异常。
- **`activeCount >= MAX_ACTIVE_SESSIONS` 用 `TOO_MANY_REQUESTS`(42900)**:严格说"会话数超限"和"请求过于频繁"不是同一件事,但开发文档的验收标准明确要求这个场景返回 42900,项目现有错误码里也没有更贴切的选项——**没必要为了语义精确去新增一个错误码**,复用现有的、含义足够接近的错误码,是更务实的选择。
- **`buildSystemPrompt` 用的是文本块(text block,`"""..."""`)**:Java 15 之后的语法,多行字符串不用再写一堆 `+` 拼接或者 `\n` 转义,缩进和换行所见即所得,写 prompt 这种大段文本特别合适。`.formatted(...)` 是 `String` 的实例方法,等价于 `String.format(...)`,把 `%s` 占位符换成传入的值。
- **`appendToContext` 每次都重新设置 `expire`,不是只在第一次创建时设置**:这是"续期"语义,和你在任务 1.10 学的"日榜 key 首次创建才设置 TTL"刚好是相反的场景——那边是"只在乎新鲜创建的这一刻",这边是"只要还有人在用这个会话,就不该让上下文过期",所以每次追加消息都主动把 TTL 打回 2 小时。这个"续期"逻辑,任务 2.3 写 `InterviewContextManager.append()` 的时候还会再遇到一次,到时候会把这块逻辑正式抽出来复用。
- **为什么这次没有把 `interviewSessionMapper.insert(session)` 单独抽出去、也没有显式开一个短事务**:MyBatis 默认每个 `insert`/`update`/`delete` 语句在没有事务包裹的情况下会用**自动提交(auto-commit)**模式立刻生效,单条插入语句本身就是原子的,不需要额外包一层事务——真正要小心的是"不要把这一条插入和后面的 AI 调用揉进同一个 `@Transactional` 方法里",而不是"这条插入本身需要额外的事务保护"。
