## 一、本任务要实现什么

两组标准 CRUD(这次只做**新增 + 查询**,删除/修改留给以后):

- **分类**:`GET /api/categories` 查两级树(公开,不需要登录);`POST /api/categories` 新增(仅 admin)。
- **标签**:`GET /api/tags` 查列表(公开);`POST /api/tags` 新增(仅 admin)。

这里出现一个新情况:**同一个路径,GET 不需要登录、POST 需要 admin 权限**。之前 `WebConfig` 里用 `excludePathPatterns` 排除白名单的方式对这种场景不够用——`excludePathPatterns("/api/categories")` 会把 GET 和 POST 一起放行,`POST` 也就没人管权限了,这显然不对。

**技术选型**(顺手记一下,不是每次都要你拍板,但要知道我为什么这么选):

| 方案 | 做法 | 问题 |
|------|------|------|
| A. 路径白名单 | `WebConfig.excludePathPatterns` 加 `/api/categories`、`/api/tags` | 不区分请求方法,`POST` 也会被一起放行,权限校验失效,**直接排除** |
| B. 拦截器里判断 `request.getMethod()` | `preHandle` 里写 `if ("GET".equals(method) && path 在某个列表里) return true;` | 能work,但路径要硬编码在拦截器里,以后每加一个"公开 GET 接口"(题目详情、热门题目都是)就要回来改一次拦截器,列表会越滚越长 |
| **C. 新增 `@Public` 注解**(本次采用) | 仿照已有的 `@RequireAdmin`,标记在方法上,拦截器识别到就直接放行 | 和现有机制对称,新增一个公开接口只需要在方法上加个注解,不用碰拦截器;唯一"代价"是多了一个新注解概念,但成本很低 |

选 C,因为开发文档接口清单里"公开 GET + 管理员 POST"这个模式后面(题目、热门题目)还会反复出现,方案 C 一次性把机制建好,以后直接复用注解,不用每次都回来改拦截器。

链路:`CategoryController/TagController → CategoryService/TagService(内存建树 / 直接返回列表 + 查重转译异常) → CategoryMapper/TagMapper`。

## 三、分步实现

### Step 1:公开注解 `annotation/Public.java`

```java
package com.zhimian.annotation;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

/**
 * 标记在 Controller 方法上,表示该接口无需登录即可访问
 * 由 JwtInterceptor 在最前面识别并直接放行
 */
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Public {
}
```

【讲解】和 `@RequireAdmin` 一模一样的写法,`RUNTIME` 保留策略是必须的(拦截器要靠反射在运行时读到它)。

### Step 2:拦截器识别 `@Public`

`interceptor/JwtInterceptor.java`,只在 `preHandle` 最前面加一段判断(其余不变):

```java
package com.zhimian.interceptor;

import com.zhimian.annotation.Public;
import com.zhimian.annotation.RequireAdmin;
import com.zhimian.common.ErrorCode;
import com.zhimian.common.UserContext;
import com.zhimian.exception.BusinessException;
import com.zhimian.util.JwtUtil;
import io.jsonwebtoken.Claims;
import io.jsonwebtoken.ExpiredJwtException;
import io.jsonwebtoken.JwtException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import lombok.RequiredArgsConstructor;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;
import org.springframework.util.StringUtils;
import org.springframework.web.method.HandlerMethod;
import org.springframework.web.servlet.HandlerInterceptor;

@Component
@RequiredArgsConstructor
public class JwtInterceptor implements HandlerInterceptor {

    private static final String TOKEN_PREFIX = "Bearer ";

    private final JwtUtil jwtUtil;
    private final StringRedisTemplate redisTemplate;

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        if (!(handler instanceof HandlerMethod handlerMethod)) {
            return true;
        }

        // 标了 @Public 的接口,连 Authorization 头都不用看,直接放行
        if (handlerMethod.hasMethodAnnotation(Public.class)) {
            return true;
        }

        String authHeader = request.getHeader("Authorization");
        if (!StringUtils.hasText(authHeader) || !authHeader.startsWith(TOKEN_PREFIX)) {
            throw new BusinessException(ErrorCode.NOT_LOGIN);
        }
        String token = authHeader.substring(TOKEN_PREFIX.length());

        Claims claims;
        try {
            claims = jwtUtil.parseToken(token);
        } catch (ExpiredJwtException e) {
            throw new BusinessException(ErrorCode.TOKEN_EXPIRED);
        } catch (JwtException | IllegalArgumentException e) {
            throw new BusinessException(ErrorCode.NOT_LOGIN);
        }

        String jti = claims.getId();
        if (Boolean.TRUE.equals(redisTemplate.hasKey(JwtUtil.BLACKLIST_KEY_PREFIX + jti))) {
            throw new BusinessException(ErrorCode.TOKEN_EXPIRED);
        }

        Long userId = Long.valueOf(claims.getSubject());
        String role = claims.get("role", String.class);
        UserContext.set(userId, role, jti, claims.getExpiration().getTime());

        boolean requireAdmin = handlerMethod.hasMethodAnnotation(RequireAdmin.class);
        if (requireAdmin && !"admin".equals(role)) {
            UserContext.remove();
            throw new BusinessException(ErrorCode.NO_AUTH);
        }
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler, Exception ex) {
        UserContext.remove();
    }
}
```

【讲解】

- `@Public` 判断必须放在**最前面**,在读 `Authorization` 头之前——`@Public` 接口的语义是"完全不需要 token",如果判断顺序放错(比如放在验签之后),没带 token 的请求会先在验签那步就被拦成 40100,`@Public` 就白标了。
- 一个方法上不会同时出现 `@Public` 和 `@RequireAdmin`(逻辑上矛盾:既不需要登录又要求管理员),这次不用专门写代码防这个"不可能场景"——`CategoryController` 里两个方法一个标 `@Public` 一个标 `@RequireAdmin`,自然不会写反,靠开发者自己保证,不需要运行时校验。

【讲解,这是本任务的核心知识点】

- `CategoryMapper.xml` 里用了显式 `<resultMap>`,`TagMapper.xml` 却直接用 `resultType`——两者查出来的结果其实**完全等价**,因为 `application.yml` 里全局开了 `map-underscore-to-camel-case: true`,`parent_id` 自动映射到 `parentId` 本来就不需要手写 `resultMap`。这里特意在 `CategoryMapper` 里手写一遍纯粹是练习语法。
- 那 `resultMap` 到底什么时候**必须**用?两种典型场景:① 多表联查,结果列里出现同名字段(比如题目和分类都有 `id`、`create_time`),`resultType` 的自动映射会冲突,必须用 `resultMap` + `column` 显式指定取哪一列填哪个属性;② 一对多嵌套查询(比如"查题目时顺带把它的所有标签也查出来,直接映射成 `List<Tag>` 属性"),要靠 `resultMap` 里的 `<collection>` 标签,`resultType` 完全做不到。**这两种场景任务 1.6/1.7(题目关联标签、分页查询)就会遇到**,今天先在简单场景里把 `<resultMap>` 的基础写法过一遍。
- **`namespace` 必须和 Mapper 接口的全限定名一致**(`com.zhimian.mapper.CategoryMapper`),这是从任务 1.2 开始反复踩的坑——`Invalid bound statement (not found)` 这个报错的根本原因基本都是 namespace 和接口路径对不上,或者 `<select id="xxx">` 的 `id` 和接口方法名拼错。今天写完先别急着往下走,自己核对一遍这两份 XML 里的 namespace。

`service/impl/CategoryServiceImpl.java`:

```java
package com.zhimian.service.impl;

import com.zhimian.common.ErrorCode;
import com.zhimian.exception.BusinessException;
import com.zhimian.mapper.CategoryMapper;
import com.zhimian.model.dto.CategoryAddDTO;
import com.zhimian.model.entity.Category;
import com.zhimian.model.vo.CategoryVO;
import com.zhimian.service.CategoryService;
import lombok.RequiredArgsConstructor;
import org.springframework.beans.BeanUtils;
import org.springframework.dao.DuplicateKeyException;
import org.springframework.stereotype.Service;

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

@Service
@RequiredArgsConstructor
public class CategoryServiceImpl implements CategoryService {

    private final CategoryMapper categoryMapper;

    @Override
    public Long addCategory(CategoryAddDTO dto) {
        Category category = new Category();
        category.setName(dto.getName());
        category.setParentId(dto.getParentId());

        try {
            categoryMapper.insert(category);
        } catch (DuplicateKeyException e) {
            throw new BusinessException(ErrorCode.CONFLICT, "分类名已存在");
        }
        return category.getId();
    }

    @Override
    public List<CategoryVO> getTree() {
        List<Category> all = categoryMapper.selectAll();

        // 按 parentId 分组,一次遍历 O(n) 把"父 id -> 子分类列表"建好
        // 如果对每个顶级分类都单独发一条"查它的子分类"的 SQL,就是 N+1 查询;
        // 或者用双重循环给每个顶级分类去 all 里找子分类,是 O(n²)——数据量小(几十条)看不出差别,
        // 但要知道这是错误的写法,数据量一大就会退化得很明显
        Map<Long, List<Category>> childrenMap = new HashMap<>();
        List<Category> topLevel = new ArrayList<>();
        for (Category c : all) {
            if (c.getParentId() == 0) {
                topLevel.add(c);
            } else {
                childrenMap.computeIfAbsent(c.getParentId(), k -> new ArrayList<>()).add(c);
            }
        }

        List<CategoryVO> tree = new ArrayList<>();
        for (Category top : topLevel) {
            CategoryVO vo = new CategoryVO();
            BeanUtils.copyProperties(top, vo);

            List<CategoryVO> childVOs = new ArrayList<>();
            for (Category child : childrenMap.getOrDefault(top.getId(), List.of())) {
                CategoryVO childVO = new CategoryVO();
                BeanUtils.copyProperties(child, childVO);
                childVOs.add(childVO);
            }
            vo.setChildren(childVOs);
            tree.add(vo);
        }
        return tree;
    }
}
```

【讲解】

- 数据库唯一索引 `uk_name` 兜底防重(靠数据库,不是先查后插),捕获 `DuplicateKeyException` 转译成业务异常——和任务 1.2 里 `register()` 处理用户名重复是一模一样的套路,能力是可以复用的,不用每次都想新写法。
- `childrenMap.computeIfAbsent(parentId, k -> new ArrayList<>()).add(c)`:`computeIfAbsent` 是"key 不存在就用后面的函数算一个初始值放进去,然后返回这个 value"的简写,等价于写一个 `if (!map.containsKey(k)) map.put(k, new ArrayList<>());` 再 `map.get(k).add(c)`,但更短、更不容易忘记判断。
- 这个方法只支持**两级**:`topLevel` 里的分类如果自己又是别人的 `parentId`(第三级),会被静默丢弃,不会报错也不会出现在结果里。这是当前设计的边界(开发文档就是按两级设计的),不是 bug,但要知道它的局限——真出现三级分类的数据,这个方法不会报错提醒你,只会"看起来正常但少了一层",这也是"内存建树"方案相对"递归 SQL"方案的一个隐藏代价:结构对不对完全靠代码逻辑保证,数据库不会帮你约束层级。

【讲解】两个 Controller 结构完全对称:`@Public @GetMapping` 查、`@RequireAdmin @PostMapping` 增。`@RequestMapping("/api/categories")` 直接写在类上,方法上的 `@GetMapping`/`@PostMapping` 不用再重复路径——这和之前 `AuthController` 在类上写 `/api/auth`、方法上只写 `/register`、`/login` 是同一个套路。

curl -s -X POST http://localhost:8080/api/categories \
