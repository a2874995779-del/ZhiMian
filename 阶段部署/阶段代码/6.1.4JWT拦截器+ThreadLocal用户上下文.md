## 一、本任务要实现什么

一句话:给所有 `/api/**` 接口加一道"门",没带 token 或 token 不合法就拦下来;合法的话,把当前用户的 `userId`、`role` 存到一个"当前请求专属"的地方,后面 Controller/Service 随时能拿到"我是谁",不用每个方法都传 userId 参数。这个"当前请求专属的地方"就是 ThreadLocal。

链路:`请求进来 → JwtInterceptor.preHandle 验证 token → 存入 UserContext → Controller 从 UserContext 取 userId → ... → 请求结束 → JwtInterceptor.afterCompletion 清理 UserContext`。

## 三、分步实现

### Step 1:管理员权限注解 `annotation/RequireAdmin.java`

```java
package com.zhimian.annotation;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

/**
 * 标记在 Controller 方法上,表示该接口仅 admin 角色可访问
 * 由 JwtInterceptor 读取并校验
 */
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RequireAdmin {
}
```

【讲解】

- `@Retention(RUNTIME)`:必须是 RUNTIME,因为要在程序运行时通过反射读取这个注解(拦截器里),`CLASS` 或 `SOURCE` 级别的注解编译后就没了,反射读不到。
- 这是一个"标记注解"(marker annotation),不带任何属性,存在与否就是全部信息——够用就不要多加字段,这也是"简单优先"的体现。

### Step 2:ThreadLocal 用户上下文 `common/UserContext.java`

```java
package com.zhimian.common;

/**
 * 保存当前请求的登录用户信息,基于 ThreadLocal 实现"线程内全局变量"
 * 必须在请求处理完成后调用 remove(),否则线程池复用线程时会导致用户信息串号
 */
public class UserContext {

    private static final ThreadLocal<LoginUser> CONTEXT = new ThreadLocal<>();

    public static void set(Long userId, String role) {
        CONTEXT.set(new LoginUser(userId, role));
    }

    public static Long getUserId() {
        LoginUser user = CONTEXT.get();
        return user == null ? null : user.userId();
    }

    public static String getRole() {
        LoginUser user = CONTEXT.get();
        return user == null ? null : user.role();
    }

    public static void remove() {
        CONTEXT.remove();
    }

    private record LoginUser(Long userId, String role) {
    }
}
```

【讲解】

- 用 Java `record` 做内部持有类:两行字段自动生成构造器、`userId()`/`role()` 访问器、`equals`/`toString`,比手写一个 POJO 省事,而且天然不可变(线程安全的一个小加分项)。
- **为什么用 `static` 方法 + `static` 字段而不是普通实例**:`ThreadLocal` 本身就是"每个线程一份独立存储",不需要也不应该 `new UserContext()`——它不是一个业务对象,是一个工具类,全项目通过类名直接调用。
- 只提供 `set`/`get`/`remove`,不提供"更新单个字段"之类的方法:上下文只应该在拦截器里整体写入一次、在业务代码里只读、在请求结束时整体清空,不需要更复杂的接口。

### Step 3:拦截器核心 `interceptor/JwtInterceptor.java`

```java
package com.zhimian.interceptor;

import com.zhimian.annotation.RequireAdmin;
import com.zhimian.common.ErrorCode;
import com.zhimian.common.UserContext;
import com.zhimian.exception.BusinessException;
import com.zhimian.util.JwtUtil;
import io.jsonwebtoken.Claims;
import io.jsonwebtoken.ExpiredJwtException;
import io.jsonwebtoken.JwtException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Component;
import org.springframework.util.StringUtils;
import org.springframework.web.method.HandlerMethod;
import org.springframework.web.servlet.HandlerInterceptor;

/**
 * 登录鉴权拦截器:验证 JWT、写入 ThreadLocal 上下文、校验管理员权限
 */
@Component
@RequiredArgsConstructor
public class JwtInterceptor implements HandlerInterceptor {

    private static final String TOKEN_PREFIX = "Bearer ";

    private final JwtUtil jwtUtil;

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        // 只处理落到 Controller 方法上的请求;非 HandlerMethod(如静态资源)直接放行
        if (!(handler instanceof HandlerMethod handlerMethod)) {
            return true;
        }

        String authHeader = request.getHeader("Authorization");
        if (!StringUtils.hasText(authHeader) || !authHeader.startsWith(TOKEN_PREFIX)) {
            throw new BusinessException(ErrorCode.NOT_LOGIN);
        }
        String token = authHeader.substring(TOKEN_PREFIX.length());

        Claims claims;
        try {
            claims = jwtUtil.parseToken(token);
        } catch (ExpiredJwtException e) {
            throw new BusinessException(ErrorCode.TOKEN_EXPIRED);
        } catch (JwtException | IllegalArgumentException e) {
            // 签名不合法、格式错误等一律按未登录处理,不向客户端暴露具体校验失败原因
            throw new BusinessException(ErrorCode.NOT_LOGIN);
        }

        Long userId = Long.valueOf(claims.getSubject());
        String role = claims.get("role", String.class);
        UserContext.set(userId, role);

        boolean requireAdmin = handlerMethod.hasMethodAnnotation(RequireAdmin.class);
        if (requireAdmin && !"admin".equals(role)) {
            // 注意:必须在抛异常前手动 remove!
            // preHandle 一旦抛异常,本拦截器的 afterCompletion 不会被调用(见下方讲解),
            // 如果不在这里清理,ThreadLocal 会带着这次请求的 userId 一直留在线程里
            UserContext.remove();
            throw new BusinessException(ErrorCode.NO_AUTH);
        }

        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                                 Object handler, Exception ex) {
        // preHandle 返回 true 之后,不管 Controller 内部是否抛异常,afterCompletion 都会执行
        // 这里是清理 ThreadLocal 的正确位置
        UserContext.remove();
    }
}
```

【讲解,这是本任务最重要的部分,建议逐条对着代码看】

- **为什么选拦截器不选过滤器(Filter)**:过滤器运行在 `DispatcherServlet` 之外,Spring MVC 的异常处理机制(`@RestControllerAdvice`)根本插不上手,过滤器里抛的异常不会被你的 `GlobalExceptionHandler` 接住,只能自己手写 try-catch 拼返回体。拦截器运行在 `DispatcherServlet` 内部,`preHandle` 抛出的 `BusinessException` 会走 Spring MVC 标准的异常解析链路,和 Controller 里抛的异常一样被 `GlobalExceptionHandler` 捕获——这也是为什么上面的代码可以直接 `throw`,不用自己拼 `Result`。
- **`postHandle` 和 `afterCompletion` 的区别**:`postHandle` 只在 Controller 方法**成功执行完**之后才会跑;`afterCompletion` 无论 Controller 是否抛异常都会跑(类似 try-finally 的 finally)。清理 ThreadLocal 这种"不管成不成功都必须做"的事情,只能放在 `afterCompletion`,放 `postHandle` 里在业务异常时会被跳过,造成泄漏。
- **`preHandle` 自己抛异常时,`afterCompletion` 不会被调用**——这是很多人写完拦截器却在高并发下偶发串号的根本原因。Spring 的规则是:只有 `preHandle` **成功返回 `true`** 的拦截器,才会在链路末尾收到 `afterCompletion` 回调。所以代码里 `@RequireAdmin` 校验失败要抛异常时,**必须先手动 `UserContext.remove()` 再 `throw`**,不能指望 `afterCompletion` 兜底。你可以试着把这两行顺序换一下,构造一个"user 角色调用管理员接口"的请求,连续打几次,理论上会观察到异常行为(线程复用时才会暴露,单次请求不一定能看出来,这里主要是理解原理)。
- `Long.valueOf(claims.getSubject())` 前面没有再包一层 try-catch:因为能走到这一行,说明 `jwtUtil.parseToken` 已经验签成功,而 `subject` 只可能是我们自己在 `generateToken` 里写入的合法数字字符串,不存在"验签通过但内容非法"的场景,不需要为不可能发生的情况写防御代码。

### Step 4:注册拦截器 `config/WebConfig.java`

```java
package com.zhimian.config;

import com.zhimian.interceptor.JwtInterceptor;
import lombok.RequiredArgsConstructor;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.InterceptorRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
@RequiredArgsConstructor
public class WebConfig implements WebMvcConfigurer {

    private final JwtInterceptor jwtInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(jwtInterceptor)
                .addPathPatterns("/api/**")
                .excludePathPatterns(
                        "/api/auth/register",
                        "/api/auth/login",
                        "/api/health"
                );
    }
}
```

【讲解】

- `addPathPatterns("/api/**")` 先把所有接口一网打尽,再用 `excludePathPatterns` 白名单式排除不需要登录的接口——这比一个个加需要登录的接口更不容易漏掉(以后新增一个受保护接口,默认就是受保护的,不用记得手动加进拦截列表)。
- 排除列表现在只有三个,以后阶段一的"热门题目"“分类列表"等公开只读接口做出来后,也要加进这里。

### Step 6:验证用的 Controller `controller/UserController.java`

```java
package com.zhimian.controller;

import com.zhimian.annotation.RequireAdmin;
import com.zhimian.common.ErrorCode;
import com.zhimian.common.Result;
import com.zhimian.common.UserContext;
import com.zhimian.exception.BusinessException;
import com.zhimian.mapper.UserMapper;
import com.zhimian.model.entity.User;
import com.zhimian.model.vo.UserVO;
import lombok.RequiredArgsConstructor;
import org.springframework.beans.BeanUtils;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api")
@RequiredArgsConstructor
public class UserController {

    private final UserMapper userMapper;

    /**
     * 当前登录用户信息。用于验证拦截器是否正确解析了 token 并写入了 ThreadLocal
     */
    @GetMapping("/users/me")
    public Result<UserVO> me() {
        Long userId = UserContext.getUserId();
        User user = userMapper.selectById(userId);
        if (user == null) {
            throw new BusinessException(ErrorCode.NOT_FOUND, "用户不存在");
        }
        UserVO vo = new UserVO();
        BeanUtils.copyProperties(user, vo);
        return Result.success(vo);
    }

    /**
     * 临时验证端点:仅用于本任务自测 @RequireAdmin 是否生效。
     * 任务 1.5 做出真正的管理员接口(分类/标签新增)后,这个方法可以删掉。
     */
    @RequireAdmin
    @GetMapping("/admin/ping")
    public Result<String> adminPing() {
        return Result.success("pong, admin=" + UserContext.getRole());
    }
}
```

【讲解】

- `/api/users/me` 不是"为了测试而造的接口",它是开发文档接口清单里本来就要有的正式接口(阶段一「认证与用户」表格里的第 4 行),今天顺手实现,一举两得。
- `/api/admin/ping` 是**临时**的,专门用来在还没有任何真正管理端接口时验证 `@RequireAdmin` 生效——文档里已经写清楚了什么时候可以删,不用纠结"是不是脏代码",这是刻意的过渡手段。
- Controller 里直接注入 `UserMapper` 而不是 `UserService`:因为这个查询单一、没有任何业务逻辑(不加密、不校验、不转译异常),严格按"Controller 不碰 Mapper"的教条反而是过度设计。**但如果你想保持分层一致性,也可以在 `UserService` 里加一个 `getById` 方法再调用**——两种写法我都能接受,你可以自己选,写完告诉我你的理由。

## 四、自测清单

```bash
# 准备:注册并登录拿到 token(替换成你自己环境里已有的账号也行)
curl -s -X POST http://localhost:8080/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username":"ctxtest","password":"abc12345"}'

TOKEN=$(curl -s -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"ctxtest","password":"abc12345"}' | grep -o '"token":"[^"]*"' | cut -d'"' -f4)
echo "TOKEN=$TOKEN"
```

1. **不带 token** → 期望 `code=40100`
   ```bash
   curl -s http://localhost:8080/api/users/me
   ```

2. **带合法 token** → 期望 `code=0`,`data` 是当前用户信息(无 password)
   ```bash
   curl -s http://localhost:8080/api/users/me -H "Authorization: Bearer $TOKEN"
   ```

3. **篡改 token**(随便改最后一个字符)→ 期望 `code=40100`
   ```bash
   curl -s http://localhost:8080/api/users/me -H "Authorization: Bearer ${TOKEN}x"
   ```

4. **token 过期** → 临时把 `application-local.yml` 里 `zhimian.jwt.expire-hours` 改成一个极小的值做测试(比如改成能在几秒内过期的配置,或者干脆改代码里 `plus()` 的单位临时调成秒来测,测完记得改回 24)。重新登录拿新 token,等它过期后再请求 `/api/users/me`,期望 `code=40101`。测完别忘了把配置改回来。

5. **普通用户访问管理员接口** → 期望 `code=40300`
   ```bash
   curl -s http://localhost:8080/api/admin/ping -H "Authorization: Bearer $TOKEN"
   ```

6. **把该用户提升为 admin 后访问** → 期望 `code=0`。注意:**必须重新登录换一个新 token**,因为 `role` 是签发时写死在 token 里的,数据库里改了 role,旧 token 里的 claim 不会变(这是你要能讲清楚的一个点)。
   ```sql
   UPDATE zhimian.user SET role = 'admin' WHERE username = 'ctxtest';
   ```
   ```bash
   NEW_TOKEN=$(curl -s -X POST http://localhost:8080/api/auth/login \
     -H "Content-Type: application/json" \
     -d '{"username":"ctxtest","password":"abc12345"}' | grep -o '"token":"[^"]*"' | cut -d'"' -f4)
   curl -s http://localhost:8080/api/admin/ping -H "Authorization: Bearer $NEW_TOKEN"
   ```

7. **ThreadLocal 不串号**(定性验证,不强求严格复现):再注册一个用户 `ctxtest2`,两个账号的 token 交替快速请求 `/api/users/me` 各 5~6 次,确认每次返回的 `data.username` 都和你传的 token 对得上,不会出现张冠李戴。
