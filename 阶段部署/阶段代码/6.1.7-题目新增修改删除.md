## 一、本任务要实现什么

三个管理员接口(对应开发文档 4.4 节接口清单):

- `POST /api/questions` 👑 新增题目(同时写 `question` 和 `question_tag` 两张表)
- `PUT /api/questions/{id}` 👑 修改题目(含标签集合的变更)
- `DELETE /api/questions/{id}` 👑 删除题目(逻辑删除,`is_deleted = 1`)

**核心难点:新增/修改都要动两张表**。比如新增时,`question` 插入成功、`question_tag` 插入失败(哪怕失败原因很离谱,比如网络闪断),库里就会留下一条"没有标签的半成品题目"——数据不一致。解决办法就是**事务**:`@Transactional` 把两次写包成一个原子操作。

**技术选型 1:修改题目时,标签关联怎么更新?**

| 方案 | 做法 | 问题 |
|------|------|------|
| **A. 先删后插**(本次采用) | `DELETE FROM question_tag WHERE question_id = ?`,再把新的 tagIds 批量插入 | 简单粗暴,两条 SQL 搞定;缺点是即使标签没变也会删了重插,但关联表数据量小(一题几个标签),这点浪费完全可接受 |
| B. 内存 diff 差集 | 查出旧标签集合,和新集合比较,只删多余的、只插新增的 | SQL 更省,但代码复杂度明显上升(三次集合运算 + 两条动态 SQL),在"一题最多几个标签"的量级下是过度优化 |
| C. INSERT IGNORE 只增不删 | 利用联合主键防重,只管插入 | 用户取消勾选的标签删不掉,功能是错的,直接排除 |

选 A。**简单方案能正确解决问题时,永远先选简单方案**;B 的思路值得知道(面试聊到"大表关联更新"可以提),但现在不写。

**技术选型 2:批量插入标签关联,`<foreach>` 拼一条 SQL vs 循环调单条 insert?**

| 方案 | 做法 | 问题 |
|------|------|------|
| **A. `<foreach>` 批量**(本次采用) | 一条 `INSERT INTO question_tag VALUES (a,b),(a,c),(a,d)` | 一次网络往返、一次 SQL 解析,标准做法 |
| B. for 循环单插 | Java 里循环调 `insert` N 次 | N 次网络往返,量小看不出差别,但这是典型的"坏习惯写法",养成了以后写批量导入会出大事 |

选 A,顺便把 `<foreach>` 语法学了——任务 1.7 的 `IN` 查询还要再用一次。

链路:`QuestionController → QuestionService(@Transactional 组合两个 Mapper) → QuestionMapper + QuestionTagMapper`。

### Step 3:`mapper/QuestionMapper.java` + XML

```java
package com.zhimian.mapper;

import com.zhimian.model.entity.Question;
import org.apache.ibatis.annotations.Mapper;

@Mapper
public interface QuestionMapper {

    int insert(Question question);

    int update(Question question);

    int logicalDelete(Long id);

    Question selectById(Long id);
}
```

`resources/mapper/QuestionMapper.xml`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="com.zhimian.mapper.QuestionMapper">

    <insert id="insert" useGeneratedKeys="true" keyProperty="id">
        INSERT INTO question (title, content, answer, difficulty, category_id, create_user_id)
        VALUES (#{title}, #{content}, #{answer}, #{difficulty}, #{categoryId}, #{createUserId})
    </insert>

    <update id="update">
        UPDATE question
        SET title       = #{title},
            content     = #{content},
            answer      = #{answer},
            difficulty  = #{difficulty},
            category_id = #{categoryId}
        WHERE id = #{id} AND is_deleted = 0
    </update>

    <update id="logicalDelete">
        UPDATE question
        SET is_deleted = 1
        WHERE id = #{id} AND is_deleted = 0
    </update>

    <select id="selectById" resultType="com.zhimian.model.entity.Question">
        SELECT id, title, content, answer, difficulty, category_id,
               view_count, create_user_id, create_time, update_time, is_deleted
        FROM question
        WHERE id = #{id} AND is_deleted = 0
    </select>

</mapper>
```

【讲解】

- 所有写操作的 WHERE 都带 `is_deleted = 0`:已删除的题目不允许再被修改/再次删除,`update`/`logicalDelete` 返回的影响行数就成了"目标存在且未删"的判据,Service 里靠返回值判断要不要抛 40400,**省掉一次先 SELECT 再 UPDATE 的查询**。
- "删除"是 `UPDATE is_deleted = 1`,不是 `DELETE`——逻辑删除。为什么?① 误删可恢复;② `answer_record` 等表还引用着题目 id,物理删除会留下孤儿引用;③ 面试标准答案:线上系统几乎不做物理删除。代价是所有查询都要带 `is_deleted = 0`(这也是 2.4 节讨论过"为什么 is_deleted 不建索引"的背景)。

### Step 4:`mapper/QuestionTagMapper.java` + XML

```java
package com.zhimian.mapper;

import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Param;

import java.util.List;

@Mapper
public interface QuestionTagMapper {

    int batchInsert(@Param("questionId") Long questionId, @Param("tagIds") List<Long> tagIds);

    int deleteByQuestionId(Long questionId);
}
```

`resources/mapper/QuestionTagMapper.xml`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="com.zhimian.mapper.QuestionTagMapper">

    <insert id="batchInsert">
        INSERT INTO question_tag (question_id, tag_id)
        VALUES
        <foreach collection="tagIds" item="tagId" separator=",">
            (#{questionId}, #{tagId})
        </foreach>
    </insert>

    <delete id="deleteByQuestionId">
        DELETE FROM question_tag
        WHERE question_id = #{questionId}
    </delete>

</mapper>
```

【讲解】

- 接口上的 `@Param`:方法有**两个以上参数**时必须加,否则 XML 里 `#{questionId}`、`#{tagIds}` 不知道绑定到哪个参数(单参数方法 MyBatis 能自动对上,多参数不行)。之前的 mapper 都是单参数所以没遇到过。
- `<foreach separator=",">` 会把列表展开成 `(1,3),(1,5),(1,7)` 这样的多值 VALUES。**关键坑:`tagIds` 为空列表时**,`<foreach>` 一个元素都不生成,最终 SQL 是 `INSERT INTO question_tag (question_id, tag_id) VALUES` ——语法错误直接炸。所以**空列表的判断必须在 Service 层做,列表为空就压根不调这个方法**,不要指望 XML 自己处理。
- 关联表的删除用的是**物理 DELETE**,和题目的逻辑删除不一样——关联表是纯关系数据,没有"恢复"的需求,留着已失效的关联反而污染查询,这里物理删除才是对的。**逻辑删除不是教条,按表的性质选**。

### Step 5:Service

`service/QuestionService.java`:

```java
package com.zhimian.service;

import com.zhimian.model.dto.QuestionAddDTO;

public interface QuestionService {

    Long addQuestion(QuestionAddDTO dto);

    void updateQuestion(Long id, QuestionAddDTO dto);

    void deleteQuestion(Long id);
}
```

`service/impl/QuestionServiceImpl.java`:

```java
package com.zhimian.service.impl;

import com.zhimian.common.ErrorCode;
import com.zhimian.common.UserContext;
import com.zhimian.exception.BusinessException;
import com.zhimian.mapper.QuestionMapper;
import com.zhimian.mapper.QuestionTagMapper;
import com.zhimian.model.dto.QuestionAddDTO;
import com.zhimian.model.entity.Question;
import com.zhimian.service.QuestionService;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.util.CollectionUtils;

@Service
@RequiredArgsConstructor
public class QuestionServiceImpl implements QuestionService {

    private final QuestionMapper questionMapper;
    private final QuestionTagMapper questionTagMapper;

    @Transactional
    @Override
    public Long addQuestion(QuestionAddDTO dto) {
        Question question = new Question();
        question.setTitle(dto.getTitle());
        question.setContent(dto.getContent());
        question.setAnswer(dto.getAnswer());
        question.setDifficulty(dto.getDifficulty());
        question.setCategoryId(dto.getCategoryId());
        question.setCreateUserId(UserContext.getUserId());

        questionMapper.insert(question);

        // 空列表必须在这里挡住:<foreach> 对空列表会生成非法 SQL
        if (!CollectionUtils.isEmpty(dto.getTagIds())) {
            questionTagMapper.batchInsert(question.getId(), dto.getTagIds());
        }
        return question.getId();
    }

    @Transactional
    @Override
    public void updateQuestion(Long id, QuestionAddDTO dto) {
        Question question = new Question();
        question.setId(id);
        question.setTitle(dto.getTitle());
        question.setContent(dto.getContent());
        question.setAnswer(dto.getAnswer());
        question.setDifficulty(dto.getDifficulty());
        question.setCategoryId(dto.getCategoryId());

        // update 的 WHERE 带 is_deleted = 0,影响行数为 0 说明题目不存在或已删除
        if (questionMapper.update(question) == 0) {
            throw new BusinessException(ErrorCode.NOT_FOUND, "题目不存在");
        }

        // 标签关联:先删后插(选型 A)
        questionTagMapper.deleteByQuestionId(id);
        if (!CollectionUtils.isEmpty(dto.getTagIds())) {
            questionTagMapper.batchInsert(id, dto.getTagIds());
        }
    }

    @Transactional
    @Override
    public void deleteQuestion(Long id) {
        if (questionMapper.logicalDelete(id) == 0) {
            throw new BusinessException(ErrorCode.NOT_FOUND, "题目不存在");
        }
        // 关联记录留不留都不影响正确性(所有查询以 question.is_deleted 为准),
        // 这里选择顺手清掉,让关联表只存有效关系
        questionTagMapper.deleteByQuestionId(id);
    }
}
```

【讲解,本任务核心】

- **`@Transactional` 为什么必须加**:`addQuestion` 里两次写库,若 `batchInsert` 失败(比如传了不存在的 tagId 触发别的错、或者数据库连接断了),没有事务的话前面的 `insert` 已经落库,留下半成品数据。加了事务,Spring 会在方法开始时开启事务、正常返回时 commit、抛出 **RuntimeException** 时 rollback——两次写变成原子操作。
- **回滚规则(面试必考)**:默认**只回滚 RuntimeException 和 Error**,受检异常(checked exception)不回滚!我们的 `BusinessException` 继承自 `RuntimeException`,所以抛它会回滚,这是它设计成运行时异常的原因之一。如果你哪天在事务方法里 `throw new Exception("...")`,事务会照常提交,这是经典事故来源。
- **自调用失效(面试最高频事务题)**:`@Transactional` 靠 Spring 的 AOP 动态代理实现——调用方拿到的是"代理对象",代理在真正的方法前后织入了开启/提交事务的逻辑。但**同一个类里 `this.xxx()` 自调用不经过代理**,事务直接失效。验收标准里要你亲手验证这一条,做法见自测清单第 6 步。
- `updateQuestion` 里"改题目 + 换标签"三条 SQL 也在同一个事务里:如果 `batchInsert` 失败,`update` 和 `delete` 都会回滚,不会出现"标签删了但新的没插上"的中间态。
- `UserContext.getUserId()` 在这里第一次有了真正的调用方(记录出题人)——之前 review 说它是"没人用的死代码",现在它活了。**这也说明"没人用"的判断是时点性的,当时删掉的话现在就要重写**;但注意,这不是"提前写没人用的代码是对的"的证据,当时写它是因为拦截器往 UserContext 存了 userId,取值方法是成对出现的基础设施。

`controller/QuestionController.java`:

```java
package com.zhimian.controller;

import com.zhimian.annotation.RequireAdmin;
import com.zhimian.common.Result;
import com.zhimian.model.dto.QuestionAddDTO;
import com.zhimian.service.QuestionService;
import jakarta.validation.Valid;
import lombok.RequiredArgsConstructor;
import org.springframework.web.bind.annotation.DeleteMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.PutMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/questions")
@RequiredArgsConstructor
public class QuestionController {

    private final QuestionService questionService;

    @RequireAdmin
    @PostMapping
    public Result<Long> add(@Valid @RequestBody QuestionAddDTO dto) {
        return Result.success(questionService.addQuestion(dto));
    }

    @RequireAdmin
    @PutMapping("/{id}")
    public Result<Void> update(@PathVariable Long id, @Valid @RequestBody QuestionAddDTO dto) {
        questionService.updateQuestion(id, dto);
        return Result.success();
    }

    @RequireAdmin
    @DeleteMapping("/{id}")
    public Result<Void> delete(@PathVariable Long id) {
        questionService.deleteQuestion(id);
        return Result.success();
    }
}
```

【讲解】`@PathVariable` 是新面孔:把路径里的 `{id}` 绑定到方法参数,REST 风格里"对某个资源的操作"都这么表达(`PUT /api/questions/5` = 修改 5 号题目)。三个方法都标 `@RequireAdmin`,和接口清单里的 👑 一一对应。

## 五、写完之后
