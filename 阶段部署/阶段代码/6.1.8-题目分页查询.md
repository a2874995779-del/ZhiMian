## 一、本任务要实现什么

一个公开接口(接口清单里无 🔒/👑 标记,和分类树同级,标 `@Public`):

```
GET /api/questions?pageNum=1&pageSize=10&categoryId=2&tagId=3&difficulty=2&keyword=线程池
```

五个筛选条件**全部可选、可任意组合**,响应体是 `PageResult` 包一页 `records` + `total`(见开发文档 4.4 节的响应示例)。**列表不返回 `answer` 字段**——刷题场景先看题后看答案,答案留给详情接口(任务 1.8)。

**技术选型 1:分页怎么做?**

| 方案 | 做法 | 问题 |
|------|------|------|
| A. PageHelper 插件 | 引依赖,`PageHelper.startPage(1,10)` 一行搞定 | 方便,但它靠 ThreadLocal + 拦截器改写 SQL,原理全被藏起来了。**学习期用它等于没学分页**,开发文档明确要求手写 |
| **B. 手写 COUNT + LIMIT**(本次采用) | 一条 `COUNT(*)` 查总数,一条 `LIMIT #{offset}, #{pageSize}` 查当页 | 两条 SQL 自己写、offset 自己算,分页的每个环节都过手。面试聊 PageHelper 原理时你也有底气——它底层生成的就是这两条 |

**技术选型 2:列表 VO 里的 `categoryName` 和 `tags` 怎么组装?**(开发文档让你先自己想,这里公布答案)

| 方案 | 做法 | 问题 |
|------|------|------|
| A. 一条大 JOIN 全查出来 | question JOIN category JOIN question_tag JOIN tag,`resultMap` 用 `<collection>` 折叠 | **行爆炸破坏分页**:一题带 3 个标签,JOIN 后变 3 行,`LIMIT 10` 拿到的是"10 行"而不是"10 题",折叠完可能只剩 4 题——分页语义直接错了。绕开它要套子查询,SQL 复杂度飙升 |
| **B. 主查询 + 内存组装**(本次采用) | 先分页查出 10 题,再用两条小查询补齐:分类全量(几十条,查一次建 id→name 映射)、当页题目的标签(一条 `IN` 查询) | 固定 3 条 SQL(COUNT + 分页 + 标签),条数不随页大小增长,不是 N+1;每条 SQL 都简单、都能走索引 |

选 B。**这是"JOIN 一定比多次查询好"这个直觉的反例**:JOIN 遇上一对多 + 分页,行爆炸的坑远比多发一条 SQL 的开销大。这个取舍面试能聊很深,记住这个具体场景。

链路:`QuestionController → QuestionService(分页计算 + VO 组装) → QuestionMapper(动态 SQL) + QuestionTagMapper + CategoryMapper(复用 selectAll)`。

## 三、分步实现

### Step 1:查询参数 `model/dto/QuestionQueryDTO.java`

```java
package com.zhimian.model.dto;

import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import lombok.Data;

@Data
public class QuestionQueryDTO {

    @Min(value = 1, message = "pageNum 最小为 1")
    private Integer pageNum = 1;

    @Min(value = 1, message = "pageSize 最小为 1")
    @Max(value = 50, message = "pageSize 最大为 50")
    private Integer pageSize = 10;

    /** 以下四个筛选条件全部可选 */
    private Long categoryId;
    private Long tagId;
    private Integer difficulty;
    private String keyword;

    /** LIMIT 的起点,统一在这里算,别在 Service 和 XML 里各算一遍 */
    public int getOffset() {
        return (pageNum - 1) * pageSize;
    }
}
```

【讲解】

- 字段直接给默认值 `= 1`、`= 10`:GET 参数不传时 Spring 绑定后保持默认,不用在 Service 里写 null 判断。`pageSize` 上限 50 是防御:不限制的话,谁传个 `pageSize=100000` 就是一次全表捞取,公开接口必须封死这个口子。
- **pageNum 从 1 开始**(对用户友好),offset 从 0 开始(SQL 语义),换算 `(pageNum-1)*pageSize` 收敛在 `getOffset()` 一个地方——开发文档"易踩的坑"里点名的"offset 计算错误、起点不统一",解法就是只算一次。XML 里 `#{offset}` 会自动调这个 getter,MyBatis 取参数走的是 getter 而不是字段。

### Step 3:动态 SQL(本任务核心)

`mapper/QuestionMapper.java` 加两个方法:

```java
long count(QuestionQueryDTO query);

List<Question> selectPage(QuestionQueryDTO query);
```

`resources/mapper/QuestionMapper.xml` 加:

```xml
<!-- COUNT 和 SELECT 共用的表连接 + 筛选条件,抽成 <sql> 片段,两边 <include> 同一份 -->
<sql id="pageCondition">
    FROM question q
    <if test="tagId != null">
        JOIN question_tag qt ON qt.question_id = q.id
    </if>
    <where>
        q.is_deleted = 0
        <if test="categoryId != null">
            AND q.category_id = #{categoryId}
        </if>
        <if test="difficulty != null">
            AND q.difficulty = #{difficulty}
        </if>
        <if test="tagId != null">
            AND qt.tag_id = #{tagId}
        </if>
        <if test="keyword != null and keyword != ''">
            AND q.title LIKE CONCAT('%', #{keyword}, '%')
        </if>
    </where>
</sql>

<select id="count" resultType="long">
    SELECT COUNT(*)
    <include refid="pageCondition"/>
</select>

<select id="selectPage" resultType="com.zhimian.model.entity.Question">
    SELECT q.id, q.title, q.difficulty, q.category_id, q.view_count, q.create_time
    <include refid="pageCondition"/>
    ORDER BY q.create_time DESC
    LIMIT #{offset}, #{pageSize}
</select>
```

【讲解,逐个知识点过】

- **`<sql>` + `<include>`**:开发文档"易踩的坑"里的"COUNT 和 SELECT 的 where 不一致导致 total 对不上",根治办法就是条件只写一份、两边引用。以后改筛选逻辑只动 `pageCondition` 一处。
- **`<where>` 标签**:自动补 `WHERE` 关键字,并把第一个条件开头多余的 `AND` 剥掉。我们首条 `q.is_deleted = 0` 是常量条件永远存在,所以其实永远触发不了"剥 AND"的逻辑,但养成用 `<where>` 的习惯——哪天首条也变成 `<if>`,裸写 `WHERE` 就会拼出 `WHERE AND ...` 的语法错误。
- **JOIN 也是条件的**:只有传了 `tagId` 才 JOIN 关联表——不筛标签时 JOIN 是纯浪费。注意 `tagId` 的两个 `<if>`(JOIN 和 AND)条件必须一致,这也是抽 `<sql>` 片段的好处:它们天然在一起,不会改了一个漏了另一个。按单个 `tagId` 筛选时一题最多命中一行关联,**不会**出现行爆炸,不需要 DISTINCT;如果以后支持"多标签任意命中"(`tag_id IN (...)`)就会重复,那时要加——边界在哪里要清楚。
- **`#{}` vs `${}`(必考)**:`#{keyword}` 走 PreparedStatement 占位符,用户输入永远被当作"值",拼不进 SQL 结构,注入天然免疫;`${}` 是字符串替换,输入直接进 SQL 文本,`keyword` 传 `' OR 1=1 --` 就把你的 WHERE 整个改写了。**动态 SQL 里唯一考虑 `${}` 的场景是表名/列名这种占位符替代不了的位置**,且必须白名单校验。自测清单里有注入实测。
- `LIKE CONCAT('%', #{keyword}, '%')`:百分号拼接放在 SQL 函数里做,而不是 Java 里拼 `"%" + keyword + "%"` 再传——两种都对,但前者让 SQL 自解释。这个 LIKE 无法走索引(最左前缀被 `%` 破坏),数据量小可接受,面试演进话术:上全文索引或 ES。

### Step 4:批量查标签名

`mapper/QuestionTagMapper.java` 加:

```java
List<QuestionTagName> selectTagNamesByQuestionIds(@Param("questionIds") List<Long> questionIds);
```

`resources/mapper/QuestionTagMapper.xml` 加:

```xml
<select id="selectTagNamesByQuestionIds" resultType="com.zhimian.model.entity.QuestionTagName">
    SELECT qt.question_id, t.name
    FROM question_tag qt
    JOIN tag t ON t.id = qt.tag_id
    WHERE qt.question_id IN
    <foreach collection="questionIds" item="qid" open="(" separator="," close=")">
        #{qid}
    </foreach>
</select>
```

【讲解】`<foreach>` 第二次出场,这次用 `open="(" close=")"` 生成 `IN (1,2,3)`。空列表同样会生成非法 SQL `IN ()`——守卫依然在 Service 层(当页没有记录就压根不调它)。这条 JOIN 为什么不怕行爆炸?因为它**不带分页**,查的就是"这 10 题的全部标签",多少行都是我们要的。

### Step 5:Service

`service/impl/QuestionServiceImpl.java` 加(注入处加上 `CategoryMapper`):

```java
@Override
public PageResult<QuestionListVO> pageQuestions(QuestionQueryDTO query) {
    long total = questionMapper.count(query);
    // 总数为 0 直接返回空页:第二条查询省了,也天然满足"空结果返回空数组而不是 null"
    if (total == 0) {
        return PageResult.of(List.of(), 0, query.getPageNum(), query.getPageSize());
    }

    List<Question> records = questionMapper.selectPage(query);

    // 补齐 categoryName:分类只有几十条,全量查一次建 id→name 映射
    Map<Long, String> categoryNameMap = new HashMap<>();
    for (Category c : categoryMapper.selectAll()) {
        categoryNameMap.put(c.getId(), c.getName());
    }

    // 补齐 tags:当页题目 id 一次 IN 查询,再按 questionId 分组
    List<Long> questionIds = new ArrayList<>();
    for (Question q : records) {
        questionIds.add(q.getId());
    }
    Map<Long, List<String>> tagMap = new HashMap<>();
    for (QuestionTagName row : questionTagMapper.selectTagNamesByQuestionIds(questionIds)) {
        tagMap.computeIfAbsent(row.getQuestionId(), k -> new ArrayList<>()).add(row.getName());
    }

    List<QuestionListVO> voList = new ArrayList<>();
    for (Question q : records) {
        QuestionListVO vo = new QuestionListVO();
        BeanUtils.copyProperties(q, vo);
        vo.setCategoryName(categoryNameMap.get(q.getCategoryId()));
        vo.setTags(tagMap.getOrDefault(q.getId(), List.of()));
        voList.add(vo);
    }
    return PageResult.of(voList, total, query.getPageNum(), query.getPageSize());
}
```

(新 import:`com.zhimian.common.PageResult`、`com.zhimian.mapper.CategoryMapper`、`com.zhimian.model.entity.Category`、`com.zhimian.model.entity.QuestionTagName`、`com.zhimian.model.vo.QuestionListVO`、`org.springframework.beans.BeanUtils`、`java.util.*`)

【讲解】

- 这个方法**不加 `@Transactional`**:纯读操作,没有"多次写要么全成要么全败"的诉求,加了只是白占一个数据库连接的事务开销。任务 1.6 加、这里不加,对比着记——**事务不是 Service 方法的标配,是写操作原子性的工具**。
- `total == 0` 提前返回,一石二鸟:省一条 SQL + 保证空结果是 `[]` 不是 `null`(验收标准 ④)。
- `tagMap.computeIfAbsent(...)` 和任务 1.5 建分类树的分组是同一个模式;`getOrDefault(..., List.of())` 保证没标签的题目 `tags` 是空数组而不是 null——**对外的 JSON 里不要让集合字段出现 null**,前端少写一堆判空。
- 三条 SQL 的总量是**固定的**(COUNT、分页、标签 IN),不随 pageSize 变大而增多——这就是它和 N+1(每题查一次标签,10 题 10 条 SQL)的本质区别。

## 五、写完之后

发我代码 + 第 8 步 EXPLAIN 前后对比的截图(或文字记录),我会重点看:`<sql>` 片段是不是真的两边共用、`tagId` 的 JOIN 和 AND 两个 `<if>` 是否一致、空页提前返回、VO 里有没有把 answer 漏出去。review 通过后拷打预告:

1. `#{}` 和 `${}` 在 MyBatis 底层分别生成什么?为什么 PreparedStatement 能防注入?什么场景不得不用 `${}`,怎么把风险关住?
2. `LIMIT 100000, 10` 为什么慢?(从"扫了多少行、丢了多少行"说起)说出至少两种优化思路(游标/记住上一页最大 id、子查询先定位 id 再回表)。
3. EXPLAIN 结果里 type、key、rows、Extra 各代表什么?`Using filesort` 是什么意思,为什么 `(category_id, create_time)` 联合索引能消掉它?
4. 为什么列表的 categoryName/tags 用"分页主查询 + 内存组装"而不是一条大 JOIN?如果一题有 3 个标签,大 JOIN 方案的 `LIMIT 10` 会拿到什么?
5. 你的 COUNT 查询和分页查询共用了同一个 `<sql>` 条件片段。如果有人把 ORDER BY 也写进片段里会发生什么?(思考 COUNT 带 ORDER BY 的代价)
