## 一、这次到底在解决什么问题

到任务 2.4 为止,`interview_session`/`interview_message` 两张表已经在持续写入数据了,但项目里还没有一个接口能把这些数据**读出来给用户看**——用户没法知道自己之前面试过哪些场、聊了什么内容。这是这次任务的第一个目标:**会话列表 + 会话详情两个查询接口**。

第二个目标更重要,是这次任务真正的核心:**水平越权(Broken Object Level Authorization,OWASP API 安全榜单常年第一名)**。现在的 `chat` 接口里有这么一段:

```java
private InterviewSession mustFindSession(Long sessionId) {
    InterviewSession session = interviewSessionMapper.selectById(sessionId);
    if(session == null){
        throw new BusinessException(ErrorCode.NOT_FOUND,"面试会话不存在");
    }
    return session;
}
```

它只检查了"这个 id 对应的会话存不存在",**完全没有检查"这个会话是不是当前登录用户自己的"**。也就是说,只要你登录了(拥有一个合法 token),把请求里的 `sessionId` 换成任意一个别人的会话 id,一样能对着别人的面试记录发消息、看到 AI 的回复——**别人的私密面试对话对你完全透明**。这在真实项目里是一个能直接被安全审计打回来的严重漏洞,这次任务要把它堵上,而且是**每一个"按会话 id 操作"的入口都要堵**,不能只堵新加的接口、放过旧的。

## 三、分步实现

### Step 1:会话归属校验——这是这次任务最先要做的事

先改已经存在的 `mustFindSession`,让 `chat` 接口"顺带"就被修好,而不是留到最后:

```java
private InterviewSession mustFindOwnSession(Long sessionId) {
    InterviewSession session = interviewSessionMapper.selectById(sessionId);
    if (session == null || !session.getUserId().equals(UserContext.getUserId())) {
        throw new BusinessException(ErrorCode.NOT_FOUND, "面试会话不存在");
    }
    return session;
}
```

改动点逐个讲:

**为什么"会话不存在"和"会话存在但不是你的"要返回**同一个**错误(`NOT_FOUND`),而不是分开成"404 不存在"和"403 无权限"两种?** 这是刻意的选择,不是偷懒。如果对"不存在"和"不是你的"给出不同的错误提示,相当于给了攻击者一个**探测器**:他可以拿一堆随机 id 挨个试,凡是返回"无权限"的 id,就说明这个 id **确实存在**(只是不属于他)——这本身就是一种信息泄露,攻击者可以用这个方法探测出系统里合法数据的 id 分布。**对当前用户来说,"不属于我的资源"和"根本不存在的资源"应从外部看起来毫无区别**——这是安全设计里"不要泄露不必要的信息"这条原则的一个具体应用。

**方法名从 `mustFindSession` 改成 `mustFindOwnSession`**:命名要如实反映这个方法现在做的事——它不再只是"确保这个会话存在",而是"确保这个会话存在**且是我的**"。如果保留旧名字,以后有人看到 `mustFindSession` 这个名字,很容易以为它只做了"存在性"校验,从而在新写的接口里忘记再加一次归属校验——**命名本身也是一种文档,含糊的名字会误导后来的人(包括几个月后的你自己)**。

改完这一个方法,`chat` 里调用它的那一行不用变(还是 `mustFindSession(sessionId)` 改成 `mustFindOwnSession(sessionId)` 这一处调用点),但语义已经从"能看存不存在"变成了"确认是我的",**这个接口的越权漏洞就已经被堵上了**——这也是为什么要先做这一步:后面新增的 `finish`(下个任务)、详情查询,都会复用这同一个方法,一次修复,处处生效,不用每个新接口各写一遍校验逻辑。

### Step 2:会话列表——分页 + 按用户过滤

`InterviewSessionQueryDTO`,和你写过的 `QuestionQueryDTO` 是同一个套路:

```java
@Data
public class InterviewSessionQueryDTO {
    @Min(value = 1, message = "pageNum 最小为 1")
    private Integer pageNum = 1;
    @Min(value = 1, message = "pageSize 最小为 1")
    @Max(value = 50, message = "pageSize 最大为 50")
    private Integer pageSize = 10;

    public int getOffset() {
        return (pageNum - 1) * pageSize;
    }
}
```

**这里故意没有加 `categoryId`/`keyword` 这类过滤条件**——会话列表本来就是"我自己的全部记录",不像题库那样面向所有用户、需要精细筛选,保持这个 DTO 精简,不要照抄题库查询 DTO 的字段抄出一堆这次用不上的东西。

`InterviewSessionListVO`:

```java
@Data
public class InterviewSessionListVO {
    private Long id;
    private String direction;
    private String title;
    private Integer status;
    private LocalDateTime createTime;
    private LocalDateTime endTime;
}
```

**为什么列表项不包含消息内容?**——列表是"扫一眼有哪些场"的场景,每场面试可能有几十条消息,如果列表接口把每场的全部消息都带出来,一次分页查询的数据量会跟着"这一页里每场聊了多长"线性膨胀,是不必要的浪费。**消息内容留给详情接口按需加载**,这是列表页/详情页的标准分工,你在 `QuestionListVO`(不含 `answer` 全文)和 `QuestionDetailVO`(含 `answer`)里已经用过同一个思路。

Mapper 新增两个方法:

```java
long countByUserId(@Param("userId") Long userId);

List<InterviewSession> selectPageByUserId(@Param("userId") Long userId,
                                           @Param("offset") int offset,
                                           @Param("pageSize") int pageSize);
```

XML:

```xml
<select id="countByUserId" resultType="long">
    SELECT count(*)
    FROM interview_session
    WHERE user_id = #{userId} AND is_deleted = 0
</select>

<select id="selectPageByUserId" resultType="com.zhimian.model.entity.InterviewSession">
    SELECT id,user_id,direction,title,status,end_time,create_time,update_time,is_deleted
    FROM interview_session
    WHERE user_id = #{userId} AND is_deleted = 0
    ORDER BY create_time DESC
    LIMIT #{offset}, #{pageSize}
</select>
```

Service 方法(套路和 `QuestionServiceImpl.pageQuestions` 完全一致,先 `count`,`total==0` 直接短路返回空分页,再查这一页记录、转换成 VO):

```java
@Override
public PageResult<InterviewSessionListVO> listSessions(InterviewSessionQueryDTO dto) {
    Long userId = UserContext.getUserId();
    long total = interviewSessionMapper.countByUserId(userId);
    if (total == 0) {
        return PageResult.of(List.of(), 0, dto.getPageNum(), dto.getPageSize());
    }
    List<InterviewSession> records = interviewSessionMapper.selectPageByUserId(userId, dto.getOffset(), dto.getPageSize());
    List<InterviewSessionListVO> voList = new ArrayList<>();
    for (InterviewSession s : records) {
        InterviewSessionListVO vo = new InterviewSessionListVO();
        BeanUtils.copyProperties(s, vo);
        voList.add(vo);
    }
    return PageResult.of(voList, total, dto.getPageNum(), dto.getPageSize());
}
```

**这里没有额外的"补关联数据"步骤**(不像 `QuestionListVO` 还要查分类名、标签),`InterviewSession` 实体本身的字段和 `InterviewSessionListVO` 基本同名,`BeanUtils.copyProperties` 一步到位就够,不用手写每个字段。

Controller:

```java
@GetMapping
public Result<PageResult<InterviewSessionListVO>> list(@Valid InterviewSessionQueryDTO dto) {
    return Result.success(interviewService.listSessions(dto));
}
```

### Step 3:会话详情——校验归属 + 消息列表要过滤掉 system 角色

`InterviewMessageVO`:

```java
@Data
public class InterviewMessageVO {
    private String role;
    private String content;
    private LocalDateTime createTime;
}
```

`InterviewSessionDetailVO`:

```java
@Data
public class InterviewSessionDetailVO {
    private Long id;
    private String direction;
    private String title;
    private Integer status;
    private LocalDateTime createTime;
    private LocalDateTime endTime;
    private List<InterviewMessageVO> messages;
}
```

Service:

```java
@Override
public InterviewSessionDetailVO getSessionDetail(Long sessionId) {
    InterviewSession session = mustFindOwnSession(sessionId);
    List<InterviewMessage> history = interviewMessageMapper.selectBySessionId(sessionId);

    List<InterviewMessageVO> messageVOList = new ArrayList<>();
    for (InterviewMessage m : history) {
        if ("system".equals(m.getRole())) {
            continue;
        }
        InterviewMessageVO vo = new InterviewMessageVO();
        BeanUtils.copyProperties(m, vo);
        messageVOList.add(vo);
    }

    InterviewSessionDetailVO detail = new InterviewSessionDetailVO();
    BeanUtils.copyProperties(session, detail);
    detail.setMessages(messageVOList);
    return detail;
}
```

**为什么要把 `role=="system"` 的那条消息过滤掉,不返回给前端?** 这条消息是你写的"面试官人设"那段 prompt(第 6.2.3 篇文档讲过的 `buildSystemPrompt`),它是**说给模型听的内部指令**,不是这场对话里"人话"的一部分——用户从来没在界面上看到过这句话,把它混进消息列表返给前端,前端要么得知道"第一条永远要跳过"(隐性约定、容易漏),要么会把这段大段的 prompt 文字直接渲染出来当成一条"面试官说的话"展示给用户,体验上是错的。**"存了什么"和"该给外部看什么"是两回事**,这次的 system 消息就是一个"该存、但不该对外暴露"的典型例子,过滤这一步必须放在 Service 层做,不能指望前端自己判断。

**为什么这里用 `interviewMessageMapper.selectBySessionId` 直接查 MySQL,而不是走 `contextManager.load()`?** `contextManager.load()` 是专门为"喂给模型下一轮对话"这个场景设计的,里面有一步**按 token 预算裁剪**——那是"喂给模型"的裁剪,不是"展示给用户"的裁剪。用户查看自己的面试详情,理应看到**完整**的历史,不能因为这个会话聊得比较久、被裁掉了早期几轮,用户翻记录的时候就发现"怎么开头几句话不见了"。**同一份原始数据,面向"喂模型"和面向"给人看"这两个场景,该用的读取路径是不一样的**,不要图省事直接复用 `contextManager.load()`。

Controller:

```java
@GetMapping("/{id}")
public Result<InterviewSessionDetailVO> detail(@PathVariable Long id) {
    return Result.success(interviewService.getSessionDetail(id));
}
```

## 四、一个只提醒、这次不强制要求改代码的知识点:异步回调里不能读 `UserContext`

开发文档特意点名了这个坑,虽然**在当前代码结构下这个坑还没有真正被踩中**,但原理必须弄懂,因为你迟早会在需要往异步回调里塞"当前用户是谁"这类信息的场景里撞上它。

回忆一下 `chat` 方法流式实现里的 `onStreamComplete`:

```java
() -> onStreamComplete(emitter, sessionId, lockKey, fullReply.toString())
```

这个回调运行在**另一个线程**上(Spring AI/Reactor 的响应式调度线程),不是处理这次 HTTP 请求的原始 Tomcat 线程。`UserContext` 底层是 `ThreadLocal`——**它存的数据是"绑定在某一个具体线程上"的,不会跟着逻辑上的"这次请求"自动漂移到另一个线程去**。`onStreamComplete` 目前之所以没出问题,是因为它需要的 `sessionId`、`lockKey`、`fullReply` 全部是作为**普通方法参数**传进去的,在还处于原始线程的时候就已经准备好、"打包"进了这个闭包里,回调真正执行的时候根本不需要再去问 `UserContext`。

**如果以后你要在类似 `onStreamComplete`/`onStreamError` 这种异步回调里用到"当前用户是谁"(比如要记一个"操作人"字段),正确做法是:在进入 `.subscribe(...)` 之前,在还处于原始线程的时候先调用 `Long userId = UserContext.getUserId();` 存成一个局部变量,再把这个局部变量传进闭包里用。绝对不能在回调内部再调用一次 `UserContext.getUserId()`——那时候原始线程早就被 Tomcat 归还线程池去处理别的请求了,这个新线程的 `ThreadLocal` 里要么是 `null`,要么(更可怕的是线程池复用场景下)是**别的请求**残留下来的数据。** 这也是为什么 `JwtInterceptor.afterCompletion` 要在请求结束时清理 `ThreadLocal`(你在 6.1.4 那次任务学过的),但那只保证"同一个线程处理下一个新请求时是干净的",完全不能解决"当前这次请求内部,换了个线程执行回调"这个问题——这是两件不同的事,分别对应"线程复用"和"线程切换",这次先理解清楚后者。
