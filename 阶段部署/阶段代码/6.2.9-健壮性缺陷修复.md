## 二、逐条修复

### 修复 1:会话锁不能在流式期间提前过期

**问题时序**(为什么会炸):

```
t=0    用户发消息,setIfAbsent 拿到锁,TTL=60s,开始流式
t=60   模型还在吐字(长回答),但锁到 TTL 自动被 Redis 删掉了 ← 锁没了!
t=61   用户(或另一个标签页)又发一条,setIfAbsent 发现 key 不存在 → 又拿到锁 → 开第二条流
       现在同一个会话有两条流在并发跑,都往 fullReply、都往 interview_message 写
t=90   第一条流结束,onStreamComplete 里 delete(lockKey) ← 删掉的其实是第二条流刚抢的锁!
```

根子是:**锁的 TTL(60s)可能短于一次流式回答的真实时长**。`AiConfig` 里读超时就设了 60s,而一次长回答是多段 chunk 累加,总时长完全可能超过 60s。

**改法(最小可行):把锁 TTL 拉到安全覆盖最长流式时长之上。**

`InterviewServiceImpl` 顶部常量:

```java
// 原来
private static final long LOCK_TTL_SECONDS = 60;
// 改成:安全覆盖单轮最长流式回答(留足余量),避免锁在流式中途过期
private static final long LOCK_TTL_SECONDS = 300;
```

**为什么这样够用**:正常情况下锁一定会被四条结束路径之一主动释放(`onStreamComplete`/`onStreamError`/`emitter.onTimeout`/`emitter.onError`),TTL 只是"进程硬崩溃、四条路径都没跑到"时的兜底。把 TTL 从 60s 提到 300s,代价仅仅是"极端硬崩溃时,这把锁最多多占 5 分钟"——而换来的是"正常长回答期间锁绝不会中途失效"。这是一个划算的取舍。

**进阶(讲得出即可,不强制写)**:更严谨的做法是给锁加**所有权校验**——加锁时 value 存一个唯一值(UUID),释放时用 Lua 脚本"value 相等才删",这样即便锁真的过期了、被别人重新持有,你也不会误删别人的锁。这和任务 1.9 详情缓存击穿锁"释放前要校验是不是自己加的"是**同一个考点**。本项目并发量小,先用"拉长 TTL"这个务实方案,但你要能说出"生产级正确解法是 唯一 value + Lua 原子比对删除"。

> 顺手:`chat` 里 catch 块那条注释还写着"要等 60 秒 TTL 到期",TTL 改成 300 后这句话就过时了(会让人低估卡死窗口 5 倍),把注释里的"60 秒"改成"300 秒"。**改常量别忘了改依赖这个常量的注释**——注释和代码不一致比没注释更坑人。

### 修复 2:模型漏给 score 时,不能让它裸奔到 NOT NULL 约束

**问题**:模型返回的报告 JSON 可能**缺字段**,而 `InterviewReportResult` 的字段全是包装类型/对象(`Integer score`、`List highlights`…),缺了就是 null。这有**两条**崩溃路径,而且都发生在 `generateReportWithRetry` **之外**、不被重试捕获,直接 500 且状态卡在 1:

- `score` 为 null → `report.setScore(null)` 插 `interview_report`(`score INT NOT NULL`)抛 `DataIntegrityViolation`;
- `highlights`/`weaknesses`/`summary` 任一为 null → `serializeReportContent` 里的 `Map.of("highlights", null, …)` **直接抛 NPE**(`Map.of` 不允许 null 值)。

**所以校验不能只看 score,四个字段都要非空。改法:把"报告完整性校验"当成解析的一部分,放进 `generateReportWithRetry` 的 try 里。** 这样任一字段缺失都被当作"这次解析失败",自动触发重试;两次都失败走原有兜底抛 `AI_SERVICE_ERROR`(50001),而不是 500。

```java
private InterviewReportResult generateReportWithRetry(String transcript) {
    for (int attempt = 1; attempt <= 2; attempt++) {
        try {
            InterviewReportResult result = chatClient.prompt()
                    .system(buildJudgePrompt())
                    .user(transcript)
                    .call()
                    .entity(InterviewReportResult.class);
            // 模型可能返回缺字段的 JSON:score 为 null 撞库里 NOT NULL,
            // highlights/weaknesses/summary 为 null 会让后面 serializeReportContent 的 Map.of 抛 NPE。
            // 四个字段任一为空,都当成"这次没解析出合法报告",抛出去触发重试,而不是等到落库才 500。
            if (result == null
                    || result.score() == null
                    || result.highlights() == null
                    || result.weaknesses() == null
                    || result.summary() == null) {
                throw new IllegalStateException("模型返回的报告字段不完整");
            }
            return result;
        } catch (Exception e) {
            log.warn("评价报告生成第{}次尝试失败", attempt, e);
        }
    }
    throw new BusinessException(ErrorCode.AI_SERVICE_ERROR, "评价报告生成失败，请稍后再试");
}
```

改动就是中间那个**四字段非空**的 `if`。**关键在位置**:它必须在 `try` 内、`return` 前——让"报告不完整"和"网络失败/JSON 解析失败"走同一条重试+兜底通道,统一收敛成 50001。

### 修复 3 + 4 + 5:重写 `finishInterview` 的收尾逻辑

这三条都在 `finishInterview` 里,一次性改完。先看**完整的改后版本**,再逐条讲每一处在修什么:

```java
@Override
public InterviewReportVO finishInterview(Long sessionId) {
    InterviewSession session = mustFindOwnSession(sessionId);
    // 幂等短路:已评价直接返回已有报告(放在抢锁之前,省一次 Redis 往返)
    if (session.getStatus() == 2) {
        InterviewReport report = interviewReportMapper.selectBySessionId(sessionId);
        // 【修复 5】status=2 却查不到报告 = 数据不一致(比如被手工删了),别让 toReportVO(null) NPE
        if (report == null) {
            throw new BusinessException(ErrorCode.SYSTEM_ERROR, "报告数据异常，请联系管理员");
        }
        return toReportVO(report);
    }

    String lockKey = LOCK_PREFIX + sessionId;
    Boolean locked = stringRedisTemplate.opsForValue().setIfAbsent(lockKey, "1", LOCK_TTL_SECONDS, TimeUnit.SECONDS);
    if (!Boolean.TRUE.equals(locked)) {
        throw new BusinessException(ErrorCode.TOO_MANY_REQUESTS, "会话正在处理中，请稍后再试");
    }
    try {
        // 【修复 3】崩溃恢复兜底:上一次可能已经把报告插进库了,只是没来得及把状态推到 2(进程中断)。
        // 这时报告行已存在,绝不能再 insert 一次(会撞 uk_session_id 唯一键 → 500,导致会话永远结束不了)。
        // 直接补上状态、返回已有报告。
        InterviewReport existing = interviewReportMapper.selectBySessionId(sessionId);
        if (existing != null) {
            interviewSessionMapper.updateStatus(sessionId, 2);
            return toReportVO(existing);
        }

        // 先把"已结束"落实(0→1),再调模型——模型失败状态也停在 1,不会出现"点了结束还能聊"
        if (session.getStatus() == 0) {
            interviewSessionMapper.updateStatus(sessionId, 1);
        }
        List<InterviewMessage> history = interviewMessageMapper.selectBySessionId(sessionId);
        InterviewReportResult result = generateReportWithRetry(buildTranscript(history));

        InterviewReport report = new InterviewReport();
        report.setSessionId(sessionId);
        report.setScore(result.score());
        report.setContent(serializeReportContent(result));
        interviewReportMapper.insert(report);
        interviewSessionMapper.updateStatus(sessionId, 2);

        // 【修复 4】从库里回读一次,拿到 DB 生成的 create_time。
        // 直接 toReportVO(report) 的话,内存里的 report.createTime 是 null(insert 没回读),
        // 前端首次看到的报告时间是"—",二次查看(走上面 status==2 分支)又有值,前后不一致。
        return toReportVO(interviewReportMapper.selectBySessionId(sessionId));
    } finally {
        stringRedisTemplate.delete(lockKey);
    }
}
```

逐条对照:

- **【修复 3】崩溃恢复**:进锁后、生成报告前,先查一次"这个会话是不是已经有报告了"。有,就说明上次生成成功了但状态没推到 2(进程在两步之间挂了),直接补状态 + 返回,**不再重新生成、不再 insert**。没有这一步,卡在 status=1 的会话每次 finish 都会重新生成再 insert,撞唯一键 500,永远结束不了。这就是"幂等的业务判断"要覆盖的**第二个场景**(第一个是 status==2 的正常重复点击)——**唯一索引是最后的兜底,但你不能真让它被撞到**,业务层要主动避开。
- **【修复 4】回读 create_time**:结尾从 `toReportVO(report)` 改成 `toReportVO(interviewReportMapper.selectBySessionId(sessionId))`。原因:`insert` 只写了 session_id/score/content,`create_time` 是数据库 `DEFAULT CURRENT_TIMESTAMP` 生成的,**不会自动回填到内存的 `report` 对象**。回读一次,保证首次返回和以后查看拿到的是同一个时间。
- **【修复 5】status==2 空值防护**:短路分支里 `selectBySessionId` 可能返回 null(数据被手工删等),加一个判空抛业务异常,别让 `toReportVO(null)` 空指针成 500。

### 修复 6:让 chat 的消息落库在「成功/失败」两条路径上都自洽(且永不卡死前端)

**问题时序**:

```
chat() 里:
  1. insert userMsg(用户这轮提问落库)
  2. contextManager.append(userMsg)(进 Redis 上下文)
  3. 订阅模型流……结果 onStreamError(模型挂了,没有 assistant 回复)
下一轮 chat():
  contextManager.load() 拿到的历史,最后一条是那条「孤儿 user 消息」,
  再 springAiMessages.add(new UserMessage(本轮内容)) → 模型收到【两条连续的 user 消息】
  → 模型分不清、回答质量下降
```

根子:**用户消息在"AI 是否成功回复"还不知道的时候,就抢先落库了**。正确做法是:**等这一轮真的成功拿到完整回复,再把"用户提问 + AI 回复"两条一起落库、一起进上下文**——要么都写、要么都不写,保持成对。

**第一步**:改 `chat` 方法里的 try 块。删掉"提前 insert/append userMsg"那几行,只保留"把本轮 user 内容拼进这次请求的消息列表"(那个是内存的,给模型用,必须留):

```java
try {
    List<InterviewMessage> history = contextManager.load(sessionId);

    // 注意:这里不再提前把 userMsg 落库 / append 到上下文。
    // 只把本轮内容拼进「这次请求要发给模型的消息列表」(内存,给模型用),
    // 真正落库延后到流式成功的 onStreamComplete 里,和 AI 回复一起写。
    List<Message> springAiMessages = toSpringAiMessages(history);
    springAiMessages.add(new UserMessage(dto.getContent()));

    // 给一个「有限」超时(不再用 0L 无限等):万一模型流卡死既不吐字也不报错,
    // 到点会触发 onTimeout 把订阅 dispose、把锁放掉,而不是干等到 300s 锁 TTL 过期后被人开第二条流。
    SseEmitter emitter = new SseEmitter(TimeUnit.MINUTES.toMillis(5));
    StringBuilder fullReply = new StringBuilder();
    String userContent = dto.getContent();   // 传给回调,避免回调里再碰请求对象

    Disposable subscription = chatClient.prompt(new Prompt(springAiMessages))
            .stream()
            .content()
            .doOnNext(fullReply::append)
            .subscribe(
                    delta -> sendEvent(emitter, Map.of("type", "delta", "content", delta)),
                    // 失败回调也要拿到 userContent 和「到目前为止吐出的半截回复」,好把已展示的内容落库(见第二步)
                    error -> onStreamError(emitter, sessionId, lockKey, userContent, fullReply.toString(), error),
                    () -> onStreamComplete(emitter, sessionId, lockKey, userContent, fullReply.toString())
            );
    // onTimeout / onError 保持不变
    ...
```

改动点:① 删掉原来的 `InterviewMessage userMsg = buildMessage(...); interviewMessageMapper.insert(userMsg); contextManager.append(sessionId, userMsg);` 三行;② `SseEmitter(0L)` 改成有限超时;③ `onStreamComplete` 和 `onStreamError` 都多传 `userContent` +(error 那条还要)`fullReply.toString()`。

> 注意 `fullReply.toString()` 写在 lambda 里:lambda 是**回调真正触发时**才求值的,所以 error 回调拿到的是"失败那一刻已经累加的半截内容",complete 回调拿到的是全文——不是订阅时的空串。

**第二步**:抽一个"成对落库"的私有助手,`complete` 和 `error` 两条路径都用它——这样落库逻辑只有一份:

```java
// 把「用户提问 + AI 回复」成对落库 + 进上下文。返回 assistant 消息(拿 id 发 done)。
// user 先 insert、assistant 后 insert,id 自增保证历史里先后顺序正确。
private InterviewMessage persistTurn(Long sessionId, String userContent, String reply) {
    InterviewMessage userMsg = buildMessage(sessionId, "user", userContent);
    interviewMessageMapper.insert(userMsg);
    contextManager.append(sessionId, userMsg);

    InterviewMessage assistantMsg = buildMessage(sessionId, "assistant", reply);
    interviewMessageMapper.insert(assistantMsg);
    contextManager.append(sessionId, assistantMsg);
    return assistantMsg;
}
```

**第三步**:`onStreamComplete` 用它落库,并且**无论落库成没成功,都必须把流关掉**(发 done 或发 error),否则前端 `reader` 永远等不到终止事件,UI 卡在"考官思考中":

```java
private void onStreamComplete(SseEmitter emitter, Long sessionId, String lockKey, String userContent, String fullReply) {
    try {
        InterviewMessage assistantMsg = persistTurn(sessionId, userContent, fullReply);
        sendEvent(emitter, Map.of("type", "done", "messageId", assistantMsg.getId()));
        emitter.complete();
    } catch (Exception e) {
        // 落库失败(比如 DB 瞬时不可用)也要把流「关掉」并告诉前端出错,
        // 不然 emitter 既不 complete 也不发 error,前端 await reader.read() 永远挂着
        log.error("流式完成后落库失败:sessionId={}", sessionId, e);
        sendEvent(emitter, Map.of("type", "error", "message", "回复保存失败，请重试"));
        emitter.completeWithError(e);
    } finally {
        stringRedisTemplate.delete(lockKey);
    }
}
```

**第四步**:`onStreamError` 也要改——它现在要拿到 `userContent`/`fullReply`,并且**如果已经吐了半截,就把这半截也成对落库**,让"前端看到的"和"后端记得的"保持一致:

```java
private void onStreamError(SseEmitter emitter, Long sessionId, String lockKey,
                           String userContent, String fullReply, Throwable error) {
    log.error("AI 流式调用失败", error);
    try {
        // 中途失败但已经吐了半截:前端会保留这半截气泡(它的 onError 只在"一个字都没收到"时才删气泡),
        // 所以后端也要把「用户这轮 + 这半截回复」存下来,否则下一轮 contextManager.load 里没有这段,
        // 模型就"忘了"用户屏幕上还看得见的内容。一个字都没吐(fullReply 空)就什么都不写——
        // 前端那边也会把空气泡删掉、把用户消息标失败,两边一致。
        if (!fullReply.isEmpty()) {
            persistTurn(sessionId, userContent, fullReply);
        }
    } catch (Exception e) {
        log.error("流式失败后落库也失败:sessionId={}", sessionId, e);
    } finally {
        sendEvent(emitter, Map.of("type", "error", "message", "AI服务异常，请稍后重试"));
        emitter.completeWithError(error);
        stringRedisTemplate.delete(lockKey);
    }
}
```

**为什么这版才是完整的**:把"落库时机延后到终止"解决了孤儿 user 消息,但它引入两个新缺口,这一步一并堵上——

1. **半截回复丢失**:delta 吐了几个字后 error,前端保留了半截气泡,但后端如果什么都不写,下一轮模型就丢了用户屏幕上还看得见的上下文。解法:error 时若 `fullReply` 非空,也 `persistTurn`。判据是"**后端存的必须等于前端展示的**"——前端保留半截 → 后端也存半截;前端删空气泡 → 后端也不存。
2. **落库失败卡死前端**:落库在响应式回调里,一旦 insert 抛异常,若不显式 `completeWithError`,emitter 永远不终止,前端 `reader` 死等。解法:`onStreamComplete` 用 try/catch 包住,失败也发 error 帧 + `completeWithError`。**每一条终止路径都必须保证 emitter 被关闭**——这是写 SSE 的铁律。

> 小提醒:这些回调都跑在**响应式回调线程**(不是原始 Tomcat 线程),但用到的 `sessionId`/`userContent`/`fullReply` 全是**参数传进来的**,没碰 `UserContext`/ThreadLocal,所以没有任务 2.5 讲的"异步回调读 ThreadLocal 拿到 null"问题——这也是当初把这些值设计成参数传入的原因。

### 附:限流位置(判断题,可以不改)

code review 还提到一点:`chat` 里限流 `tryAcquire` 放在抢会话锁**之前**,如果会话锁没抢到(上一轮还在处理)就抛异常返回,但那个 10s 的限流冷却 key 已经落下去了——用户没真正触发 AI 调用,却被冷却了 10s。

这是我在任务 2.7 设计时的**有意取舍**:"锁忙"和"限流"都表示"稍等再来",冷却照走可以接受。**倾向维持现状,不改**。如果你觉得体验上要更干净,可以把限流挪到抢锁**之后**——但那样"会话锁竞争"这条路径就不受每用户频率保护了,是另一种取舍。你想清楚哪种更合理,能讲出理由就行,这条不算 bug。

### 修复 7:finish 时补上 `end_time`(小完整性缺口)

`interview_session` 表有一列 `end_time`(注释"结束时间"),但 `finishInterview` 只调了 `updateStatus(sessionId, 2)`,**从来没写过 end_time**,所以每场结束的会话这列永远是 NULL,列表/详情里的"结束时间"永远空着。

给 Mapper 加一个专门的"结束"方法(把状态和结束时间一起写),而不是复用通用的 `updateStatus`:

```java
// InterviewSessionMapper.java
void finishSession(@Param("id") Long id);
```

```xml
<!-- InterviewSessionMapper.xml -->
<update id="finishSession">
    UPDATE interview_session
    SET status = 2, end_time = NOW()
    WHERE id = #{id} AND is_deleted = 0
</update>
```

然后把 `finishInterview` 里**两处** `interviewSessionMapper.updateStatus(sessionId, 2)`(正常生成成功那处、以及修复 3 的 `existing != null` 恢复那处)都换成 `interviewSessionMapper.finishSession(sessionId)`。注意 0→1 那处仍然用 `updateStatus`(1 不是"结束"、不该写 end_time)。
