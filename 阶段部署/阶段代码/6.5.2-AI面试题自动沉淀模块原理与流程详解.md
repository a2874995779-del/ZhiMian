# 6.5.2 AI 面试题自动沉淀模块原理与流程详解

> 配套文档：6.5.1-AI面试题自动沉淀与去重实现指南.md
>
> 这份文档不以“把代码复制进去”为目标，而是解释这套功能为什么要这样设计、每段代码在整个链路中负责什么、它解决了什么问题，以及你在运行和调试时应该如何思考。

---

## 一、先明确这个模块要解决什么问题

智面目前有两类题目来源：

1. 管理员手动录入的正式题库。
2. AI 面试过程中动态产生的问题。

AI 面试中的问题很有价值，因为它们是根据面试方向和候选人回答动态生成的。但 AI 生成的内容不能直接写进正式题库，原因有很多：

- AI 的一句回复里可能同时包含点评、提示和下一道题。
- AI 可能重复询问已经存在的题目。
- AI 生成的题目可能不完整，或者依赖上文才能理解。
- AI 能生成题目，但不一定能准确选择系统里的分类和标签。
- AI 生成的参考答案可能需要人工修正。
- 多个面试会话可能在同一时间生成相同问题。

因此，这个模块的核心不是“调用一次 AI”，而是建立一条可靠的数据流水线：

~~~text
AI 产生问题
    ↓
从完整回复中提取问题
    ↓
把问题标准化
    ↓
计算唯一指纹
    ↓
使用数据库唯一索引并发去重
    ↓
写入候选题表
    ↓
异步调用 AI 补全答案、难度、分类、标签
    ↓
管理员审核
    ↓
写入正式题库
~~~

最终目标是：

~~~text
聊天体验不被影响
题目不会因为并发重复写入
不可靠的 AI 内容不会直接污染正式题库
管理员可以修改后再收录
所有阶段都可以追踪和排查
~~~

## 二、整体架构：每一层负责什么

这不是一个类完成的功能，而是多个层次共同完成的。

| 层次 | 当前项目中的类或文件 | 主要职责 |
| --- | --- | --- |
| AI 对话层 | InterviewServiceImpl | 接收用户回答、请求 AI、保存 AI 回复 |
| 文本提取层 | AiQuestionExtractor | 从 AI 完整回复中提取“下一题” |
| 调度层 | AiQuestionCollectDispatcher | 把收集任务提交到独立线程池 |
| 业务收集层 | AiQuestionCollectorServiceImpl | 标准化、判断重复、插入候选题、调用 AI 补全 |
| 标准化层 | QuestionTextNormalizer | 统一题目文本并生成 SHA-256 指纹 |
| 持久化层 | AiQuestionCandidateMapper 和 XML | 执行候选题的插入、更新、分页和状态变更 |
| 数据库层 | ai_question_candidate | 保存候选题、唯一去重、记录状态 |
| 审核层 | AiQuestionCandidateController | 提供管理员分页、通过、忽略接口 |
| 正式题库层 | QuestionServiceImpl | 创建正式题目和题目标签关系 |

可以把它理解成一条工厂流水线：

~~~text
InterviewServiceImpl
        │ 只负责触发
        ▼
AiQuestionCollectDispatcher
        │ 只负责排队
        ▼
AiQuestionCollectorServiceImpl
        │ 负责业务判断和 AI 补全
        ▼
AiQuestionCandidateMapper
        │ 负责 SQL
        ▼
ai_question_candidate
        │ 管理员审核
        ▼
QuestionServiceImpl
        │ 正式入库
        ▼
question + question_tag
~~~

这里有一个重要的设计原则：每个类只做自己擅长的事。

- AiQuestionExtractor 不应该访问数据库。
- AiQuestionCollectorServiceImpl 不应该负责发送 SSE。
- Mapper 不应该调用 AI。
- Controller 不应该直接拼 SQL。
- QuestionServiceImpl 不应该知道题目来自 AI 还是管理员。

这样做的好处是：每一层都容易测试，出问题时也容易定位。

## 三、一次题目从产生到入库的完整流程

先用一个真实例子理解全链路。

用户在一次 Java 并发面试中回答：

~~~text
线程池可以复用线程，减少线程创建和销毁的开销。
~~~

AI 返回：

~~~text
你的回答说明了线程池的基本价值，还可以继续补充任务队列和拒绝策略。

【下一题】
ThreadPoolExecutor 的核心参数有哪些？
~~~

### 3.1 AI 流式输出

InterviewServiceImpl.chat 调用 Spring AI：

~~~java
chatClient.prompt(new Prompt(springAiMessages))
        .stream()
        .content()
        .doOnNext(fullReply::append)
        .subscribe(
                delta -> sendEvent(emitter, Map.of(
                        "type", "delta",
                        "content", delta
                )),
                error -> onStreamError(...),
                () -> onStreamComplete(...)
        );
~~~

这里有两个并行发生的事情：

1. 每个文本片段通过 SSE 发给前端。
2. 每个文本片段追加到 fullReply，用于最终保存完整回复。

假设 AI 分三次返回：

~~~text
第 1 次：你的回答说明了线程池的基本价值，
第 2 次：还可以继续补充任务队列和拒绝策略。\n\n【下一题】\n
第 3 次：ThreadPoolExecutor 的核心参数有哪些？
~~~

经过：

~~~java
0.doOnNext(fullReply::append)
~~~

最终的 fullReply 是完整字符串。

### 3.2 回复完成后保存消息

只有流正常结束，才进入：

~~~java
onStreamComplete(...)
~~~

在这里调用：

~~~java
InterviewMessage assistantMsg = persistTurn(
        sessionId,
        userContent,
        fullReply
);
~~~

persistTurn 做两件事：

~~~text
保存 user 消息
保存 assistant 消息
把两条消息加入上下文缓存
~~~

保存 assistant 消息后，数据库会生成一个真实的消息 id：

~~~java
assistantMsg.getId()
~~~

这个 id 后面非常重要，因为候选题表要记录：

~~~text
这道题是由哪一条 assistant 消息产生的
~~~

### 3.3 提取下一题

~~~java
aiQuestionExtractor.extract(fullReply)
        .ifPresent(question -> questionCollectDispatcher.dispatch(
                sessionId,
                assistantMsg.getId(),
                direction,
                question
        ));
~~~

如果提取成功，得到：

~~~text
ThreadPoolExecutor 的核心参数有哪些？
~~~

如果 AI 没有输出标记，或者标记后没有有效内容，Optional.empty() 不会执行 ifPresent 里的代码。

### 3.4 异步提交收集任务

dispatch 不直接调用收集业务，而是提交到线程池：

~~~java
questionCollectExecutor.execute(() -> collectorService.collect(
        sessionId,
        assistantMessageId,
        direction,
        question
));
~~~

此时聊天请求可以立即结束，用户不需要等待：

~~~text
AI 回复保存完成
    ↓
发送 SSE done
    ↓
前端结束 loading

后台线程继续：
    ↓
去重
    ↓
调用 AI 补全候选题
~~~

### 3.5 进入候选题表

收集线程执行 collectorService.collect，它会依次完成：

~~~text
校验问题
    ↓
检查 source_message_id 是否处理过
    ↓
标准化题目
    ↓
生成 fingerprint
    ↓
检查正式题库
    ↓
INSERT IGNORE 候选题
    ↓
只有真正插入成功的线程才调用 AI 补全
~~~

### 3.6 管理员审核

AI 补全成功后，候选题状态从：

~~~text
0 补全中
~~~

变成：

~~~text
1 待审核
~~~

管理员可以调用：

~~~text
GET /api/admin/ai-question-candidates
PUT /api/admin/ai-question-candidates/{id}/approve
PUT /api/admin/ai-question-candidates/{id}/ignore
~~~

管理员可以修改 AI 生成的内容，然后通过审核接口写入：

~~~text
question
question_tag
~~~

## 四、为什么要修改 AI Prompt

### 4.1 机器必须有稳定的边界

如果 Prompt 只写：

~~~text
请继续进行面试。
~~~

AI 可能输出：

~~~text
你的回答不错。你还可以考虑缓存一致性。接下来我们聊聊 JVM，也可以顺便说一下垃圾回收器和类加载机制。
~~~

程序无法稳定判断：

- 哪一段是点评？
- 哪一段是问题？
- 这是一个问题还是三个问题？
- “接下来我们聊聊 JVM”是否算正式题目？

所以需要给 AI 一个机器可识别的协议：

~~~text
每次回复可以先简短点评候选人的回答，但最后必须使用下面的固定格式提出下一题：

【下一题】
这里写一个完整、脱离上下文也能理解的问题

“【下一题】”后只能出现一道题。
~~~

这相当于约定了一种简单的文本协议。

### 4.2 Prompt 不是绝对可靠的接口

AI 可能仍然出现：

~~~text
[下一题]
~~~

或者：

~~~text
【下一题】：什么是 JVM？
~~~

甚至：

~~~text
【下一题】
1. 什么是 JVM？
~~~

所以程序仍然需要校验和清理。Prompt 负责提高格式稳定性，Java 代码负责最后的防御。

这体现了一个重要思想：

~~~text
Prompt 是软约束，代码和数据库约束才是硬约束。
~~~

## 五、AiQuestionExtractor 如何提取题目

对应实现文件：

~~~text
src/main/java/com/zhimian/util/AiQuestionExtractor.java
~~~

### 5.1 完整代码

~~~java
package com.zhimian.util;

import org.springframework.stereotype.Component;
import org.springframework.util.StringUtils;

import java.util.Optional;

@Component
public class AiQuestionExtractor {

    public static final String QUESTION_MARKER = "【下一题】";

    public Optional<String> extract(String assistantReply) {
        if (!StringUtils.hasText(assistantReply)) {
            return Optional.empty();
        }

        int markerIndex = assistantReply.lastIndexOf(QUESTION_MARKER);
        if (markerIndex < 0) {
            return Optional.empty();
        }

        String afterMarker = assistantReply
                .substring(markerIndex + QUESTION_MARKER.length())
                .strip();

        if (!StringUtils.hasText(afterMarker)) {
            return Optional.empty();
        }

        String firstLine = afterMarker.lines()
                .map(String::strip)
                .filter(StringUtils::hasText)
                .findFirst()
                .orElse("");

        String question = firstLine
                .replaceFirst("^[-*]+\\s*", "")
                .strip();

        if (question.length() < 4 || question.length() > 256) {
            return Optional.empty();
        }

        return Optional.of(question);
    }
}
~~~

### 5.2 为什么它是一个独立工具类

提取题目是一个纯文本问题，不需要数据库、Redis、AI 客户端、当前用户或 HTTP 请求。

因此它可以独立出来：

~~~java
@Component
public class AiQuestionExtractor {
    public Optional<String> extract(String assistantReply) {
        // 只处理字符串
    }
}
~~~

这样可以直接写单元测试，不需要启动完整 Spring 应用：

~~~java
AiQuestionExtractor extractor = new AiQuestionExtractor();

Optional<String> result = extractor.extract(
        "点评内容\n\n【下一题】\n什么是 JVM？"
);
~~~

### 5.3 空文本判断

~~~java
if (!StringUtils.hasText(assistantReply)) {
    return Optional.empty();
}
~~~

StringUtils.hasText 不只是判断 null 和空字符串，还会排除只包含空格、换行、制表符的内容。

它比下面的写法更完整：

~~~java
if (assistantReply == null || assistantReply.isEmpty()) {
}
~~~

因为下面这个值：

~~~text
"   \n\t"
~~~

虽然 isEmpty() 返回 false，但实际上没有有效文字。

### 5.4 lastIndexOf 的含义

~~~java
int markerIndex = assistantReply.lastIndexOf(QUESTION_MARKER);
~~~

lastIndexOf 返回最后一次出现的位置。没有找到时返回 -1。

为什么选择最后一个标记？因为点评内容可能引用“下一题”：

~~~text
你刚才对下一题的预测不太准确。

【下一题】
什么是 JVM 的垃圾回收？
~~~

真正的题目应该从最后一个标记之后开始。

### 5.5 substring 的下标计算

~~~java
String afterMarker = assistantReply
        .substring(markerIndex + QUESTION_MARKER.length())
        .strip();
~~~

假设：

~~~text
【下一题】什么是 JVM？
~~~

标记从下标 0 开始，标记长度为 5。substring(0 + 5) 会从标记结束位置开始截取：

~~~text
什么是 JVM？
~~~

如果误写成：

~~~java
substring(markerIndex)
~~~

结果会包含标记本身。

strip 用来清除开头和结尾的空白字符。

### 5.6 Stream 代码逐段理解

~~~java
String firstLine = afterMarker.lines()
        .map(String::strip)
        .filter(StringUtils::hasText)
        .findFirst()
        .orElse("");
~~~

这段代码等价于下面更容易理解的普通写法：

~~~java
String firstLine = "";

for (String line : afterMarker.split("\\R")) {
    String cleanedLine = line.strip();
    if (StringUtils.hasText(cleanedLine)) {
        firstLine = cleanedLine;
        break;
    }
}
~~~

Stream 写法的每一部分含义：

~~~java
afterMarker.lines()
~~~

把字符串变成一个按行处理的 Stream。

~~~java
.map(String::strip)
~~~

对每一行执行 strip。它等价于：

~~~java
.map(line -> line.strip())
~~~

~~~java
.filter(StringUtils::hasText)
~~~

过滤空行。它等价于：

~~~java
.filter(line -> StringUtils.hasText(line))
~~~

~~~java
.findFirst()
~~~

找到第一行有效内容后停止。

~~~java
.orElse("")
~~~

如果没有有效内容，就使用空字符串作为默认值。

### 5.7 正则表达式清理列表符号

~~~java
String question = firstLine
        .replaceFirst("^[-*]+\\s*", "")
        .strip();
~~~

正则表达式是：

~~~text
^[-*]+\s*
~~~

| 部分 | 含义 |
| --- | --- |
| ^ | 必须从字符串开头匹配 |
| [-*] | 匹配 - 或 * |
| + | 前面的字符出现一次或多次 |
| \s* | 匹配零个或多个空白字符 |

因此：

~~~text
- 什么是 JVM？
~~~

会变成：

~~~text
什么是 JVM？
~~~

而：

~~~text
1. 什么是 JVM？
~~~

不会被这条正则清理，因为它没有处理数字和句点。

### 5.8 为什么返回 Optional

不推荐这样写：

~~~java
public String extract(String reply) {
    if (没有找到) {
        return null;
    }
    return question;
}
~~~

调用方很容易忘记判断 null。使用 Optional 后，调用方更自然地表达“有值才执行”：

~~~java
extractor.extract(reply).ifPresent(question ->
        dispatcher.dispatch(sessionId, messageId, direction, question)
);
~~~

Optional 适合表示“可能没有结果”，但不应该把它用于所有实体字段或数据库字段。

## 六、为什么只能在流成功完成后收集

InterviewServiceImpl 中有三个重要回调：

~~~java
error -> onStreamError(...)
~~~

~~~java
() -> onStreamComplete(...)
~~~

以及连接层面的：

~~~java
emitter.onTimeout(...)
emitter.onError(...)
~~~

### 6.1 成功回调中的内容是完整回复

~~~java
private void onStreamComplete(...) {
    InterviewMessage assistantMsg = persistTurn(
            sessionId,
            userContent,
            fullReply
    );

    aiQuestionExtractor.extract(fullReply)
            .ifPresent(question ->
                    questionCollectDispatcher.dispatch(
                            sessionId,
                            assistantMsg.getId(),
                            direction,
                            question
                    )
            );
}
~~~

此时 fullReply 已经收到了 AI 的全部内容。

### 6.2 失败回调里的内容可能是半截文本

模型流可能输出到一半就失败：

~~~text
你的回答基本正确，不过还需要考虑
~~~

如果此时收集题目，就可能把不完整文本当成问题。

所以失败路径只负责保存已经输出的半截内容，不负责自动收集：

~~~java
if (!fullReply.isEmpty()) {
    persistTurn(sessionId, userContent, fullReply);
}
~~~

### 6.3 保存消息后再 dispatch

正确顺序：

~~~java
InterviewMessage assistantMsg = persistTurn(...);

questionCollectDispatcher.dispatch(
        sessionId,
        assistantMsg.getId(),
        direction,
        question
);
~~~

不能在 insert 之前 dispatch，因为异步任务需要真实的 assistantMessageId。

source_message_id 是幂等控制的重要字段。没有真实消息 id，就无法准确判断同一条回复是否被重复处理。

### 6.4 为什么 done 事件可以先于候选题完成

候选题补全包含一次新的 AI 调用，可能耗时数秒，甚至失败。它不应该阻塞面试聊天。

正确时间顺序：

~~~text
保存 assistant 消息
    ↓
提交收集任务到线程池
    ↓
发送 done 事件
    ↓
SSE 结束

后台线程：
    ↓
写候选题
    ↓
调用补全 AI
    ↓
更新 status
~~~

浏览器收到 done 时，候选题可能还在补全中，这是异步设计的正常表现。

## 七、为什么必须使用独立线程池

### 7.1 线程池解决什么问题

如果每次收集题目都直接新建线程：

~~~java
new Thread(() -> collectorService.collect(...)).start();
~~~

大量面试并发时会产生：

- 线程创建和销毁成本。
- 没有统一的最大线程数。
- 没有任务队列上限。
- 应用关闭时不容易统一管理。
- 异常和拒绝行为不容易观察。

线程池把“任务提交”和“线程执行”分开：

~~~text
业务代码提交 Runnable
    ↓
线程池决定立即执行、排队或拒绝
    ↓
工作线程执行任务
~~~

### 7.2 为什么不能复用报告线程池

当前项目已经有 reportExecutor，用于异步生成面试报告。报告生成和候选题收集是两种不同的后台任务：

| 任务 | 特点 |
| --- | --- |
| 报告生成 | 一场面试结束后执行，数量相对有限 |
| 题目收集 | 每轮 AI 回复都可能执行，频率更高 |

如果共用一个线程池，候选题任务突然增多，可能占满报告线程，导致报告生成延迟。

因此增加独立 Bean：

~~~java
@Bean("questionCollectExecutor")
public Executor questionCollectExecutor() {
    return new ThreadPoolExecutor(
            1,
            2,
            60,
            TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(100),
            runnable -> {
                Thread thread = new Thread(runnable);
                thread.setName("question-collector-" + thread.getId());
                return thread;
            },
            new ThreadPoolExecutor.AbortPolicy()
    );
}
~~~

### 7.3 ThreadPoolExecutor 参数

~~~java
new ThreadPoolExecutor(
        1,       // corePoolSize
        2,       // maximumPoolSize
        60,      // keepAliveTime
        TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(100),
        threadFactory,
        new AbortPolicy()
)
~~~

- 核心线程数 1：线程池通常至少保留一个工作线程。
- 最大线程数 2：队列有任务且核心线程忙时，可以扩展到两个线程。
- 空闲存活时间 60 秒：非核心线程空闲后可以回收。
- 队列容量 100：最多暂存 100 个等待处理的任务。
- 线程命名：便于从日志中识别任务来源。

### 7.4 为什么使用 AbortPolicy

如果线程池和队列都满了，AbortPolicy 会抛出 RejectedExecutionException。

调度器捕获它：

~~~java
try {
    questionCollectExecutor.execute(task);
} catch (RejectedExecutionException e) {
    log.warn("候选题收集队列已满:messageId={}", assistantMessageId);
}
~~~

目标是：收集任务失败可以记录日志，但不能让聊天请求执行完整个 AI 补全流程。

如果使用 CallerRunsPolicy，队列满时，提交任务的线程会自己执行任务。提交线程可能正是 SSE 线程，于是会出现：

~~~text
聊天结束
    ↓
提交任务失败
    ↓
SSE 线程亲自调用候选题 AI
    ↓
用户感觉回复结束很慢
~~~

### 7.5 两个 Executor 的注入问题

当前 InterviewServiceImpl 使用 Lombok 生成构造器，并在字段上写了：

~~~java
@Qualifier("reportExecutor")
private final Executor reportExecutor;
~~~

增加第二个 Executor 后，字段上的 Qualifier 在某些配置下不会复制到生成的构造器参数，Spring 可能报 NoUniqueBeanDefinitionException。

简单处理方式是给旧的报告线程池加 Primary：

~~~java
@Bean("reportExecutor")
@Primary
public Executor reportExecutor() {
    // 原来的线程池代码
}
~~~

题目收集线程池在需要时显式指定：

~~~java
public AiQuestionCollectDispatcher(
        @Qualifier("questionCollectExecutor")
        Executor questionCollectExecutor,
        AiQuestionCollectorService collectorService) {
    this.questionCollectExecutor = questionCollectExecutor;
    this.collectorService = collectorService;
}
~~~

更严格的做法是给 InterviewServiceImpl 手写构造器，并在构造器参数上明确写 Qualifier。

## 八、异步线程为什么不能读取 UserContext

项目中的 UserContext 通常基于 ThreadLocal 保存当前登录用户：

~~~java
public class UserContext {
    private static final ThreadLocal<Long> USER_ID = new ThreadLocal<>();

    public static Long getUserId() {
        return USER_ID.get();
    }
}
~~~

ThreadLocal 的含义是：

~~~text
同一个线程可以拿到自己的值
另一个线程默认拿不到这个值
~~~

HTTP 请求线程中可能有 userId = 1001，但候选题收集线程中：

~~~java
UserContext.getUserId()
~~~

很可能得到 null。

因此异步收集接口不要设计成依赖 userId：

~~~java
void collect(Long userId, Long sessionId, String question);
~~~

本模块只需要：

~~~java
void collect(Long sessionId,
             Long assistantMessageId,
             String direction,
             String question);
~~~

审核入正式题库则不同。审核请求是正常的管理员 HTTP 请求，QuestionServiceImpl.addQuestion 需要读取 UserContext，此时仍然在请求线程中，可以正常读取管理员 id。

## 九、为什么要先标准化，再计算指纹

### 9.1 原始文本不能直接判断重复

以下题目人类会认为是同一道题：

~~~text
请问，什么是 JVM 垃圾回收？
什么是JVM垃圾回收?
什么是 JVM 垃圾回收？
~~~

但 Java 的字符串比较结果是 false，因为它们包含不同的前缀、空格、标点和大小写。

所以先定义标准化函数：

~~~java
public String normalize(String source) {
    if (!StringUtils.hasText(source)) {
        return "";
    }

    return Normalizer.normalize(source, Normalizer.Form.NFKC)
            .toLowerCase(Locale.ROOT)
            .replaceAll("[\\p{P}\\p{S}\\s]+", "")
            .replaceFirst(
                    "^(请问|请介绍一下|请说明|请解释一下|请解释|谈谈你对|你了解)",
                    ""
            )
            .strip();
}
~~~

### 9.2 NFKC 的作用

~~~java
Normalizer.normalize(source, Normalizer.Form.NFKC)
~~~

Unicode 中可能存在看起来一样、实际编码不同的字符，例如全角和半角字符：

~~~text
ＪＶＭ
JVM
~~~

NFKC 会尽量将兼容字符统一到标准形式。

### 9.3 统一大小写

~~~java
.toLowerCase(Locale.ROOT)
~~~

让 JVM、jvm 和 Jvm 统一成一种形式。使用 Locale.ROOT 是为了不依赖用户电脑的语言环境。

### 9.4 删除标点、符号和空白

~~~java
.replaceAll("[\\p{P}\\p{S}\\s]+", "")
~~~

这里使用 Unicode 正则类别：

| 类别 | 含义 |
| --- | --- |
| \\p{P} | 标点符号 |
| \\p{S} | 数学符号、货币符号等符号 |
| \\s | 空白字符 |

例如：

~~~text
什么是 JVM 垃圾回收？
~~~

可能变成：

~~~text
什么是jvm垃圾回收
~~~

### 9.5 删除无意义前缀

~~~java
.replaceFirst(
        "^(请问|请介绍一下|请说明|请解释一下|请解释|谈谈你对|你了解)",
        ""
)
~~~

^ 表示只匹配字符串开头，不会误删题目正文中间出现的词。

### 9.6 SHA-256 的作用

~~~java
public String fingerprint(String normalizedText) {
    if (!StringUtils.hasText(normalizedText)) {
        throw new IllegalArgumentException("标准化题目不能为空");
    }

    try {
        MessageDigest digest = MessageDigest.getInstance("SHA-256");
        byte[] bytes = digest.digest(
                normalizedText.getBytes(StandardCharsets.UTF_8)
        );
        return HexFormat.of().formatHex(bytes);
    } catch (NoSuchAlgorithmException e) {
        throw new IllegalStateException(
                "当前 JDK 不支持 SHA-256",
                e
        );
    }
}
~~~

同一个标准化文本会得到同一个指纹。数据库只需要给 fingerprint 建唯一索引：

~~~sql
UNIQUE KEY uk_fingerprint (fingerprint)
~~~

不要使用 String.hashCode() 作为数据库去重键。它只有 32 位，而且不是为持久化唯一标识设计的。

### 9.7 指纹去重不是语义去重

下面两个问题可能意思接近：

~~~text
线程池的核心参数有哪些？
ThreadPoolExecutor 构造方法中的主要参数分别有什么作用？
~~~

标准化后仍然不一定相同。因此第一版只能解决字符层面的重复，语义相似问题交给管理员审核。

未来可以使用 Embedding：

~~~text
题目文本 → 向量 → 相似度检索 → 判断是否相似
~~~

但这会引入模型、向量存储和相似度阈值，第一版不建议同时实现。

## 十、数据库唯一索引才是真正的并发去重保证

### 10.1 只在 Java 中查询是不安全的

初学者常见的写法：

~~~java
if (!candidateMapper.existsByFingerprint(fingerprint)) {
    candidateMapper.insert(candidate);
}
~~~

两个线程同时执行时可能发生：

~~~text
线程 A：查询，不存在
线程 B：查询，不存在
线程 A：插入成功
线程 B：插入成功
~~~

最终产生重复记录。这是检查和执行之间的竞态条件。

### 10.2 正确做法：数据库约束兜底

候选表建立：

~~~sql
UNIQUE KEY uk_fingerprint (fingerprint)
~~~

插入使用：

~~~sql
INSERT IGNORE INTO ai_question_candidate (...)
VALUES (...)
~~~

两个线程同时插入相同指纹时：

~~~text
线程 A：成功，影响行数 1
线程 B：唯一索引冲突，影响行数 0
~~~

业务代码根据影响行数判断自己是不是第一个成功插入的人：

~~~java
int inserted = candidateMapper.insertIgnore(candidate);

if (inserted == 0) {
    candidateMapper.incrementDuplicate(fingerprint);
    return;
}
~~~

只有插入成功的线程继续调用 AI 补全。

### 10.3 uk_source_message 解决什么问题

指纹唯一索引解决的是不同面试消息产生相同问题。但还要防止同一条 assistant 消息被重复处理：

~~~sql
UNIQUE KEY uk_source_message (source_message_id)
~~~

两个唯一索引分别守护两个不同的不变量：

| 唯一索引 | 防止什么 |
| --- | --- |
| uk_fingerprint | 相同题目重复出现 |
| uk_source_message | 同一条消息重复处理 |

### 10.4 INSERT IGNORE 的边界

INSERT IGNORE 主要用于处理唯一索引冲突，不应该被理解为“所有错误都可以忽略”。

使用前提：

1. 已检查必要字段。
2. 表结构有明确的唯一索引。
3. 插入返回值会被业务代码检查。
4. 其他严重数据库错误仍然通过日志暴露。

## 十一、候选表为什么不能直接使用正式题目表

正式题目代表“可以被用户学习”，会被题库、详情、收藏夹、错题本和热门题目等功能使用。

候选题代表“等待判断”，允许处于补全中、待审核、补全失败、已忽略、收录中等中间状态。

如果 AI 生成的数据直接写入 question 表，一条不完整答案就可能被所有正式功能看到。

所以候选表是一道隔离层：

~~~text
不可靠的 AI 原始数据
        ↓
候选题表
        ↓
机器补全和人工审核
        ↓
正式题库
~~~

如果只有 is_reviewed 这样的布尔字段，就无法区分补全中、补全失败、已忽略和收录中。状态字段应该表达完整的业务生命周期。

---

## 十二、候选题状态机

| status | 名称 | 含义 |
| --- | --- | --- |
| 0 | 补全中 | 已经去重插入，正在调用 AI 补全 |
| 1 | 待审核 | AI 补全成功，等待管理员处理 |
| 2 | 已收录 | 已经写入正式题库 |
| 3 | 已忽略 | 管理员认为不适合收录 |
| 4 | 补全失败 | AI 调用失败或返回数据不合法 |
| 5 | 收录中 | 管理员已经抢到处理权 |

状态流转：

~~~text
                    ┌──────────────┐
                    │              │
                    ▼              │
                0 补全中 ───────► 4 补全失败
                    │                  │
                    │                  │ 管理员处理
                    ▼                  │
                1 待审核 ◄─────────────┘
                 │  │
                 │  └────────► 3 已忽略
                 │
                 ▼
                5 收录中
                 │
                 ▼
                2 已收录
~~~

### 12.1 为什么更新 SQL 必须带原状态

不能写成：

~~~sql
UPDATE ai_question_candidate
SET status = 5
WHERE id = #{id}
~~~

两个管理员同时点击通过时，可能都继续创建正式题目。

正确写法：

~~~sql
UPDATE ai_question_candidate
SET status = 5,
    update_time = NOW()
WHERE id = #{id}
  AND status IN (1, 4)
~~~

Java 检查影响行数：

~~~java
if (candidateMapper.markPublishing(id) == 0) {
    throw new BusinessException(
            ErrorCode.CONFLICT,
            "候选题状态已变化，请刷新后重试"
    );
}
~~~

只有真正把状态从 1 或 4 改成 5 的请求，才获得创建正式题目的资格。

### 12.2 这是乐观并发控制

它不要求先锁住整行，而是把“我预期它还是某个状态”写入更新条件：

~~~text
如果当前状态仍然符合预期，就更新
如果状态已经变了，就更新 0 行
~~~

这和版本号乐观锁的思想类似：

~~~sql
UPDATE table
SET value = ..., version = version + 1
WHERE id = ? AND version = ?
~~~

## 十三、AiQuestionCollectorServiceImpl 的执行顺序

收集服务的核心方法：

~~~java
public void collect(Long sessionId,
                    Long assistantMessageId,
                    String direction,
                    String question) {
    if (!StringUtils.hasText(question)) {
        return;
    }

    if (candidateMapper.existsBySourceMessage(assistantMessageId)) {
        return;
    }

    String title = question.strip();
    String normalizedTitle = normalizer.normalize(title);

    if (normalizedTitle.length() < 4) {
        return;
    }

    if (questionMapper.existsByTitle(title)) {
        return;
    }

    String fingerprint = normalizer.fingerprint(normalizedTitle);

    AiQuestionCandidate candidate = new AiQuestionCandidate();
    candidate.setTitle(title);
    candidate.setNormalizedTitle(normalizedTitle);
    candidate.setFingerprint(fingerprint);
    candidate.setDirection(direction);
    candidate.setSourceSessionId(sessionId);
    candidate.setSourceMessageId(assistantMessageId);

    int inserted = candidateMapper.insertIgnore(candidate);
    if (inserted == 0) {
        candidateMapper.incrementDuplicate(fingerprint);
        return;
    }

    try {
        enrich(candidate);
    } catch (Exception e) {
        log.error("AI 候选题补全失败:candidateId={}",
                candidate.getId(), e);
        candidateMapper.markFailed(
                candidate.getId(),
                "候选题补全失败，请人工处理"
        );
    }
}
~~~

### 13.1 第一步：验证输入

虽然提取器已经做过校验，但服务层仍然应该自己再次验证，因为将来可能有其他地方直接调用 collect。

### 13.2 第二步：按消息 id 做幂等检查

~~~java
if (candidateMapper.existsBySourceMessage(assistantMessageId)) {
    return;
}
~~~

幂等表示同一个任务执行一次和执行多次，最终结果应该一致。

### 13.3 第三步：保存三种去重数据

~~~java
String title = question.strip();
String normalizedTitle = normalizer.normalize(title);
String fingerprint = normalizer.fingerprint(normalizedTitle);
~~~

| 字段 | 作用 |
| --- | --- |
| title | 展示给管理员、保留原始可读文本 |
| normalized_title | 排查去重规则、辅助调试 |
| fingerprint | 作为唯一索引键 |

如果只保存指纹，之后无法解释为什么两道题被认为相同。

### 13.4 第四步：检查正式题库

~~~java
if (questionMapper.existsByTitle(title)) {
    return;
}
~~~

SQL：

~~~sql
SELECT COUNT(*) > 0
FROM question
WHERE is_deleted = 0
  AND LOWER(TRIM(title)) = LOWER(TRIM(#{title}))
~~~

这个检查能处理大小写和首尾空格差异，但不能完成复杂语义去重。

### 13.5 第五步：先插入，再调用 AI

~~~java
int inserted = candidateMapper.insertIgnore(candidate);

if (inserted == 0) {
    candidateMapper.incrementDuplicate(fingerprint);
    return;
}
~~~

关键顺序是：

~~~text
先竞争“新题资格”
再消耗 AI 调用
~~~

如果先调用 AI，再插入数据库，多个线程会重复消耗补全模型。现在只有真正插入成功的线程才补全。

### 13.6 第六步：补全失败也要记录状态

~~~java
try {
    enrich(candidate);
} catch (Exception e) {
    candidateMapper.markFailed(
            candidate.getId(),
            "候选题补全失败，请人工处理"
    );
}
~~~

不能让异常导致候选题消失。候选题已经成功插入，所以正确结果是：

~~~text
候选题存在
status = 4
error_message = 补全失败原因
管理员仍然可以查看并人工补齐
~~~

## 十四、为什么 AI 补全必须使用结构化结果

候选题补全需要：

~~~text
answer
difficulty
categoryId
tagIds
~~~

不推荐让 AI 返回普通自然语言，因为程序还要自己解析答案、难度、分类和标签。

使用 record：

~~~java
public record AiQuestionEnrichment(
        String answer,
        Integer difficulty,
        Long categoryId,
        List<Long> tagIds
) {
}
~~~

调用：

~~~java
AiQuestionEnrichment result = chatClient
        .prompt()
        .system(systemPrompt)
        .user(userPrompt)
        .call()
        .entity(AiQuestionEnrichment.class);
~~~

Spring AI 会尝试把模型返回结果转换成 Java 类型。

### 14.1 分类和标签必须使用白名单

假设数据库已有分类：

~~~text
1 - Java 基础
2 - Java 并发
3 - JVM
~~~

Prompt 可以把合法选项传给 AI，但 Prompt 仍然不是硬约束。返回后要再次校验：

~~~java
boolean categoryExists = categories.stream()
        .anyMatch(category ->
                category.getId().equals(result.categoryId())
        );

if (!categoryExists) {
    throw new IllegalStateException("AI 返回了不存在的分类 id");
}
~~~

难度也要校验：

~~~java
if (result.difficulty() == null
        || result.difficulty() < 1
        || result.difficulty() > 3) {
    throw new IllegalStateException("AI 返回的难度不合法");
}
~~~

标签需要过滤、去重和限制数量：

~~~java
List<Long> safeTagIds = result.tagIds() == null
        ? List.of()
        : result.tagIds().stream()
                .filter(validTagIds::contains)
                .distinct()
                .limit(5)
                .toList();
~~~

这体现了一个后端原则：

~~~text
外部数据进入系统前，必须做白名单校验。
~~~

### 14.2 为什么候选标签存 JSON

候选题只是中间数据，第一版可以把推荐标签保存为：

~~~json
[1, 3, 5]
~~~

写入前：

~~~java
String tagIdsJson = objectMapper.writeValueAsString(safeTagIds);
~~~

读取后：

~~~java
objectMapper.readValue(
        json,
        new TypeReference<List<Long>>() {}
);
~~~

正式题目仍然使用 question、question_tag、tag 三张表。候选表的 JSON 只是暂存 AI 推荐结果。

## 十五、MyBatis Mapper 如何配合业务流程

### 15.1 Java 接口和 XML

Java 接口：

~~~java
@Mapper
public interface AiQuestionCandidateMapper {
    int insertIgnore(AiQuestionCandidate candidate);

    int incrementDuplicate(@Param("fingerprint") String fingerprint);

    int markEnriched(@Param("id") Long id,
                     @Param("answer") String answer,
                     @Param("difficulty") Integer difficulty,
                     @Param("categoryId") Long categoryId,
                     @Param("tagIdsJson") String tagIdsJson);
}
~~~

XML：

~~~xml
<insert id="insertIgnore"
        useGeneratedKeys="true"
        keyProperty="id">
    INSERT IGNORE INTO ai_question_candidate (...)
    VALUES (...)
</insert>
~~~

id 必须和 XML 的 id 一致：

~~~java
candidateMapper.insertIgnore(candidate);
~~~

MyBatis 会根据方法名找到 XML 中的 SQL。

### 15.2 为什么使用 @Param

单个对象参数可以直接使用对象属性，但多个简单参数必须明确名字：

~~~java
int markEnriched(@Param("id") Long id,
                 @Param("answer") String answer,
                 @Param("difficulty") Integer difficulty);
~~~

XML 中才能写：

~~~xml
#{id}
#{answer}
#{difficulty}
~~~

如果没有 @Param，MyBatis 可能只能识别成 arg0、arg1，导致参数绑定错误。

### 15.3 下划线和驼峰

数据库使用：

~~~text
normalized_title
source_message_id
duplicate_count
~~~

Java 使用：

~~~java
normalizedTitle
sourceMessageId
duplicateCount
~~~

项目的 MyBatis 配置通常会把下划线自动映射为驼峰。JSON 字段可以显式转换：

~~~sql
CAST(tag_ids AS CHAR) AS tag_ids_json
~~~

这样实体中的 String tagIdsJson 就能接收 JSON 字符串。

### 15.4 动态查询中的 where

候选题分页支持 status、direction 和 keyword：

~~~xml
<sql id="candidateWhere">
    <where>
        <if test="query.status != null">
            status = #{query.status}
        </if>
        <if test="query.direction != null and query.direction != ''">
            AND direction = #{query.direction}
        </if>
        <if test="query.keyword != null and query.keyword != ''">
            AND title LIKE CONCAT('%', #{query.keyword}, '%')
        </if>
    </where>
</sql>
~~~

MyBatis 的 where 标签会自动添加 WHERE，并处理开头多余的 AND。

### 15.5 为什么状态更新返回影响行数

Mapper 应该返回 int：

~~~java
int markPublishing(@Param("id") Long id);
~~~

业务层需要知道条件更新是否成功：

~~~java
int affectedRows = candidateMapper.markPublishing(id);

if (affectedRows == 0) {
    // 状态已经变化，或者候选题不存在
}
~~~

影响行数是数据库向业务层反馈并发结果的重要方式。

## 十六、事务如何保证审核入库的一致性

管理员点击通过时，需要完成：

~~~text
候选题 status: 1 → 5
创建正式题目
候选题 status: 5 → 2，并写入 question_id
~~~

核心代码：

~~~java
@Transactional
public Long approve(Long id, AiQuestionApproveDTO dto) {
    AiQuestionCandidate candidate = mustFind(id);

    if (Integer.valueOf(2).equals(candidate.getStatus())) {
        return candidate.getQuestionId();
    }

    if (candidateMapper.markPublishing(id) == 0) {
        throw new BusinessException(
                ErrorCode.CONFLICT,
                "候选题状态已变化，请刷新后重试"
        );
    }

    QuestionAddDTO questionDTO = new QuestionAddDTO();
    questionDTO.setTitle(dto.getTitle().strip());
    questionDTO.setContent(dto.getContent());
    questionDTO.setAnswer(dto.getAnswer().strip());
    questionDTO.setDifficulty(dto.getDifficulty());
    questionDTO.setCategoryId(dto.getCategoryId());
    questionDTO.setTagIds(dto.getTagIds());

    Long questionId = questionService.addQuestion(questionDTO);

    if (candidateMapper.markAccepted(id, questionId) == 0) {
        throw new IllegalStateException(
                "正式题目已创建，但候选题状态更新失败"
        );
    }

    return questionId;
}
~~~

### 16.1 没有事务会怎样

可能出现：

~~~text
候选题改成 5
正式题目创建成功
更新候选题为 2 失败
~~~

数据库会留下正式题目，但候选题一直是收录中，管理员再次点击时可能重复创建正式题目。

### 16.2 事务能保证什么

有 Transactional 时，中间任何一步抛异常，前面的数据库修改都会回滚：

~~~text
markPublishing 回滚
question.insert 回滚
markAccepted 回滚
~~~

### 16.3 为什么复用 QuestionServiceImpl

QuestionServiceImpl.addQuestion 已经负责：

- 写入题目基本字段。
- 设置 create_user_id。
- 写入 question_tag 关系。
- 处理空标签列表。

审核服务不应该复制一份插入 question 的 SQL，而应该复用正式题库服务：

~~~java
questionService.addQuestion(questionDTO);
~~~

这样管理员手动新增题目和 AI 候选题审核使用同一套正式入库规则。

---

## 十七、审核接口为什么需要管理员权限

候选题可能包含不准确答案、尚未公开的题目、面试会话来源信息以及未确认的分类标签。

所以接口必须加：

~~~java
@RequireAdmin
~~~

不能加：

~~~java
@Public
~~~

接口层负责权限，Service 层负责业务正确性，Mapper 负责数据库执行：

~~~text
Controller：谁可以调用
Service：调用后应该发生什么
Mapper：数据库怎样执行
~~~

## 十八、为什么候选题收集服务不加大事务

收集服务中有一次不可控的 AI 网络调用：

~~~java
chatClient
        .prompt()
        .system(...)
        .user(...)
        .call()
        .entity(AiQuestionEnrichment.class);
~~~

如果把整个 collect 方法加 Transactional，可能发生：

~~~text
打开数据库事务
    ↓
插入候选题
    ↓
等待 AI 3 秒
    ↓
解析 AI 结果
    ↓
更新候选题
    ↓
提交事务
~~~

这会让数据库连接和事务等待 AI 网络请求。

更合理的状态分段是：

~~~text
短事务：插入 status = 0
事务结束

无事务：调用 AI

短事务：更新 status = 1 或 4
~~~

候选题可以暂时处于 0 补全中，系统也能看见它，不需要保持长事务。

## 十九、失败场景如何处理

| 失败场景 | 处理方式 | 结果 |
| --- | --- | --- |
| AI 回复没有标记 | extract 返回空 | 不创建候选题 |
| 标记后没有题目 | extract 返回空 | 不创建候选题 |
| 题目过短或过长 | 提取器过滤 | 不进入候选表 |
| 正式题库已有相同标题 | existsByTitle 返回 true | 不创建候选题 |
| 候选题指纹重复 | INSERT IGNORE 返回 0 | duplicate_count 加一 |
| AI 补全失败 | markFailed | status = 4 |
| 分类 id 不存在 | 白名单校验失败 | status = 4 |
| 标签 id 不存在 | 白名单校验失败 | status = 4 |
| 线程池已满 | 捕获 RejectedExecutionException | 记录日志，不影响聊天 |
| 管理员重复点击通过 | markPublishing 返回 0 | 返回冲突 |
| 正式题目创建失败 | 事务回滚 | 候选题回到原状态 |
| 普通用户访问审核接口 | RequireAdmin 拦截 | 返回无权限 |

不同失败应该区别处理：

- 网络临时失败：可以考虑有限重试。
- AI 返回结构错误：检查 Prompt 和结构化映射。
- 分类为空：属于系统数据配置问题。
- 指纹冲突：不是失败，而是正常去重。
- 队列满：需要监控、限流或后续补偿。

第一版的重点是把状态记录清楚，后续再针对具体错误增加补偿策略。

## 二十、测试应该测试什么

### 20.1 文本提取单元测试

~~~java
@Test
void shouldExtractQuestionAfterMarker() {
    String reply = "点评内容\n\n【下一题】\n什么是 JVM？";

    Optional<String> result = extractor.extract(reply);

    assertThat(result).contains("什么是 JVM？");
}
~~~

至少覆盖：

~~~text

没有标记
标记后为空
标记后有空行
带 - 或 * 前缀
题目短于 4 个字符
题目超过 256 个字符
多个标记时取最后一个
~~~

### 20.2 标准化测试

~~~java
@Test
void equivalentQuestionsShouldHaveSameFingerprint() {
    String first = normalizer.normalize(
            "请问，什么是 JVM 垃圾回收？"
    );
    String second = normalizer.normalize(
            "什么是JVM垃圾回收?"
    );

    assertThat(normalizer.fingerprint(first))
            .isEqualTo(normalizer.fingerprint(second));
}
~~~

### 20.3 服务层重复测试

用 Mockito 验证重复题不会再次调用 AI：

~~~java
when(candidateMapper.existsBySourceMessage(100L))
        .thenReturn(false);
when(candidateMapper.insertIgnore(any()))
        .thenReturn(0);

collector.collect(
        1L,
        100L,
        "jvm",
        "什么是 JVM？"
);

verify(candidateMapper).incrementDuplicate(anyString());
verifyNoInteractions(chatClient);
~~~

重要断言是：重复题不应该消耗一次补全 AI 调用。

### 20.4 审核并发测试

模拟 markPublishing 返回 0，确认 Service 返回冲突异常，而不是继续创建正式题目。

### 20.5 数据库联调测试

单元测试无法证明 MySQL 唯一索引真的生效，还要手动或集成测试：

~~~text
插入两条相同 fingerprint 的候选题
确认数据库只保留一条
确认 duplicate_count 增加
~~~

log.info(

## 二十三、你需要掌握的 Java 和后端知识

### 23.1 Optional

表示可能有值，也可能没有值：

~~~java
Optional<String> result = extractor.extract(reply);
result.ifPresent(System.out::println);
~~~

适合查找结果和解析结果，不应滥用于所有字段。

### 23.2 方法引用

~~~java
String::strip
StringUtils::hasText
validTagIds::contains
~~~

分别等价于：

~~~java
line -> line.strip()
line -> StringUtils.hasText(line)
id -> validTagIds.contains(id)
~~~

### 23.3 Stream

~~~java
tags.stream()
        .filter(...)
        .distinct()
        .limit(5)
        .toList();
~~~

适合表达“对一组数据进行连续处理”。

### 23.4 正则表达式

正则适合处理结构简单、规则明确的文本清理，不要试图用正则解析复杂自然语言。

### 23.5 线程池

线程池解决任务如何排队和执行，不自动解决任务重复、数据一致性和异常重试。这些仍然需要数据库唯一索引、状态机和异常处理。

### 23.6 事务

事务保证多个数据库操作要么一起成功，要么一起回滚，但不应该包住不可控的外部网络调用。

### 23.7 乐观并发控制

~~~sql
WHERE id = ? AND status = ?
~~~

通过影响行数判断谁抢到了处理权。

### 23.8 数据库唯一索引

Java 查询只能提前优化，真正的并发安全必须由数据库约束兜底。

## 二十四、按照什么顺序学习和实现

### 第一步：先学会提取器

完成 AiQuestionExtractor、QuestionTextNormalizer 和单元测试，确认：

~~~text
正常文本能提取
异常文本返回 Optional.empty()
相同题目产生相同 fingerprint
~~~

### 第二步：理解数据库表和状态

完成 ai_question_candidate、status、uk_fingerprint 和 uk_source_message。手动插入测试数据，理解每个字段。

### 第三步：完成 Mapper

完成 insertIgnore、incrementDuplicate、markEnriched、markFailed、markPublishing 和 markAccepted。

每写一个 SQL，就单独确认影响行数。

### 第四步：完成同步收集服务

暂时可以直接调用：

~~~java
collectorService.collect(...);
~~~

先确认新题能插入、重复题不会新增、正式题库已有题不会新增。

### 第五步：完成 AI 补全

确认结构化返回、分类校验、标签过滤、补全成功 status=1、补全失败 status=4。

### 第六步：接入独立线程池

确认聊天 SSE 不等待补全，线程名称能在日志中看到，线程池满时不会阻塞 SSE。

### 第七步：接入 InterviewServiceImpl

确认只有完整回复触发收集，assistantMessageId 已经生成，失败半截回复不触发收集，开场题也能收集。

### 第八步：完成管理员审核

确认普通用户无权限，管理员能分页查看，管理员可以修改内容，重复点击不会创建两条正式题，事务失败会回滚。

## 二十五、遇到问题时应该怎么思考

### 问题一：聊天正常，但没有候选题

按顺序检查：

1. AI 回复是否包含 【下一题】。
2. Prompt 的标记和常量是否完全一致。
3. extract 是否返回 Optional.empty()。
4. 是否调用 dispatch。
5. 线程池是否拒绝了任务。
6. 数据库是否创建候选表。
7. 是否因为正式题库已有题而提前返回。

### 问题二：候选题很多，但 status 一直是 0

检查：

1. 收集线程是否执行。
2. AI 客户端是否返回。
3. enrich 是否抛异常。
4. markEnriched 的 SQL 是否带 status = 0。
5. 是否有数据库连接或事务问题。

### 问题三：Spring 启动报两个 Executor

检查：

1. reportExecutor 是否加了 Primary。
2. 收集线程池注入是否写了 Qualifier。
3. 是否手写了明确构造器。

### 问题四：重复题没有增加 duplicate_count

检查：

1. fingerprint 是否真的相同。
2. 唯一索引是否存在。
3. insertIgnore 返回值是否为 0。
4. incrementDuplicate 的 SQL 条件是否使用相同 fingerprint。

### 问题五：审核后正式题目重复

检查：

1. markPublishing 是否带状态条件。
2. 是否检查了影响行数。
3. approve 是否加了 Transactional。
4. 是否在事务中复用了 QuestionService.addQuestion。

## 二十六、最终要形成的正确理解

这个模块不是简单的：

~~~text
AI 回复 → 保存题目
~~~

而是：

~~~text
AI 输出协议
    + 文本提取
    + 标准化
    + 哈希指纹
    + 数据库唯一约束
    + 异步线程池
    + 结构化 AI 补全
    + 白名单校验
    + 候选状态机
    + 管理员审核
    + 事务入库
~~~

每个部分解决不同的问题：

| 机制 | 解决的问题 |
| --- | --- |
| 固定 Prompt 标记 | 让程序知道题目从哪里开始 |
| AiQuestionExtractor | 从自然语言中取出可处理文本 |
| QuestionTextNormalizer | 让不同写法尽量统一 |
| SHA-256 | 为统一文本生成稳定指纹 |
| 唯一索引 | 在并发环境下最终保证不重复 |
| 独立线程池 | 不让候选题处理拖慢聊天 |
| 结构化 DTO | 让 AI 返回结果可以被程序使用 |
| 白名单校验 | 防止 AI 编造分类和标签 id |
| 候选表 | 隔离不可靠的 AI 数据和正式题库 |
| 状态机 | 描述题目处于哪个处理阶段 |
| 条件更新 | 防止管理员并发重复审核 |
| 事务 | 保证正式题目和候选状态一致 |
| 管理员审核 | 给 AI 结果增加最后一道质量控制 |

当你真正理解这些机制之后，以后实现自动收集用户反馈、自动沉淀搜索关键词、自动生成知识卡片等功能时，也可以复用同一套思路：

~~~text
先接收原始数据
再进入中间表
进行清洗和校验
使用唯一约束去重
异步执行耗时任务
人工或规则审核
最后进入正式数据表
~~~

这就是这个模块最值得掌握的工程思想。
