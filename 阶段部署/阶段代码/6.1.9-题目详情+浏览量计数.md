## 一、本任务要实现什么

两件事,一个接口:

1. **题目详情**:`GET /api/questions/{id}`,读缓存 `zhimian:cache:question:detail:{id}`,命中直接返回;不命中查库、组装 VO、写入缓存(30 分钟)。
2. **浏览量计数**:每次访问详情,不直接 `UPDATE question SET view_count = view_count + 1`,而是往 Redis 计数器 `zhimian:question:view:{id}` 里 `INCR` 一次;写一个 `@Scheduled` 定时任务,每隔一段时间把这些计数器的增量批量合并回写到 MySQL,写完删掉计数器。

**为什么浏览量不直接 `UPDATE`**:详情接口是全站访问最频繁的接口,如果每次访问都对 `question` 表这一行发一次 `UPDATE`,高并发下同一行会有大量行锁竞争,请求互相排队——这是纯审计性质的计数,不需要"用户点开的瞬间数据库里的数字就精确 +1"这种强一致性,所以把高频写操作挪到 Redis(纯内存、单线程无锁、天生支持原子自增),攒一段时间再合并成一次低频的 MySQL 写。**这次任务不处理缓存穿透/雪崩/击穿**(不存在的 id、并发重建这些场景),那是下一个任务(1.9)专门系统讲的,这次先把"缓存怎么读写"和"计数怎么异步合并"这两个点吃透。

链路:`QuestionController.detail() → QuestionService.getDetail()(查缓存→未命中查库→回填缓存→Redis 计数 +1)`;另一条独立链路:`@Scheduled 定时任务 → 扫描所有计数器 key → 逐个取值删除 → 批量 UPDATE`。

【讲解】

- **这个方法有两个基本类型参数(`id`、`delta`),必须用 `@Param` 显式命名**,不然 MyBatis 不知道 XML 里 `#{id}`、`#{delta}` 分别对应哪个方法参数(方法只有一个参数时可以省略,比如你写的 `selectById(Long id)` 就没加——多参数场景必须加,这是本项目里第一次踩到这个规则,`QuestionTagMapper.batchInsert` 其实也用了 `@Param`,可以对照着看)。
- `SET view_count = view_count + #{delta}` 是**原地累加**,不是 `SET view_count = #{delta}`——这是开发文档"易踩的坑"里明确点出来的:Redis 计数器里存的只是"这一批时间窗口内的新增量",不是"题目的总浏览量"。如果写成覆盖式的 `SET view_count = #{delta}`,会把数据库里已经存在的历史浏览量全部冲掉。

### Step 3:Service 新增 `getDetail`

`service/impl/QuestionServiceImpl.java`(只贴新增部分,其余方法不变;记得在类顶部补上新用到的字段和 import):

```java
private static final String DETAIL_CACHE_PREFIX = "zhimian:cache:question:detail:";
private static final String VIEW_COUNT_PREFIX = "zhimian:question:view:";
private static final long DETAIL_CACHE_TTL_MINUTES = 30;

private final StringRedisTemplate redisTemplate;
private final ObjectMapper objectMapper;

@Override
public QuestionDetailVO getDetail(Long id) {
    String cacheKey = DETAIL_CACHE_PREFIX + id;
    String cached = redisTemplate.opsForValue().get(cacheKey);

    QuestionDetailVO vo;
    if (cached != null) {
        vo = deserialize(cached);
    } else {
        vo = loadDetailFromDb(id);
        redisTemplate.opsForValue().set(cacheKey, serialize(vo), DETAIL_CACHE_TTL_MINUTES, TimeUnit.MINUTES);
    }

    // 不管这次是缓存命中还是查了库,这次访问都要算一次浏览量;只累加 Redis 计数器,不碰 MySQL
    redisTemplate.opsForValue().increment(VIEW_COUNT_PREFIX + id);
    return vo;
}

private QuestionDetailVO loadDetailFromDb(Long id) {
    Question question = questionMapper.selectById(id);
    if (question == null) {
        throw new BusinessException(ErrorCode.NOT_FOUND, "题目不存在");
    }

    QuestionDetailVO vo = new QuestionDetailVO();
    BeanUtils.copyProperties(question, vo);

    Map<Long, String> categoryNameMap = new HashMap<>();
    for (Category c : categoryMapper.selectAll()) {
        categoryNameMap.put(c.getId(), c.getName());
    }
    vo.setCategoryName(categoryNameMap.get(question.getCategoryId()));

    List<String> tags = new ArrayList<>();
    for (QuestionTagName row : questionTagMapper.selectTagNamesByQuestionIds(List.of(id))) {
        tags.add(row.getName());
    }
    vo.setTags(tags);
    return vo;
}

private String serialize(QuestionDetailVO vo) {
    try {
        return objectMapper.writeValueAsString(vo);
    } catch (JsonProcessingException e) {
        // VO 就是几个基础字段和字符串列表,不存在序列化失败的可能,包一层非受检异常往上抛即可
        throw new RuntimeException(e);
    }
}

private QuestionDetailVO deserialize(String json) {
    try {
        return objectMapper.readValue(json, QuestionDetailVO.class);
    } catch (JsonProcessingException e) {
        throw new RuntimeException(e);
    }
}
```

新增的 import:

```java
import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.zhimian.model.vo.QuestionDetailVO;
import org.springframework.data.redis.core.StringRedisTemplate;

import java.util.concurrent.TimeUnit;
```

【讲解,这是本任务最重要的部分】

- **`loadDetailFromDb` 里查 `categoryName` 的写法,是照抄你自己在 `pageQuestions()` 里已经写过的模式**(查全量分类建 Map,再按 id 取)——这里只是查一条题目也这么写,不是必须,是为了两处保持一致、你以后看代码不用记两套写法。真要抠性能可以给 `CategoryMapper` 加一个 `selectById`,但这次任务不涉及,不做这个额外改动。
- **为什么用 `StringRedisTemplate` 手动转 JSON,而不是直接存对象**:`StringRedisTemplate` 的泛型就是 `RedisTemplate<String, String>`,只能存字符串。要缓存一个 `QuestionDetailVO` 对象,得先用 `ObjectMapper` 把它变成 JSON 字符串再 `set`,取的时候再 `readValue` 转回对象。`ObjectMapper` 不用自己配置——`spring-boot-starter-web` 已经把它自动注册成一个 Spring Bean 了,直接在构造器里声明依赖就能注入。
- **`serialize`/`deserialize` 里 catch 到异常直接包一层 `RuntimeException` 往上抛,没有做更精细的处理**:`JsonProcessingException` 是受检异常,方法签名不写 `throws` 就必须在方法体内处理掉;但这里序列化的对象就是自己定义的、字段类型都很简单的 VO,不存在真的会抛这个异常的场景,所以不用为"不可能发生的情况"设计精细的异常处理,包一层直接抛出即可。
- **`redisTemplate.opsForValue().increment(key)`**:对应 Redis 的 `INCR` 命令,如果 key 不存在会先当作 0 处理,自增后变成 1——不需要你先判断 key 存不存在,`INCR` 本身就是"不存在则初始化为 0 再自增"的原子操作。
- **缓存里的 `viewCount` 是"旧值"这件事,要想清楚、接受它**:比如某道题此刻数据库里 `view_count=100`,详情被缓存了,接下来 200 次访问全部命中缓存直接返回,返回的 `viewCount` 一直是 100,直到缓存过期重新查库、或者定时任务已经把这 200 次的增量刷回数据库为止——用户看到的浏览量和"真实"浏览量之间存在滞后。这是刻意接受的不一致(浏览量不需要强一致),换来的是详情接口的读性能不被浏览量计数拖累。**这个取舍能主动说出来,是这道题的加分项**,面试官问起"你的缓存数据和数据库会不会不一致"时,直接讲这个例子。

### Step 4:定时任务批量回写 `task/ViewCountFlushTask.java`

```java
package com.zhimian.task;

import com.zhimian.mapper.QuestionMapper;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.data.redis.connection.RedisConnection;
import org.springframework.data.redis.core.Cursor;
import org.springframework.data.redis.core.RedisCallback;
import org.springframework.data.redis.core.ScanOptions;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

import java.nio.charset.StandardCharsets;
import java.util.HashSet;
import java.util.Set;

/**
 * 定期把 Redis 里的浏览量增量计数器批量合并回写到 MySQL
 */
@Slf4j
@Component
@RequiredArgsConstructor
public class ViewCountFlushTask {

    private static final String VIEW_COUNT_PREFIX = "zhimian:question:view:";

    private final StringRedisTemplate redisTemplate;
    private final QuestionMapper questionMapper;

    @Scheduled(fixedRate = 5 * 60 * 1000)
    public void flush() {
        Set<String> keys = scanKeys(VIEW_COUNT_PREFIX + "*");
        if (keys.isEmpty()) {
            return;
        }

        int flushed = 0;
        for (String key : keys) {
            // getAndDelete 是原子操作:一步到位"取值 + 删除",中间不会有新的 INCR 插进来丢计数
            String countStr = redisTemplate.opsForValue().getAndDelete(key);
            if (countStr == null) {
                continue;
            }
            Long questionId = Long.valueOf(key.substring(VIEW_COUNT_PREFIX.length()));
            int delta = Integer.parseInt(countStr);
            questionMapper.incrementViewCount(questionId, delta);
            flushed++;
        }
        log.info("浏览量批量回写完成,共处理 {} 个题目", flushed);
    }

    /**
     * 用 SCAN 游标遍历匹配的 key,而不是 KEYS 命令——KEYS 会遍历整个 keyspace 且阻塞其他请求,
     * 生产环境是明确不推荐使用的;SCAN 分批游标遍历,不会阻塞
     */
    private Set<String> scanKeys(String pattern) {
        Set<String> keys = new HashSet<>();
        redisTemplate.execute((RedisCallback<Void>) connection -> {
            try (Cursor<byte[]> cursor = connection.scan(ScanOptions.scanOptions().match(pattern).count(100).build())) {
                while (cursor.hasNext()) {
                    keys.add(new String(cursor.next(), StandardCharsets.UTF_8));
                }
            }
            return null;
        });
        return keys;
    }
}
```

【讲解】

- `@Scheduled(fixedRate = 5 * 60 * 1000)`:每 5 分钟触发一次,`fixedRate` 是"从上次任务**开始**算起过多久再触发下一次"(如果任务本身跑得比间隔还久,下一次会紧接着开始,不等)——对比另一个常见选项 `fixedDelay`("从上次任务**结束**算起过多久再触发"),这个场景用哪个都行,这里数据量小、任务很快跑完,差别不大。`@EnableScheduling` 已经在 `ZhiMianApplication` 上开着,不用再加。
- **`getAndDelete` 对应"易踩的坑"里明确点出的正确写法**:如果写成"先 `GET` 读值,再单独 `DEL` 删除"两步操作,这两步之间如果有新的详情访问触发了 `INCR`,这次新增量会在 `GET` 之后、`DEL` 之前被计入,然后被这次 `DEL` 一起冲掉,永久丢失。`getAndDelete` 是 Redis 的原子命令 `GETDEL`,一步到位,不存在这个中间窗口。
- **为什么用 SCAN 不用 KEYS**:`KEYS pattern` 会遍历 Redis 里**所有** key 去做模式匹配,数据量大时是一个耗时的阻塞操作(Redis 是单线程,这段时间处理不了任何其他请求),官方文档明确写了"不要在生产环境使用"。`SCAN` 用游标分批返回,每次只扫一小部分,不会长时间阻塞——这个项目数据量小用 `KEYS` 也感觉不出差别,但这是"正确姿势",现在养成习惯,以后到大数据量场景不用再改一遍。
- **本地测试这个定时任务时,5 分钟等起来太慢**:可以临时把 `fixedRate = 5 * 60 * 1000` 改成 `10 * 1000`(10 秒)方便自测,测完记得改回去。
