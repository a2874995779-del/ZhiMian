# 智面后续学习路线：高并发、Redis、Lua、SSE 与工程化编程思想

> 适用对象：已经能够完成传统 Spring Boot CRUD，希望真正理解并发、缓存、流式响应和系统设计的开发者。
>
> 学习方式：本文不是一份只背概念的八股笔记，而是一份以智面项目为案例的学习与实践手册。建议边读边打开源码、运行测试、修改参数、观察日志和 Redis 状态。

## 0. 先判断自己的学习位置

你已经会写传统 Spring 项目的 CRUD，这说明你已经掌握了：

- Controller 接收请求并返回结果。
- Service 编排业务逻辑。
- Mapper 或 Repository 访问数据库。
- 基本的实体、DTO、分页、参数校验和异常处理。

接下来真正需要升级的不是再写更多的 `insert`、`update`，而是回答下面这些问题：

1. 同一时刻有一万个人访问热门题目，数据库会发生什么？
2. 为什么查询结果可以放 Redis，但用户答题记录不能只放 Redis？
3. 两个请求同时给同一个题目加浏览量，怎样保证不丢失？
4. 两个请求同时解锁，怎样保证后来的请求不会删掉前一个请求持有的锁？
5. AI 回答还没有结束时，HTTP 请求为什么不能直接结束？
6. 浏览器如何知道一段文本属于哪一次面试、哪一个事件？
7. 一次面试的“回答完成、评分成功、下一题出现”到底哪一步算提交成功？
8. 代码出了问题时，怎样通过日志、指标和测试定位，而不是凭感觉猜？

这些问题属于系统设计和工程化能力。它们的共同核心是：**在多个请求、多个线程、多个服务组件同时运行时，仍然能够保持正确、可恢复、可观察。**

## 2. 高并发到底在解决什么

### 2.1 高并发不是“代码加一个线程池”

高并发表示在一个时间窗口内，有很多请求同时访问系统。它带来的问题至少有四类：

1. **容量问题**：CPU、内存、连接池、线程池、数据库连接不够。
2. **等待问题**：大量请求都在等待数据库、远程 AI 服务或锁。
3. **正确性问题**：并发更新导致覆盖、重复写入、库存或计数丢失。
4. **稳定性问题**：一个依赖变慢，线程全部阻塞，最终整个服务雪崩。

因此高并发设计不是简单追求“每秒处理更多请求”，而是在明确业务正确性的前提下，减少不必要的等待，并把压力放到适合承受压力的组件上。

### 2.2 用一个请求拆开看

一个题目详情请求可能是：

```text
浏览器
  -> Nginx
  -> Spring Boot
  -> Redis 查询题目缓存
  -> MySQL 查询题目
  -> 返回 JSON
```

如果每次都直接查 MySQL，1000 个并发请求可能同时执行相同 SQL。数据库不仅要返回数据，还要解析 SQL、检查索引、创建结果集、传输数据。即使查询本身很快，连接池也可能先被占满。

使用缓存后，理想路径变成：

```text
大多数请求 -> Redis -> 返回
少量缓存未命中请求 -> MySQL -> 写回 Redis -> 返回
```

这叫 **Cache Aside（旁路缓存）**：应用程序自己决定什么时候读缓存、什么时候查数据库、什么时候删除缓存。

### 2.3 容量估算的最小思维模型

先不要急着优化代码，先估算：

```text
峰值 QPS = 峰值请求数 / 时间窗口秒数
并发数   ≈ QPS × 平均响应时间（秒）
```

例如每秒 200 个请求，平均响应时间 0.2 秒，平均在途请求大约是：

```text
200 × 0.2 = 40 个
```

如果 AI 流式接口平均持续 30 秒，则 20 个新面试请求/秒可能产生：

```text
20 × 30 = 600 条长期占用的流连接
```

这就是为什么 SSE 不能只看普通 CRUD 的 QPS。它会长期占用浏览器连接、服务器连接、代理连接和业务状态。

### 2.4 高并发优化的一般顺序

推荐按下面顺序思考：

1. 先确认功能正确，尤其是并发下不能重复、不能丢失、不能乱序。
2. 用日志和指标找到最慢的依赖，而不是凭感觉优化。
3. 给查询加合适索引，减少 SQL 返回的数据量。
4. 对读多写少的数据使用 Redis 缓存。
5. 对可以异步完成的任务使用队列或定时批处理。
6. 对同一资源的互斥操作使用数据库唯一约束、乐观锁或分布式锁。
7. 最后再考虑线程池、连接池、JVM 参数和水平扩容。

一个很实用的判断是：**如果不知道瓶颈在哪里，就先做观测，不要先加线程。**

## 3. Redis 在智面中的正确定位

### 3.1 Redis 不是“更快的 MySQL”

Redis 是内存数据结构服务，优势是访问快、数据结构丰富、原子命令多，适合做：

- 查询缓存。
- 短期会话或临时上下文。
- 计数器。
- 排行榜。
- 限流器。
- 分布式协调信号。

MySQL 适合做：

- 最终需要长期保存的业务数据。
- 需要复杂查询、关联、事务和审计的数据。
- 用户答题记录、面试报告、题库等事实数据。

在智面中可以用一句话记忆：

> MySQL 负责保存事实，Redis 负责加速访问和协调并发。

如果 Redis 清空后，用户的题目、答题记录、面试报告全部消失，说明这些数据的归属放错了。Redis 可以暂时保存面试上下文，但面试回合和报告仍应落 MySQL。

### 3.2 智面当前 Redis 使用场景

#### 场景 A：题目详情和热门题目缓存

题目详情被大量重复读取，适合缓存。典型流程：

```java
String key = "question:detail:" + id;
Question cached = redisTemplate.opsForValue().get(key);
if (cached != null) {
    return cached;
}

Question question = mapper.selectById(id);
if (question != null) {
    redisTemplate.opsForValue().set(key, question, 10, TimeUnit.MINUTES);
}
return question;
```

这里要理解三个问题：

1. 缓存命中时不访问数据库。
2. 缓存未命中时查数据库并写回。
3. 数据修改或删除后必须删除旧缓存。

`QuestionServiceImpl` 中的缓存失效逻辑就是学习入口。修改数据库成功后再删除缓存，避免数据库事务回滚但缓存已经被提前删除。

#### 场景 B：浏览量计数器

题目浏览量是高频写入。如果每次浏览都执行：

```sql
UPDATE question SET view_count = view_count + 1 WHERE id = ?
```

大量用户会频繁竞争数据库行和连接。更适合先在 Redis 中累加：

```text
question:view:123 = 37
```

定时任务 `ViewCountFlushTask` 周期性把 Redis 增量刷入 MySQL。这里的业务含义是：

```text
请求到达 -> Redis 原子加一 -> 快速返回
定时任务 -> 取出增量 -> MySQL 批量累加
```

这叫 **最终一致性**。用户刚浏览后，数据库中的数字可能暂时没有变化，但系统最终会把增量写入数据库。适合浏览量这种允许短暂延迟的数据，不适合支付余额或考试成绩。

#### 场景 C：AI 面试上下文

AI 多轮对话需要历史消息。上下文短期、读取频繁，而且可以根据面试生命周期清理，因此放 Redis 很合适。`InterviewContextManager` 负责：

- 追加用户消息和 AI 消息。
- 限制上下文长度。
- 保留完整的最近一轮问答。
- 面试结束后删除上下文。

注意：上下文只是模型调用的辅助数据，不能替代 `interview_message`、`interview_turn` 等数据库记录。

#### 场景 D：面试请求互斥锁

同一个面试会话不应该同时处理两次“下一条回答”。否则可能出现：

- 两个 AI 流同时生成。
- 回合顺序错乱。
- 一次用户回答被评分两次。
- 下一题被生成两次。

`RedisLockManager` 的锁键类似：

```text
interview:chat:lock:{sessionId}
```

它使用随机 token 区分锁的持有者，不能只使用一个固定值。

## 4. Cache Aside 的完整正确性

### 4.1 查询流程

```text
1. 读 Redis
2. 命中：直接返回
3. 未命中：读 MySQL
4. MySQL 有数据：写 Redis，设置 TTL
5. 返回结果
```

### 4.2 更新流程为什么通常是“先库后缓存删除”

推荐流程：

```text
1. 更新 MySQL
2. 事务提交成功
3. 删除 Redis 旧缓存
```

不要简单理解为“更新数据库后更新缓存”。直接更新缓存会引出更多问题：缓存对象可能包含多个字段，更新逻辑可能与数据库事务不一致，多个写请求还可能把旧值重新写回。

一种常见竞态是：

```text
线程 A：读到旧值
线程 B：更新数据库，删除缓存
线程 A：把旧值写回缓存
```

因此写库后删除缓存仍然可能遇到极端竞态。高要求场景可以使用：

- 延迟双删。
- 消息队列按实体串行失效。
- 版本号校验。
- 直接绕过缓存读取强一致数据。

智面题库的修改频率远低于读取频率，当前“事务提交后删除缓存”是合理的第一版方案；之后可以增加缓存重建锁和监控。

### 4.3 缓存穿透、击穿、雪崩

#### 缓存穿透

请求一个不存在的题目 ID，缓存没有，数据库也没有。恶意请求可以不断打数据库。

应对：

- 参数校验，拒绝非法 ID。
- 对不存在结果缓存短 TTL 的空值。
- 布隆过滤器拦截明显不存在的 ID。
- 限制单 IP 或用户的请求频率。

#### 缓存击穿

某个特别热门的题目缓存刚好过期，瞬间大量请求同时查数据库。

应对：

- 互斥锁，只允许一个请求重建缓存。
- 逻辑过期，后台异步刷新。
- 给 TTL 增加随机抖动。

#### 缓存雪崩

大量 key 同时过期，或 Redis 整体不可用，导致请求集中打向数据库。

应对：

- TTL 增加随机值，避免同一时刻过期。
- 缓存分批预热。
- Redis 高可用和持久化。
- 数据库限流、降级和熔断。
- 非关键功能允许返回降级结果。

### 4.4 TTL 是保护机制，不是正确性机制

TTL 可以防止旧数据永久存在，也可以回收锁和临时上下文，但 TTL 到期本身不保证业务正确。比如锁的 TTL 过期后，旧持有者可能仍然在执行；这就是为什么锁释放必须校验 token，业务流程还要有状态判断。

## 5. Lua 脚本：从原子性开始理解

### 5.1 Redis 的单条命令为什么安全

Redis 处理命令时，会把一条命令完整执行完，再处理下一条命令。下面的命令是原子的：

```text
INCR question:view:123
SET lock-key token NX EX 900
HINCRBY user:1 score 10
```

但是下面两条命令合起来不是原子的：

```text
GET lock-key
DEL lock-key
```

### 5.2 为什么普通 GET + DEL 会误删锁

假设锁 TTL 是 10 秒：

```text
时间 0：线程 A 获取锁，值为 token-A
时间 11：A 执行太久，锁过期
时间 12：线程 B 获取锁，值为 token-B
时间 13：A 执行结束，GET 读到 token-B 或直接 DEL
时间 14：A 删除了 B 的锁
```

A 已经不再拥有这把锁，却把 B 的锁删掉了。即使写成“先比较再删除”：

```text
if GET(key) == myToken {
    DEL(key)
}
```

在 `GET` 和 `DEL` 之间仍然可能被另一个客户端插入操作。

### 5.3 Lua 把判断和删除放在同一个 Redis 执行单元

`RedisLockManager` 使用的核心脚本可以抽象成：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
end
return 0
```

参数含义：

- `KEYS[1]`：锁的 Redis key。
- `ARGV[1]`：当前线程生成的 token。
- 返回 `1`：成功删除自己的锁。
- 返回 `0`：key 不存在或 token 不匹配。

这段脚本执行期间，Redis 不会穿插另一个普通客户端命令，所以比较和删除具有原子性。

### 5.4 Java 中如何执行 Lua

项目中的调用可以按这个模型理解：

```java
DefaultRedisScript<Long> script =
        RedisScript.of("...lua...", Long.class);

Long result = redisTemplate.execute(
        script,
        Collections.singletonList(lockKey),
        token
);
```

RedisTemplate 会把：

```text
KEYS[1] <- lockKey
ARGV[1] <- token
```

传给 Redis。学习 Lua 时先记住这条规则：**key 放 KEYS，普通参数放 ARGV。** 在 Redis Cluster 中，key 的声明也关系到脚本能否被正确路由。

### 5.5 Lua 不等于所有操作都要写 Lua

适合 Lua 的场景：

- 判断值后删除或修改。
- 判断库存后扣减。
- 限流时检查计数并递增。
- 一次操作多个相关 key，且必须整体完成。

不适合 Lua 的场景：

- 复杂业务流程。
- 需要访问 MySQL 的操作。
- 执行时间很长的计算。
- 把大量数据传给 Redis 脚本处理。

Lua 脚本运行时会占住 Redis 执行线程。脚本过长会阻塞其他请求，所以脚本应短小、确定、只处理必要数据。

### 5.6 项目中的第二个 Lua 示例：取出并删除计数

`ViewCountFlushTask` 使用 Lua 兼容 Redis 5：

```lua
local value = redis.call('get', KEYS[1])
if value then
    redis.call('del', KEYS[1])
end
return value
```

它解决的是“读取增量后删除 key”的原子性问题。不能先 `GET` 再 `DEL`，因为新的浏览请求可能在两条命令之间执行 `INCR`，随后被误删。

正确的时序是：

```text
定时任务执行 Lua：读取 37 并删除 key
新的浏览请求执行 INCR：从 0 增加为 1
定时任务把 37 写入 MySQL
下一轮再处理新的 1
```

### 5.7 Redis 5 与 Redis 6 的兼容性

不同 Redis 版本支持的命令不完全相同。Redis 6.2 才有 `GETDEL`，如果部署环境是 Redis 5，就不能假设它存在。项目当前通过 Lua 实现等价的原子操作，因此本地 Redis `5.0.14.1` 也可以运行。

学习时养成习惯：

```bash
redis-cli INFO server
redis-cli COMMAND INFO GETDEL
```

先确认线上版本和命令支持，再选择实现。

## 6. 分布式锁应该怎样理解

### 6.1 锁解决的是“同一资源的互斥”，不是性能问题

以面试会话为例，同一个 `sessionId` 的并发聊天请求应该互斥；不同用户、不同面试会话不需要互相阻塞。

锁的粒度应当是：

```text
interview:chat:lock:{sessionId}
```

而不是全局只有一把：

```text
interview:chat:lock
```

全局锁会让所有用户串行，吞吐量会迅速下降。

### 6.2 一把可用的 Redis 锁至少需要什么

1. `SET key token NX EX ttl`：只有 key 不存在时获取，并设置过期时间。
2. 每个持有者有不同 token：防止误删别人的锁。
3. 释放时使用 Lua 比较 token 后删除。
4. TTL 必须覆盖通常执行时间，但不能无限长。
5. 业务层要有状态检查，不能只依赖锁。
6. 对关键操作考虑幂等键或数据库唯一约束。

### 6.3 为什么 TTL 不是万能的

如果 AI 模型响应超过锁 TTL，锁会自动释放，第二个请求可能进入。解决思路有：

- 设置合理的 TTL。
- 续租机制，但续租本身也需要可靠实现。
- 使用任务队列，让同一会话的任务按顺序消费。
- 用数据库状态机拒绝已经处理过的回合。
- 用唯一业务 ID 保证重复请求只落一次库。

当前智面已经把“状态机 + token 锁 + 事务持久化”组合起来。你学习时要把它看成三道防线：

```text
锁：尽量阻止并发进入
状态：即使并发进入，也拒绝非法状态转换
事务/唯一约束：即使发生重复尝试，最终数据仍然正确
```

### 6.4 什么时候不应该使用分布式锁

如果数据库可以直接保证约束，优先使用数据库能力。例如收藏夹的唯一约束可以防止同一用户重复收藏；条件更新可以防止报告重复完成。

不要为了“看起来高级”给每个 CRUD 都加 Redis 锁。锁会增加网络往返、超时和死锁风险。

## 7. SSE 流式输出：从 HTTP 到浏览器

### 7.1 SSE 是什么

SSE（Server-Sent Events）是服务器通过一个长期保持的 HTTP 响应，持续向浏览器推送文本事件。它的特点是：

- 客户端到服务器仍然是普通 HTTP 请求。
- 服务器到客户端可以持续发送数据。
- 文本协议，浏览器或前端可以逐块读取。
- 通常是单向推送，不适合客户端持续发送大量实时消息。

一个最小 SSE 事件是：

```text
event: delta
data: 你好

```

空行表示一个事件结束。常见事件字段：

```text
event: delta
data: {"content":"请介绍一下你的项目"}

event: done
data: {"sessionId":1,"turnId":8}

event: error
data: {"message":"模型调用失败"}

```

### 7.2 为什么 AI 面试适合 SSE

AI 模型通常不是一次性返回完整答案，而是不断生成 token。一次性响应需要等待几十秒，用户会看到长时间空白；SSE 可以让用户实时看到生成过程。

用户体验流程变成：

```text
用户提交回答
  -> 后端创建流
  -> AI 产生一小段文本
  -> 后端发送 delta
  -> 浏览器追加到当前消息
  -> AI 继续生成
  -> 后端持久化完整回答和评分
  -> 发送 done
```

### 7.3 后端要区分三个生命周期

#### HTTP 生命周期

连接是否还存在、客户端是否断开、代理是否超时。

#### 模型流生命周期

模型是否继续产生内容、是否完成、是否报错、是否超时。

#### 业务回合生命周期

用户回答是否已经保存、评分是否已经保存、当前回合是否完成、下一题是否生成。

这三个生命周期不是一回事。浏览器断开并不一定意味着模型立刻停止；模型完成也不代表数据库事务已经提交。

### 7.4 智面后端的核心流程

阅读 `InterviewServiceImpl` 时，可以按下面顺序画时序图：

```text
Controller
  -> 校验 session 和当前状态
  -> Redis 获取 session 锁
  -> 保存用户消息或准备上下文
  -> 调用 Spring AI 流
  -> 每个片段发送 SSE delta
  -> 订阅完成
  -> 解析 AI 的评分和下一题
  -> InterviewPersistenceService 开启事务
       保存 assistant 消息
       保存面试回合
       更新回合状态
  -> 事务提交
  -> 清理 Redis 上下文
  -> 生成下一题或报告
  -> 发送 SSE done
  -> token 校验后释放锁
```

其中最重要的概念是：**流式输出是展示过程，事务持久化是业务结果。** 不能因为已经发送过几个 `delta` 就认为数据库已经成功。

### 7.5 前端为什么不能只用字符串拼接

`frontend/src/api/interview.ts` 负责读取 `fetch` 返回的 `ReadableStream`。浏览器拿到的数据块可能被切在任意位置：

```text
数据块 1：event: del
数据块 2：ta\ndata: 你好\n\n
```

所以前端必须：

1. 用 `TextDecoder` 解码字节。
2. 把新数据追加到缓冲区。
3. 按空行拆分完整事件。
4. 保留最后一个不完整片段，等下一次读取。
5. 解析 `event` 和 `data`。
6. 收到 `delta` 就追加内容。
7. 收到 `done` 才把本轮标记为完成。
8. 收到 `error` 或 EOF 未收到终止事件时，显示失败并允许重试。

这也是当前前端代码中 `terminalReceived` 和最后 flush 逻辑存在的原因。不能把一次 `reader.read()` 当成一个完整事件。

### 7.6 SSE 常见问题

#### 问题一：代理缓冲

Nginx 可能缓存响应，导致后端已经发送内容，浏览器却很久才收到。需要针对 SSE 关闭代理缓冲，并正确设置：

```text
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
X-Accel-Buffering: no
```

#### 问题二：连接断开

前端关闭页面、网络变化、Nginx 超时都可能使连接断开。后端应释放订阅和锁，前端应清理 loading 状态。

#### 问题三：重复提交

用户双击提交或网络重试可能创建两条流。后端必须用会话锁、回合状态和幂等设计保护。

#### 问题四：先发 done 后写库

如果先通知前端成功，随后数据库事务失败，用户看到的结果和服务端事实不一致。正确顺序通常是：

```text
完成模型解析 -> 事务提交成功 -> 发送 done
```

如果业务必须先展示结果，也要把事件命名为 `model_complete`，不要冒充 `persisted`。

#### 问题五：超时只断流，不改变状态

只关闭网络连接是不够的。服务端还要决定当前回合是失败、可重试，还是保持处理中。智面当前通过失败状态和回合状态记录这件事。

## 8. 用状态机理解一场面试

很多复杂 bug 不是语法错误，而是状态转换不清楚。建议把面试会话和回合分别画成状态机。

### 8.1 面试会话状态

```text
进行中(0) -> 已完成(1)
进行中(0) -> 已取消(2)
```

报告生成还可能有：

```text
未生成 -> 生成中 -> 成功
                  \-> 失败
```

### 8.2 面试回合状态

```text
待回答 -> 评分中 -> 评分成功
                   \-> 评分失败
```

每个箭头都要问：

- 谁可以触发？
- 触发前必须满足什么条件？
- 重复触发会怎样？
- 触发失败后能否重试？
- 数据库如何表示这个状态？

### 8.3 条件更新比“先查再改”更可靠

不够严谨的写法：

```text
SELECT status FROM interview_report WHERE session_id = ?
如果 status == 0：UPDATE status = 1
```

两个请求可能同时查到 0，然后都认为自己可以完成。

更可靠的写法：

```sql
UPDATE interview_report
SET status = 1, score = ?, update_time = NOW()
WHERE session_id = ? AND status = 0;
```

再检查影响行数：

- 影响 1 行：本次完成成功。
- 影响 0 行：可能已经完成、已经失败或记录不存在。

项目中的 `markSuccess` 和 `markFailed` 就是这个思路。它体现了一个重要编程思想：**让数据库直接执行带条件的状态转换，而不是把判断全部放在 Java 内存中。**

## 9. 事务边界：什么应该一起成功

`InterviewPersistenceService` 的存在，是为了把一次面试回合的持久化集中到一个事务中。一次评分回合通常需要一起完成：

1. 保存用户消息。
2. 保存 AI 消息。
3. 保存面试回合。
4. 更新会话进度或报告状态。

如果第 1、2 步成功，第 3 步失败，就会产生半条数据。事务可以让它们一起提交或一起回滚。

### 9.1 Redis 操作和 MySQL 事务不是同一个事务

`@Transactional` 只能管理 Spring 配置的数据库事务，不能自动回滚已经执行的 Redis 命令，也不能回滚已经发给 AI 模型的请求。

因此要区分：

```text
数据库事务：保证 MySQL 内部多条写入的一致性
Redis 操作：需要自己设计顺序、补偿和 TTL
远程调用：需要超时、重试、幂等和降级
```

### 9.2 为什么通常先提交数据库，再清理上下文

如果先删除 Redis 上下文，再写数据库失败，本轮历史可能丢失；如果先写库提交成功，再删除上下文，即使删除失败，也可以通过 TTL 回收，或者下次重新加载数据库历史。

所以当前流程采用：

```text
MySQL 事务提交 -> 清理 Redis 上下文 -> 继续下一步
```

### 9.3 事务同步回调的意义

题目修改后的缓存删除使用了事务提交后的回调。原因是：

```text
事务还没提交时删除缓存
数据库随后回滚
缓存暂时没有旧数据，下一次读可能把旧数据库值重新写入
```

把缓存删除放到 `afterCommit`，能让缓存失效和数据库成功提交保持更好的顺序。

## 10. 编程思想：从“把代码写出来”到“让系统长期正确”

### 10.1 单一职责

一个类最好有一个主要变化原因：

- Controller 负责协议转换和参数接收。
- Service 负责业务规则。
- Persistence Service 负责事务内写入组合。
- RedisLockManager 负责锁的获取和释放。
- ContextManager 负责上下文生命周期。
- Mapper 负责 SQL。

如果 `InterviewServiceImpl` 变得很长，不要立刻把每十行代码抽成一个方法；先按变化原因划分边界。当前抽出 `InterviewPersistenceService`，是因为事务写入组合与流式编排的变化原因不同。

### 10.2 先定义不变量

不变量就是任何时刻都应该成立的规则，例如：

- 一个面试回合只能被成功评分一次。
- 一个用户不能重复收藏同一个题目。
- 题目浏览量只能增加，不能因为并发刷库而减少。
- 同一个面试会话同一时刻最多有一个进行中的回答流。
- `done` 事件只在持久化成功后发送。

写代码之前先写出不变量，才能选择合适的数据库约束、锁、状态条件和测试。

### 10.3 幂等性

幂等是同一个业务请求执行一次或多次，最终结果一样。常见来源：

- 浏览器重试。
- 用户双击。
- 网关重试。
- 消费者重复消费。
- SSE 断开后前端重新提交。

实现方式：

- 请求携带唯一 `requestId`，数据库建立唯一索引。
- 使用状态条件更新。
- 使用业务唯一键，例如 `user_id + question_id`。
- 操作前检查已完成状态，但不能只依赖内存检查。

收藏夹的唯一约束、面试报告的条件更新、面试锁都属于幂等和并发控制的不同层次。

### 10.4 失败优先设计

不要只设计成功路径，还要逐个回答：

```text
Redis 挂了怎么办？
MySQL 慢了怎么办？
AI 超时怎么办？
客户端中途关闭怎么办？
同一个请求重试怎么办？
定时任务执行到一半进程宕机怎么办？
```

例如浏览量刷库任务：

1. 原子取出并删除 Redis 增量。
2. 尝试批量写 MySQL。
3. MySQL 失败时，把取出的增量恢复回 Redis。
4. 记录日志，等待下一轮重试。

它仍然不是严格的分布式事务，但比“取出后失败就直接丢失”可靠得多。

### 10.5 让日志回答问题

关键日志应该包含：

- `sessionId`。
- `turnId`。
- `userId`。
- 请求或流的 traceId。
- 状态转换前后的状态。
- Redis key 的业务类型，不要打印敏感 token。
- AI 调用耗时和异常类型。

不要在生产日志中打印完整用户回答、AI Key、JWT 或 Redis 锁 token。日志要帮助排错，也要保护隐私。

### 10.6 测试是设计工具，不只是验收工具

当前项目已经有 Service 测试、面试持久化测试、缓存提交后失效测试和 AI 候选题测试。阅读测试时，关注它们表达了什么业务规则：

```text
AiQuestionCandidateServiceImplTest
  -> 正式题库中已有归一化标题时不能重复收录

InterviewPersistenceServiceTest
  -> 用户消息、AI 消息和回合必须在一个事务方法中组合

QuestionServiceImplTest
  -> 数据库事务提交后才删除题目缓存

AnswerServiceImplTest
  -> 排行榜类型非法或 limit 超过上限时拒绝请求
```

好的测试名称本身就是业务文档。

## 11. 你应该如何一步步学习 Redis

### 阶段 1：命令和数据结构

目标：能在命令行中独立完成基础操作。

必须掌握：

```text
SET / GET / DEL
SET NX EX
INCR / INCRBY
HSET / HGET / HINCRBY
SADD / SISMEMBER
ZADD / ZRANGE
EXPIRE / TTL
SCAN
```

练习：

1. 为一个题目实现浏览量 `INCRBY`。
2. 用 Hash 保存用户学习统计。
3. 用 Set 保存收藏题目 ID。
4. 用 ZSet 实现排行榜。
5. 给所有临时 key 设置 TTL，并观察过期。

验收标准：你能解释每种结构的时间复杂度、适用场景和过期策略。

### 阶段 2：Spring Data Redis

目标：理解 Java 对 Redis 命令的映射，而不是只会复制 `redisTemplate.opsForValue()`。

学习内容：

- `RedisTemplate` 和序列化器。
- String、JSON、Hash、Set、ZSet 的 Java API。
- key 命名规范。
- TTL 和空值缓存。
- 连接池、超时和异常处理。
- 测试时如何清理 key。

练习：给智面题目详情增加一个独立缓存服务，并写命中、未命中、失效三个测试。

### 阶段 3：缓存一致性

目标：能够解释“先删缓存还是先更新数据库”以及每种方案的风险。

需要自己画出这些时序：

- 读未命中。
- 写库后删缓存。
- 并发读写。
- Redis 不可用。
- 数据库回滚。

练习：故意让缓存删除失败，观察系统是否仍能依靠 TTL 恢复；再增加日志和重试策略。

### 阶段 4：Lua 和分布式锁

目标：能独立写出“校验 token 后删除”和“取出后删除”的 Lua 脚本。

实践顺序：

1. 用 `SET NX EX` 写一个最简单锁。
2. 用错误的 GET + DEL 制造误删锁问题。
3. 用 Lua 修复。
4. 增加 token 不匹配测试。
5. 模拟 TTL 到期，理解锁失效风险。
6. 用状态机和唯一约束补上锁之外的保护。

验收标准：你能解释为什么“Redis 单线程”不代表多条命令天然原子，以及 Lua 的原子边界在哪里。

### 阶段 5：高并发计数和异步刷库

目标：理解“请求快速返回，数据稍后落库”的最终一致性方案。

以 `ViewCountFlushTask` 为实验对象：

1. 用多个线程并发执行 `INCRBY`。
2. 定时任务原子取出增量。
3. 批量写入 MySQL。
4. 在写库前抛异常，验证增量恢复。
5. 连续运行多轮，检查是否重复计算或丢失。

验收标准：能够说明这套方案适合浏览量，不适合考试分数，并能说出原因。

## 12. 你应该如何一步步学习 SSE

### 阶段 1：先不用 AI，做一个假流

先写一个后端接口，每隔 500 毫秒发送一条：

```text
event: delta
data: 第 1 段

event: delta
data: 第 2 段

event: done
data: {}

```

前端只完成三件事：读取、拆分事件、追加文本。这样可以把 SSE 协议和 AI 调用分开学习。

### 阶段 2：模拟异常和断开

分别测试：

- 第 3 个片段后发送 error。
- 后端直接关闭连接。
- 前端取消读取。
- 数据块刚好切断在 `event:` 或 JSON 中间。
- 最后一段没有额外换行。

验收标准：界面不会无限 loading，且未收到终止事件时不会误判为成功。

### 阶段 3：接入 Spring AI

接入顺序：

1. 后端先拿到模型流，不做数据库写入。
2. 把模型片段映射为 `delta`。
3. 完成时拼出完整 AI 文本。
4. 解析评分和下一题。
5. 事务保存结果。
6. 提交成功后发送 `done`。

不要一开始把模型、Redis、MySQL、SSE、报告生成全部写在一个方法中，否则出问题时无法判断是哪一层的错误。

### 阶段 4：理解取消和超时

至少实现：

- 单次模型调用超时。
- 客户端断开时取消订阅。
- 同一会话的重复提交被拒绝。
- 异常后锁能够释放。
- 失败回合能够查看和重试。

### 阶段 5：用 Nginx 验证真实部署

本地直接访问 Spring Boot 时可能一切正常，经过 Nginx 后要额外验证：

- SSE 是否被缓冲。
- 连接超时是否足够。
- `/api` 是否正确反向代理。
- 前端静态文件刷新时是否回退到 `index.html`。
- WebSocket 和 SSE 是否混用导致配置错误。

## 13. 推荐的 8 周学习计划

### 第 1 周：并发基础

学习 Java 线程、线程池、锁、CAS、可见性、有序性和原子性。用小程序演示多个线程给同一个计数器加一，比较普通 `int`、`synchronized` 和 `AtomicInteger`。

完成数据结构、TTL、序列化、key 规范、命令行练习。把题目详情、浏览量、排行榜分别映射到 String、计数器和 ZSet。

### 第 3 周：缓存设计

完成题目详情缓存、热门题目缓存、缓存失效和异常降级。画出穿透、击穿、雪崩的时序图，并为每一种情况写一个测试或实验。

### 第 4 周：Lua 与锁

实现锁、token、Lua 释放、超时和重试。用并发测试验证同一面试会话不能同时完成两个回合。

### 第 5 周：事务、幂等与状态机

整理 `interview_session`、`interview_turn`、`interview_report` 的状态。为每个状态转换写 SQL 条件和测试。重点学习影响行数、唯一索引和事务回滚。

### 第 6 周：SSE 协议

### 第 7 周：观测和压测

学习日志结构化、接口耗时、数据库慢查询、Redis `INFO`、线程池指标。用 JMeter、k6 或同类工具压测题目查询、排行榜和 SSE 连接。

### 第 8 周：部署与复盘

用 Docker 部署 MySQL、Redis、Spring Boot 和前端 Nginx。模拟重启、Redis 清空、AI 超时、数据库不可用，记录系统如何恢复。

## 15. 当前项目下一步应该做什么

### 15.1 先固定当前基线

每次学习新模块前，先执行：

```bash
mvn test
```

当前项目已验证：后端测试通过，前端生产构建通过。前端构建仍有主包体积偏大的提示，属于后续性能阶段，不要在学习 Redis 和 SSE 的第一阶段同时处理。

### 15.2 第一优先级：写 Redis 实验代码

建议在测试目录增加一个独立实验类，依次验证：

- `SET NX EX` 获取锁。
- 错误释放锁会造成什么问题。
- Lua 正确释放锁。
- Lua 取出并删除计数。
- TTL 到期。
- Redis 异常时业务降级。

这些实验不要一开始放进正式业务，先让每个行为可观察。

### 15.3 第二优先级：补面试并发测试

至少覆盖：

- 同一 `sessionId` 两个并发提交，只有一个成功。
- 不同 `sessionId` 可以并行。
- AI 流超时后锁最终释放。
- 持久化失败后不能发送成功完成状态。
- 已完成回合重复请求不会重复计分。

### 15.4 第三优先级：补 SSE 集成测试

单元测试无法完全验证浏览器的字节分块，因此需要一个轻量集成测试：

- 后端分多次写入事件。
- 客户端按任意边界读取。
- 验证事件顺序和最终拼接内容。
- 验证异常 EOF 不被当成成功。

### 15.5 第四优先级：做一次真实压测

不要只看本机浏览器手动点击。为以下接口准备压测数据：

- 题目详情。
- 热门题目。
- 排行榜。
- 面试创建。
- SSE 面试聊天。

记录：P50、P95、P99 响应时间、错误率、Redis 命中率、数据库连接数、线程池队列长度和长连接数量。

### 15.6 第五优先级：部署工程化

面试展示版本可以按下面结构部署：

```text
公网域名
   |
   v
Nginx：HTTPS、静态文件、/api 反向代理、SSE 配置
   |
   v
Spring Boot
   |             |
   v             v
MySQL          Redis
```

部署时重点检查：

- 敏感配置使用环境变量，不进入 Git。
- MySQL 和 Redis 不直接暴露公网。
- 数据库迁移脚本按顺序执行。
- Spring Boot 启动时能连接依赖。
- Nginx 正确代理 SSE，关闭缓冲并设置超时。
- 使用 `/api/health` 做健康检查。
- 日志和备份可查看。

## 16. 面试时如何讲清楚这些技术

### 16.1 如何回答“你为什么用 Redis”

可以这样组织：

```text
智面中的题目详情和热门题目是读多写少的数据，使用 Cache Aside 降低数据库重复查询；
浏览量使用 Redis 原子计数并定时批量刷库，降低高频写数据库的压力；
AI 面试上下文是短期数据，放 Redis 并通过 TTL 回收；
同一面试会话的并发提交用带 token 的 Redis 锁做互斥，最终正确性仍由数据库事务、状态条件和唯一约束兜底。
```

### 16.2 如何回答“为什么使用 Lua”

```text
Redis 的单条命令是原子的，但 GET 和 DEL 两条命令之间可能插入其他客户端操作。
释放分布式锁时，如果不比较 token 就可能误删别人的锁。
Lua 把比较和删除放在同一次 Redis 脚本执行中，保证操作不可插入；
项目的浏览量刷库也用同样思路原子地取出并删除增量，避免新产生的计数被误删。
```

### 16.3 如何回答“为什么使用 SSE”

```text
AI 生成答案具有明显的等待时间，SSE 可以把模型生成的片段实时推送给浏览器，改善等待体验。
前端不能把一次网络读取当成一个事件，而要按空行拆分 SSE 帧并处理 delta、done、error。
后端把流式展示和业务持久化分开，只有数据库事务提交成功后才发送业务完成事件；
同时处理客户端断开、模型超时、重复提交和锁释放。
```

### 16.4 如何回答“高并发下怎么保证正确”

```text
先区分读压力、写压力和长连接压力；
读多写少用缓存，计数用 Redis 原子累加和异步批量刷库；
同一资源通过唯一约束、条件更新、幂等键和必要的分布式锁控制重复；
关键写入放在数据库事务中；
最后通过限流、超时、降级、监控和压测验证方案，而不是只依赖代码表面看起来合理。
```

## 17. 最后形成自己的工程判断

以后遇到一个新需求，按照这张清单思考：

### 数据

- 这是事实数据还是临时数据？
- 是否必须持久化？
- 能否接受最终一致性？
- 是否需要历史和审计？

### 并发

- 哪个资源会被多个请求同时修改？
- 能否用数据库唯一约束或条件更新解决？
- 锁的粒度是什么？
- 锁失效后会发生什么？

### Redis

- key 如何命名？
- TTL 是多少？
- 缓存未命中怎么办？
- Redis 不可用时是否降级？
- 是否存在穿透、击穿、雪崩风险？

### 远程调用

- 超时时间是多少？
- 是否可以重试？
- 重试会不会导致重复写入？
- 是否需要幂等键？
- 失败后用户能否恢复？

### 可观测性

- 如何知道请求慢在哪里？
- 如何知道缓存命中率？
- 如何知道 SSE 断开原因？
- 如何知道定时任务是否丢数据？
- 出问题时是否有可以复现的测试？

当你能稳定回答这些问题时，你的能力就从“会写 Spring CRUD”进入了“能够设计和维护一个真实系统”的阶段。

## 18. 本文对应的源码阅读顺序

最后给出一次完整的阅读路线，建议严格按顺序：

1. 阅读 `InterviewController`，只看接口输入输出和 SSE 返回类型。
2. 阅读 `InterviewServiceImpl.createInterview`，看一次面试如何创建。
3. 阅读 `InterviewServiceImpl.chat`，标出加锁、读上下文、调用 AI、完成和异常路径。
4. 阅读 `InterviewPersistenceService`，理解事务方法为什么独立出来。
5. 阅读 `InterviewContextManager`，观察 Redis 临时上下文如何裁剪和清理。
6. 阅读 `RedisLockManager`，逐行解释 `SET NX EX`、token 和 Lua。
7. 阅读 `ViewCountFlushTask`，解释计数为什么允许最终一致性。
8. 阅读 `QuestionServiceImpl`，理解事务提交后缓存失效。
9. 阅读 `frontend/src/api/interview.ts`，手动模拟被切开的 SSE 数据块。
10. 阅读对应测试，尝试先删掉一个保护逻辑，观察哪个测试失败。

每读完一个文件，都写三句话：

```text
它解决了什么问题？
它依赖了什么前提？
它在什么异常情况下仍然可能失败？
```

这三句话就是从代码阅读走向系统设计的桥梁。
