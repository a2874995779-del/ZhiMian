## 一、本任务要实现什么

两个接口:

1. **提交答题结果**:`POST /api/questions/{id}/answer`,登录用户提交 `{ "result": 1 }`(1 答对 / 0 答错)。不管对错都要写一行 `answer_record`(纯流水表,只插不改);**答对**的时候,额外把这个用户在 Redis 里的"总榜"和"日榜"两个 ZSet 分数各 +1。
2. **查排行榜**:`GET /api/ranks/answer?type=total&limit=10`,直接读 Redis ZSet 取 TopN(不查 `answer_record` 表),再批量查这几个用户的昵称拼成返回结构。

**为什么排行榜不直接对 `answer_record` 表 `GROUP BY user_id ORDER BY COUNT(*) DESC LIMIT 10`**:这张表在你之前的表设计里已经能想到——它没有为"按用户分组计数排序"这种查询建对应的索引(`idx_user_time` 是给"查某个用户自己的答题历史"用的,左边是 `user_id` 但排序字段是 `create_time` 不是聚合结果),而且这是排行榜接口,大概率是首页/个人主页会频繁访问的高频查询,每次都全表 `GROUP BY` 聚合代价很高。改用 Redis **ZSet(有序集合)**:每次答对只是对一个 member 的 score 做 `+1`(`ZINCRBY`,底层跳表实现,O(logN)),取榜单是 `ZREVRANGE ... WITHSCORES`(O(logN + M),M 是取的条数)——写和读都是这张表做不到的复杂度。

**`answer_record` 表存在的意义,不是给排行榜用的,是"事实来源"(source of truth)**:如果 Redis 数据丢了(重启没配持久化、或者被误删),榜单可以靠这张表重新跑一遍统计脚本重建;反过来如果只有 Redis 没有这张表,数据一旦丢失就永久丢了,无法恢复。这是"MySQL 与 Redis 双写"场景下一个常见的设计模式:**允许 Redis 里的实时视图和 MySQL 里的持久化事实之间存在短暂的最终不一致(比如 Redis 刚好在两次操作之间挂了,丢了一次 `ZINCRBY`),但不允许数据永久丢失**——这也是接下来 review 会问你的问题之一。

先把这次用到的 Redis 命令和 `StringRedisTemplate` 的 API 对应关系过一遍:

| Redis 命令 | 作用 | `StringRedisTemplate` API |
|------|------|------|
| `ZINCRBY key increment member` | 给 `member` 的 score **原子性** `+increment`(`member` 不存在则视为从 0 开始,顺带把它加入集合) | `opsForZSet().incrementScore(key, member, delta)` |
| `ZREVRANGE key start stop WITHSCORES` | 按 score **从高到低**取名次区间内的 member 和它的 score | `opsForZSet().reverseRangeWithScores(key, start, end)` |
| `EXPIRE key seconds` | 给已存在的 key 设置过期时间 | `expire(key, timeout, unit)` |
| `TTL key` | 查看剩余过期时间,`-1` 表示永不过期,`-2` 表示 key 不存在 | `getExpire(key)` |

### Step 8:`AnswerServiceImpl` —— 提交答题

`service/impl/AnswerServiceImpl.java`:

```java
package com.zhimian.service.impl;

import com.zhimian.common.ErrorCode;
import com.zhimian.common.UserContext;
import com.zhimian.exception.BusinessException;
import com.zhimian.mapper.AnswerRecordMapper;
import com.zhimian.mapper.QuestionMapper;
import com.zhimian.mapper.UserMapper;
import com.zhimian.model.dto.AnswerSubmitDTO;
import com.zhimian.model.entity.AnswerRecord;
import com.zhimian.model.entity.Question;
import com.zhimian.model.entity.User;
import com.zhimian.model.vo.RankVO;
import com.zhimian.service.AnswerService;
import lombok.RequiredArgsConstructor;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.ZSetOperations;
import org.springframework.stereotype.Service;

import java.time.LocalDate;
import java.time.format.DateTimeFormatter;
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Set;
import java.util.concurrent.TimeUnit;

@Service
@RequiredArgsConstructor
public class AnswerServiceImpl implements AnswerService {

    private static final String RANK_TOTAL_KEY = "zhimian:rank:answer:total";
    private static final String RANK_DAILY_PREFIX = "zhimian:rank:answer:";
    private static final long RANK_DAILY_TTL_DAYS = 7;
    private static final DateTimeFormatter DAILY_KEY_FORMATTER = DateTimeFormatter.ofPattern("yyyyMMdd");

    private final AnswerRecordMapper answerRecordMapper;
    private final QuestionMapper questionMapper;
    private final UserMapper userMapper;
    private final StringRedisTemplate redisTemplate;

    @Override
    public void submitAnswer(Long questionId, AnswerSubmitDTO dto) {
        Question question = questionMapper.selectById(questionId);
        if (question == null) {
            throw new BusinessException(ErrorCode.NOT_FOUND, "题目不存在");
        }

        Long userId = UserContext.getUserId();

        AnswerRecord record = new AnswerRecord();
        record.setUserId(userId);
        record.setQuestionId(questionId);
        record.setResult(dto.getResult());
        answerRecordMapper.insert(record);

        if (dto.getResult() == 1) {
            String member = userId.toString();

            redisTemplate.opsForZSet().incrementScore(RANK_TOTAL_KEY, member, 1);

            String dailyKey = RANK_DAILY_PREFIX + LocalDate.now().format(DAILY_KEY_FORMATTER);
            redisTemplate.opsForZSet().incrementScore(dailyKey, member, 1);
            // 只在这把 key 第一次被创建出来时设置 7 天过期,避免每次答题都重新续期
            Long ttl = redisTemplate.getExpire(dailyKey);
            if (ttl != null && ttl == -1) {
                redisTemplate.expire(dailyKey, RANK_DAILY_TTL_DAYS, TimeUnit.DAYS);
            }
        }
    }

    // getRank 见下一步
}
```

【讲解】

- **先查 `questionMapper.selectById(questionId)` 判空,再写答题记录**:防止客户端传一个根本不存在的 `questionId`,往 `answer_record` 里插一条指向"幽灵题目"的垃圾数据。这一步查询的开销很小,换来的是数据完整性,值得做。
- **不管答对答错,`answerRecordMapper.insert(record)` 都要执行**:这张表是"流水表",职责是完整记录每一次答题行为,不是只记对的——用户查"我的答题历史"时错题也要能看到。只有下面涉及排行榜的 Redis 操作,才是"只在答对时才做"。
- **为什么是 `ZINCRBY`,不是"先 `ZSCORE` 查当前分数,再算好新分数用 `ZADD` 写回去"**:后一种写法是**先查后写**,两步之间不是原子的。想象两个请求并发提交同一个用户的答对结果:请求 A 和请求 B 同时执行 `ZSCORE` 读到当前分数都是 10,各自在内存里算出"新分数 = 11",然后各自执行 `ZADD key 11 member`——两次答对最终分数只涨了 1,不是 2,**丢更新**。`ZINCRBY`(对应这里的 `incrementScore`)是 Redis 单个命令完成"读旧值 + 加 + 写回"整个过程,不会被其他命令insert 到中间,天然并发安全。这也是任务验收标准第二条"并发提交 20 次答对,榜单分数恰好 +20"能成立的根本原因——测试的就是这个原子性。
- **判断"日榜 key 是否首次创建"的写法**:`incrementScore` 之后立刻 `getExpire(dailyKey)`。如果这把 key 是刚被这次调用创建出来的,Redis 里全新创建的 key **默认没有过期时间**(`TTL` 结果是 `-1`,代表"永不过期",不是"不存在"——"不存在"对应的是 `-2`),所以 `ttl == -1` 就说明"这是这把 key 第一次被写入,还没设置过过期时间",这时候才调用 `expire` 补上 7 天;如果这把 key 之前已经被别的答题请求创建过、也设置过 7 天 TTL 了,这次 `ttl` 会是一个具体的正整数(比如 604793,表示还剩 604793 秒),不等于 `-1`,就不会重复设置。**为什么要专门判断"首次",不能每次答对都无脑 `expire` 一下**:虽然这个场景下每次都重设 7 天不会导致真正的功能性 bug(因为 `dailyKey` 里带着当天日期,只有"今天"才会被写入,不存在"过期时间被不断续到未来某天导致该过期的没过期"这种连锁问题),但①每次答题都多发一条 `EXPIRE` 命令是纯浪费;②更重要的是练习"精确控制副作用发生的时机"这个意识——分布式锁那种场景里,TTL 该不该重设直接决定锁语义对不对,这里是一次低风险的练手。
- **`member` 用 `userId.toString()`**:ZSet 的 member 类型只能是字符串,`Long` 类型的 `userId` 必须先转成 `String` 才能作为 member 传进去,取出来的时候还要转回 `Long`(下一步 `getRank` 里会看到)。

### Step 9:`AnswerServiceImpl` —— 查排行榜

紧接着 Step 8 的类里追加:

```java
    @Override
    public List<RankVO> getRank(String type, int limit) {
        String key = resolveRankKey(type);
        Set<ZSetOperations.TypedTuple<String>> tuples =
                redisTemplate.opsForZSet().reverseRangeWithScores(key, 0, limit - 1);
        if (tuples == null || tuples.isEmpty()) {
            return List.of();
        }

        List<Long> userIds = new ArrayList<>();
        for (ZSetOperations.TypedTuple<String> tuple : tuples) {
            userIds.add(Long.valueOf(tuple.getValue()));
        }
        Map<Long, String> nicknameMap = new HashMap<>();
        for (User u : userMapper.selectByIds(userIds)) {
            nicknameMap.put(u.getId(), u.getNickname());
        }

        List<RankVO> result = new ArrayList<>();
        int rank = 1;
        for (ZSetOperations.TypedTuple<String> tuple : tuples) {
            Long userId = Long.valueOf(tuple.getValue());
            RankVO vo = new RankVO();
            vo.setRank(rank++);
            vo.setUserId(userId);
            vo.setNickname(nicknameMap.get(userId));
            vo.setCount(tuple.getScore().intValue());
            result.add(vo);
        }
        return result;
    }

    private String resolveRankKey(String type) {
        if ("daily".equals(type)) {
            return RANK_DAILY_PREFIX + LocalDate.now().format(DAILY_KEY_FORMATTER);
        }
        return RANK_TOTAL_KEY;
    }
```

【讲解】

- **`reverseRangeWithScores(key, 0, limit - 1)`**:对应 `ZREVRANGE key 0 (limit-1) WITHSCORES`,按 score **从高到低**取下标 `[0, limit-1]` 区间的元素——ZSet 的下标语义和数组一样是**闭区间**,取前 10 名要传 `0, 9`,不是 `0, 10`,这里传 `limit - 1` 就是为了对齐这个语义。
- **返回值类型是 `Set<ZSetOperations.TypedTuple<String>>`,但顺序其实是有保证的**:虽然类型写的是 `Set`(听起来像无序集合),但 Spring Data Redis 这里返回的具体实现是按 Redis 响应顺序填充的有序结构,`for` 循环遍历到的顺序就是 `ZREVRANGE` 返回的名次顺序,不需要自己再排一次序。`TypedTuple` 是 Redis 对 ZSet 元素的抽象,`getValue()` 拿到 member(这里是字符串形式的 `userId`),`getScore()` 拿到对应的 score(`Double` 类型)。
- **两次遍历 `tuples`**:第一次遍历只是为了收集所有 `userId`,凑齐一个 `List<Long>` 去做**一次性**批量查询(对应 Step 6 新增的 `selectByIds`);第二次遍历才真正组装 `RankVO` 列表、顺便按遍历顺序编上名次(`rank++`)。**如果图省事把这两步合并成一次遍历、在循环里查一次昵称,就变成了循环里发 SQL,又是一次 N+1**——这是这个方法唯一需要留意的坑,也是验收标准第三条"排行榜接口只发出 1 条用户查询 SQL"要考察的点。
- **`nicknameMap.get(userId)` 万一取不到怎么办**:如果这个用户后来被删掉了(`is_deleted=1`,`selectByIds` 的 SQL 里过滤掉了),`nicknameMap` 里就没有这个 `userId`,`get` 返回 `null`,`vo.setNickname(null)`——不会报错,前端会看到昵称是空的。这次任务不专门处理这个边界情况(用户被删除但历史答题记录还占着榜单名次),知道这个点、能在被问到时讲出来就够了。
- **`type` 参数只简单判断是不是 `"daily"`,不是就一律按 `"total"` 处理**:没有对非法值(比如传了 `type=weekly`)做参数校验报错,直接兜底成总榜——这不是本任务的验收点,没必要为一个不存在的枚举值写额外的校验分支。

```java
package com.zhimian.controller;

import com.zhimian.annotation.Public;
import com.zhimian.common.Result;
import com.zhimian.model.vo.RankVO;
import com.zhimian.service.AnswerService;

@RestController
@RequestMapping("/api/ranks")
@RequiredArgsConstructor
public class RankController {
    private final AnswerService answerService;

    @Public
    @GetMapping("/answer")
    public Result<List<RankVO>> rank(@RequestParam(defaultValue = "total") String type,
                                      @RequestParam(defaultValue = "10") int limit) {
        return Result.success(answerService.getRank(type, limit));
    }

```

【讲解】

- **拆成两个 Controller,而不是塞进一个**:项目里 Controller 的划分一直是按 URL 前缀对应的资源来的(`QuestionController` 管 `/api/questions`、`CategoryController` 管 `/api/categories`)。提交答题挂在 `/api/questions/{id}/answer` 下(语义上是"对某道题的一个子操作"),查排行榜是完全独立的资源 `/api/ranks/answer`,两个不同的 URL 前缀,所以拆成两个 Controller,但业务逻辑都在同一个 `AnswerService` 里——**Controller 按资源路径拆分,Service 按业务领域内聚**,这是两条不冲突的划分维度。
- **`AnswerController.submit` 没有标 `@Public` 也没有标 `@RequireAdmin`**:回顾 `JwtInterceptor.preHandle` 的逻辑——默认所有接口都要求登录,只有标了 `@Public` 的才跳过登录校验,标了 `@RequireAdmin` 的在登录基础上还要求 `role=admin`。提交答题只要求"登录",不要求管理员身份,所以两个注解都不用加,直接享受拦截器的默认行为。对照开发文档接口清单:`POST /api/questions/{id}/answer` 标了 🔒(需要登录)但没标 👑(不需要管理员),`GET /api/ranks/answer` 什么标记都没有(公开),和这里的注解一一对应。
- **`@RequestParam(defaultValue = "total")` / `defaultValue = "10"`**:给查询参数设置默认值,客户端请求 `/api/ranks/answer` 不传 `type`/`limit` 也能拿到"总榜前 10"的默认结果,不会因为缺参数直接报错。
