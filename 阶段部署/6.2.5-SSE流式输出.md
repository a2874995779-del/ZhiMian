## 一、为什么需要流式输出

先想清楚这个问题:**不流式,用户体验上到底差在哪?**

大模型生成一段几百字的回答,可能要 5~10 秒甚至更久。非流式接口的做法是:服务端等模型**完整生成完**,才把整段文字一次性返回给前端——用户在这几秒里,页面上什么都看不到,只能盯着一个转圈的 loading。而 ChatGPT、豆包这些产品你用的时候,文字是**一个字一个字往外蹦**的,你几乎感觉不到等待——这就是流式输出带来的体验差异,**内容生成的总耗时其实没有变化,只是把"用户能不能实时看到进度"这件事解决了**。

### SSE vs WebSocket vs 轮询,先分清楚为什么选它

| 方案 | 方向 | 协议 | 特点 |
|------|------|------|------|
| **轮询(polling)** | 单向(客户端主动问) | 普通 HTTP | 客户端每隔几百毫秒发一次请求"有新内容吗",简单粗暴,延迟高、浪费请求 |
| **WebSocket** | 双向 | 独立协议(`ws://`),握手时从 HTTP 升级 | 全双工,客户端服务端都能随时发消息,适合聊天室、协作编辑这种双向高频场景,但握手复杂、服务端要维护连接状态 |
| **SSE(Server-Sent Events)** | 单向(只能服务端推给客户端) | 就是普通 HTTP,`Content-Type: text/event-stream` | 建立一次连接,服务端持续往外写数据,客户端只能收不能通过这条连接发——但这次场景里客户端本来就只需要"发一次问题、收一连串回复片段",不需要双向 |

**这次场景为什么选 SSE 不选 WebSocket**:AI 对话在这个接口里的通信模式是"一问一答",用户发一次 `chat` 请求,服务端流式吐出这一轮的完整回复,吐完这次交互就结束了——**天然是单向的**。WebSocket 的双向能力在这里用不上,反而要多维护一层协议升级和连接生命周期管理,是不必要的复杂度。SSE 建立在普通 HTTP 之上,复用你已经很熟悉的一切(拦截器、`@RequestBody` 校验……),这也是为什么开发文档推荐这条路线。

**SSE 还有一个隐藏优点**:它是纯文本协议,**断线后浏览器的 `EventSource` API 会自动重连**(这次后端用 `curl`/自己写前端调用测试,重连这块了解即可,不是这次任务的重点)。

## 二、SSE 在 Spring MVC 里是怎么实现的:`SseEmitter` 背后的机制

这是本任务"核心难点"标签的由来,值得多花点篇幅讲清楚原理,不然代码背下来也不知道为什么这么写。

### 一个普通 Controller 方法为什么没法"边算边发"

正常情况下,一个 `@RestController` 方法是这样运作的:Tomcat 分配一个工作线程处理这个请求 → 你的方法执行 → `return` 一个对象 → Spring 把它序列化成 JSON 写进响应 → **这个工作线程才被释放**,可以去处理别的请求。整个过程中,这个线程从头到尾都被这一个请求占着。

如果直接在这个模型上硬做"流式",意味着这个工作线程要一直卡在这个方法里,每生成一小段文字就手动往响应流里写一点——**这个线程会被占用好几秒甚至更久,期间完全没法处理别的请求**。Tomcat 的工作线程数是有限的(默认 200 个左右),如果同时有几十个用户在流式对话,线程池很快就会被占满,新请求全部排队甚至超时。

### `SseEmitter` 解决的正是这个问题:Servlet 3 异步机制

`SseEmitter` 的原理是:**Controller 方法立刻 `return` 一个 `SseEmitter` 对象,Tomcat 工作线程随即被释放去处理别的请求**;真正往响应里写数据这件事,交给**另一个线程**(通常是 Spring AI 内部的响应式调度线程)在后台异步完成,写一点发一点,直到调用 `emitter.complete()` 才真正关闭这次 HTTP 响应。

这背后依赖的是 Servlet 3.0 引入的**异步请求处理(Async Servlet)**能力:一个请求可以先被 Tomcat "挂起"(`request.startAsync()`,`SseEmitter` 内部帮你做了这件事),工作线程归还给线程池;等异步任务真正有数据要写的时候,再通过 `AsyncContext` 把数据写回这个还没关闭的连接。**"不占用 Tomcat 工作线程死等"是 `SseEmitter` 相对于"手写阻塞式流式输出"的核心优势**,也是这次会被问到的一个面试考点。

### 响应式流的背压(了解级)

Spring AI 的 `.stream()` 返回的是一个 `Flux<String>`(Reactor 库的响应式流类型)。响应式流有一个叫"背压(backpressure)"的概念:如果生产数据的速度(模型吐字的速度)比消费数据的速度(网络往客户端发送的速度)快,消费方可以"告诉"生产方"慢一点,我处理不过来了",避免内存里堆积过多还没处理的数据。**这次任务不需要你手动处理背压**(Spring AI 和 Reactor 内部已经处理好了),了解这个词是干什么的就够,不用深挖实现。

## 四、分步实现

### Step 1:约定 SSE 的事件格式

开发文档定好了这次的响应格式(不是标准 SSE 的 `event:` 字段区分类型,而是把 `type` 塞进 `data` 的 JSON 里):

```
data: {"type":"delta","content":"嗯,"}

data: {"type":"delta","content":"那么它能保证原子性吗?"}

data: {"type":"done","messageId":88}
```

`type=delta` 是增量文本片段,`type=done` 标记这一轮结束、带上落库后的消息 id,`type=error` 携带错误信息。**为什么错误也要通过一个 SSE 事件下发,而不是让接口返回 HTTP 500?**——因为这条 HTTP 连接在生成 `SseEmitter` 那一刻起,响应头(包括状态码)就已经确定是 `200 text/event-stream` 了,SSE 协议本身**不支持流已经开始之后再改状态码**。所以但凡在流式过程中出了错,唯一能告诉客户端"出错了"的办法就是**再发一个 `data` 事件,内容里注明这是个错误**,客户端拿到之后自己判断该怎么处理(比如提示用户重试)。这是 SSE 这种协议本身的固有约束,不是这个项目设计得不好,是个考点。

### Step 2:`InterviewServiceImpl.chat` 改造成流式

`service/InterviewService.java` 里把 `chat` 的返回类型换掉:

```java
SseEmitter chat(Long sessionId, ChatMessageDTO dto);
```

`service/impl/InterviewServiceImpl.java`:

```java
@Override
public SseEmitter chat(Long sessionId, ChatMessageDTO dto) {
    InterviewSession session = mustFindSession(sessionId);
    if (session.getStatus() != 0) {
        throw new BusinessException(ErrorCode.CONFLICT, "会话已结束,无法继续对话");
    }

    String lockKey = LOCK_PREFIX + sessionId;
    Boolean locked = stringRedisTemplate.opsForValue().setIfAbsent(lockKey, "1", LOCK_TTL_SECONDS, TimeUnit.SECONDS);
    if (!Boolean.TRUE.equals(locked)) {
        throw new BusinessException(ErrorCode.TOO_MANY_REQUESTS, "上一轮对话还在处理中,请稍候");
    }

    List<InterviewMessage> history = contextManager.load(sessionId);
    InterviewMessage userMsg = buildMessage(sessionId, "user", dto.getContent());
    interviewMessageMapper.insert(userMsg);
    contextManager.append(sessionId, userMsg);

    List<Message> springAiMessages = toSpringAiMessages(history);
    springAiMessages.add(new UserMessage(dto.getContent()));

    // 0L = 不超时。默认 30 秒对长回答来说太短,面试官型的长回复很容易被提前掐断
    SseEmitter emitter = new SseEmitter(0L);
    StringBuilder fullReply = new StringBuilder();

    Disposable subscription = chatClient.prompt(new Prompt(springAiMessages))
            .stream()
            .content()
            .doOnNext(fullReply::append)
            .subscribe(
                    delta -> sendEvent(emitter, Map.of("type", "delta", "content", delta)),
                    error -> onStreamError(emitter, lockKey, error),
                    () -> onStreamComplete(emitter, sessionId, lockKey, fullReply.toString())
            );

    // 客户端中途断开/连接异常/超时,停止继续消费模型的输出、释放锁,不做无用功
    emitter.onTimeout(() -> {
        log.warn("SSE 超时: sessionId={}", sessionId);
        subscription.dispose();
        stringRedisTemplate.delete(lockKey);
    });
    emitter.onError(throwable -> {
        log.warn("SSE 连接异常: sessionId={}", sessionId, throwable);
        subscription.dispose();
        stringRedisTemplate.delete(lockKey);
    });

    return emitter;
}

private void onStreamComplete(SseEmitter emitter, Long sessionId, String lockKey, String fullReply) {
    try {
        InterviewMessage assistantMsg = buildMessage(sessionId, "assistant", fullReply);
        interviewMessageMapper.insert(assistantMsg);
        contextManager.append(sessionId, assistantMsg);
        sendEvent(emitter, Map.of("type", "done", "messageId", assistantMsg.getId()));
        emitter.complete();
    } finally {
        stringRedisTemplate.delete(lockKey);
    }
}

private void onStreamError(SseEmitter emitter, String lockKey, Throwable error) {
    log.error("AI 流式调用失败", error);
    sendEvent(emitter, Map.of("type", "error", "message", "AI 服务异常,请稍后重试"));
    emitter.completeWithError(error);
    stringRedisTemplate.delete(lockKey);
}

private void sendEvent(SseEmitter emitter, Map<String, Object> payload) {
    try {
        emitter.send(SseEmitter.event().data(payload, MediaType.APPLICATION_JSON));
    } catch (IOException e) {
        // 客户端大概率已经断开连接,这条消息送不到了。发送失败本身不需要再抛出去处理,
        // 真正的清理(释放锁、停止订阅)交给上面注册的 onError/onTimeout 回调
        log.warn("SSE 事件发送失败,客户端可能已断开", e);
    }
}
```

新增 import:`org.springframework.web.servlet.mvc.method.annotation.SseEmitter`、`reactor.core.Disposable`、`org.springframework.http.MediaType`、`java.io.IOException`。类上加 `@Slf4j`。

【讲解,这是本任务最核心的部分,逐段拆开讲】

**为什么方法一开始的部分(校验会话、抢锁、读历史、落用户消息)全是同步代码,到 `chatClient.prompt(...).stream()...subscribe(...)` 这一行才"异步"起来?** 这些前置步骤(查会话、写用户消息、读取并裁剪历史)本身都很快,没有必要也异步化。**真正耗时的只有"等模型把回复生成完"这一步**,所以只有这一步需要用响应式的方式处理。`subscribe(...)` 这一行本身**不会阻塞**——它把"收到一段文字该怎么办、遇到错误该怎么办、正常结束该怎么办"这三个逻辑注册好之后,方法立刻继续往下走(注册 `onTimeout`/`onError`,然后 `return emitter`),不会卡在这里等模型说完。真正"消费"模型输出这件事,是在**另一个线程**上,随着模型不断吐出新内容,持续触发 `subscribe` 里的第一个回调(`delta -> sendEvent(...)`)。

**`.subscribe(onNext, onError, onComplete)` 三个回调分别对应什么**:

- 第一个(`onNext`,这里是 `delta -> sendEvent(...)`):**每收到一小段增量文本就触发一次**,直接包成 `type=delta` 的事件发给客户端,同时这段文字也通过 `doOnNext(fullReply::append)` 被记录进 `fullReply`——**流式发给客户端和攒完整内容落库,是两件并行发生的事,不冲突**。
- 第二个(`onError`):这一轮 AI 调用本身失败了(比如网络问题、API 报错),对应 `onStreamError`。
- 第三个(`onComplete`):模型正常把这一轮回复说完了(没有更多内容),对应 `onStreamComplete`——**这时候 `fullReply` 里已经攒好了完整的回复文本**,在这里把 assistant 消息落库、追加进上下文、发 `done` 事件、真正关闭连接(`emitter.complete()`)。

**为什么 `emitter.onTimeout`/`emitter.onError` 里要调用 `subscription.dispose()`?** 想象客户端中途断开连接(用户直接关掉了浏览器标签页,或者你自测时 `curl` 按了 Ctrl+C)——这条 HTTP 连接没了,但 `chatClient.prompt(...).stream()` 这个响应式流**默认不会自动知道"客户端已经不在了",它会继续跑,继续从模型那里消费token、生成内容**,只是这些内容再也发不出去了(`emitter.send()` 会抛 `IOException`,被 `sendEvent` 悄悄吃掉)。**这是白白浪费模型调用的成本**——`Disposable`(`subscribe(...)` 方法的返回值)就是用来手动"取消订阅"的句柄,调用它的 `dispose()` 方法,会让这条响应式流停止继续拉取模型的输出,及时止损。`SseEmitter` 提供的 `onTimeout`/`onError`/`onCompletion` 回调,正是**给你一个"连接生命周期结束"的信号**,是清理资源(取消订阅、释放锁)的正确挂载点。

**为什么锁的释放要在好几个地方各写一遍(`onStreamComplete`、`onStreamError`、`onTimeout`、`onError` 都有 `stringRedisTemplate.delete(lockKey)`)?** 这几个回调对应的是**互斥的不同结束路径**(正常完成、AI 调用出错、SSE 超时、SSE 连接异常),任意一条路径走完,这次对话都算"结束"了,锁都应该被释放——`DEL` 命令本身是幂等的,就算极端情况下两条路径都触发、锁被删了两次,也不会有副作用,**这里宁可"可能重复释放"也不能有任何一条路径"忘了释放"(那样锁会一直占到 60 秒 TTL 到期才自动解开,期间这个会话没法再对话)**。

### Step 4:处理拦截器被 SSE 异步分发二次触发的问题

这是开发文档点名的一个坑,原理值得展开讲。

**背景**:`SseEmitter` 底层依赖 Servlet 3 的异步请求处理——一个请求会先经历"主线程处理到 `return emitter` 为止"这一次分发(`DispatcherType.REQUEST`),之后随着 `emitter.complete()`/`completeWithError()` 被调用,Servlet 容器会**再触发一次分发**,把这次异步处理的"收尾"工作走一遍(`DispatcherType.ASYNC`)。**问题在于:Spring MVC 默认会让注册的拦截器在每一次分发里都执行一遍**,也就是说,`JwtInterceptor.preHandle` 可能会在同一个请求上被调用**两次**——第一次是正常的登录校验,第二次是这次"异步收尾分发"触发的,而这次分发压根不需要再校验一次登录。

先自己验证一下这个现象是否存在(不同 Spring Boot 版本行为可能有细节差异,建议先验证再决定要不要改):在 `JwtInterceptor.preHandle` 开头加一行日志,打印 `request.getDispatcherType()`,跑一次 SSE 请求,看控制台是不是真的打出了两次日志、第二次的 `DispatcherType` 是不是 `ASYNC`。

如果确认存在这个现象,处理方式是在 `preHandle` 一开始就放行异步分发,不再重复校验:

```java
@Override
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
    if (request.getDispatcherType() == DispatcherType.ASYNC) {
        // SSE/异步请求收尾时的二次分发,登录态已经在第一次分发里校验过了,不用再校验一遍
        return true;
    }
    if (!(handler instanceof HandlerMethod handlerMethod)) {
        return true;
    }
    // ……原来的逻辑不变……
}
```

补一个 import:`jakarta.servlet.DispatcherType`。

【讲解】这里特意让你先加日志验证、再决定要不要改,是因为**这类"框架底层机制"的坑,光靠背答案记不住,亲眼在自己项目里看到"日志打印了两次"这个现象,才会真正理解"异步分发"这四个字到底在说什么**。如果你验证下来发现并没有二次触发(不同 Spring Boot 小版本、不同 Servlet 容器配置可能表现不同),这段防御性代码加不加都不影响功能正确性,但了解这个机制本身仍然是这次任务要掌握的知识点。
