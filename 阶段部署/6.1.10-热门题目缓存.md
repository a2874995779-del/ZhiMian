## 一、本任务要实现什么

两件事:

1. **新增热门题目接口**:`GET /api/questions/hot`,按 `view_count` 降序取 Top10,整块结果缓存成一个 JSON。
2. **回头给任务 1.8 写的详情接口打两个补丁**:加空值缓存防**穿透**、加互斥锁防**击穿**。热门列表本身也要处理 TTL 抖动防**雪崩**。

先把三个问题和这次的对应关系说清楚,别混着记:

| 问题 | 定义 | 这次怎么解决 | 解决在哪 |
|------|------|------|------|
| **缓存穿透** | 查询一个数据库里**根本不存在**的 key,缓存和数据库都没有,每次请求都穿透缓存打到数据库 | 查不到也缓存一个"空值"标记,给一个较短的 TTL | 详情接口 |
| **缓存雪崩** | **大量** key 在**同一时刻**集中过期,瞬间涌入数据库的请求暴涨 | 缓存 TTL 在基础值上加一段随机抖动,让同一批 key 不会同时到期 | 详情缓存 + 热门列表缓存 |
| **缓存击穿** | 一个**被高频访问的热点 key** 恰好过期,大量并发请求同时发现缓存不命中,一起去重建缓存、一起打到数据库 | 缓存重建时加互斥锁,只让一个请求真正查库重建,其他请求等待或读旧值 | 详情接口 |

### Step 2:抽取复用方法,消除重复代码

在写 `getHotQuestions()` 之前,先看一眼你自己在任务 1.7 写的 `pageQuestions()`——"查一批 `Question`,补上 `categoryName` 和 `tags`,转成 `QuestionListVO`" 这段逻辑,`getHotQuestions()` 要做的事跟它**一模一样**,只是"这一批 `Question`"的来源不同(一个来自分页查询,一个来自 Top10)。两个方法各写一遍是重复代码,抽成一个私有方法,两边调用。

`service/impl/QuestionServiceImpl.java` 里新增这个私有方法:

```java
private List<QuestionListVO> enrichToListVO(List<Question> records) {
    if (records.isEmpty()) {
        return List.of();
    }

    Map<Long, String> categoryNameMap = new HashMap<>();
    for (Category c : categoryMapper.selectAll()) {
        categoryNameMap.put(c.getId(), c.getName());
    }

    List<Long> questionIds = new ArrayList<>();
    for (Question q : records) {
        questionIds.add(q.getId());
    }
    Map<Long, List<String>> tagMap = new HashMap<>();
    for (QuestionTagName row : questionTagMapper.selectTagNamesByQuestionIds(questionIds)) {
        tagMap.computeIfAbsent(row.getQuestionId(), k -> new ArrayList<>()).add(row.getName());
    }

    List<QuestionListVO> voList = new ArrayList<>();
    for (Question q : records) {
        QuestionListVO vo = new QuestionListVO();
        BeanUtils.copyProperties(q, vo);
        vo.setCategoryName(categoryNameMap.get(q.getCategoryId()));
        vo.setTags(tagMap.getOrDefault(q.getId(), List.of()));
        voList.add(vo);
    }
    return voList;
}
```

然后把 `pageQuestions()` 改成调用它:

### Step 3:热门题目 `getHotQuestions()`

`service/QuestionService.java` 追加:

```java
List<QuestionListVO> getHotQuestions();
```

`service/impl/QuestionServiceImpl.java` 追加:

```java
private static final String HOT_CACHE_KEY = "zhimian:cache:question:hot";
private static final int HOT_LIMIT = 10;
private static final long HOT_TTL_BASE_SECONDS = 5 * 60;
private static final long HOT_TTL_JITTER_SECONDS = 60;

@Override
public List<QuestionListVO> getHotQuestions() {
    String cached = redisTemplate.opsForValue().get(HOT_CACHE_KEY);
    if (cached != null) {
        return deserializeList(cached);
    }

    List<Question> records = questionMapper.selectHot(HOT_LIMIT);
    List<QuestionListVO> voList = enrichToListVO(records);

    long ttl = HOT_TTL_BASE_SECONDS + ThreadLocalRandom.current().nextInt((int) HOT_TTL_JITTER_SECONDS);
    redisTemplate.opsForValue().set(HOT_CACHE_KEY, serializeList(voList), ttl, TimeUnit.SECONDS);
    return voList;
}

private String serializeList(List<QuestionListVO> list) {
    try {
        return objectMapper.writeValueAsString(list);
    } catch (JsonProcessingException e) {
        throw new RuntimeException(e);
    }
}

private List<QuestionListVO> deserializeList(String json) {
    try {
        return objectMapper.readValue(json, new TypeReference<List<QuestionListVO>>() {});
    } catch (JsonProcessingException e) {
        throw new RuntimeException(e);
    }
}
```

新增 import:`com.fasterxml.jackson.core.type.TypeReference`、`java.util.concurrent.ThreadLocalRandom`。

【讲解】

- **这是全项目第一次真正意义上"防雪崩"**:`HOT_TTL_BASE_SECONDS + 随机 0~60 秒`,而不是固定 5 分钟。热门列表只有一个 key,单独看好像谈不上"大量 key 同时过期",但道理是通的——真正的雪崩场景是"成百上千个题目详情缓存,如果全部设置成一样的固定 TTL(比如都是应用启动时统一预热、统一设置 30 分钟过期),就会在 30 分钟后同一秒内全部失效",这次给热门列表加抖动是练手,下一步给详情缓存加抖动才是真正针对雪崩场景的修复。
- **反序列化 `List<QuestionListVO>` 为什么要用 `TypeReference`,不能像详情那样直接写 `.class`**:Java 的泛型在运行时会被"擦除"(`List<QuestionListVO>` 和 `List<String>` 编译后其实都是同一个 `List.class`),`ObjectMapper.readValue(json, List.class)` 没法知道列表里装的具体是什么类型,只能反序列化成一堆 `LinkedHashMap`。`TypeReference` 是 Jackson 提供的一个技巧,靠匿名内部类把完整的泛型信息(`List<QuestionListVO>`)保留到运行时,`ObjectMapper` 才能读到"列表元素是 `QuestionListVO`"这个信息,正确反序列化。

### Step 4:详情接口打补丁——防穿透 + 防击穿

这是本任务的核心,把任务 1.8 写的 `getDetail()` 重写成下面这样(完整贴出,方便直接对照替换):

```java
private static final String DETAIL_CACHE_PREFIX = "zhimian:cache:question:detail:";
private static final String VIEW_COUNT_PREFIX = "zhimian:question:view:";
private static final String LOCK_PREFIX = "zhimian:lock:question:detail:";
private static final String NULL_PLACEHOLDER = "NULL";
private static final long DETAIL_TTL_BASE_MINUTES = 30;
private static final long DETAIL_TTL_JITTER_SECONDS = 5 * 60;
private static final long NULL_CACHE_TTL_MINUTES = 1;
private static final long LOCK_TTL_SECONDS = 10;
private static final int LOCK_WAIT_RETRY = 5;
private static final long LOCK_WAIT_MS = 100;

@Override
public QuestionDetailVO getDetail(Long id) {
    String cacheKey = DETAIL_CACHE_PREFIX + id;
    String cached = redisTemplate.opsForValue().get(cacheKey);

    QuestionDetailVO vo = (cached != null) ? readFromCacheOrThrow(cached) : loadDetailWithLock(id, cacheKey);

    redisTemplate.opsForValue().increment(VIEW_COUNT_PREFIX + id);
    return vo;
}

/**
 * 缓存未命中时的重建逻辑,用互斥锁防止大量并发同时打到数据库(缓存击穿)
 */
private QuestionDetailVO loadDetailWithLock(Long id, String cacheKey) {
    String lockKey = LOCK_PREFIX + id;

    for (int i = 0; i < LOCK_WAIT_RETRY; i++) {
        Boolean locked = redisTemplate.opsForValue().setIfAbsent(lockKey, "1", LOCK_TTL_SECONDS, TimeUnit.SECONDS);
        if (Boolean.TRUE.equals(locked)) {
            try {
                return rebuildCache(id, cacheKey);
            } finally {
                redisTemplate.delete(lockKey);
            }
        }

        // 没抢到锁:说明有别的请求正在重建,睡一小段时间再看看缓存是不是已经建好了
        sleepQuietly(LOCK_WAIT_MS);
        String cached = redisTemplate.opsForValue().get(cacheKey);
        if (cached != null) {
            return readFromCacheOrThrow(cached);
        }
    }
    // 等了 LOCK_WAIT_RETRY 轮还没等到重建结果,不再无限期阻塞用户请求,直接查库放行兜底
    return buildDetailVO(mustFindQuestion(id));
}

/**
 * 真正查库、写缓存(含穿透防护:查不到也缓存空值)
 */
private QuestionDetailVO rebuildCache(Long id, String cacheKey) {
    Question question = questionMapper.selectById(id);
    if (question == null) {
        redisTemplate.opsForValue().set(cacheKey, NULL_PLACEHOLDER, NULL_CACHE_TTL_MINUTES, TimeUnit.MINUTES);
        throw new BusinessException(ErrorCode.NOT_FOUND, "题目不存在");
    }

    QuestionDetailVO vo = buildDetailVO(question);
    long ttlSeconds = DETAIL_TTL_BASE_MINUTES * 60 + ThreadLocalRandom.current().nextInt((int) DETAIL_TTL_JITTER_SECONDS);
    redisTemplate.opsForValue().set(cacheKey, serialize(vo), ttlSeconds, TimeUnit.SECONDS);
    return vo;
}

private QuestionDetailVO buildDetailVO(Question question) {
    QuestionDetailVO vo = new QuestionDetailVO();
    BeanUtils.copyProperties(question, vo);

    Map<Long, String> categoryNameMap = new HashMap<>();
    for (Category c : categoryMapper.selectAll()) {
        categoryNameMap.put(c.getId(), c.getName());
    }
    vo.setCategoryName(categoryNameMap.get(question.getCategoryId()));

    List<String> tags = new ArrayList<>();
    for (QuestionTagName row : questionTagMapper.selectTagNamesByQuestionIds(List.of(question.getId()))) {
        tags.add(row.getName());
    }
    vo.setTags(tags);
    return vo;
}

private Question mustFindQuestion(Long id) {
    Question question = questionMapper.selectById(id);
    if (question == null) {
        throw new BusinessException(ErrorCode.NOT_FOUND, "题目不存在");
    }
    return question;
}

private QuestionDetailVO readFromCacheOrThrow(String cached) {
    if (NULL_PLACEHOLDER.equals(cached)) {
        throw new BusinessException(ErrorCode.NOT_FOUND, "题目不存在");
    }
    return deserialize(cached);
}

private void sleepQuietly(long millis) {
    try {
        Thread.sleep(millis);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
}
```

`loadDetailFromDb`(任务 1.8 写的那个)现在被拆成了 `buildDetailVO` + 查库判空两部分,可以删掉了。`serialize`/`deserialize` 两个私有方法不变,继续保留。

【讲解,逐个问题对应着看】

**穿透防护(`rebuildCache` 里)**:`question == null` 时,不是直接抛异常完事,而是先往 `cacheKey` 写一个哨兵字符串 `"NULL"`,TTL 只给 1 分钟(比正常详情缓存的 30 分钟短得多)。下次同一个不存在的 id 再被访问,`getDetail()` 一开始的 `redisTemplate.opsForValue().get(cacheKey)` 就能读到这个 `"NULL"`,`readFromCacheOrThrow` 识别出是空值标记直接抛 `NOT_FOUND`,**根本不会再查数据库**。TTL 故意给短:如果这个 id 的题目以后被真的创建出来了,最多 1 分钟后空值缓存自然过期,不会一直挡着。

**击穿防护(`loadDetailWithLock` 里)**:核心是 `setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS)`,对应 Redis 的原子命令 `SET key value NX EX 10`——"key 不存在才设置成功,同时给这个锁设 10 秒过期"。抢到锁的请求(`Boolean.TRUE.equals(locked)`)才有资格去查库重建缓存,其他并发请求抢不到锁,不会一窝蜂全部打进数据库,而是：睡 100 毫秒 → 再看一眼缓存建好了没 → 建好了就直接用,没建好就再抢一次锁,最多重试 5 轮(约 500 毫秒)。如果 500 毫秒后还是没等到(比如持锁方异常卡住了),不再无限期阻塞用户,直接查库放行——**这是刻意的兜底策略:宁可这一次多查一次库,也不能让用户的请求一直挂着没有响应**。

**这次实现的锁是简化版,面试如果追问会追出一个经典坑,提前说清楚**:释放锁用的是 `redisTemplate.delete(lockKey)`,**没有校验这把锁是不是自己加的**。设想一个极端场景:请求 A 拿到锁后,业务逻辑跑得比锁的 10 秒 TTL 还久,锁自动过期释放了;这时请求 B 抢到了同一把锁,开始自己的重建;A 的业务终于跑完,执行 `delete(lockKey)`,把 **B 刚加上的锁**误删了——B 还没重建完,C 又能抢到锁,多个请求"同时持锁"的保护就失效了。生产级的解法是:锁的 value 存一个唯一标识(比如 `UUID`),释放时用 Lua 脚本做"先判断 value 是不是自己存的、是才删除"的原子操作(`GET` + `DEL` 分两步不是原子的,必须用 Lua 保证原子性)。这次任务不实现这个加固版,但**面试被问"释放锁校验过归属吗",要能讲出这个坑和它的正确解法**,这是 Redis 分布式锁最常见的追问点。

**为什么加锁重建、而不是"缓存不命中就直接放行去查库"**:如果不加锁,一个热点题目的详情缓存刚好过期的瞬间,如果同时有 1000 个用户在看这道题,这 1000 个请求会同时判断"缓存未命中",同时去查数据库、同时各自重建一次缓存——数据库瞬间被 1000 条一模一样的查询打中,这就是"击穿"。加锁之后,这 1000 个请求里只有 1 个真正查库,其余 999 个要么等到锁释放后直接读到已经建好的缓存,要么在重试超时后才兜底查库(概率很低,只有极端情况才会发生)。

**② 雪崩防护(定性检查,不强求精确复现)**

```bash
redis-cli DEL zhimian:cache:question:detail:1 zhimian:cache:question:detail:2
curl -s http://localhost:8080/api/questions/1 > /dev/null
curl -s http://localhost:8080/api/questions/2 > /dev/null

redis-cli TTL zhimian:cache:question:detail:2
```
两次 `TTL` 的值大概率不完全一样(基础 30 分钟 + 各自随机的 0~5 分钟抖动),这就是抖动生效的直接证据。

**③ 击穿防护(重点,需要并发)**

```bash
# 先删掉这道题的详情缓存,模拟"热点缓存恰好过期"
redis-cli DEL zhimian:cache:question:detail:$QID

# 20 个并发请求同时打详情接口
for i in $(seq 1 20); do
  curl -s http://localhost:8080/api/questions/$QID > /dev/null &
done
wait
```
盯着 IDEA 控制台的 SQL 日志:**理想情况下这一轮只应该出现 1 次 `selectById` 查询**(加上分类、标签各 1 次),而不是 20 次。如果看到远多于 1 次(比如 5~10 次),大概率是抢锁的时机太密集导致部分请求在重试窗口内没等到缓存建好、兜底查了库——这在真实网络环境下是正常的(不追求 100% 只有 1 次),但应该**明显少于 20 次**,不能是"完全没起作用、20 次全部查库"。

**④ 热门列表**

```bash
curl -s http://localhost:8080/api/questions/hot
redis-cli GET zhimian:cache:question:hot
redis-cli TTL zhimian:cache:question:hot
```
第一次请求返回按 `viewCount` 降序排列的最多 10 条题目;`TTL` 应该在 300~360 秒之间(5 分钟 + 0~60 秒抖动)。
