## 一、本任务要做什么,以及一个关键的技术选型调整

目标很单纯:把 Spring AI 接进项目,写一个临时测试接口验证"能调通模型、能拿到回复"就算完成,**不涉及面试业务逻辑**(那是任务 2.2 的事)。

**但选型上要偏离开发文档一步**:开发文档的思路提示里写的是"引入 `spring-ai-starter-model-deepseek`(或 openai starter 改 base-url 指向 DeepSeek,两者选一)"——这是给"直连 DeepSeek 官方 API"设计的。你现在用的是硅基流动转发,情况变了:

- `spring-ai-starter-model-deepseek` 这个 starter 的自动配置内部把 `base-url` 默认指向了 `https://api.deepseek.com`,虽然它走的也是 OpenAI 兼容协议,但这个 starter 没有把"换一个转发地址"当成一等公民场景来设计,改起来别扭。
- 硅基流动本质是一个"模型聚合平台",对外暴露的接口格式**完全遵循 OpenAI 的 Chat Completions 协议**,只是 `base-url` 换成了硅基流动的地址、`model` 换成了它平台内的模型名。这正是 `spring-ai-starter-model-openai` 这个 starter 存在的意义——不只是给官方 OpenAI 用的,**任何遵循 OpenAI 协议的第三方服务(硅基流动、其他模型聚合平台、企业自建网关)都能通过重写 `base-url`+`model` 接进来**,不需要为每个厂商都单独装一个 starter。

所以这次选型是:**`spring-ai-starter-model-openai` + 自定义 `base-url` 指向硅基流动**。开发文档里"openai starter 改 base-url"这条路线,只是把目标地址从"DeepSeek 官方"换成"硅基流动",思路完全一致,面试被问起"为什么不用官方 deepseek starter"时,把上面这段讲出来就是加分项——**能看穿"协议兼容"和"官方专用 SDK"的区别,这本身就是一个考点**。

## 三、分步实现

### Step 1:`pom.xml` 换成 openai starter

项目里已经预先埋了 `spring-ai-bom` 版本管理和一段注释掉的依赖(打开 `pom.xml` 能看到),把注释的 `spring-ai-starter-model-deepseek` 换成下面这个,取消注释:

```xml
<!-- Spring AI:走 OpenAI 兼容协议,base-url 改指向硅基流动(任务 2.1) -->
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-openai</artifactId>
</dependency>
```

`spring-ai-bom` 的 `<dependencyManagement>` 部分不用动,版本已经统一管理了。

### Step 2:`application-local.yml` 配置密钥和转发地址

```yaml
spring:
  ai:
    openai:
      api-key: sk-你的硅基流动key
      base-url: https://api.siliconflow.cn
      chat:
        options:
          model: deepseek-ai/DeepSeek-V4-Pro   # ⚠️ 占位,见下面的注意事项
          temperature: 0.7
```

【讲解】

- **`base-url` 不要带 `/v1` 后缀**:Spring AI 的 `OpenAiApi` 内部会自动在你配的 `base-url` 后面拼 `/v1/chat/completions`,如果你自己在配置里又加了一遍 `/v1`,会变成 `/v1/v1/chat/completions`,请求直接 404——这是接入 OpenAI 协议第三方服务时**最容易踩的一个坑**,任何"改 base-url"的接入(不止硅基流动)都要留意这一点。
- **`model` 这一行是占位符,你必须自己去硅基流动控制台确认精确的模型字符串再填**:平台上的模型名一般是 `厂商/模型名` 这种带斜杠的格式(比如 `deepseek-ai/DeepSeek-V3` 是我确认存在过的一种命名风格),"DeepSeek V4 Pro"具体对应的字符串我没有把握替你确认,直接抄我写的占位符大概率调不通——去硅基流动的模型广场或者 API 文档页,找到你要用的那个模型,复制它给出的**调用示例代码里 `model` 字段的原文**,一个字符都不要改。
- **`api-key` 千万不要直接写死提交进 git**:这里写在 `application-local.yml` 里是因为这个文件已经在 `.gitignore` 里(前面任务已经确认过),`git status` 看不到它才是对的。如果不小心把 key 提交上去了,唯一正确的处理方式是**立刻去硅基流动控制台作废这个 key、重新生成一个**,而不是"删掉这次提交"——git 历史里还留着,删了本地文件没用。

### Step 3:`AiConfig.java` 组装 `ChatClient`

```java
package com.zhimian.config;

import org.springframework.ai.chat.client.ChatClient;
import org.springframework.boot.http.client.ClientHttpRequestFactoryBuilder;
import org.springframework.boot.http.client.ClientHttpRequestFactorySettings;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.client.RestClient;

import java.time.Duration;

@Configuration
public class AiConfig {

    @Bean
    public ChatClient chatClient(ChatClient.Builder builder) {
        return builder.build();
    }

    /**
     * Spring AI 默认的 HTTP 超时较短,面试官型的长回答(尤其是流式场景)容易被提前掐断。
     * 提供自己的 RestClient.Builder,Spring AI 装配 OpenAiApi 时会优先用这个,而不是默认的。
     */
    @Bean
    public RestClient.Builder restClientBuilder() {
        ClientHttpRequestFactorySettings settings = ClientHttpRequestFactorySettings.defaults()
                .withConnectTimeout(Duration.ofSeconds(10))
                .withReadTimeout(Duration.ofSeconds(60));
        return RestClient.builder()
                .requestFactory(ClientHttpRequestFactoryBuilder.detect().build(settings));
    }
}
```

【讲解】

- **`ChatClient.Builder` 从哪来**:引入 `spring-ai-starter-model-openai` 且配置了 `api-key` 之后,Spring Boot 的自动配置机制(和你在任务 1.5 学的 `@ConditionalOnClass` 那一套是同一个原理)会自动往容器里注册一个 `OpenAiChatModel` bean,进而注册一个 `ChatClient.Builder` bean——这里不用你手写任何创建逻辑,直接在构造方法/方法参数里声明依赖,Spring 就能注入进来。我们要做的只是拿这个 `Builder` `.build()` 一下,变成一个可以直接用的 `ChatClient`,注册成 bean 供其他地方注入。
- **超时配置这块,说实话我也没有百分百确定过在你这个 Spring AI 版本上一定生效**——`RestClient.Builder` 是 Spring 标准的 HTTP 客户端构建器,`ClientHttpRequestFactorySettings`/`ClientHttpRequestFactoryBuilder` 是 Spring Boot 3.4+ 提供的超时配置工具类,原理上你在容器里放一个自己的 `RestClient.Builder` bean,会顶替掉 Spring Boot 自动配置的默认那个,Spring AI 装配 `OpenAiApi` 时如果是从容器里取 `RestClient.Builder` 依赖,自然会用到你这个自定义的。**如果实测这段代码启动报错或者超时没有真的变长,不用死磕,先注释掉这个 bean,只留 `chatClient` 那个,把超时问题留到任务 2.7(AI 调用的健壮性)系统解决就行**——这次任务的验收标准里也没有强制要求超时一定要配成功,能讲清楚"为什么要关注超时"这个点更重要。

### Step 4:临时测试接口

```java
package com.zhimian.controller;

import com.zhimian.annotation.RequireAdmin;
import com.zhimian.common.Result;
import lombok.RequiredArgsConstructor;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequiredArgsConstructor
public class AiTestController {
    private final ChatClient chatClient;

    @RequireAdmin
    @GetMapping("/api/ai/ping")
    public Result<String> ping(@RequestParam String message) {
        String reply = chatClient.prompt()
                .user(message)
                .call()
                .content();
        return Result.success(reply);
    }
}
```

【讲解】

- **标了 `@RequireAdmin`,不是 `@Public`**:这个接口每调一次就是一次真金白银的模型调用,虽然硅基流动这类平台通常价格便宜,但完全公开的测试接口一旦被外部扫到,可能被刷调用刷掉你的余额——临时接口也要有基本的访问控制意识。
- **`chatClient.prompt().user(message).call().content()`**:这是 Spring AI `ChatClient` 的链式调用风格,`.prompt()` 开始构建一次请求,`.user(...)` 设置用户消息,`.call()` 同步发起调用(等待完整响应,不是流式),`.content()` 直接拿到回复的纯文本内容(如果要拿更完整的结构,比如 token 用量,可以用 `.chatResponse()` 代替 `.content()`)。这次没有 `.system(...)`,意味着模型没有任何角色设定,就是"裸模型"回答你的问题——**面试官人设是任务 2.2 才引入的**,这次只验证链路通不通。
- **这是个临时接口,任务 2.2 开始写真正的面试接口后,记得把这个类删掉**,它不属于开发文档接口总览里的任何一条,留着容易和正式接口混淆。

## 四、自测清单

```bash
# 1. 用 admin token 打临时测试接口
ADMIN_TOKEN=$(curl -s -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"你的admin账号","password":"你的密码"}' | grep -o '"token":"[^"]*"' | cut -d'"' -f4)

curl -s "http://localhost:8080/api/ai/ping?message=用一句话介绍一下你自己" \
  -H "Authorization: Bearer $ADMIN_TOKEN"
```

1. **期望返回 `code:0`,`data` 是模型的真实自然语言回复**——不是报错、不是空字符串。
2. **不带 token 访问应该被拦截**(`@RequireAdmin` 生效)。
3. **改错 `api-key` 后重启,再调用一次**:期望不是裸 500,能看到一个还算清晰的报错(即便这次任务不强制要求你捕获转成 `AI_SERVICE_ERROR`,至少控制台日志能看出是认证失败,不是别的问题——健壮性统一处理是任务 2.7 的工作)。
4. **控制台看一眼请求耗时**:正常问题应该几秒内有响应;如果经常超过 10 秒甚至超时,回头检查 Step 3 的超时配置有没有生效,或者硅基流动那边这个模型本身响应慢(换个更小的模型测一下排除网络问题)。
