## 一、这次到底在解决什么问题

到任务 2.6 为止,功能是完整的,但有几个"平时看不出来、出事就致命"的隐患:

1. **没有频率限制**:用户(或者一段脚本)可以对着 `chat` 接口疯狂点发送。每一次 chat 都会触发一次真金白银的大模型调用——既烧 token 费用,又占着 Redis 会话锁和后端线程。**任何直接触发付费外部调用、且面向公网的接口,都必须有"每用户多久能调一次"的闸**,这是这次任务最核心、也是唯一需要新写代码的部分。

2. **超时到底设没设、设在哪**:AI 调用是一次网络请求,如果对端(DeepSeek)卡住不返回,而我们**没有显式设超时**,这个请求就会一直挂着,占着的那个线程永远回不到线程池——并发一上来,线程池被这些"僵尸请求"占满,整个服务连正常接口都响应不了。**"没有超时的外部调用会拖垮整个线程池"是这次的头号考点**,好消息是这一层你在任务 2.1 就已经做了(`AiConfig` 里的 `RestClient.Builder`),这次要做的是**讲清楚它为什么在、以及它保护的是什么**。

3. **底层异常裸奔**:api-key 配错、对端返回 401/500 时,Spring AI 会抛出它自己的异常类型。如果这些异常没人接,会一路冒泡到全局兜底 handler,变成一个笼统的 `50000 系统内部异常`——但这明明是"AI 服务调不通",语义上应该是 `50001`。**错误码要如实反映"是哪一层出的问题"**,运维看到 50001 能立刻判断"去查 AI 网关/key",看到 50000 只能一脸茫然从头排查。

一句话总结这次的定位:**功能已经对了,这次让它在"外部依赖抽风"时也不至于崩。**

## 三、分步实现

### Step 1:通用限流器 `RateLimiter`

新建包 `com.zhimian.ratelimit`,放一个小组件:

```java
package com.zhimian.ratelimit;

import lombok.RequiredArgsConstructor;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;

import java.util.concurrent.TimeUnit;

@Component
@RequiredArgsConstructor
public class RateLimiter {

    private final StringRedisTemplate stringRedisTemplate;

    /**
     * 固定窗口 + 单次配额:同一个 key 在 windowSeconds 秒内只放行一次。
     *
     * @param key           限流维度的 key(务必带上 userId,否则会变成全局限流)
     * @param windowSeconds 冷却窗口秒数
     * @return true=本次放行;false=还在冷却窗口内,应当拒绝
     */
    public boolean tryAcquire(String key, long windowSeconds) {
        Boolean ok = stringRedisTemplate.opsForValue()
                .setIfAbsent(key, "1", windowSeconds, TimeUnit.SECONDS);
        return Boolean.TRUE.equals(ok);
    }
}
```

只有一行核心逻辑,但每一处都要能讲出来:

**为什么用 `setIfAbsent(key, "1", windowSeconds, ...)` 这一条命令,而不是"先 `hasKey` 判断存不存在,不存在再 `set`"?** 因为"判断"和"设置"如果拆成两步,两步之间存在**并发窗口**:用户手一抖连点两下(或者前端没做防抖),两个请求几乎同时进来,都执行了"判断",都发现 key 不存在,于是**都通过了**——限流形同虚设。`setIfAbsent` 对应的是 Redis 原生的 `SET key value NX EX seconds` 命令,**"key 不存在才写入"和"写入的同时带上过期时间"是同一条命令、在 Redis 单线程里原子完成的**,根本不给并发留缝隙。这和你在 `chat`/`finishInterview` 里用的会话锁是**同一个 `setIfAbsent`、同一套原子性道理**,只是用途不同:那里是"同一会话同一时刻只能有一轮在处理"(互斥锁),这里是"同一用户每 10 秒只能发起一轮"(冷却限流)。

**这个 key 一定要带 `userId`(方法注释里特意点了名)。** 这是本任务开发文档明确列出的坑:如果 key 写成固定的 `"zhimian:interview:rate"`,不带用户维度,那就变成了**全局限流**——全站所有用户加起来 10 秒只能有一个人能发消息,A 发了一条,B 在 10 秒内就被拦住了,这显然是错的。限流的"维度"必须由 key 精确表达,"每用户限流"就必须 `rate:{userId}`,"每 IP 限流"就必须 `rate:{ip}`。

**为什么这个 key 设置后不需要、也不能去主动删除它?** 它和会话锁的生命周期正好相反。会话锁是"这轮处理完就该马上释放,好让下一轮能进来",所以 `chat` 里有 `finally { delete(lockKey) }`。而限流 key 的语义是"这 10 秒的冷却期必须完整走完",它就是要**靠 TTL 自然过期**来结束冷却,谁要是在处理完之后手贱把它删了,冷却窗口直接归零,限流又白做了。所以它是"设置后就不管了,交给 Redis 到点自动清"。

### Step 2:把限流接到 `chat` 入口

先在 `InterviewServiceImpl` 顶部补两个常量、注入 `RateLimiter`:

```java
private static final String RATE_PREFIX = "zhimian:interview:rate:";
private static final long RATE_WINDOW_SECONDS = 10;

// 构造器注入(类上已有 @RequiredArgsConstructor,加一个 final 字段即可)
private final RateLimiter rateLimiter;
```

然后在 `chat` 方法里,**归属校验、状态校验都通过之后,抢会话锁之前**,插入限流检查:

```java
@Override
public SseEmitter chat(Long sessionId, ChatMessageDTO dto) {
    InterviewSession session = mustFindOwnSession(sessionId);
    if (session.getStatus() != 0) {
        throw new BusinessException(ErrorCode.CONFLICT, "会话已结束，无法继续对话");
    }

    // —— 本次任务新增:每用户对话频率限制 ——
    // userId 在这里(还是处理 HTTP 请求的原始线程)取,ThreadLocal 里还有值;
    // 这一步只是同步的入口拦截,不涉及后面的异步回调,不存在跨线程读 ThreadLocal 的问题
    Long userId = UserContext.getUserId();
    if (!rateLimiter.tryAcquire(RATE_PREFIX + userId, RATE_WINDOW_SECONDS)) {
        throw new BusinessException(ErrorCode.TOO_MANY_REQUESTS, "操作太频繁，请过几秒再发");
    }

    String lockKey = LOCK_PREFIX + sessionId;
    Boolean locked = stringRedisTemplate.opsForValue().setIfAbsent(lockKey, "1", LOCK_TTL_SECONDS, TimeUnit.SECONDS);
    // ……下面保持原样
```

**为什么把限流放在归属校验和状态校验之后,而不是方法第一行?** 因为限流一旦通过,那个冷却 key 就落下去了、占满 10 秒。如果把它放最前面,那么一个连"会话根本不是你的""会话早就结束了"都没通过的**无效请求**,也会白白消耗掉这个用户的冷却配额——用户被自己的一个错误请求罚站 10 秒,体验不合理。**先做便宜且必然要做的合法性校验,让明显非法的请求尽早失败;把"会真正触发昂贵 AI 调用"的限流闸放在合法性确认之后**,这样冷却配额只花在"确实是一次合法的、要打模型的请求"上。

**为什么限流(每用户)要和会话锁(每会话)同时存在,不能只留一个?** 两者拦的是不同的东西,缺一不可:

- **会话锁**拦的是"同一场会话、同一时刻的并发":你在 A 会话里上一轮 AI 还在流式吐字,你又对 A 发了下一条——这一条会被会话锁挡住("上一轮还在处理中")。但它**管不到**你换去 B、C、D 会话疯狂发:每个会话有自己的锁,互不影响。
- **限流**拦的是"同一用户、跨会话的总频率":哪怕你在 3 个不同会话之间来回切换发消息,只要 10 秒内发了第二条,就被这个每用户的闸挡住。

一个是"防同一资源的并发",一个是"防同一主体的高频",维度正交,所以要各管各的。

### Step 3:AI 异常统一兜底成 `50001`

在 `GlobalExceptionHandler` 里加一个专门接 AI 异常的 handler:

```java
import org.springframework.ai.retry.NonTransientAiException;
import org.springframework.ai.retry.TransientAiException;
import org.springframework.web.client.RestClientException;

/**
 * AI 调用相关异常:api-key 错误、对端 4xx/5xx、连接超时等。
 * 统一收敛成 50001,让"AI 服务调不通"这件事在错误码层面一眼可辨,
 * 不至于混进笼统的 50000 系统异常里。
 */
@ExceptionHandler({NonTransientAiException.class, TransientAiException.class, RestClientException.class})
public Result<Void> handleAiException(Exception e) {
    log.error("AI 服务调用失败", e);
    return Result.error(ErrorCode.AI_SERVICE_ERROR);
}
```

**这三个异常类型分别是什么:**

- `NonTransientAiException`:**不可重试**的 AI 异常。典型就是 api-key 错误(401)、请求参数非法(400)这类——你重试一百次结果都一样,重试没有意义。这次验收里"把 api-key 改错"命中的就是它。
- `TransientAiException`:**瞬时的、可重试**的 AI 异常(429 限流、502/503 等)。它理论上重试可能成功,但到了这一层还没被内部重试消化掉,说明重试也没救回来,对外就该报 50001。
- `RestClientException`:更底层的 HTTP 客户端异常(连接超时、读超时、连不上对端)。`AiConfig` 里设的读超时真被触发时,冒上来的就是这一类。

**为什么要单独加这个 handler,`createInterview` 里不是已经 try/catch 包住、也会抛 50001 了吗?** 是的,`create` 和 `finishInterview` 在**调用点局部**都已经把 AI 异常兜成了业务异常——这次加的全局 handler 是**防御纵深(defense in depth)**:它保证的是"**任何**一条 AI 调用路径,哪怕将来某个新接口的作者忘了在调用处包 try/catch,底层 AI 异常也不会裸奔成 50000,而是被这张网统一接成 50001"。局部 try/catch 依赖"每个写代码的人都记得包",全局 handler 是"就算有人忘了也兜得住"——两者不冲突,后者是系统级的保底。这也是"外部依赖故障隔离"思想在异常处理上的体现:**把某一类外部依赖的失败,收敛到一个统一的、语义明确的出口**。

> 注:`chat` 是 SSE 流式接口,它的 AI 异常走的是另一条路——在响应式流的 `onStreamError` 回调里被捕获,通过 SSE 的 `{"type":"error"}` 帧发给前端(见任务 2.4),**不会**经过这个全局 handler。所以这个 handler 实际保护的是 `create`、`finish` 这类同步返回 `Result` 的接口。验收第 2 条("api-key 改错返回 50001")用创建会话接口测最直接。

### 4.1 超时:没有超时的外部调用会拖垮线程池(代码已在任务 2.1)

回看 `AiConfig`:

```java
ClientHttpRequestFactorySettings settings = ClientHttpRequestFactorySettings.defaults()
        .withConnectTimeout(Duration.ofSeconds(10))   // 建立连接最多等 10 秒
        .withReadTimeout(Duration.ofSeconds(60));      // 连上后等对端返回最多 60 秒
```

**为什么这是整个健壮性里最不能省的一环?** 设想不设读超时:某次调用 DeepSeek,对端因为过载卡住了,既不返回数据也不断开连接。处理这次请求的 Tomcat 工作线程,就会**一直阻塞在"等 AI 返回"这一行**,永远回不到线程池。线程池大小是有限的(比如 200),这样的僵尸请求攒够 200 个,线程池就被占满了——**此时哪怕是一个只查数据库、根本不碰 AI 的普通接口,也会因为拿不到工作线程而被拖死**。一个外部依赖的慢,通过"共享线程池"这个通道,**传染成了整个服务的不可用**。显式设置超时,本质是给这种传染画一条止损线:"最多等 60 秒,再不返回我就放弃、把线程还回去",让故障被**隔离**在这一次调用里,不扩散。

**为什么连接超时(10s)比读超时(60s)短很多?** 连接建立是"握手",正常都是毫秒级,等 10 秒还连不上基本就是网络/对端挂了,没必要久等;而读超时覆盖的是"模型生成一大段回答"的时间,大模型出长答案本来就慢,给 60 秒是留足生成余量——**两个超时对应两个不同性质的等待,不能用同一个值一刀切**。

### 4.2 重试:只有幂等、非流式的调用才能自动重试(代码已在任务 2.6)

回看 `generateReportWithRetry`:失败最多重试到第 2 次,再不行抛 `50001`。

**为什么"生成评价报告"可以自动重试,而"流式对话 `chat`"绝对不能?**

- 生成报告是**幂等**的:输入是同一份完整对话记录,重试一次无非是"再让模型基于同样的输入算一遍分",不会产生副作用,重试前也还没往库里写任何东西——所以失败了悄悄再试一次,对用户完全透明,是安全的。
- 流式对话**不能自动重试**:第一,它已经在往客户端一个字一个字地推了,推到一半失败,你没法"把已经吐出去的字收回来"再重发;第二,重试会让模型**重复生成**,用户会看到半句话之后又从头来一遍。所以开发文档明确写了"流式对话不自动重试"——流式场景下,失败就是失败,老老实实发一个 error 帧告诉前端,让**用户自己决定**要不要重发,而不是后端偷偷替他重试。

**判断"能不能自动重试"的通用准则:这次调用是不是幂等的、有没有已经产生对外可见的副作用。** 幂等且无副作用 → 可以重试;非幂等或已有副作用(已扣款、已发消息、已推流)→ 不能盲目重试。

### 4.3 限流算法对比 + 降级预案(讲思路即可)

**四种常见限流算法,面试常让你对比:**

| 算法 | 一句话原理 | 优点 | 缺点 |
|------|-----------|------|------|
| 固定窗口 | 每个时间窗口内计数,超了就拒 | 实现最简单(一个 INCR + EXPIRE 就行) | **临界问题**:窗口交界处可能瞬时放行两倍流量 |
| 滑动窗口 | 把大窗口切成小格,滚动统计最近一段 | 缓解了固定窗口的临界毛刺 | 实现更复杂,要存更多计数 |
| 令牌桶 | 匀速往桶里放令牌,来请求就取一个,取不到就拒 | **允许一定突发**(桶里攒了令牌就能一次多放几个) | 参数(桶容量、放令牌速率)要调 |
| 漏桶 | 请求先进桶,以固定速率漏出去处理 | 输出速率绝对平滑 | 不允许突发,应对流量尖峰不够灵活 |

**固定窗口的"临界问题"是什么(高频追问点):** 假设限流是"每分钟 100 次"。如果 100 个请求全挤在第 1 分钟的最后 1 秒,又有 100 个全挤在第 2 分钟的最前 1 秒——从"每分钟不超 100"看两个窗口都没违规,但**在这跨越窗口边界的 2 秒内实际放行了 200 次**,是限流值的两倍。滑动窗口就是为了消掉这种边界毛刺而生的。

**本项目为什么固定窗口就够?** 我们的诉求是"每用户 10 秒最多发起 1 次对话",配额本来就是 1、窗口很短,`SET NX EX` 实现的正是"固定窗口、配额为 1"这个最简形态。**用户体感上就是一个 10 秒冷却**,临界问题在"配额=1"这种场景下也几乎不产生实际影响,没必要上滑动窗口/令牌桶那套复杂实现——**限流算法要按业务实际需要选,不是越高级越好**。

**如果配额不是 1,而是"每分钟 N 次"呢(理解 `INCR`+`EXPIRE` 的坑):** 那就得用计数:`INCR key` 自增,第一次自增后 `EXPIRE key 60` 设过期,值超过 N 就拒。**这里有个开发文档点名的坑——`INCR` 和 `EXPIRE` 是两条命令,不原子**:如果第一次 `INCR` 之后、还没来得及 `EXPIRE`,进程刚好崩了,这个 key 就**永远没有过期时间**,该用户被永久限流。解法是把两步合成一个原子操作:用 Lua 脚本把 `INCR`+(首次)`EXPIRE` 打包执行,或者对"配额=1"的场景直接用 `SET NX EX`(就是我们现在的做法,天生原子,压根绕开了这个坑)。

**降级预案(开发文档说"能讲出思路即可,不强制实现"):** 核心思路是**配置化的备用模型**——把主用模型和备用模型都写进配置,当主模型连续失败(触发熔断阈值)时,自动切到一个更便宜/更稳的备用模型顶上,保证"服务降级但不中断"。落地一般靠熔断器(如 Resilience4j)统计失败率、超阈值后开路,并提供 fallback 分支切模型。本项目**不要求实现**,面试时能说清"配置备用模型 + 熔断触发切换 + 降级不等于不可用"这条链路即可。

10 秒内连发两次 chat,第二次必须被拦:

```bash
# 第一次:正常进入流式
curl -sN -X POST http://localhost:8080/api/interviews/$SESSION_ID/chat \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"content":"第一次提问"}'

# 紧接着第二次(10 秒内)
curl -s -X POST http://localhost:8080/api/interviews/$SESSION_ID/chat \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"content":"10 秒内的第二次"}'
```

期望第二次返回 **`42900`**("操作太频繁，请过几秒再发")。等 10 秒后再发,恢复正常。

> 顺带验证 key 带了 userId:用**另一个用户**的 token 在同一 10 秒内发一次,应当**正常放行**(不受第一个用户冷却的影响)——如果这里也被拦了,说明限流 key 忘了带 userId,变成全局限流了。

**② api-key 错误返回 50001 而不是裸 500**

把 `application-local.yml` 里的 AI api-key 改成一个错的,重启,然后创建会话:

```bash
curl -s -X POST http://localhost:8080/api/interviews \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"direction":"redis"}'
```

期望返回 **`50001`**("AI 服务调用失败"或"开场白生成失败"),而**不是** `50000` 系统内部异常。测完记得把 key 改回来。

**③ 超时不拖垮服务(理解性验证,不强制)**

不用真的制造超时。确认 `AiConfig` 里 `withReadTimeout` 确实设了值即可——能对着代码讲清楚"如果这行没有,一个卡住的 AI 请求会怎样一步步拖垮线程池",这一条就算过。
