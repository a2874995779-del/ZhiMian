## Step 0:建表 `interview_report`

在 Navicat 里对你的库执行(和之前 `interview_session`/`interview_message` 一样,照着敲):

```sql
CREATE TABLE `interview_report` (
  `id`          BIGINT   NOT NULL AUTO_INCREMENT,
  `session_id`  BIGINT   NOT NULL COMMENT '会话 id',
  `score`       INT      NOT NULL COMMENT '总分 0-100',
  `content`     JSON     NOT NULL COMMENT '结构化报告:亮点/薄弱点/总评',
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_session_id` (`session_id`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT '面试评价报告表';
```

同时把这段**追加进 `sql/init.sql`**(顺手把 `interview_session`/`interview_message` 的建表语句也补进去,它们当时也没进过这个脚本——不补的话换台机器初始化数据库,这三张表都会凭空消失)。

【讲解】两个设计点,都是面试考点:

- **`content` 为什么用 JSON 类型而不是 TEXT**:MySQL 8 的 `JSON` 列在写入时会校验必须是合法 JSON(不合法直接插入失败,坏数据进不来),还能用 `JSON_EXTRACT` 直接查里面的子字段——`TEXT` 两样都做不到。而 **`score` 单独拉成普通列**,是因为它是唯一以后可能要被排序/筛选/算平均分的字段(比如"我的历次面试分数趋势"),普通列能直接建索引、直接 `ORDER BY`;JSON 内部字段做这些要么低效要么得上"虚拟列+索引"这种复杂方案。**判断标准:要被数据库直接筛选/排序/计算的字段拉成普通列,整存整取的部分打包进 JSON。**
- **`uk_session_id` 唯一索引**:保证一个会话只有一份报告。这是幂等的"数据库兜底"——就算业务层的判断被并发绕过,数据库这一层也绝不允许插入第二条。

## Step 3:结构化输出的目标类型 `InterviewReportResult.java`

`model/dto/InterviewReportResult.java`:

```java
package com.zhimian.model.dto;

import java.util.List;

/**
 * 模型生成评价报告的目标结构:Spring AI 会把这个类型的字段结构拼进 prompt,
 * 要求模型按这个 JSON 格式回答,再把回复解析成这个类型的实例
 */
public record InterviewReportResult(
        Integer score,
        List<String> highlights,
        List<String> weaknesses,
        String summary
) {
}
```

【讲解】这一步要先弄懂"结构化输出"的原理,不然后面 `.entity(...)` 那行代码是黑盒:

**大模型没有"输出 Java 对象"的模式开关**,它的本质永远是"输入一串文字,生成下一串文字"。所谓结构化输出,是 Spring AI 帮你做了两件事:① 请求发出前,根据这个 record 的字段结构自动生成一段"请按如下 JSON 格式回答"的指令,**偷偷追加到你的 prompt 后面**;② 拿到回复后,用 Jackson 把回复文本**解析**成这个 record,解析失败抛异常。这套逻辑封装在 `BeanOutputConverter` 里,`ChatClient` 的 `.entity(Class)` 就是它的省事入口。**本质上和你自己写"prompt 里要求返回 JSON + ObjectMapper 解析"是同一件事,只是框架封装好了。**

两个写法细节:

- **用 record 不用 `@Data` 类**:这份数据从模型解析出来后只读不改,record 天然不可变,恰好匹配;Jackson 原生支持 record 反序列化。
- **字段名取得直白**(`score` 不缩写成 `s`):字段名会被拼进发给模型的格式说明里,**模型是照字面意思理解每个字段该填什么的**,名字含糊,模型的理解也含糊。

### 5.2 实现 `InterviewServiceImpl.java`

**先看整体设计,再抄代码。** 状态机是理解这段逻辑的钥匙:

| status | 含义 | 能做什么 |
|--------|------|---------|
| 0 | 进行中 | 能 `chat`,能 `finish` |
| 1 | 已结束,报告未生成(生成中/生成失败) | 不能 `chat`,能再次 `finish` 重试生成报告 |
| 2 | 已结束,报告已生成 | `finish` 直接返回已有报告,不再调模型 |

为什么不是 0 直接跳 2?——生成报告是一次**可能失败的外部调用**。如果"报告生成成功才改状态",那么用户点了结束、模型调用失败时,状态还停在 0,**用户明明点了结束,聊天框却还开着**,语义矛盾。所以:一进 `finish` 就先把 0→1("不能再聊"立刻生效),然后才调模型;成功了 1→2,失败了停在 1,下次 `finish` 可以重试。**你现在代码里的最简版 `finishInterview` 恰好就是"只做 0→1"这一半,这次把后一半补上。**

把现有的 `finishInterview` **整个替换**成:

```java
@Override
public InterviewReportVO finishInterview(Long sessionId) {
    InterviewSession session = mustFindOwnSession(sessionId);

    // 幂等短路:报告已经生成过,直接返回已有的,不再调模型(放在抢锁之前,不用为它付一次 Redis 往返)
    if (session.getStatus() == 2) {
        return toReportVO(interviewReportMapper.selectBySessionId(sessionId));
    }

    // 和 chat 用同一把会话锁:结束面试和继续对话不能同时进行,
    // 不然 finish 拼对话记录时可能刚好错过 chat 还没落库的最后一条回复
    String lockKey = LOCK_PREFIX + sessionId;
    Boolean locked = stringRedisTemplate.opsForValue().setIfAbsent(lockKey, "1", LOCK_TTL_SECONDS, TimeUnit.SECONDS);
    if (!Boolean.TRUE.equals(locked)) {
        throw new BusinessException(ErrorCode.TOO_MANY_REQUESTS, "会话正在处理中，请稍后再试");
    }

    try {
        // 先把"已结束"落实(0→1),再调模型——模型调用失败状态也停在 1,不会出现"点了结束还能聊"
        if (session.getStatus() == 0) {
            interviewSessionMapper.updateStatus(sessionId, 1);
        }

        List<InterviewMessage> history = interviewMessageMapper.selectBySessionId(sessionId);
        InterviewReportResult result = generateReportWithRetry(buildTranscript(history)	);

        InterviewReport report = new InterviewReport();
        report.setSessionId(sessionId);
        report.setScore(result.score());
        report.setContent(serializeReportContent(result));
        interviewReportMapper.insert(report);
        interviewSessionMapper.updateStatus(sessionId, 2);

        return toReportVO(report);
    } finally {
        stringRedisTemplate.delete(lockKey);
    }
}
```

再补四个私有方法(放在 `buildSystemPrompt` 附近):

```java
/**
 * 评委的 system prompt,和面试官的 buildSystemPrompt 是两个角色,绝不复用——
 * 面试官那套 prompt 的行为约束是"接着问下一个问题",拿来生成报告模型会答非所问
 */
private String buildJudgePrompt() {
    return """
            你是一位资深技术面试评委,下面会给你一场完整的模拟面试问答记录(面试官提问与候选人回答交替出现)。
            请基于候选人的整体表现给出结构化评价:
            1. score:总分,0~100 的整数,综合回答的准确性、深度、表达清晰度。
            2. highlights:候选人表现好的地方,2~4 条,每条一句话,要具体(引用候选人实际提到的技术点),不说空泛的场面话。
            3. weaknesses:回答中不足或值得继续深挖的地方,2~4 条,同样要具体。
            4. summary:1~2 句话的总体评价,像面试官写给 HR 的结论。
            只依据对话记录里实际出现的内容打分和点评,不要编造候选人没有说过的内容。
            """;
}

/**
 * 把整场对话拼成一份"记录稿"喂给评委。评委不是对话的参与者,而是事后读材料的第三方,
 * 所以不用 chat 那套 List<Message> 角色消息,直接拼成一整段文本;system prompt 是给面试官
 * 角色的内部指令,不属于对话内容,过滤掉
 */
private String buildTranscript(List<InterviewMessage> history) {
    StringBuilder sb = new StringBuilder();
    for (InterviewMessage m : history) {
        if ("system".equals(m.getRole())) {
            continue;
        }
        String speaker = "assistant".equals(m.getRole()) ? "面试官" : "候选人";
        sb.append(speaker).append(":").append(m.getContent()).append("\n\n");
    }
    return sb.toString();
}

/**
 * 调模型生成结构化报告,解析失败重试 1 次(模型输出格式偶发跑偏是小概率抖动,再问一次大概率就好;
 * 若是 prompt 或服务本身的问题,重试再多次也没用,所以只重试 1 次不恋战),两次都失败转统一错误码
 */
private InterviewReportResult generateReportWithRetry(String transcript) {
    for (int attempt = 1; attempt <= 2; attempt++) {
        try {
            return chatClient.prompt()
                    .system(buildJudgePrompt())
                    .user(transcript)
                    .call()
                    .entity(InterviewReportResult.class);
        } catch (Exception e) {
            log.warn("评价报告生成第 {} 次尝试失败", attempt, e);
        }
    }
    throw new BusinessException(ErrorCode.AI_SERVICE_ERROR, "评价报告生成失败，请稍后重试");
}

// highlights/weaknesses/summary 打包成 JSON 文本存进 content 列(score 单独成列,不进 JSON)
private String serializeReportContent(InterviewReportResult result) {
    try {
        return objectMapper.writeValueAsString(Map.of(
                "highlights", result.highlights(),
                "weaknesses", result.weaknesses(),
                "summary", result.summary()
        ));
    } catch (JsonProcessingException e) {
        throw new RuntimeException(e);
    }
}

private InterviewReportVO toReportVO(InterviewReport report) {
    InterviewReportVO vo = new InterviewReportVO();
    vo.setScore(report.getScore());
    vo.setCreateTime(report.getCreateTime());
    try {
        Map<String, Object> content = objectMapper.readValue(report.getContent(), new TypeReference<>() {});
        vo.setHighlights((List<String>) content.get("highlights"));
        vo.setWeaknesses((List<String>) content.get("weaknesses"));
        vo.setSummary((String) content.get("summary"));
    } catch (JsonProcessingException e) {
        throw new RuntimeException(e);
    }
    return vo;
}
```

(`toReportVO` 里 `TypeReference` 需要 `import com.fasterxml.jackson.core.type.TypeReference;`——为什么反序列化带泛型的类型必须用它,`docs/数据组装与转换专题.md` 第六节讲过,忘了回去翻。)

【讲解,对着上面代码看】

- **`.entity(InterviewReportResult.class)`**:和你熟悉的 `.call().content()` 只差最后一步——`.content()` 拿纯文本,`.entity(...)` 拿解析好的对象,Step 3 讲的两件事(格式指令注入 + 回复解析)都发生在这一步里。
- **为什么 `finish` 和 `chat` 抢同一把锁**:用户一个标签页在聊(流式回复还没落库),另一个标签页点结束——`finish` 拼记录稿时会刚好错过最后一条回复,报告漏评最后一轮;更糟的是 `chat` 的回复在状态已改成 1 之后才落库,出现"报告生成完了消息表还在追加"的不一致。同一把会话级锁保证"这场会话同一时刻只有一个 AI 相关操作在跑"。
- **`status == 2` 的幂等短路放在抢锁之前**:它只读不写、不调模型,没必要为它付一次 Redis 网络往返。
- **幂等双保险**:业务层的 `status` 判断覆盖正常场景;Step 0 的 `uk_session_id` 唯一索引兜住极端并发——即使两个请求同时通过了状态检查,数据库也绝不允许第二条插进去。
- **拼记录稿为什么直接查 MySQL 全量,不走 `contextManager.load()`**:`load()` 里有 token 裁剪,那是"喂模型继续对话"的裁剪;生成报告要评的是**整场**表现,裁掉早期几轮报告就失真了。"喂模型接着聊"和"喂模型做总结"是两个读取场景——6.2.6 详情接口讲过同样的判断,这是第二次应用。

### 5.3 一个已知的遗留问题,这次先不解决

前端 `restart()` 现在调 `finishInterview` 只是为了把会话从"进行中"里摘出去,它并不需要报告。这次把 `finish` 改造成"必生成报告"之后,restart 那次调用也会触发一次模型调用(花钱、慢)。**先接受这个浪费把主流程跑通**,下一步前端任务里再把"只结束"和"结束+要报告"分开(比如 `finish` 带个参数,或 restart 换个轻量接口)。在文档里记下这一笔,是为了让你知道这不是没发现,而是刻意延后。


**② 幂等(最该测的一条)**:同一个会话**连续调两次** `finish`——第二次应该明显更快(不再等模型几秒),内容和第一次完全一致;`interview_report` 表里始终只有一条。

**⑤ 失败重试**:临时把 `buildJudgePrompt()` 里的格式约束删掉换成"随便聊聊,不要用任何固定格式",重启后调 `finish`,观察日志有没有"第 1 次尝试失败"后重试的痕迹;两次都失败时确认返回 `50001` 且会话状态停在 1(不是卡在 0 或者错进 2),然后**把 prompt 改回来**,再调一次 `finish` 验证"状态 1 可以重试补生成报告"。
